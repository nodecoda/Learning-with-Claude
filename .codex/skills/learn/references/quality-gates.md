# 正確性關卡、深度 checklist 與規模指引

教材最致命的失敗不是文風差，是**內容錯**——而學習者分辨不出來，他就是來學的。文風管得嚴，正確性至少要一樣嚴。以下是硬規定，不是建議。

## 正確性關卡

### code 要真的跑過，不是看起來對

帶 code 的章節、範例、練習解答，**寫進教材之前先在對應環境實際執行一遍**（Bash / 編譯器 / REPL）。

- 貼進教材的**輸出必須是真的跑出來的**，不是憑記憶或推測。編譯錯誤訊息、程式輸出、報錯行號——照抄真實結果。
- 「先故意寫錯再改對」的教學手法，**錯的版本也要真的跑一遍**，確認它真的以你說的方式失敗。錯誤訊息常和你想的不同。
- **在這環境跑不了的**（特定硬體、kernel 模組、其他 OS、需要 root 或特定網路）→ 不要假裝跑過。明確標注「**本段未實測，為理論預期行為**」，並說明在什麼環境該怎麼驗證。
- 跑不過就別貼。一段編不過的 code 貼進教材，比不貼更糟——讀者會卡在你的 bug 上以為是自己的問題。

### 事實斷言要查，不要靠記憶

可查證的斷言——版本行為、API 語意、旗標與預設值、syscall 號、效能數字、歷史事件、某工具某版本何時加了什麼功能——沒十足把握就查（官方文件、man page、原始碼、規格）。模型記憶對這類細節錯誤率高，而且錯得很自信。

- 查得到 → 用查到的，必要時把來源放進延伸閱讀。
- 查不到或不確定 → **降級措辭**（「就我所知」「一般而言」「這點請以你的環境實測為準」），不要用確定語氣包裝不確定的知識。這是「認識論誠實」的落地：不只標版本差異，連「我不確定」本身都要誠實。

### 標清楚「驗證過」vs「推測」

不標的話讀者無法分辨哪句是實測／查證過的、哪句是推的。**凡是沒實測、沒查證的斷言，用措辭標出來。** 不要用「範例僅供示意」當免死金牌塞沒跑過的 code——要嘛跑，要嘛明說沒跑。

### 每個數字要能追來源

magic number、常數、效能倍率、複雜度——每一個都要能說出「這個值為什麼是這個值」。效能宣稱要嘛有你實測的 benchmark，要嘛給明確條件（「在 X 前提下，因為 Y」）。說不出來源的數字不要寫。

> 順序：**先跑 / 先查 → 再寫**。不要先寫完整章再回頭補驗證，那時你已經傾向相信自己寫的了。帶 code 的章節，把「跑範例」當成寫這章的第一個動作。

## 每章深度 checklist

每章送出前自己跑一遍。某項答「否」，補完再繼續，不要跳過。

```
教學設計
□ 第一個 code block 出現之前，有沒有先建立心智模型或直覺？
□ 有沒有解釋歷史背景：這個設計之前，人們怎麼做？為什麼不夠好？
□ 有沒有說明「為什麼不選替代方案 B 或 C」，而不只是說「我們選了 A」？
□ 所有術語有沒有在第一次出現時定義，或標注「見 Ch N」？
□ 有沒有橫向連結到之前學過的相關概念？
□ 如果是工具章節，有沒有在開頭釘定版本與環境？

內容深度
□ 底層機制的部分，讀者讀完之後能不能在腦中畫出執行流程？
□ 有沒有說清楚「為什麼這樣設計」，而不只是「怎麼用」？
□ 有沒有對行為的不確定性、版本差異、平台差異誠實標注？

範例品質
□ 範例有沒有至少 2 個，覆蓋正常路徑和至少一個失敗 / 邊界情況？
□ 範例裡有沒有未解釋的 magic number 或 magic constant？（有就是扣分）
□ 有沒有任何無根據的效能或安全宣稱？（有就是扣分）

正確性（最優先，答否就是不能出）
□ 每一段 code 都真的在對應環境跑過了嗎？貼的輸出是真跑出來的？
□ 跑不了的段落，有沒有明確標「未實測，理論預期」而不是假裝跑過？
□ 版本行為 / API 語意 / 旗標 / 效能數字這類可查證斷言，有把握或查過了嗎？沒把握的有沒有降級措辭？
□ 每個數字 / 常數 / 效能宣稱都說得出來源或條件嗎？

收尾
□ 踩雷有沒有至少 3 條，每條有明確的「錯誤直覺 → 正確認識」？
□ 有沒有一個「進階延伸」區塊，讓讀者知道下一步去哪？
□ 延伸閱讀有沒有至少 3 條高品質資源，且每條都說明讀哪裡、學什麼、和本章關聯？
□ 延伸閱讀的資源有沒有通過品質標準（不是 SEO 農場文 / 無署名教程）？
□ 自我檢核的問題有沒有要求主動回憶，而非只是能翻書找答案？
```

## 延伸閱讀品質標準

### 什麼資源算「值得列」

**論文**：優先 USENIX（OSDI、ATC、NSDI）、ACM（SOSP、PLDI、CCS）、IEEE S&P、NDSS、頂級期刊，或某個技術的原始論文（「我們就是從這裡開始的」那篇）。不要列引用數個位數的隨機論文。

**部落格 / 技術文章**：優先
- 工具或語言的**核心開發者 / 維護者**寫的（Brendan Gregg 寫 perf、Russ Cox 寫 Go runtime、Dan Luu、Julia Evans、Eli Bendersky、Aphyr……）
- 大廠的**系統工程部落格**（Netflix Tech Blog、Cloudflare Blog、LMAX Disruptor blog……）
- 解釋**底層原理**而非「10 分鐘學會 X」的文章
- 有明確**作者署名**且查得到背景的文章

避免：SEO 農場文、Medium 上的「入門 X 的 5 個步驟」、沒有作者署名的教程、純生成內容的技術部落格。

**官方文件 / Spec**：RFC、W3C spec、語言標準、工具官方 manual。標明具體小節，不要只丟首頁 URL。

**書籍**：優先業界公認的「那本書」（《CSAPP》《APUE》《OSTEP》《Dragon Book》《The Linux Programming Interface》……），或特定領域標準教科書。列出版年；超過 10 年的書要說明是否仍適用。

### 每條資源的必填說明

不管哪種類型，每條資源都必須回答：

1. **讀什麼**：具體章節、小節或段落，不是「整本書」「官網」
2. **能學到什麼**：補充本章哪個沒展開的地方，或把哪個概念推得更深
3. **前提知識**：讀者需要先懂什麼才看得懂（避免開了連結兩分鐘就關掉）

查證資源真實存在是作者責任。不要用「你可以自行搜尋」敷衍，也不要不確定就編一個看起來合理的 URL。

## 章節數規模指引

| 主題範疇 | 建議章節數 | 建議練習數 |
|---|---|---|
| 一個工具（如 GDB、Docker） | 20–30 章 | 3–4 個 |
| 一個語言（如 C++、Go） | 30–45 章 | 4–6 個 |
| 一個領域（如密碼學、網路） | 35–50 章 | 4–6 個 |
| 一個子主題（如 GDB remote） | 12–18 章 | 2–3 個 |

課綱草稿明顯低於下限時先確認：是範圍縮窄了，還是某些主題要合併？合理原因包括主題本身就小、使用者只要入門。沒有好原因就擴展，不要留白。

使用者說「快速入門就好，不要太深」時：章節可縮到 12–18 章；每章仍有底層機制區塊但可縮短（至少給「這邊可以更深入的方向」一段）；踩雷只列 2–3 條；延伸閱讀縮到 1–2 條。**不能完全省略深度**——差別是「少說一點」而不是「不說」。
