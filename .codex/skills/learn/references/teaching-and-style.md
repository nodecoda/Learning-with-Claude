## 教學設計原則

### 直覺先行，形式化後補

永遠先給讀者一個心智圖像或直覺，再引入精確定義或程式碼。讀者腦中沒有模型時，看再多 code 也只是在抄。

錯誤順序：「`epoll_wait()` 的語意是監控一組 fd，當有事件觸發時返回就緒列表。以下是範例。」
正確順序：「想像一個服務員看著 N 張桌子——不是輪流跑每桌問『你好了嗎』，而是站在中間等任何一桌叫他。這就是 epoll 的模型。現在看 code。」

### 具體先行，抽象後補

先給具體例子讓讀者看到，再歸納一般規律。不要先寫「X 的一般化定義是...」然後才給例子。人腦從具體歸納抽象，不是從抽象演繹具體。

### 歷史演進脈絡

每個核心概念都要說：在這個東西出現之前，人們怎麼做？為什麼舊方法不夠好？歷史背景讓讀者理解「為什麼要這樣設計」，而不是死記規則。

### 設計決策的「為什麼不」

好的教材不只解釋「選了什麼」，還解釋「為什麼沒選 B 或 C」。設計空間的形狀比最終選擇更有教育意義。例：「Rust 為什麼不用 GC？不是 GC 不好——是 GC 無法保證 latency，而這對系統程式設計是硬限制。」

### 橫向連結

用到之前學過的概念時明確標示，不要讓讀者在腦中自己找：

```
> 如果你對 X 還不熟，先回看 [Ch N — 標題](./0N-xxx.md) 的「Y 節」。
```

讀者不會記得所有內容，幫他們連線是作者的責任。

### 認識論誠實

遇到以下情況**一定要明確標示**，不能假裝不存在：

- 行為是版本特定的（「這是 Linux kernel 5.15+ 的行為；舊版不同」）
- 行為是平台特定的（「Windows 上這個 syscall 不存在」）
- 效能宣稱是有條件的（「在 cache hit rate 高的情況下；否則反而更慢」）
- 主題有真實爭議（「這個領域對 X 沒有共識；主流實作做法是 Y，但 Z 也有道理」）
- 某個說法是簡化模型（「這個類比在 A 和 B 的情況下成立，但碰到 C 就會出問題」）

不說清楚的後果：讀者帶著絕對化認知去實作，碰壁後不知道為什麼。

### 主動回憶，而非被動閱讀

自我檢核要逼讀者**回憶**，不是逼讀者翻書抄答案。

好的問題：「不看筆記，能不能用自己的話解釋 X？」「如果面試問你 Y，你會怎麼回答？」「想一個你現在工作遇到的問題，這章的概念怎麼應用？」
壞的問題：「X 是什麼？」「Y 的用法是什麼？」——翻回去就有答案，對記憶沒幫助。

### 版本與環境釘定

工具類章節開頭一定要有：

```
> **環境**：本章以 <工具名> <版本> 在 <OS/架構> 上操作。<版本 X 以下有行為差異的地方會特別標注。>
```

不釘版本的教材時效性很差，讀者在不同環境跑出不同結果時找不到原因。

### 失敗是教學素材

先**故意展示錯誤做法或失敗輸出**，再展示正確做法，比直接給正確答案更有效。讓讀者理解「為什麼要這樣」而不只是「這樣做」。

特別適合：編譯錯誤、記憶體問題、並發 bug、效能退化。

## 風格指南

以 `compilers/compiler_frontend/` 為基準。既有課程繁體與簡體並存（`compiler_frontend`／`web/firebase` 繁體，`mlir_core`／`ai_compiler` 簡體），所以**沿用使用者當下使用的字形**，不要擅自轉換；整個 repo 沒有單一語言政策。

### 語言

- 中文，字形（繁／簡）跟隨使用者當下輸入；同一門課內保持一致，不要混用
- 專有名詞第一次出現寫中英並陳：「詞法分析（Lexer / Scanner）」
- 程式碼、工具名、flag 保持英文原文

### 口吻

- 直接、有觀點、不官腔。「別只讀」「工具會幫你罵你」「這樣做比較好」
- 第一人稱複數「我們」，把讀者拉進來
- 敢下判斷，不要什麼都寫「可以考慮」
- 承認歷史與誤解：「有人問過...」「一個常見誤解是...」

### 結構細節

- 章節開頭一律 `> **目標**：...` blockquote
- 流程或架構先放一張 ASCII code block 圖
- 概念對照用 markdown 表格
- 「XXX **不關心** YYY」「**不會** 生成 ZZZ」——粗體強調邊界
- 結尾一律 `## 自我檢核` + checkbox（含理解性問題，不只操作）+ `## 延伸閱讀` + 一句話 + `→ [下一章連結]`

### 範例要求

- 具體、能跑、有輸出。不要抽象碼（`foo()`, `bar`）
- **多個例子**：最小可工作例子、真實情境例子、邊界或錯誤例子
- 工具類主題給 before → after 對照
- 「把分號刪掉，看它怎麼罵你」——故意弄錯是這套教材的核心手法
- 範例必須在對應環境真的能跑，不允許只是示意的偽代碼（除非整章都是概念性的）

### 長度

- 普通章：300–450 行
- 原理深挖章（底層機制為主）：400–550 行
- 練習：400–600 行
- Final Project：500–700 行
- README：60–100 行

寧可長也不要短。一章寫完只有 150 行，表示某個維度沒寫到，找出來補上。

## 不要做的事

### 口吻與用語

- 不要寫純 AI 腔 meta 話（「在本章中，我們將探討...」「讓我們開始吧！」）
- 不要無意義過場句（「接下來，我們繼續...」「綜上所述...」）
- 不要用 emoji（除非使用者明確要求）
- **嚴禁輕描淡寫詞**：`just`、`simply`、`trivially`、`obviously`、`easily`、`只需要`、`很簡單`、`顯然`。這些詞在告訴讀者「你應該覺得這很簡單」，讓卡住的讀者覺得是自己的問題。刪掉。

### 概念說明

- 不要在術語**未定義**的情況下使用它——第一次出現要定義，或標注「這在 Ch N 有介紹」
- 不要「之後會說明」的延遲交代。現在不能解釋就說「先用著，之後你會看到為什麼，這不影響現在的理解」，不要讓讀者帶著懸念以為自己漏看了
- 不要用**誤導性的類比**。類比在邊界條件下給出錯誤心智模型，比沒有類比更糟；有限制就說清楚
- 不要做**假精確**。「這個演算法是 O(n log n)」卻省略「在平均情況下、假設 hash 均勻分布」——精確要麼完整，要麼說「粗略地說」
- 不要用**被動語態掩蓋主語**。「記憶體被釋放了」不如「OS 把這個 physical page 回收進 free list」

### 範例品質

- 不要只有 happy path——每個概念至少一個展示**失敗或邊界**的例子
- 不要有未解釋的 **magic number**——`0x400000`、`4096`、`255` 為什麼是這個值，說清楚
- 不要只給 snippet、不給 **runnable context**——讀者要能複製貼上跑起來；篇幅不允許時至少說明缺什麼、怎麼補
- 不要做**無根據的效能或安全宣稱**——要嘛給 benchmark 或具體條件，要嘛換成「在 X 場景下通常比較快，原因是 Y」

### 平台與版本

- 不要**平台差異手波**——「在 Windows 上行為可能不同」毫無意義。要嘛說清楚差異，要嘛說「本課只涵蓋 Linux，Windows 差異不在範圍內」
- 不要省略版本資訊——工具行為、API 語意、編譯器行為都可能隨版本改變

### 資源

- 不要把完整解答直接貼在練習正文——一定用 `<details>` 摺起來
- 不要把延伸閱讀寫成泛泛的「可以參考官方文件」
- 不要列沒有解釋的裸連結
- 不要因為找不到論文就只列部落格——多數成熟技術都有原始論文或頂會論文
- 不要列「N 分鐘學會 X」或 SEO 農場文
