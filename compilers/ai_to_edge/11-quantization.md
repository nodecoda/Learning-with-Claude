# Ch 11 — 量化在编译器中的位置

> **目标**：搞清量化不是一个「API 调用」，而是**改写了图里每个算子的数值域**，因此它在编译器的三层（图级、调度级、代码生成级）都有落点。学完这章，你能手算一个仿射量化方案的 scale 和 zero point，能解释为什么累加器必须是 `int32`，能判断逐通道量化该沿哪个轴，也能在「量化好像没生效」时用三条检查把它抓出来。

> **环境**：torch 2.9.1+cpu、gcc 11.4、Ubuntu 22.04、x86_64（AVX2）。本章的 C 代码同时用 `gcc` 与 `aarch64-linux-gnu-gcc` 编过；`aarch64` 那侧只验证了编译通过，未上真机跑。

> **证据分级**：标「实测」的输出都是本机真实运行结果，脚本在 `code/08_quant/`。标「理论」的推导过程（比如累加器上界）是算术推演，可以自己验算。

## 为什么需要这个？

Ch 10 结束时的状态是：`linalg.matmul` 已经变成了三层 `scf.for`，再往下就是 LLVM 的 `load` / `fmul` / `fadd` / `store`。这段循环本身没有问题——**问题是它算的东西边缘设备可能承受不起**。

三个具体的约束，按严重程度排：

**一、没有浮点单元。** Cortex-M3 这类 MCU 是 `soft-float`。Ch 14 实测的 target features 里有 `+soft-float` 这个标志，意思是每次 `fadd` 都要调用一段软件模拟例程。Ch 15 里那条 `undefined reference to '__aeabi_fmul'` 就是这件事的现场：链接器找不到浮点乘法例程。一个 `784×64` 的矩阵乘在软浮点下会慢到没法用。

**二、带宽。** 权重是只读的，每次推理都要从 FLASH 读进 RAM。`float32` 每参数 4 字节，`int8` 是 1 字节。一个 100 万参数的模型，权重从 4 MB 降到 1 MB。MCU 的 FLASH 常常只有 256 KB 到 1 MB，这个差别决定「装不装得下」。

**三、算力。** `int8` 乘加在多数 DSP 和 NPU 上是原生指令，吞吐是 `float32` 的 2 到 16 倍。这跟带宽是两件独立的事。

于是量化要做的事情是：**把图里每个张量的数值从 `float32` 搬到 `int8` 的格子上，同时保证算出来的结果还落在可接受的误差内**。这句话里每个词都有工程后果，后面逐个拆。

## 先建立直觉

量化的本质是**用一把有刻度的尺子去量连续量**。

```
真实值轴（连续）            ────●─────────●────●───────────────●────►
                                 x1        x2   x3              x4

int8 刻度（256 格）  ├──┼──┼──┼──┼──┼──┼──┼──┼──┼──┼──┼──┼──┼──┼──┼──┤
                    -128                    0                   127

                     x1 → 最近刻度           x2 → 最近刻度
                     误差 ≤ scale/2          误差 ≤ scale/2
```

两个参数就够描述这把尺子：

- **scale（步长）**：相邻两格差多少真实值。`scale = (max - min) / (qmax - qmin)`
- **zero point（零点）**：真实值 `0.0` 落在哪个刻度上。有符号 `int8` 用 `qmin=-128, qmax=127`；无符号 `uint8` 用 `0..255`

于是「实数 → 整数」的正向变换是：

```
q = round(x / S) + Z
```

反向（反量化）是：

```
x ≈ S * (q - Z)
```

`round` 那一步引入的误差最大是 `S/2`。这就是量化误差的**唯一来源**（在不考虑溢出和累加的情况下）。记住这句话，后面所有分析都从这里出发。

**为什么需要 `Z`。** 如果数据是非对称的（比如 ReLU 之后的激活全是正数，范围 `[0, 6.0]`），把它硬塞进 `[-128, 127]` 会浪费一半刻度。做法是把 `0.0` 映射到某个非零刻度上，让整个 `[0, 6.0]` 铺满 `[-128, 127]`。这个「零点偏移」就是 `Z`。

## 底层机制一：scale 与 zero point 怎么算

拿实测数据走一遍。取一个 128 维的随机向量（模拟一层激活），实测：

```
[int8]  scale=0.023500 zp=0     levels=256 max_err=0.01173 mean_err=0.00605
[uint8] scale=0.023500 zp=128   levels=256 max_err=0.01173 mean_err=0.00605
```

两种表示给出**完全相同**的误差，因为 `levels` 都是 256。差别只在 `Z`：

- `int8`：范围 `[-128, 127]`，`Z = 0`。数据本身关于 0 对称（随机正态），零点正好在中间
- `uint8`：范围 `[0, 255]`，`Z = 128`。把真实 `0.0` 放到刻度 128 上

误差对不对得上公式？`S/2 = 0.0235/2 = 0.01175`，实测 `max_err = 0.01173`。差的那一点点是 `round` 的边界效应——`max_err` 取的是样本最大值，不一定正好撞到 `S/2`。**这个吻合度说明公式没写错**。

再看 ReLU 输出这种非对称数据。实测（`code/08_quant/asym.py`，真值夹在 `[0, 6.0]` 的 4096 个激活）：

```
int8 对称(zp=0)          scale=0.047059 zp=   0 用到刻度=128/256  max_err=0.023530  mean_err=0.010790
int8 非对称               scale=0.023529 zp=-128 用到刻度=256/256  max_err=0.011757  mean_err=0.005288
uint8 非对称               scale=0.023529 zp=   0 用到刻度=256/256  max_err=0.011757  mean_err=0.005288
```

三行的差别值得逐行读：

| 方案 | `scale` | `zp` | 用到的刻度 | 最大误差 | 平均误差 |
|---|---|---|---|---|---|
| `int8` 对称 | `0.047059` | `0` | **128 / 256** | `0.023530` | `0.010790` |
| `int8` 非对称 | `0.023529` | `-128` | 256 / 256 | `0.011757` | `0.005288` |
| `uint8` 非对称 | `0.023529` | `0` | 256 / 256 | `0.011757` | `0.005288` |

**第一行是坑。** 对称量化要求「范围关于 0 对称」，所以它把 `[0, 6.0]` 扩成 `[-6.0, 6.0]` 来算 `scale = 12/255 = 0.047`。结果**误差整整翻倍**（`0.0235` vs `0.0118`），而且 256 个刻度只用了一半。

**第二行和第三行数值完全相同。** 这不是巧合：`int8` 的 `zp=-128` 与 `uint8` 的 `zp=0` 描述的是同一把尺子，只是坐标系平移了 128。选哪个纯粹看硬件——多数 NPU 的 MAC 吃 `int8`，而 TFLite 的激活用 `uint8`。

所以「`int8` 还是 `uint8`」不是精度问题，是**对称还是非对称**的问题。判断规则：

- 数据关于 0 对称（权重、`tanh` 前的激活）→ 对称量化，`zp=0`，省掉零点修正的几项加法
- 数据单边（ReLU 后、`sigmoid` 后、量化输入图像）→ 非对称，别浪费一半刻度

**公式对但方案错**在量化里非常常见：`scale = (max-min)/(qmax-qmin)` 永远算得对，但 `max`/`min` 取的是谁的范围、有没有先对称化，决定了这个 `scale` 有没有意义。

## 底层机制二：为什么累加器必须是 int32

这是量化实现里最容易出错的一处。看实测（`code/08_quant/acc_width.c`）：

```
K=256, all 127*127:
  int32 = 4129024   (true = 4129024)
  int16 = 256   (溢出了，差 4128768)
  int32 上限 2147483647 / (127*127) = 133144 次乘加才溢出
  (-128)*(-128) = 16384  <- 超出 int8 上界 127
  127*127 = 16129
```

三行关键事实：

1. **`int8` 乘 `int8`，乘积放不进 `int8`。** 最大乘积 `127×127 = 16129`，`int8` 的上界是 127。甚至 `(-128)×(-128) = 16384`，比 `127×127` 还大。所以乘法结果**必须**提升到更宽的整型，通常是 `int16` 或直接 `int32`。
2. **`int16` 累加会溢出，而且溢出得很难看。** `256` 次 `16129` 相加，真值 `4129024`，`int16` 给出 `256`——差值 `4128768`，正好是 `4129024 - 256`。这不是「误差」,是彻底错误的结果。
3. **`int32` 有 133144 次乘加的余量。** 实际模型的 K（内积长度）很少超过 8192，余量足够。

所以标准做法是：

```
int8 × int8  →  int32 累加  →  重新缩放  →  int8
```

中间那个 `int32` 是**硬约束**，不是优化选择。GPU 的 Tensor Core 和 DSP 的 MAC 单元内部都是 `int32` 累加器，原因就是这一条。

**零点修正。** 反量化公式 `x = S(q - Z)` 代入矩阵乘，会多出几项：

```
sum((a - Za)(b - Zb)) = sum(a·b) - Za·sum(b) - Zb·sum(a) + K·Za·Zb
```

四个项里只有 `sum(a·b)` 是真正的乘加，其余三个是加法和常数。实际实现里通常把 `sum(a)` 和 `sum(b)` 预先算好（每行/每列一个标量），然后对累加结果做一次修正。**这就是为什么 `int8` 卷积核里会看到额外的几行加减**，它们不是算错了，是零点修正。

## 底层机制三：逐通道 vs 逐张量

实测（`code/08_quant/quant_axis.py`），权重 `W` 形状 `(64, 128)`，用 `×3.0` 放大以拉开动态范围：

```
per-tensor        max_err=  0.0482  matmul_rel_err=0.00879
per-channel dim0  max_err=  0.0426  matmul_rel_err=0.00577
per-channel dim1  max_err=  0.0414  matmul_rel_err=0.00536
```

逐通道比逐张量的相对误差从 `0.00879` 降到 `0.00536`，**改善 39%**。原因很直接：一个 64×128 的权重矩阵，每行（一个输出通道）的数值范围不同。逐张量必须用**全矩阵**的最大最小值算一个 `scale`，范围大的那个通道决定了所有人的精度；逐通道让每个通道用自己的 `scale`。

**该沿哪个轴？** 这是实测里最值得说的一点：`dim0` 和 `dim1` 都有效，但**深度学习里的惯例是沿输出通道**（`Linear` 的 `out_features`，即 `dim0`；`Conv2d` 的 `out_channels`，即 `dim0`）。理由不在数值，在**实现**：矩阵乘按输出行累加，一个输出行的所有乘加共用同一个 `scale`，重新缩放只需在行尾做一次。沿 `dim1` 也能降误差（本例甚至略好一点），但每次乘加都要用不同的 `scale`，硬件上没法做定点乘加——**除非你的硬件支持每通道缩放**。

所以决策规则是：

| 硬件能力 | 选哪个 | 理由 |
|---|---|---|
| 只有整型 MAC | 沿输出通道（`dim0`） | 行尾统一重缩放 |
| 支持 per-channel scale（多数 NPU） | 沿输出通道 | 惯例一致，工具链兼容 |
| 纯软件演示、只求精度 | 两个轴都试，测误差 | 本例 `dim1` 略好，但不可移植 |

**误差传播。** 单元素误差 `0.0426` 看着不大，但矩阵乘会把 `K=128` 个误差累加。实测 `matmul_rel_err` 是 `0.00536`，约 `0.5%`。这个量级对分类任务通常无害（`top-1` 不变），对回归任务可能致命。**这就是为什么量化必须做端到端精度验证，不能只看单层误差**——Ch 25 会用完整方法重做这件事。

## 底层机制四：量化在编译器的三个落点

量化不是一个 pass，它在三个层次都有落点，而且**每层的做法完全不同**：

```
① 图级（Ch 7 的位置）
   float32 图  →  int8 图
   插入 quantize / dequantize 节点，改算子签名
   由 PyTorch 的 pt2e / torchao 或 TFLite converter 做
        ↓
② 调度级（Ch 8 的位置）
   int8 kernel 的循环结构
   向量宽度变成 16/32（int8 每寄存器装更多）
   累加顺序可能改（影响数值，见 Ch 25）
        ↓
③ 代码生成级（Ch 9 的位置）
   int8 × int8 → int32 累加 → 重缩放 → int8
   目标指令：SDOT/UDOT（ARMv8.2）、VNNI（x86）、SIMD 的 pmaddubsw
```

三层的**证据形态**不同。第一层看 IR 里多了什么节点；第二层看 kernel 的循环；第三层看汇编里出现了哪条指令。调试量化问题时，先定位是哪一层错了，比盲改有效得多（Ch 27 会给完整的诊断流程）。

## 底层机制五：位宽如何改变向量化

量化最直接的收益不在算术，在**一次能搬多少元素**。同一段「逐元素相加」循环，实测生成（`code/08_quant/vec_width.c`，`-O3`）：

x86-64 + AVX2，`int8_t`：

```
add_i8:
	vmovdqu	(%rsi,%rax), %ymm1
	vpaddb	(%rdi,%rax), %ymm1, %ymm0
	vmovdqu	%ymm0, (%rdi,%rax)
	addq	$32, %rax
	cmpq	$4096, %rax
	jne	.L2
```

x86-64 + AVX2，`float`：

```
add_f32:
	vmovups	(%rsi,%rax), %ymm1
	vaddps	(%rdi,%rax), %ymm1, %ymm0
	vmovups	%ymm0, (%rdi,%rax)
	addq	$32, %rax
	cmpq	$16384, %rax
	jne	.L6
```

两段代码**结构完全一样**，指令数也一样（3 条访存/算术 + 2 条循环控制）。区别只在两处：

- `vpaddb` 对 `int8` 做 32 路并行加法（256 位 / 8 位）；`vaddps` 对 `float` 只做 8 路（256 位 / 32 位）
- 循环边界 `4096` vs `16384`——同一个 4 KB 数组，`int8` 只要 4096 个元素，`float` 要 16384 个

**结论：同样的指令数、同样的时间，`int8` 处理 4 倍的数据。** 这是「带宽收益」在代码层面的样子，不是靠什么特殊指令，靠的是每条指令装更多元素。

AArch64 侧同样（`aarch64-linux-gnu-gcc -O3 -S`）：

```
add_i8:                          add_f32:
	ldr	q1, [x0, x2]             ldr	q1, [x0, x2]
	ldr	q0, [x1, x2]             ldr	q0, [x1, x2]
	add	v0.16b, v0.16b, v1.16b   fadd	v0.4s, v0.4s, v1.4s
	str	q0, [x0, x2]             str	q0, [x0, x2]
	add	x2, x2, 16               add	x2, x2, 16
```

`add v0.16b` 一次 16 个字节，`fadd v0.4s` 一次 4 个浮点。又是 4 倍。

### 但「整数点积」没有这么便宜

上面是逐元素加法，`int8` 和 `float` 的直接对应。**点积不是这样**。实测同一个 `dot_i8` 函数在 AArch64 上的核心循环：

```
	smull	v2.8h, v1.8b, v3.8b
	smull2	v1.8h, v1.16b, v3.16b
	saddw	v0.4s, v0.4s, v2.4h
	saddw2	v0.4s, v0.4s, v2.8h
	saddw	v0.4s, v0.4s, v1.4h
	saddw2	v0.4s, v0.4s, v1.8h
```

六条指令处理 16 个元素。逐条看它在做什么：`smull` 把 8 个 `int8` 乘成 8 个 `int16`（这就是 Ch 11 前面说的「乘积放不进 `int8`」在指令层的体现，`smull` 的目标是 `.8h`——**8 个半字**）；`smull2` 处理高 8 字节；四条 `saddw` 把 `int16` 结果符号扩展累加到 `int32`。

**这六条指令正是「int8 → int16 乘 → int32 累加」那条链的硬件形态。** 编译器没有偷懒，是架构就这么设计的：基础 ARMv8-A 没有 `SDOT` 指令。

如果目标是 ARMv8.2 的 dot product 扩展，同样的循环会变成：

```
	sdot	v0.4s, v1.16b, v3.16b
```

一条。16 个元素、16 次乘加，一个周期级指令。**这就是 `-march=armv8.2-a+dotprod` 能让量化模型快好几倍的原因**，也是为什么部署前要确认目标 CPU 的扩展。

这条事实有个直接的工程后果：**`int8` 的收益取决于目标架构，不是位宽本身**。逐元素运算稳拿 4 倍（指令宽度）；点积在无 `SDOT` 的核上只有约 2.7 倍（6 条指令 vs 16 个元素，而 `fmla` 是 1 条 4 个元素 = 4 条指令 16 个元素）；有 `SDOT` 才是真正的量级差。

## 底层机制六：校准——`min`/`max` 从哪来

前面所有公式都假定你**知道**数据的 `min` 和 `max`。但推理时激活值在运行时才产生，编译期怎么知道？

答案是用**校准集**（calibration set）跑一遍浮点模型，记录每层激活的统计量。这一步的质量直接决定量化模型的成败，而且它有一个残酷的性质：**样本少的时候估计出的范围会偏窄，导致大量值被裁剪**。

实测（`code/08_quant/calib.py`，真实分布 `N(0.5, 2.0)`，用前 `n` 个样本估范围，再用全量 4096 个样本测裁剪比例）：

```
n=    8  scale=0.023247  裁剪比例=20.12%  quant_err_max=0.0116
n=   32  scale=0.031123  裁剪比例= 4.76%  quant_err_max=0.0156
n=  128  scale=0.047246  裁剪比例= 0.49%  quant_err_max=0.0236
n= 1024  scale=0.056904  裁剪比例= 0.05%  quant_err_max=0.0285
n= 4096  scale=0.064276  裁剪比例= 0.00%  quant_err_max=0.0321
```

这张表有个反直觉的形状：**样本越多，`scale` 越大，量化误差越大，但裁剪越少**。

- `n=8` 时 `scale` 很小（`0.0232`），因为 8 个样本的范围窄。看着精度高（`quant_err_max = 0.0116`），代价是 **20% 的激活被裁到边界外**。裁剪误差不体现在 `quant_err_max` 里，因为那些值直接被压平了
- `n=4096` 时 `scale` 大（`0.0643`），量化误差翻了三倍，但没有值被裁

这是量化的核心权衡：**`scale` 小 = 分辨率高但容易裁剪；`scale` 大 = 不裁剪但分辨率低**。选哪边取决于任务：

| 任务类型 | 偏哪边 | 理由 |
|---|---|---|
| 分类（`softmax` 输出） | 宁可裁剪 | 极端值多半是异常样本，压平它们反而稳定 |
| 回归 / 检测（输出要精确） | 宁可分辨率低 | 裁剪会直接改变输出数值 |
| 中间层激活（ReLU 后） | 用小 `scale` + 百分位裁剪 | 长尾分布，最大值常是离群点 |

工程上的常见做法不是用真 `min`/`max`，而是用**百分位**（比如 `99.9%` 分位）作为范围端点，牺牲 0.1% 的极端值换取更好的分辨率。这个选择要在端到端指标上验证，不能靠单层数字定。

## 实测：一个完整的 int8 矩阵乘

`code/08_quant/int8_kernel.c` 是一个能跑的完整实现，包含整数路径、零点修正的框架、重缩放与饱和。实测输出：

```
int32 accum == float ref : yes
int32 max = 231
out_scale = 0.54978353  (1/out_scale = 1.8189)
elements needing saturation if scale=1 : 2 / 16
int8 round-trip max|err| = 0.771652  (相对 max 0.003340)

first row, int32 -> int8 -> dequant
      -5 ->    -3 ->   -5.457  (ref   -5.000)
      -4 ->    -2 ->   -3.638  (ref   -4.000)
     119 ->    65 ->  118.228  (ref  119.000)
      86 ->    47 ->   85.488  (ref   86.000)
```

逐行解读：

**`int32 accum == float ref : yes`** —— 输入是 `[-10, 10]` 的小整数，`int32` 累加与浮点参考**完全一致**。这说明整数路径本身没有精度损失，损失全部来自「输入被量化」和「输出被重缩放」两步，**不来自乘加**。这个结论很重要：如果你的实现出现「乘加结果对不上」，那是 bug，不是量化误差。

**`elements needing saturation if scale=1 : 2 / 16`** —— 如果偷懒不重缩放（`out_scale = 1`），16 个元素里有 2 个超出 `int8` 范围。这两个必须饱和到 `127` 或 `-128`。**饱和与环绕是两回事**：饱和是 `min(max(v, -128), 127)`，环绕是 `(int8_t)v` 直接截断低位。前者误差有界，后者可能把 `231` 变成 `-25`。C 语言里 `(int8_t)231` 是**实现定义行为**（多数编译器给 `-25`），所以生产代码必须显式 clamp。

**`int8 round-trip max|err| = 0.771652`** —— 绝对误差看着大，但相对矩阵最大值 `231` 只有 `0.334%`。**这就是量化误差的正常形态：绝对误差随数值大小线性增长，相对误差才是稳定的那个指标**。下一章讲数值对齐时会反复用到这个区分。

**最后四行**是同一行的四个元素，走完 `int32 → int8 → dequant`。注意 `-5` 变成 `-3`（误差 `0.457`），`119` 变成 `65`（误差 `0.772`）。误差不等，因为 `scale` 是统一的 `0.5498`，小数值被相对地伤得更重。这解释了为什么**逐通道量化对小通道特别有价值**——如果某个通道的值本来就小，用全局 `scale` 会把它的有效位数压没。

## 对比例子：五种量化方案的取舍

同一条公式，工程上有五种组装方式。它们不是「新旧替代」关系，到现在（2026 年）五种都还在生产里用：

| 方案 | 权重 | 激活 | 累加 | 校准 | 体积 | 算力收益 | 典型精度损失 | 用在哪 |
|---|---|---|---|---|---|---|---|---|
| 无量化 | fp32 | fp32 | fp32 | 不需要 | 4 B/参数 | 无 | 0 | 服务器、精度基线 |
| 权重量化 | int8 | fp32 | fp32 | 不需要 | 1 B/参数 | 无（只省带宽） | < 0.5% | CPU 上跑大模型（`llama.cpp` 的 Q8_0） |
| 4-bit 权重 | int4 | fp16 | fp16 | 不需要 | 0.5 B/参数 | 无（只省带宽） | 1–3% | 端侧 LLM |
| 全整数量化（PTQ） | int8 | int8 | int32 | **需要** | 1 B/参数 | 2–4× | 0.5–2% | TFLite、MCU 部署 |
| 量化感知训练（QAT） | int8 | int8 | int32 | 不需要（训练时已模拟） | 1 B/参数 | 2–4× | 0.1–0.5% | 精度敏感场景 |

读这张表要注意三件事：

**第一，「省带宽」和「省算力」是两条独立收益。** 权重量化只动权重，激活还是浮点，乘加还在浮点单元上——所以它在 MCU 上**一点用都没有**（MCU 本来就没有浮点单元，省了带宽还是要软浮点）。全整数量化才让乘加跑在整数单元上。这解释了为什么 `llama.cpp` 在 PC 上用 4-bit 权重效果好，而这套方案搬到 Cortex-M3 上完全行不通。

**第二，PTQ 与 QAT 的差别只在「校准够不够」。** PTQ 用校准集估范围，一次搞定，几分钟；QAT 在训练时插入伪量化节点，让模型学会适应量化误差，代价是要重训。精度差一个数量级（`0.5–2%` vs `0.1–0.5%`）。**先试 PTQ，精度不够再上 QAT**——这是标准顺序，不要一上来就 QAT。

**第三，`int4` 不是「更小的 `int8`」。** 4 位只有 16 个刻度，非对称量化会浪费掉一半，所以 `int4` 几乎总是对称量化（`Z = 0`）。而且 4 位不能直接做乘加——硬件要先解包成 8 位或 16 位。这层解包开销在 GPU 上有专门指令，在 MCU 上就是纯粹的额外指令。**位宽越低位，收益越依赖硬件支持。**

再对照 Ch 10 的 oop：MLIR 的 `linalg` 层看到的还是「矩阵乘」这个语义，量化改动的是**它的操作数类型**（`tensor<4x8xf32>` → `tensor<4x8xi8>`）和**它周围的 quantize/dequantize 节点**。语义没变，类型变了——这就是为什么量化可以在图级完成，而不必重写整个后端。

## 踩雷集锦

1. **「量化成功了」但根本没生效。** 这是本章最严重的坑，实测抓到了：在 torch 2.9.1 上 `torch.ao.quantization.quantize_dynamic(nn.Linear, dtype=torch.qint8)` 返回的对象**仍然是 `torch.nn.modules.linear.Linear`**，`weight.dtype == torch.float32`，没有 `_packed_params` 属性，`forward` 的输出与浮点模型 `torch.equal(...) == True`、`max|diff| == 0.0`。把引擎切成 `x86` / `fbgemm` / `qnnpack` / `onednn` 四个，**结果完全一样**。
   纠正：不要相信「没报错就是生效了」。三条检查缺一不可：
   ```python
   print(type(m))                        # 应该是 QuantizedLinear 之类，不是 Linear
   print(m.weight.dtype)                 # 应该是 torch.qint8，不是 float32
   print(hasattr(m, "_packed_params"))    # 应该是 True
   ```
   三条里有一条不对，量化就没发生。`torch.ao.quantization` 在 2.9 已标记 deprecated，官方迁移路径是 `torchao`（`quantize_` / `prepare_pt2e` + `convert_pt2e`）；继续用旧 API 会遇到这类静默失效。

2. **以为 `int8` 存储就等于 `int8` 计算。** 权重量化（W8A16、W4）只把**权重**压到低位宽，激活仍是浮点，计算也在浮点单元上做。它的收益是**带宽和体积**，不是算力。全整数量化（W8A8）才把两边都变成整数，才能吃到整数 MAC 的吞吐。两个目标不同，别混为一谈。

3. **逐通道轴选错。** 上面实测 `dim0` 和 `dim1` 都能降误差，于是有人随手选了一个。但如果选的是「每次乘加都要换 scale」的轴，硬件没法实现，工具链会拒绝编译或者退化成逐张量。惯例是**沿输出通道**，理由是重新缩放可以放在行尾。选之前先确认硬件支持什么。

4. **忘了饱和与环绕的区别。** `(int8_t)231` 在 GCC 上给 `-25`，值是错的但程序不崩。这类 bug 在生产里表现为「精度莫名其妙掉了一大截」。所有从宽整型转窄整型的地方都要显式 `clamp`，并记住 `int8` 的范围是 `[-128, 127]`——`127` 不是 `128`。

5. **用单层误差判断整模型能不能用。** 单元素误差 `0.0426`、矩阵乘相对误差 `0.5%`，看着都能接受。但误差会跨层累积，而且在 `softmax`、`layernorm` 这类对输入范围敏感的算子上会放大。判断标准只能是**端到端任务指标**（`top-1` 一致率、输出余弦相似度），不是任何单层数字。

6. **在量化模型上用 `torch.allclose` 的默认容差。** 默认 `rtol=1e-5` 对 `int8` 模型是不现实的要求，它必然失败。容差要按量化步长推：输出 `scale` 为 `S` 时，单元素误差上界约 `S/2`，你再留 2 到 3 倍余量。

## 本章重点整理

- 仿射量化只有两个参数：`scale = (max-min)/(qmax-qmin)`、`zero_point` 把真实 `0.0` 映射到刻度上。正向 `q = round(x/S) + Z`，反向 `x ≈ S(q-Z)`。
- 量化误差的唯一来源是 `round`，上界 `S/2`。乘加本身在 `int32` 里没有损失（实测 `int32 accum == float ref : yes`）。
- `int8 × int8` 的乘积放不进 `int8`（`127×127=16129`）；`int16` 累加 `K=256` 次就溢出（实测给出 `256` 而非 `4129024`）；所以累加器必须是 `int32`，余量 133144 次乘加。
- 逐通道量化沿输出通道，相对误差实测从 `0.00879` 降到 `0.00577`；沿输入通道数值上也能降（`0.00536`），但硬件不可移植。
- 量化在编译器的图级、调度级、代码生成级各有一个落点，三层的调试手段不同。
- 绝对误差随数值线性增长，**相对误差才是稳定指标**（实测 `0.771652 / 231 = 0.334%`）。
- 判断量化是否生效要查三样：类型、`weight.dtype`、`_packed_params`。只看「没报错」会被静默失效骗过去。
