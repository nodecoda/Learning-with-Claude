# Ch 29 取舍与决策表

> **目标**：把「编译器怎么工作」换成「工程上怎么选」。学完这章，面对一个模型和一块板子，你能在六个决策点上各选一格，并说清代价落在精度、体积、延迟还是维护成本上。

> **环境**：本章引用的本机数字来自 PyTorch 2.9.1+cpu、`aarch64-linux-gnu-gcc` 11.4、`arm-none-eabi-gcc` 10.3、QEMU 6.2，全部在 Final 的可复现实验中产生（目录 `mlp-edge/`，命令见 Final）。ExecuTorch/TVM/IREE/ORT/TFLite 未安装，涉及它们的结论标「源码/文档依据」。

## 先建立直觉

选型不是「哪个框架最好」，而是**六个互相牵制的旋钮**：

```
        ┌──────────── 精度预算 ────────────┐
        │                                  │
   shape 策略 ── 融合强度 ── 量化方案       │
        │            │           │         │
        └──── 算子实现方式 ── 后端 ── 运行时形态
                     │
                体积 / 延迟 / 维护成本
```

动一个旋钮，另外几个的代价会变。把量化从 fp32 改成 int8，体积降到 1/4，但精度预算被吃掉一部分；为了补精度去做 QAT，维护成本上升；为了压延迟去激进融合，数值风险上升。**没有全局最优，只有约束下的可行解**。

下面六个决策，每个给一张表和一个「5 分钟版」：它直接指出表里哪一行最该先看，以及什么条件下才需要往下读。

## 决策 1：动态 shape 支持到什么程度

| 方案 | 做法 | 代价 | 适用场景 |
| --- | --- | --- | --- |
| 静态导出 | 编译期固定所有维度（batch=1、序列长度固定） | 换 shape 必须重编译；但 kernel 可完全特化，内存可静态规划 | 边缘推理的绝大多数场景；MCU 唯一现实选择 |
| 动态维度 | 用符号维度导出（`Dim("batch")`），运行时接受范围内任意值 | 运行时多一层 shape 检查与分支；部分算子/后端不支持；性能通常低于特化 | 服务端批处理、手机端变长输入 |
| 运行时特化 | 先按动态图编译，首次遇到某 shape 再生成专用 kernel（JIT/AOT 缓存） | 首次延迟高；需要缓存与版本管理；体积可能翻倍 | 形状集合有限但已知（几个固定分辨率） |

### 实测：静态导出拒绝「意外 shape」

本机 `torch.export` 用 batch=1 导出后，喂 batch=2：

```
Guard failed: x.size()[0] == 1
torch._dynamo.exc.UserError: Constraints violated (batch)!
```

改成符号维度后，batch 1/2/7 都能跑（实测）。注意：`Dim("batch")` 在 batch=1 上导出时，如果模型内部把 batch 特化成常量，会报 `You marked batch as dynamic but your code specialized it to be a constant (1)`；此时应改用 `Dim.AUTO` 或换一个 batch>1 的样例导出。

### 代价怎么算

静态化的收益不只是「省掉检查」，而是**内存可以静态规划**（Ch 22）。本课 Final 的 MLP 静态化后，激活只需 `64 × 4 = 256 B` 的 `hidden` 加 `10 × 4 = 40 B` 的 logits，全部在栈上，`.bss = 0`（实测）。如果 batch 动态，`hidden` 大小就要在运行时算，栈上放不下，必须引入 arena 或堆。

> **5 分钟版**：先看「静态导出」那一行的代价栏。如果「换 shape 要重编译」你能接受，就停在这一行；不能接受再看「运行时特化」行，但要把首次延迟写进验收。

## 决策 2：融合激进程度

| 档位 | 典型变换 | 数值风险 | 收益 | 适用 |
| --- | --- | --- | --- | --- |
| 保守 | 只融 elementwise 链（`mul → add → relu`） | 极低：保持运算顺序时逐位相同（本课实测） | 减少中间张量与内存往返 | 默认选择；数值敏感模型 |
| 中等 | 加入 reduction 融合、layout 变换 | 中：归约顺序改变会引入舍入差 | 减少 kernel 启动与中间 buffer | 卷积/Transformer 主干 |
| 激进 | 重结合（reassociation）+ fast-math + 跨算子代数化简 | 高：可改变结果最后几位，甚至改变分类 | 更好的向量化与指令选择 | 延迟极限、可接受精度回归 |

### 实测：融合本身不改数值，重排才改

- 同序 `relu((x*2 + y*3) - z)` 与融合 `relu(x*2+y*3-z)`：**逐位相同**，`max|diff| = 0.0`。
- 重结合 `relu(x*2 + (y*3 - z))`：`bitwise_equal = False`，`max|diff| = 9.5367431640625e-07`，256 个元素里 36 个不同。
- `1e8 + 1e-8 - 1e8`：float32 得 `0.0`，float64 得 `1.4901161193847656e-08`。

结论：**融合是内存优化，重排是数值变换**，两者要分开评估。允许融合不等于允许重排。

### 激进档在本课的实测代价

QEMU 上的 AArch64 计时无法分辨优化档位：同一份 `-O2` 二进制，单次运行在 443–918 µs 之间波动（主机负载 28 核、平均负载 54），`-O3 -ffast-math` 也是 417–719 µs。**所以这里不报「快百分之几」**，那会是假精确。

能复现的是代码形态：`-O2` 生成标量 `fmadd s0, s2, s1, s0` 的单元素循环（`mlp_forward` 共 68 条指令），`-O3 -ffast-math` 生成 4 lane 的 `fmla v0.4s` 向量循环加水平归约（104 条指令；寄存器压力上升，栈帧从 `#0x120` 变成 `#0x140`）。这是 Ch 13 讲过的向量化差异，不是时间测量。

数值上，`-ffast-math` 版本对 PyTorch 参考的 `max_abs` 是 `1.19e-07`，`-O2` 是 `4.17e-07`——更接近只是这次数据上的巧合，不构成保证；两者都 `bitwise = False`。真正的教训是：**收益要上硬件量，数值代价要写测试**。

> **5 分钟版**：看「保守」行的数值风险栏。只要你能做到「保持运算顺序」，这一行的风险就是零；只有在保守行仍达不到延迟预算时，才往下读「中等」和「激进」。

## 决策 3：量化方案

| 方案 | 权重 | 激活 | 精度损失量级（本课实测/依据） | 硬件收益 | 适用 |
| --- | --- | --- | --- | --- | --- |
| 无量化 | fp32 | fp32 | 0（基准） | 无 | 精度优先、算力充足 |
| 权重量化 W8A16 | int8 | fp16/bf16 | 本课 MLP 仅量化权重：`max_abs 1.85e-3` | 权重体积 4× 下降；需 fp16 算力 | 权重带宽瓶颈、激活精度敏感 |
| 权重量化 W4 | int4 | fp16 | 通常大于 W8（**未实测**，依赖分组与校准） | 权重再降 2× | LLM 权重带宽瓶颈 |
| 全整数量化 W8A8 | int8 | int8 | 本课 MLP 固件（含 hidden requantize）：`max_abs 5.47e-3`，`rel 2.2e-2`；纯 NumPy 模拟为 `4.996e-3` | 体积 4×、整数 SIMD 吞吐高、无 FPU 也能跑 | MCU、手机 CPU、量化 kernel 成熟的后端 |
| QAT | int8 | int8 | 通常最小（**未实测**；依赖训练） | 同 W8A8 | 精度掉点不可接受、有训练管线 |

### 实测：体积与精度的交换比

同一个 MLP：

- fp32 的 `W1+W2` 共 `203,264 B`（加 bias 是 `203,560 B`）；int8 权重 `50,816 B`（4×，实测）。
- Cortex-M3 固件：fp32 软浮点 `text 208,646 B`；int8 `text 54,686 B`（约 3.8×）。int8 版内层循环不再调 `__aeabi_fmul`，但外层反量化仍有 18 个 `__aeabi_*` 符号（实测 `nm`）。
- 精度：W8A8 固件输出的 `max_abs = 5.47e-03`、`max_rel = 2.22e-02`；同一量化方案在 NumPy 里不模拟第二层 requantize 时是 `4.996e-03`。参考 logits 量级约 0.6，最大误差约 0.9%；top-1 仍是类别 2。
- 只量化权重（激活保 fp32）把误差压到 `1.85e-3`，但省下的只有权重带宽，不省激活带宽，也不省乘法器。

这里有个容易忽略的点：**W8A8 的收益要乘以「目标是否有 int8 点积指令」**。Cortex-M3 没有 DSP 扩展，int8 乘加仍是标量指令，收益主要来自体积和缓存；Cortex-M4/M7 的 SIMD 才有 2–4 路并行（**未在本机实测**，需查对应内核手册）。

### 校准与 per-channel

Ch 11 的实测：per-tensor 量化 64×128 权重 `max_err 0.0482`，per-channel(dim0) `0.0426`，per-channel(dim1) `0.0414`；matmul 相对误差从 `8.79e-3` 降到 `5.77e-3` / `5.36e-3`。**per-channel 几乎总是值得做**，代价只是多存几十个 scale（本课 MLP 的 74 个 scale 共 296 B）。

> **5 分钟版**：先看「全整数量化 W8A8」行的硬件收益栏，确认目标有 int8 点积指令；没有就停在「权重量化 W8A16」行。W4 那一行在你没有校准集时直接跳过。

## 决策 4：算子库 vs 代码生成 vs 混合

这是 Ch 23 的决策表，这里给出可直接查的判据。

| 方案 | 判据（算子数 × 形状稳定性 × 体积预算） | 优点 | 缺点 |
| --- | --- | --- | --- |
| 纯算子库 | 算子少（< 20）、形状稳定、有现成 kernel 或愿意手写 | 每个 kernel 可手工调优；运行时无编译器；体积可控 | 新算子要人写；形状多则 kernel 爆炸 |
| 纯代码生成 | 算子多、形状多变、团队有编译器能力 | 一套后端覆盖所有算子；新模型无需新 kernel | 生成代码质量依赖调度；工具链体积大 |
| 混合 | 热点算子手写/调库，其余生成 | 兼顾峰值性能与覆盖 | 两套路径要维护；边界处易出数值/布局不一致 |

### 用本课数字做一次判断

Final 的 MLP 有 3 个算子（`linear/relu/linear`），形状固定（1×784 → 1×64 → 1×10），Flash 预算紧。手写 `mlp_forward`：

- Cortex-M3 `-O2` 编译后 `.text = 176 B`（仅函数，不含权重）。
- 整个固件 `208,646 B`，其中权重与输入占 `206,696 B`，代码不到 1%。

换成「通用代码生成 + 完整运行时」这一侧：`libc.a` 单文件就 `4,939,918 B`（实测），本课 MLP 的 AArch64 静态二进制 `850,224 B`。作为极端对照，Ch 19 的 `compute` 在裸机上只有 `289 B`，而同样走 AArch64 静态链接的 `add` 是 `641,112 B`——**641,112 对 289，约 2,218 倍**。这个倍率不是「代码生成低效」，而是「通用运行时 vs 无运行时」的差距。

反过来，如果你有 200 个算子，手写 kernel 的成本是 200 份测试、200 份边界处理；这时候代码生成的「一套逻辑覆盖全部」就是压倒性优势。

> **5 分钟版**：看「纯算子库」行的判据栏。算子数 < 20 且形状稳定就选它；判据不成立再跳到最后一行「混合」，把热点留给手写。

## 决策 5：后端选择

| 后端 | 算力 | 内存 | 工具链成熟度 | 生态 | 典型场景 |
| --- | --- | --- | --- | --- | --- |
| AArch64 | 高（多核、NEON、可选 SVE） | 大（GB 级） | 高（GCC/Clang/LLVM 完整） | 极好 | 边缘服务器、网关、树莓派类 |
| Cortex-M | 低（几十–几百 MHz，无 MMU） | 极小（几十–几百 KB） | 高（`arm-none-eabi-gcc`，但无 OS 设施） | 好（CMSIS、厂商 SDK） | 传感器节点、家电、MCU 推理 |
| RISC-V | 跨度大（MCU 到应用处理器） | 跨度大 | 中（工具链可用，碎片化） | 成长中 | 自研芯片、开放指令集产品 |
| NPU | 高（TOPS 级，但受限于算子集） | 中（片上 SRAM 紧） | 低–中（厂商编译器封闭） | 依赖厂商 | 手机、摄像头、车载 |

### 本课实测的三后端差异

同一个 `int add(int a,int b){return a*b+1;}`：

- AArch64：`mul w8, w1, w0` / `add w0, w8, #1`（`llc -O2`）。
- RISC-V 64：`mulw a0, a1, a0` / `addiw a0, a0, 1`。
- Cortex-M3：`muls` + `adds`（`arm-none-eabi-gcc -O2`，没有 `mla` 合并）。

同一个 MLP 固件：Cortex-M3 fp32 `208,646 B`，int8 `54,686 B`；AArch64 静态 `850,224 B`，动态 `218,200 B`。**后端选择首先决定的是「有没有 FPU、有没有操作系统」，而不是指令集名字**。

Cortex-M3 的浮点会降到 `__aeabi_fmul/fadd`（实测反汇编），必须链接 `-lgcc`；一旦忘了，链接期就是 `undefined reference to '__aeabi_fmul'`。这不是「性能差一点」，是「根本跑不起来」。

> **5 分钟版**：看「Cortex-M」行的工具链成熟度栏。如果你的板子有 OS 且内存是 GB 级，直接跳到「AArch64」行；只有芯片已定且是自研核时才看「RISC-V」。

## 决策 6：运行时形态

| 形态 | 启动 | 内存管理 | 可用设施 | 体积量级 | 适用 |
| --- | --- | --- | --- | --- | --- |
| 无 OS 裸机 | 复位向量直接跑 | 全静态：栈 + `.data`/`.bss`，无堆 | UART、定时器，全部自己写 | 数百 B–数百 KB | MCU、深嵌入式 |
| RTOS | 调度器 + 任务 | 静态分配或固定池，少用堆 | 任务、队列、信号量 | 数 KB–数十 KB | 需要并发与外设管理的 MCU |
| Linux 用户态 | 进程启动 | `malloc`/`mmap` 可用 | 文件、线程、动态链接 | 数百 KB–数 MB | 边缘网关、工业 PC |
| Android NNAPI | App 进程 + 系统服务 | 系统管理 | 硬件加速器抽象 | 系统内置 | 手机 App |

### 裸机 vs 用户态的实测落差

- 裸机 `compute` 固件：`text 289 B`，`data 0`，`bss 0`，`firmware.bin 289 B`。
- AArch64 静态链接的 `add`：`641,112 B`，其中 `text 512,834 B`、`data 22,520 B`、`bss 22,256 B`。
- 同一个 MLP：裸机 `208,646 B`（含 206,696 B 权重与输入），AArch64 静态 `850,224 B`，动态 `218,200 B`。

裸机版本没有 `malloc`，也不需要；`model.c` 里 `float hidden[64]` 直接在栈上，链接脚本给 64 KB RAM，实测 `.bss = 0`。这说明**只要 shape 静态、内存规划得当，推理不需要堆**。一旦引入动态 shape 或变长序列，这个结论立刻失效。

> **5 分钟版**：看「无 OS 裸机」行的内存管理栏。能接受「全静态、无堆」就选它；一旦需要并发任务，直接跳到「RTOS」行。

## 按设备选型的完整流程

从 MCU 到 SoC 四档，每档给一条决策路径。

### 第 1 档：MCU（Flash ≤ 512 KB，RAM ≤ 128 KB，无 OS）

```
1. 算子数 < 20 且形状固定？
   ├─ 否 → 换更大的芯片，或选带 NPU 的 MCU（本档不适用）
   └─ 是 → 2
2. 有 FPU？
   ├─ 有（M4F/M7）→ fp32 手写 kernel，先跑通再考虑 int8
   └─ 无（M0/M3）→ 直接 W8A8，避免软浮点（本课 M3 实测软浮点）
3. 体积预算：权重 + 代码 + 栈 ≤ Flash 的 70%
   └─ 超了 → 量化到 int8；仍超 → 换芯片或剪模型
4. 验收：定点/浮点输出与参考的 max_abs、top-1 一致；`size` 三项有记录
```

本课 Final 路线 B 就是这一档：Cortex-M3、无 FPU、64 KB RAM、`text 208,646 B`（fp32）或 `54,686 B`（int8）。

### 第 2 档：MCU + RTOS / 带 DSP 扩展

```
1. 需要并发采集与外设？ → RTOS，任务间用静态队列传 tensor 指针
2. 有 DSP 扩展（M4/M7、RISC-V P 扩展）？ → int8 SIMD，收益 2–4×（需实测）
3. 内存：arena 预分配，禁止在推理路径 malloc
4. 验收：最坏情况延迟（含抢占）而非平均延迟
```

### 第 3 档：嵌入式 Linux（AArch64 / RISC-V 应用核）

```
1. 模型是否频繁更新？ → 是：保留解释器/动态加载；否：AOT 静态链接
2. 延迟预算 < 10 ms？ → 关掉动态链接与多余 libc，静态链接 + 精简运行时
3. 需要多模型？ → 共享 arena，按峰值而非总和分配（Ch 22）
4. 验收：p99 延迟、RSS、二进制 `size`
```

### 第 4 档：SoC + NPU / GPU

```
1. 算子集是否被厂商编译器完整支持？ → 查 operator support 表，不靠猜
2. 不支持的算子回退到 CPU 的比例？ → 回退 > 20% 时端到端收益可能归零
3. 量化是否匹配 NPU 要求（int8/int16、per-channel）？ → 不匹配就先量化
4. 验收：端到端而非单算子；含 H2D/D2H 拷贝与同步开销
```

第 4 档最容易翻车：单算子 benchmark 快 10×，端到端因为回退与拷贝只快 1.2×。

## 三条最常见的错误决策

### 错误 1：「先上动态 shape，以后再说」

后果：静态导出失败（`Guard failed: x.size()[0] == 1`），团队改成动态图；到了 MCU 上发现动态 shape 需要运行时 arena 与 shape 分支，`hidden` 放不进栈，`bss` 暴涨，最后又退回静态。**代价是两周返工**。正确做法是先静态跑通，确有变长需求再加动态路径。

### 错误 2：「int8 一定更快，先量化再说」

后果：目标没有 int8 点积指令，权重解量化（`int8 → float`）的开销吃掉了收益；或者 per-tensor 量化遇到离群通道，精度掉点超预算（本课 per-tensor 权重 `max_err 0.0482`，per-channel 降到 `0.0426`）。**代价是精度回归 + 性能不升**。正确做法是先确认目标指令集与 kernel 支持，再选 per-channel。

### 错误 3：「体积按源码大小估」

后果：源码 200 KB，静态链接后 850 KB（本课实测），Flash 装不下；更隐蔽的是**优化级别救不了体积**——同一个 AArch64 静态二进制，`-O0` 为 850,240 B，`-O2` 为 850,224 B，`-Os` 为 850,200 B，三者只差几十字节，因为体积由静态 libc（`libc.a` 单文件 4,939,918 B）主导，你自己的代码只占千分之一。**代价是临上线换芯片或砍功能**。正确做法是每次构建都跑 `size`，先看 `text` 里有多少是 libc，再决定是换运行时还是砍功能。

## 六个决策的耦合：三个真实组合

单看表容易以为可以逐项最优。实际项目里，选一格会锁死另一格。下面三个组合都来自本课实测数据，可以直接当模板。

### 组合 A：MCU 传感器节点（约束最紧）

| 决策 | 选择 | 被谁锁死 |
| --- | --- | --- |
| shape | 静态 | RAM 64 KB，动态 arena 放不下 |
| 融合 | 保守 | 没有 FPU，重排误差无法用测试覆盖 |
| 量化 | W8A8 | 无 FPU，fp32 会降到 `__aeabi_fmul` |
| 实现 | 手写 kernel | 3 个算子，形状固定 |
| 后端 | Cortex-M3 | 芯片已定 |
| 运行时 | 裸机 | 无 OS，无堆 |

结果：`text 54,686 B`，`.bss 0`，栈上 `hidden[64]` 占 256 B。这里**量化不是为了快，是为了能跑**——fp32 版本 `208,646 B` 也能放进 256 KB Flash，但每次乘法都要进软件浮点库。

### 组合 B：边缘网关（约束中等）

| 决策 | 选择 | 被谁锁死 |
| --- | --- | --- |
| shape | 静态 + 多份特化 | 输入分辨率只有 2–3 种 |
| 融合 | 中等 | 有 NEON，reduction 融合收益明显 |
| 量化 | W8A8 或 fp32 | 有 FPU，fp32 可接受；量化看吞吐 |
| 实现 | 混合 | 主干手写，边缘算子生成 |
| 后端 | AArch64 | 有 Linux、有 GB 级内存 |
| 运行时 | Linux 用户态 | 需要网络与文件 |

这一档最常见的错误是照搬组合 A 的「裸机思维」，把所有东西静态化，结果失去模型热更新能力。

### 组合 C：手机 App（约束最松但最杂）

| 决策 | 选择 | 被谁锁死 |
| --- | --- | --- |
| shape | 动态 | 用户输入尺寸不可控 |
| 融合 | 中等 | 依赖框架的图优化 |
| 量化 | W8A8 / QAT | 功耗与发热 |
| 实现 | 调库 | 算子多、更新快 |
| 后端 | NPU + CPU 回退 | 厂商编译器算子覆盖不全 |
| 运行时 | Android NNAPI | 系统 API |

这一档的验收必须端到端：NPU 单算子快 10×，回退 20% 的算子就可能把收益吃光。

## 把决策写进一页选型记录

选型讨论最常见的失败是「各说各的」：有人说精度，有人说体积，没人把它们放进同一张纸。下面这份模板可以直接抄进设计文档，六行填完，分歧会自然收敛。

```
目标设备：____________（芯片型号 / OS / Flash / RAM）
模型：______ 个算子，shape ______，更新频率 ______
决策 1 shape：静态 / 动态 / 运行时特化     理由：______
决策 2 融合：保守 / 中等 / 激进           理由：______
决策 3 量化：无 / W8A16 / W4 / W8A8 / QAT  理由：______
决策 4 实现：库 / 生成 / 混合             理由：______
决策 5 后端：AArch64 / Cortex-M / RISC-V / NPU
决策 6 运行时：裸机 / RTOS / Linux / NNAPI
验收：max_abs ≤ ____；text+data ≤ ____ B；p99 ≤ ____ ms
```

最后一行是重点：**没有验收数字的选型等于没选**。本课 Final 的验收标准就是按这个模板写的（`max_abs ≤ 1e-5`、`text ≤ 256 KB`、单次推理 ≤ 10 ms）。

## 决策速查卡

| 你的约束 | 先看哪个决策 | 默认答案 |
| --- | --- | --- |
| Flash < 256 KB | 决策 3、4、6 | W8A8 + 手写 kernel + 裸机 |
| 延迟 p99 < 5 ms | 决策 2、5 | 中等融合 + AArch64/NEON |
| 模型每周更新 | 决策 4 | 代码生成或解释器 |
| 精度不能掉 | 决策 2、3 | 保守融合 + 无量化/QAT |
| 输入尺寸可变 | 决策 1 | 动态维度或运行时特化 |
| 多硬件平台 | 决策 5、6 | 代码生成 + 可裁剪运行时 |

## 本章重点整理

- 六个决策点互相牵制，不存在「全都选最优」；先定约束，再查表。
- 静态 shape 的收益是**内存可静态规划**，不只是省几条检查。
- 融合不改数值，重排才改；`-ffast-math` 的收益要上硬件量，数值代价要用回归测试换。
- 量化的收益取决于目标是否有 int8 指令；per-channel 几乎总是值得。
- 算子少、形状稳、体积紧 → 手写；反之 → 代码生成；中间 → 混合。
- 后端首先决定「有没有 FPU、有没有 OS」，而不是指令集名字。
- 无堆推理是可行的，前提是 shape 静态且内存规划正确。
- 体积必须用 `size` 实测，源码大小与最终二进制没有可靠比例关系。
