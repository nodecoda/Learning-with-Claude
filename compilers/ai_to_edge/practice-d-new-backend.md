# 练习 D — 给一个算子换后端

> **任务**：拿一份已经在 AArch64 上跑通的算子，把它编到 Cortex-M3 与 RISC-V 上，逐条对比三个后端的产物，回答「同一个语义，为什么指令数、体积、库依赖完全不同」。做完这个练习，你拿到任何一份新的目标架构文档，都知道该先看哪几项。
>
> **难度**：中等。需要 Ch 18–21 的内容。
>
> **预计时间**：3–4 小时。

> **环境**：LLVM 14、aarch64-linux-gnu-gcc 11.4、arm-none-eabi-gcc 10.3、riscv64-linux-gnu-gcc 11.4、qemu 6.2。全部在 `code/12_newbackend/` 可复现。

## 为什么练这个

Ch 18–20 分别讲了三个后端「长什么样」，但真实工程里你要做的是**同一个算子在三者之间迁移**。迁移时会遇到四类决策：

1. 哪些操作有硬件指令（除法？浮点？位操作？）
2. 没有硬件指令时，编译器生成什么（库调用？软件模拟序列？）
3. 代码体积差多少（对 MCU 是硬约束）
4. ABI 差异怎么影响调用方

这四件事单独看都很琐碎，**放在一起对比才看得出规律**。这个练习就做这件事。


## 先做一个 5 分钟的热身

在动手前，先确认三个工具链都在，并且能各编出一条指令。这三条命令的输出就是后面所有对比的锚点：

```bash
cd compilers/ai_to_edge/code/12_newbackend

# AArch64：看 32 位除法
aarch64-linux-gnu-gcc -O2 -S softmax.c -o /tmp/a.s && grep -n sdiv /tmp/a.s

# Cortex-M3：看 64 位除法变成了什么
arm-none-eabi-gcc -mcpu=cortex-m3 -mthumb -O2 -S softmax.c -o /tmp/t.s && grep -n -E 'bl|sdiv' /tmp/t.s

# RISC-V：看指令助记符风格
riscv64-linux-gnu-gcc -O2 -S softmax.c -o /tmp/r.s && grep -n -E 'div|call' /tmp/r.s
```

三条命令的实测输出：

```
/tmp/a.s:40:	sdiv	w0, w0, w6
/tmp/a.s:55:	sdiv	x0, x0, x1

/tmp/t.s:53:	sdiv	r3, r3, r1
/tmp/t.s:72:	bl	__aeabi_ldivmod

/tmp/r.s:39:	divw	a5,a5,a0
/tmp/r.s:48:	div	a0,a0,a1
```

（`/tmp/r.s:45-48` 中间那几行是 `.globl div_i64` 之类的汇编指示符，不是指令，`grep` 会一起匹配到，属正常。）

**从这三段输出就能看出本章的全部骨架**：

- AArch64 有 `sdiv w`（32 位）和 `sdiv x`（64 位），两个都是硬件
- Cortex-M3 的 32 位除法是 `sdiv`（硬件），64 位是 `bl`（库调用）——**同一个文件里两种机制并存**
- RISC-V 用 `divw`（32 位 word）和 `div`（64 位）区分，且**没有任何库调用**

一次热身就定位到了本章的核心差异。后面 7 个问题是把这个差异拆开、量化、并算清楚代价。

## 对比方法：三张表

做后端移植时，按这三张表逐项填，填完就知道能不能移植、代价多大：

### 表 1：硬件能力清单

| 能力 | AArch64 | Cortex-M3 | RISC-V 64 | 查法 |
|---|---|---|---|---|
| 32 位整数除法 | 硬件 `sdiv` | 硬件 `sdiv` | 硬件 `divw` | 汇编里找 `sdiv`/`divw` |
| 64 位整数除法 | 硬件 `sdiv x` | **库调用** | 硬件 `div` | 找 `bl` / `call` |
| 硬件浮点 | NEON/VFP | **无**（软浮点） | 可选（`D` 扩展） | target features 里找 `soft-float` |
| 128 位整数 | 部分支持 | **不支持**（编译报错） | 部分支持 | 试编 `__int128` |
| 位操作（`clz`/`rev`） | 有 | 有 | 有（`Zbb` 扩展才有更多） | 找 `clz`/`rbit` |

**这张表决定「哪些代码要改写」**。Cortex-M3 那两行（64 位除法、硬件浮点）是移植的主要工作量来源。

### 表 2：体积口径

| 口径 | 怎么量 | 适合回答什么问题 |
|---|---|---|
| 目标文件 `.text` | `size foo.o` | 「我的代码有多大」 |
| 加必需库例程 | 加上 `nm --print-size` 查到的库函数 | 「链接后真实增加多少」 |
| 加启动代码 + 运行时 | 加上 Ch 19/24 的成本 | 「固件总量是多少」 |
| 加权重数据 | 加上量化后权重的字节数 | 「装得进 FLASH 吗」 |

**四层口径给出四个不同的数**，报告时必须写清是哪一层。Q4 会用实测演示这个差距。

### 表 3：ABI 差异

| 项目 | AArch64 (AAPCS64) | Cortex-M3 (AAPCS) | RISC-V (lp64d) |
|---|---|---|---|
| 整数参数寄存器 | `x0`–`x7` | `r0`–`r3` | `a0`–`a7` |
| 浮点参数寄存器 | `v0`–`v7` | 无（走通用寄存器） | `fa0`–`fa7` |
| 栈对齐 | 16 字节 | 8 字节（AAPCS 要求） | 16 字节 |
| 返回地址 | `x30`（LR） | `lr` | `ra` |
| callee-saved | `x19`–`x28` | `r4`–`r11` | `s0`–`s11` |

**这张表解释「参数一多为什么就慢」**：Cortex-M3 只有 4 个参数寄存器，`softmax_i32` 的 3 个参数刚好够；一旦到 5 个，第 5 个就落栈。Ch 21 那个 21 参数的 memref 在 Cortex-M3 上会有 **17 个参数走栈**。

## 任务规格

给定 `code/12_newbackend/softmax.c`：

```c
#define N 8

void softmax_i32(const int32_t *in, int32_t *out, int32_t scale) {
  int32_t mx = in[0];
  for (int i = 1; i < N; i++) if (in[i] > mx) mx = in[i];   /* 归约 */
  int32_t sum = 0;
  for (int i = 0; i < N; i++) { out[i] = (in[i] - mx) * scale; sum += out[i]; }
  for (int i = 0; i < N; i++) out[i] = out[i] / sum;        /* 除法 */
}

int64_t div_i64(int64_t a, int64_t b) { return a / b; }
```

（这是整数版的「softmax 形状」，省掉了 `exp`，因为 Cortex-M3 没有浮点单元，加 `exp` 会引入大量软浮点代码，淹没本章要观察的差异。归约、乘法、除法、控制流四类操作都保留了。）

你要交付一份**三后端对比报告**，回答 7 个问题。

### Q1：三个后端的 `.text` 段各多大？

先用 `-O2 -c` 编成 `.o`，用 `size` 看。**先预测再验证**：你觉得哪个最小？

提示：AArch64 是 64 位定长指令（每条 4 字节），Thumb-2 是 16/32 位混合，RISC-V 有压缩指令扩展 `C`。指令密度直接影响体积。

### Q2：`int32_t / int32_t` 在三个后端分别变成什么？

`softmax_i32` 里那句 `out[i] / sum` 是 32 位有符号除法。在三个后端各找出来。

提示：AArch64 有 `sdiv`，RISC-V 有 `divw`，Cortex-M3 也有 `sdiv`——但要确认是**硬件指令**还是**库调用**。看汇编里是不是 `bl`。

### Q3：`int64_t / int64_t` 在三个后端分别变成什么？

这一问的答案差异最大。**为什么 64 位除法在 32 位机上这么麻烦？** 给出一个具体数字：一次 64 位除法需要多少次 32 位操作？

### Q4：Cortex-M3 的体积最小，是不是说明它「更好」？

这是本章最需要想清楚的一问。答案不是「是」或「不是」，而是「取决于你把什么算进体积」。

提示：`softmax_thumb.o` 的 `.text` 是 84 字节，但它有一条 `bl __aeabi_ldivmod`。**那个函数在哪里？多大？** 用 `arm-none-eabi-gcc -print-libgcc-file-name` 找到库，用 `nm` / `size` 看。

### Q5：`div_i64` 在 AArch64 上是几条指令？

对比 Q3 的答案。AArch64 有 64 位寄存器，`sdiv x0, x0, x1` 一条搞定。RISC-V 64 也是 `div`。**这说明什么？**

### Q6：为什么 RISC-V 的 `.text` 是 94 字节，比 Cortex-M3 的 84 大，比 AArch64 的 184 小？

三者的大小关系不是「位宽越大越大」。解释这个排序。

### Q7：如果把 `N` 从 8 改成 64，三个后端各增长多少？

改 `#define N 64`，重新编译，看 `.text` 增长。增长率说明什么（循环没展开 vs 展开）？

### Q1 答案

实测（`./build.sh` 最后一段）：

```
===== 三后端 .text 体积 =====
AArch64        184 bytes
Cortex-M3      84 bytes
RISC-V 64      94 bytes
```

**预测通常错在这里**：很多人以为 64 位的一定更大，或者 Cortex-M3 因为没有硬件除法会更大。实际是 `Cortex-M3 (84) < RISC-V (94) < AArch64 (184)`。

原因是**指令编码密度**，不是位宽：

- AArch64：所有指令 4 字节，定长。`softmax_i32` 大约 46 条指令 × 4 = 184
- Thumb-2：常用指令 16 位（2 字节），复杂指令 32 位。同样 46 条左右的逻辑，压到 84 字节
- RISC-V：基础指令 4 字节，但有 `C` 扩展（压缩指令）把常用的压到 2 字节。默认的 `riscv64-linux-gnu-gcc` 通常带 `C`，所以接近 Thumb-2

**这个对比的第一个教训：体积由编码决定，不由位宽决定。** 这也是为什么 MCU 更偏爱 Thumb-2 和 RISC-V `C` 扩展。

### Q2 答案

三个后端的 32 位除法：

```
AArch64:     sdiv	w0, w0, w6
Cortex-M3:   sdiv	r3, r3, r1
RISC-V:      divw	a5,a5,a0
```

**三个都是硬件指令**，包括 Cortex-M3。这点常被搞错：ARMv7-M（Cortex-M3/M4/M7）**有**硬件 `sdiv`/`udiv`。ARMv6-M（Cortex-M0/M0+）**没有**，那里才会变成库调用。

这解释了一个实践问题：为什么给 Cortex-M0 移植代码时性能会突然掉一截——所有除法都变成了 `__aeabi_idiv` 调用。**选 MCU 时 `-mcpu` 的差别不只是主频。**

### Q3 答案

```
AArch64:     sdiv	x0, x0, x1          （一条）
RISC-V 64:   div	a0,a0,a1            （一条）
Cortex-M3:   bl	__aeabi_ldivmod         （一次库调用）
```

Cortex-M3 的 `.text` 里只有一条 `bl`：

```
	push	{r3, lr}
	bl	__aeabi_ldivmod
```

`push {r3, lr}` 是保存返回地址（因为要调用别的函数），然后就是一次库调用。**函数本体只有 2 条指令、8 字节**——这就是 84 字节总量里最小的一块。

**为什么 64 位除法在 32 位机上麻烦？** 手算一下：一个 64 位被除数除以 64 位除数，用移位减法的经典算法需要 **64 次迭代**，每次迭代做一次 64 位比较和一次 64 位减法。而 64 位减法在 32 位机上是 2 条指令（低 32 位 + 借位 + 高 32 位）。所以最少约 `64 × 3 = 192` 条指令，加上符号处理和边界情况，真实实现通常在 300–600 条指令、1–2 KB 之间。

**这就是 Q4 的关键。**

### Q4 答案

体积最小不等于成本最低。把隐藏成本算进去：

```bash
# 找到 libgcc
arm-none-eabi-gcc -print-libgcc-file-name
# 看 __aeabi_ldivmod 的大小
arm-none-eabi-nm --print-size --size-sort <libgcc.a 路径> | grep ldivmod
```

本机实测（`arm-none-eabi-gcc 10.3.1`）：

```
libgcc: /usr/lib/gcc/arm-none-eabi/10.3.1/libgcc.a        9409088 字节（9 MB）
_aeabi_ldivmod.o   .text = 212 字节
__aeabi_ldivmod 里面调 __udivmoddi4
_udivmoddi4.o      __udivmoddi4 大小 = 0x128 = 296 字节
```

所以一次 64 位除法的**真实体积成本 = 212 + 296 = 508 字节**，不是 84 字节里那 8 字节的 `bl`。把 84 加上 508，Cortex-M3 的实际占用是 **592 字节**，是 AArch64 的 184 字节的 **3.2 倍**。

**结论反过来了：代码密度最小的那个后端，实际体积最大。**

但这笔账还有第三种算法：如果整个程序里只有一处 64 位除法，那 1 KB 的库只被链接一次，摊到整个固件上可能可以接受。**如果模型里有几十处，那还是 1 KB（库是共享的），不会线性增长。**

所以正确的说法是：

| 口径 | AArch64 | Cortex-M3 | 谁最小 |
|---|---|---|---|
| 只看本目标文件 `.text` | 184 | **84** | Cortex-M3 |
| 加上必需的 libgcc 例程 | 184 | 84 + 508 = **592** | AArch64 |
| 再加上启动代码（Ch 19 实测 289 B 含 UART 输出） | 184 | 592 + 289 = 881 | AArch64 |

**同一个程序，换个口径，结论从「MCU 省 100 字节」变成「MCU 多花 697 字节」。** 这就是为什么体积报告必须写清口径。

**「体积」这个词必须带口径。** 报告体积时不说清「含不含库、含不含运行时」，数字就没有比较意义。这是本章最重要的方法论。

### Q5 答案

AArch64 上 `div_i64` 是**一条**指令：

```
div_i64:
	sdiv	x0, x0, x1
	ret
```

RISC-V 64 也是两条（含 `ret`）。两个都是 64 位原生架构，除法器硬件直接支持 64 位操作数。

**这说明**：Cortex-M3 的那次库调用不是「编译器不够聪明」，是**硬件能力缺失**。编译器能做的最好的事就是调一个经过优化的库函数。你在 MCU 上看到 `bl __aeabi_*` 时，应该想的是「这颗芯片没有这个能力」，而不是「换个编译器试试」。

延伸一条实践建议：**在 MCU 上避免 64 位运算**。能用 `int32_t` 就用 `int32_t`，能改成定点就用定点。Ch 11 的量化不只是为了省带宽，也是为了让运算落在硬件支持的宽度内。

### Q6 答案

排序 `Cortex-M3 (84) < RISC-V (94) < AArch64 (184)` 的原因：

| 后端 | 编码 | `softmax_i32` 的指令数（估） | 平均字节/指令 |
|---|---|---|---|
| Cortex-M3 | Thumb-2，16/32 位混合 | ~46 | **~1.8** |
| RISC-V 64 | 基础 4 字节 + `C` 扩展 2 字节 | ~50 | **~1.9** |
| AArch64 | 全部 4 字节 | ~46 | **4.0** |

AArch64 的指令数并不比另外两个多，**它只是每条指令都占 4 字节**。这是设计选择：定长编码让译码简单、流水线友好，代价是代码密度。

RISC-V 比 Cortex-M3 多 10 字节，差在几处：RISC-V 需要显式的 `ret`（`jalr x0, 0(ra)`，或压缩成 `c.ret` 2 字节）、循环控制需要单独的 `addi` + `blt`（Thumb-2 有更丰富的条件执行和 `ldr ... !` 写回寻址，能把几条合成一条）。**这是 CISC 风格寻址模式对代码密度的一点优势。**

### Q7 答案

把 `N` 从 8 改成 64，实测：

| 后端 | `N=8` `.text` | `N=64` `.text` | 增量 | `N=8` 指令数 | `N=64` 指令数 |
|---|---|---|---|---|---|
| AArch64 | 184 | 200 | **+16** | — | — |
| Cortex-M3 | 84 | 88 | **+4** | 32 | 34 |
| RISC-V 64 | 94 | 92 | **−2** | 32 | 32 |

三个后端几乎都没增长，因为循环**没有被展开**——`N` 只是循环边界里的一个比较值，从 8 改成 64，改的只是那条 `cmp` 的立即数。**8 倍的循环次数，4 到 16 字节的代码增长。**

`RISC-V` 甚至变小了 2 字节：这是对齐填充的抖动（`.p2align` 让函数起始地址对齐，`N` 变了导致指令编码长度变化，填充量跟着变）。**这类 ±几字节的抖动不承载任何信息**，别去解读它。

Cortex-M3 多出 2 条指令（+4 字节）：因为 `N=64` 让某个常量的加载方式从「编码进指令」变成「需要单独装载」。这是立即数范围的边界效应。

**增长率说明的是优化决策，不是架构能力**：循环没展开 = 编译器判断展开不划算（`-O2` 的默认代价模型拒绝展开 64 次的循环）。想验证「展开到底值不值」，用 `perf stat` 看分支预测失败次数的变化，而不是只看体积。

## 卡点提示

1. **`arm-none-eabi-gcc` 报 `No such file or directory`。** 如果命令里把 `-mcpu=cortex-m3 -mthumb` 写在错误位置（比如当成一个整体参数），会报这个错。正确写法是每个选项分开：`arm-none-eabi-gcc -mcpu=cortex-m3 -mthumb -O2 -S`。

2. **`riscv64-linux-gnu-size` 不存在。** 有的发行版里 RISC-V 工具链没有独立的 `size` 命令，用 `riscv64-linux-gnu-objdump -h` 看段大小，或者直接用 `stat -c%s` 看整个 `.o`。

3. **`__aeabi_ldivmod` 找不到。** 它是 libgcc 的一部分，路径用 `arm-none-eabi-gcc -print-libgcc-file-name` 问编译器。不要硬编码 `/usr/lib/gcc/arm-none-eabi/...`，版本号会变。

4. **`grep -c` 返回 0 却以为出错。** `grep -c` 找到 0 个匹配时退出码是 1，`set -e` 会中断脚本。写成 `grep -c ... || echo 0`。

5. **`-O2` 下看不到循环。** 小循环（固定 8 次）可能被完全展开或闭式化。想看循环结构，用 `-O1` 或把 `N` 改大。

6. **以为 `sdiv` 一定是硬件指令。** 在 ARMv6-M（Cortex-M0）上，`sdiv` 这个助记符不会出现，取而代之的是 `bl __aeabi_idiv`。确认方式：看有没有 `bl`，以及 `.text` 大小是否突然跳变。

## 加分挑战

1. **加浮点版本。** 写一个 `float softmax_f32`，在三个后端各编一次。Cortex-M3 上会看到大量 `__aeabi_fadd` / `__aeabi_fmul` 调用（Ch 15 实测过链接失败）。统计调用了多少个不同的 `__aeabi_f*` 符号，这就是「软浮点税」。

2. **换成 Cortex-M0。** `arm-none-eabi-gcc -mcpu=cortex-m0 -mthumb`，对比 `sdiv` 变成什么。体积增长多少？

3. **开 `-Os`。** 三个后端各编一次 `-Os`，对比 `-O2`。Cortex-M 上的 `-Os` 通常能省 10–20%（Ch 19 实测 `-O2` 289 B → `-Os` 240 B，省 17%）。

4. **让 `div_i64` 变成热点。** 写一个循环调用它 100 万次，在 `qemu-system-arm` 上跑（需要 UART 输出计时）。测出单次调用的周期数，和 AArch64 的 `sdiv` 对比。这个数字能直接换算成「如果用 MCU 跑这个算子，光除法要多久」。

5. **看 RISC-V 的 `M` 扩展是否必需。** 用 `-march=rv64i`（不带 `M`）编译，`div` 会变成什么？再对比 `-march=rv64im`。这解释了为什么嵌入式 RISC-V 核（如 ESP32-C3 的 RV32IMC）必须带 `M` 扩展才有硬件乘除。

## 全章回顾

这个练习把 Ch 18–21 的四条线索收在一起：

```
同一份 C
  ├─ 指令密度 → 体积（Thumb-2 < RISC-V+C < AArch64）
  ├─ 硬件能力 → 除法/浮点 是硬件还是库（Cortex-M3 的 i64 除法要 1 KB 库）
  ├─ ABI      → 参数怎么传（Ch 21 的 21 参数 memref 在这里会变成栈溢出）
  └─ 优化决策 → 循环展不展开（-O2 的代价模型，不是架构限制）
```

**下次拿到一块新板子，先问这四件事。** 问完再决定要不要移植，比直接编译一遍试错快得多。
