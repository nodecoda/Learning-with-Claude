# 练习 C — 读一条指令的完整来历

> **任务**：给出一条 AArch64 指令，从它出发**逆向走完整条链路**：这条指令对应哪段 C、哪条 LLVM IR、哪个优化把它变成这样、哪个 pass 决定它进哪个寄存器、哪个重定位在链接时修补它。做完这个练习，你再看任何一段汇编，都能说出「它是谁生成的、为什么长这样」。
>
> **难度**：中等偏难。需要 Ch 13–17 全部内容。
>
> **预计时间**：3–5 小时（含读源码）。

> **环境**：LLVM 14.0.0、aarch64-linux-gnu-gcc 11.4、qemu-aarch64-static 6.2。所有命令都在 `code/11_trace/` 下可复现。

## 为什么练这个

Ch 15 教你「合法化与指令选择」，Ch 16 教你「寄存器分配与栈帧」，Ch 17 教你「重定位」。三章分别讲了一层的机制，但真实调试时你是**从一条陌生指令往回查**的：

- 线上崩溃的 PC 落在一个 `umull` 上，它从哪来？
- 反汇编里有一对 `stp`/`ldp` 把 `x29, x30` 存到栈上，为什么函数要保存它们？
- `adrp` + `ldr` 两条指令取一个全局变量，为什么不直接 `ldr`？

这个练习就是训练这条反向路径。**正向「C → 汇编」你已经会了，反向才是工程里真正用到的方向。**

## 任务规格

给定 `code/11_trace/trace.c`：

```c
extern int ext_var;              /* 来自另一个目标文件 */
extern int ext_fn(int);          /* 来自另一个目标文件 */

int gvar = 7;                    /* 本文件的全局变量 */

/* 参数用运行时值，避免被常量折叠成常数 */
int compute(int x, int n) {
  int s = 0;
  for (int i = 0; i < n; i++) s += x * (i + 1);
  return s + gvar + ext_var + ext_fn(x);
}
```

配套 `drv.c` 提供 `ext_var = 100`、`ext_fn(v) = v * 3`、`main` 调用 `compute(4, 3)`。

你要交付一份**溯源报告**，回答下面 8 个问题。每个答案都要有命令、有输出、有一句解释。

### Q1：`compute(4, 3)` 返回什么？先预测，再验证

不运行，先手算：`s = 4*1 + 4*2 + 4*3 = 24`；`24 + 7 + 100 + 12 = 143`。然后跑 `./build.sh` 确认。

**这一步的意义**：如果实测和手算不符，后面所有分析都白做。先建立数值基准。

### Q2：`-O0` 与 `-O1` 的 IR 差多少？差在哪一类指令上？

用 `clang -O0` 和 `clang -O1` 各生成一次 `.ll`，统计：
- 总行数
- `alloca` 的数量
- `load` / `store` 的数量
- 有没有 `optnone` 属性

**提示**：`-O0` 的 IR 里每个局部变量都有自己的 `alloca`，参数也先 `store` 进 `alloca`。这是「不做 mem2reg」的样子。

### Q3：循环去哪了？

`-O1` 的 IR 里，`for` 循环**完全消失了**，变成了一段闭式算术：

```
%5 = shl i32 %1, 1
%6 = add i32 %1, -1
%7 = zext i32 %6 to i33
%8 = add i32 %1, -2
%9 = zext i32 %8 to i33
%10 = mul i33 %7, %9
%11 = lshr i33 %10, 1
%12 = trunc i33 %11 to i32
%13 = add i32 %5, %12
%14 = add i32 %13, -1
%15 = mul i32 %14, %0
```

解释这段在算什么，并回答：**为什么中间要用 `i33` 而不是 `i32`？** 去掉 `zext` 到 `i33` 会怎样（把 `i33` 改成 `i32` 试试，对比结果）？

### Q4：`umull` 从哪来？

汇编里有一条：

```
umull	x8, w8, w9
lsr	x8, x8, #1
```

它对应 IR 里的 `%10 = mul i33 %7, %9` 和 `%11 = lshr i33 %10, 1`。回答：
- `umull` 是什么（提示：`u` = unsigned，`mull` = multiply long）
- 为什么是 `w8`/`w9`（32 位源）而不是 `x8`/`x9`
- 为什么目标是 `x8`（64 位）
- `i33` 在指令层怎么体现

### Q5：`stp x29, x30, [sp, #-32]!` 为什么出现？

这行在汇编的第 28 字节处。回答：
- `x29` 和 `x30` 分别是什么寄存器
- 为什么这个函数要保存它们（对比一个叶函数，比如 `code/04_aarch64/` 里的 `add`）
- `[sp, #-32]!` 里的 `!` 是什么意思（写回寻址）
- 为什么是 32 不是 16（提示：数一数这个函数里被 spill 的寄存器有几个）

### Q6：`adrp` + `ldr` 凭什么取到全局变量？

```
adrp	x9, gvar
ldr	w9, [x9, :lo12:gvar]
```

回答：
- `adrp` 做什么（提示：Address of 4KB Page）
- `:lo12:` 是什么
- 为什么不用一条 `ldr w9, gvar`
- 为什么 `ext_var` 走的是 `:got:` 而不是 `:lo12:`（对比 `gvar`）

### Q7：`.rela.text` 里有 5 条重定位，各是什么？

用 `aarch64-linux-gnu-readelf -r trace.o` 看。对照 Ch 17 的内容，说出每条重定位：
- 修补的是哪条指令的哪个位段
- 由谁定义（本文件 / 外部）
- 链接后变成什么

### Q8：`ext_fn` 的调用为什么是 `bl ext_fn`？

`bl` 是相对调用（26 位偏移，范围 ±128 MB）。回答：
- 如果 `ext_fn` 在 4 GB 之外会怎样（提示：链接器会报什么）
- `-fPIC` 编译时会不会变
- 静态链接与动态链接下，这条 `bl` 的目标地址在哪一步确定

### Q1 答案

### Q2 答案

实测对比：

| 指标 | `-O0` | `-O1` |
|---|---|---|
| IR 总行数 | 74 | 61 |
| `alloca` 数量 | 4 | **0** |
| `optnone` | 2 处 | 0 |
| `.s` 行数 | 68 | 54 |

`-O0` 的 `compute` 开头：

```llvm
define dso_local i32 @compute(i32 noundef %0, i32 noundef %1) #0 {
  %3 = alloca i32, align 4
  %4 = alloca i32, align 4
  %5 = alloca i32, align 4
  %6 = alloca i32, align 4
  store i32 %0, i32* %3, align 4
  store i32 %1, i32* %4, align 4
  store i32 0, i32* %5, align 4
  store i32 0, i32* %6, align 4
```

四个 `alloca` 依次是 `x`、`n`、`s`、`i`。参数 `%0`/`%1` 先用 `store` 写进内存，之后每次用都 `load` 回来。**`-O0` 的汇编里那句 `str w0, [x29, #28]` 就是第一个 `store`**——参数一进函数就落栈。

`-O1` 的 `compute` 里 `alloca` 数量是 0。不是「编译器把 `alloca` 优化掉了」这么简单的说法——是 `mem2reg` 把内存提升成 SSA 值（Ch 13 实测过这个 pass：alloca 4→0，phi 0→2）。

**`optnone` 值得单独说。** `-O0` 生成的 IR 带 `optnone` 属性，`opt` 看到它会**直接跳过这个函数**。所以拿 `-O0` 的 IR 去跑 `opt -O2` 是无效的——你会以为优化没生效，其实是被属性挡住了。Ch 13 讲过这个坑，这里是它的现场。

### Q3 答案

那段 IR 算的是**求和公式**：

```
sum_{i=0}^{n-1} (i+1) = n(n+1)/2
s = x * n(n+1)/2
```

IR 里的算法不同但等价，它算的是 `n * (2n-1+... )` 的展开形式：

```
%5  = 2n
%6  = n - 1
%10 = (n-1)(n-2)          [零扩展到 i33]
%11 = (n-1)(n-2) / 2
%13 = 2n + (n-1)(n-2)/2
%14 = 2n + (n-1)(n-2)/2 - 1
%15 = x * (%14)
```

先用脚本验一下等价性（`n = 0..199` 全部与 `4 * sum(1..n)` 一致，已实测）：

```
n=0..199 全部一致: True
n=3 -> 24  expect 24
```

再化简 `%14`：

```
2n + (n-1)(n-2)/2 - 1 = 2n + (n²-3n+2)/2 - 1 = (4n + n² - 3n + 2 - 2)/2 = (n² + n)/2 = n(n+1)/2
```

**为什么用 `i33`？** `(n-1)(n-2)` 在 `n` 接近 `INT32_MAX` 时会溢出 `i32`。`i33` 多一位，保证乘积不溢出，然后 `lshr 1` 除以 2 再 `trunc` 回 `i32`。**这是「中间计算用更宽的类型，最后截回来」的标准模式**——和 Ch 11 里「`int8×int8` 累加必须用 `int32`」是同一个道理，只是这里发生在 IR 层、由 LLVM 自动插入。

改成 `i32` 会怎样：`(n-1)*(n-2)` 在 `n > 46341` 附近溢出，结果完全错。这个 bug 只在 `n` 很大时出现，**小测试用例抓不到**。这是「优化引入的溢出」的典型形态。

### Q4 答案

`umull` = **Unsigned Multiply Long**：两个 32 位无符号数相乘，结果 64 位。

- 源是 `w8`/`w9`（32 位）：因为 `%7` 和 `%9` 是 `zext i32 to i33`，低 32 位就是原值
- 目标是 `x8`（64 位）：因为乘积需要 64 位装（`i33` 的实际载体）
- `i33` 在指令层**没有对应的寄存器**——AArch64 的通用寄存器是 32 位（`w`）或 64 位（`x`），没有 33 位。所以 LLVM 用 `x` 寄存器（64 位）装这个值，高位补 0。**「多出来的那一位」是靠选择更宽的寄存器实现的**，不是靠某个特殊类型

紧跟的 `lsr x8, x8, #1` 就是 IR 的 `lshr i33 %10, 1`。两步合起来实现了「乘完除以 2」。

**关键洞察**：IR 里的 `i33` 是个**逻辑类型**，指令选择时才映射到物理寄存器。这解释了为什么有时 IR 看着奇怪（`i33`、`i128`、`<4 x i32>`）但汇编很正常——类型宽度是编译器的记账工具，硬件只认 32/64/128 位寄存器。

### Q5 答案

- `x29` = 帧指针（FP），`x30` = 链接寄存器（LR，存返回地址）
- 这个函数**不是叶函数**：它调用 `bl ext_fn`。`bl` 会把返回地址写进 `x30`，所以调用前必须把原来的 `x30`（本函数的返回地址）存起来，否则回不去
- `[sp, #-32]!` 的 `!` 是**写回**（pre-index with writeback）：先 `sp = sp - 32`，再用新的 `sp` 存。这样一条指令同时完成「分配栈帧」和「保存寄存器」
- 是 32 不是 16：因为除了 `x29`/`x30`（16 字节）还 spill 了 `x19`（8 字节），加上对齐到 16 的填充，共 32

对照 `code/04_aarch64/add_a64` 里的 `add`：它是叶函数，没有 `bl`，所以**没有** `stp x29, x30` 这对指令。这就是 Ch 18 里「叶函数无此序列」那条实测的来源。

`w19` 的选择值得多说：`bl ext_fn` 会破坏 caller-saved 寄存器（`x0`–`x18`），但 `x19`–`x28` 是 callee-saved（被调用者负责保存）。所以跨调用的活跃值 `%21` 必须放进 `x19`，代价是本函数要自己保存它——那句 `str x19, [sp, #16]` 就是代价。**这是一个完整的权衡闭环：省一次内存访问 → 换一次 spill。**

### Q6 答案

- `adrp x9, gvar`：取 `gvar` 所在 **4 KB 页**的基址，左移 12 位后放进 `x9`。`adrp` 的立即数范围是 ±4 GB，页对齐
- `:lo12:gvar`：取 `gvar` 在页内的**低 12 位偏移**，作为 `ldr` 的立即数
- 两条指令合起来覆盖 64 位地址空间。一条 `ldr w9, gvar` 做不到——AArch64 的 `ldr` 立即数只有 12 位（±4095 字节），装不下完整地址
- `ext_var` 走 `:got:`（Global Offset Table）：因为它是**外部符号**，地址在链接时才定（如果动态链接，甚至运行时才定）。`gvar` 是本文件定义的，链接器知道它的相对位置，用 `:lo12:` 就够

`readelf -r` 的实测输出印证了这个区别：

```
000000000034  ...  R_AARCH64_ADR_GOT_PAGE   ext_var + 0
000000000038  ...  R_AARCH64_ADR_PREL_PG_HI21  gvar + 0
00000000003c  ...  R_AARCH64_LD64_GOT_LO12_NC  ext_var + 0
000000000040  ...  R_AARCH64_LDST32_ABS_LO12_NC  gvar + 0
```

**四条重定位成对出现**：`ext_var` 是 `ADR_GOT_PAGE` + `LD64_GOT_LO12_NC`（走 GOT），`gvar` 是 `ADR_PREL_PG_HI21` + `LDST32_ABS_LO12_NC`（直接页相对）。这就是 Ch 17 讲的「同一件事，两种寻址」。

### Q7 答案

5 条重定位：

| 偏移 | 类型 | 符号 | 修补什么 |
|---|---|---|---|
| `0x34` | `R_AARCH64_ADR_GOT_PAGE` | `ext_var` | `adrp x10, :got:ext_var` 的页地址 |
| `0x38` | `R_AARCH64_ADR_PREL_PG_HI21` | `gvar` | `adrp x9, gvar` 的页地址 |
| `0x3c` | `R_AARCH64_LD64_GOT_LO12_NC` | `ext_var` | `ldr x10, [x10, :got_lo12:ext_var]` 的页内偏移 |
| `0x40` | `R_AARCH64_LDST32_ABS_LO12_NC` | `gvar` | `ldr w9, [x9, :lo12:gvar]` 的页内偏移（`32` 表示 32 位访问） |
| `0x50` | `R_AARCH64_CALL26` | `ext_fn` | `bl ext_fn` 的 26 位相对偏移 |

`.rela.text` 有 5 条，`.rela.eh_frame` 有 1 条（`R_AARCH64_PREL32`，给异常处理表用）。**`.text` 只有 0x64 = 100 字节左右，重定位表却要 5 × 24 = 120 字节**——这就是 Ch 17 实测「重定位表比代码还大」的现象，小函数特别明显。

链接后，`objdump -d trace_bin` 能看到 `bl` 的目标被填成真实地址，`adrp` 的立即数变成正确的页号。**这一步只能在链接后看**，目标文件里这些位段是 0。

### Q8 答案

`bl` 是 26 位有符号偏移（实际编码里低 2 位隐含为 0，所以范围是 ±2^27 字节 = ±128 MB）。

- 超出范围：链接器报 `relocation truncated to fit: R_AARCH64_CALL26 against symbol 'ext_fn'`。这是静态链接大型程序时的经典错误
- `-fPIC` 下：外部函数调用通常走 `adrp` + `ldr`（从 GOT 取地址）+ `blr`，三条指令。因为 PIC 不能假定函数在 ±128 MB 内
- 静态链接：`bl` 的目标在**链接时**确定，写死成相对偏移
- 动态链接：如果函数在共享库，链接器生成 PLT 桩，`bl` 跳到 PLT，PLT 再间接跳转。**多一次跳转**就是动态链接的调用开销

这个区别对边缘部署有实际影响：静态链接的固件里所有 `bl` 都是直接跳转，没有 PLT；一旦引入 `.so`，调用路径就多一层。

## 卡点提示

1. **`-O1` 的 IR 里找不到循环，别以为工具坏了。** 闭式化（loop-to-closed-form）是 `-O1` 就有的优化，`for` 循环在这类「迭代次数可变但求和有公式」的场景下会被整段替换。想看循环，用 `-O0`，或者把循环体改成不可闭式化的形式（比如加个 `s += x * (i*i % 7)`）。

2. **`opt` 对 `-O0` 的 IR 无效。** 因为 `optnone` 属性。要去掉，用 `-Xclang -disable-O0-optnone`，或者直接从 `-O1` 的 IR 往下做。

3. **`llc -print-after=regalloc` 没有输出。** Ch 16 实测过：pass 名要写 `greedy`（寄存器分配器的实际名字是 `greedy`，不是 `regalloc`）。写成 `-print-after=greedy`。

4. **`readelf -r` 的输出被截断。** 默认列宽不够，`R_AARCH64_LDST32_ABS_LO12_NC` 这种长名字会被切。用 `-W` 参数：`readelf -Wr trace.o`。

5. **`adrp` 的立即数看不懂。** `objdump` 给的是编码后的值，不是字节偏移。要算实际地址，用 `objdump -d` 结合符号表，或者直接看链接后的反汇编。

## 加分挑战

1. **改成 `i32` 并构造溢出用例。** 把 IR 里两处 `i33` 改成 `i32`，用 `n = 100000` 调用，证明结果错误。然后解释：为什么 LLVM 选择了 `i33` 而不是 `i64`（提示：看 `zext` 的成本，`i33` 只多一位，`i64` 多 32 位）。

2. **让 `ext_fn` 超出 ±128 MB。** 用链接脚本把代码段放到很远的地址，观察 `R_AARCH64_CALL26` 的截断错误。然后改成 `-fPIC` 编译，看生成什么。

3. **把 `gvar` 改成 `static`。** 重定位会变成什么样？`adrp` + `:lo12:` 还在吗，还是被优化成别的形式（比如 PC 相对的直接寻址）？

4. **在 Cortex-M3 上做同样的事。** 用 `arm-none-eabi-gcc -mcpu=cortex-m3 -mthumb -O1`，看同一段 C 生成什么。你会看到 `ldr r3, .LCPI` 这样的**字面量池**加载（Thumb-2 没有 `adrp`），以及 `bl` 的 24 位范围限制。这对比能讲清「同一份 IR 在不同后端上的寻址策略差异」。

5. **用 GlobalISel 走一遍。** Ch 15 实测过 GlobalISel 在 LLVM 14 的 AArch64 上可用（`sel.s` 57 行 vs `gi.s` 59 行）。用 `llc -global-isel` 生成这个函数的汇编，和 SelectionDAG 的版本逐条对比。差异在哪里？哪一版更短？

## 全章回顾

这个练习把 Ch 13–17 串成了一条线：

```
C 源码
  │  clang -O1 -S -emit-llvm        ← Ch 13（优化管线）
  ▼
LLVM IR（循环闭式化，i33 中间类型）
  │  llc -march=aarch64
  │    ├─ 合法化（i33 → x 寄存器）        ← Ch 15
  │    ├─ 指令选择（umull / mul / add）    ← Ch 15
  │    ├─ 寄存器分配（w19 spill 到栈）      ← Ch 16
  │    └─ 栈帧布局（stp/ldp, 32 字节帧）    ← Ch 16
  ▼
汇编（含 5 条重定位占位）
  │  as + ld
  │    └─ 重定位修补（adrp/bl 填真实地址）   ← Ch 17
  ▼
可执行文件 → qemu 输出 143
```

**反向走这条路，就是工程调试的日常**：从一条指令出发，一层层问「谁决定了我长这样」。练熟之后，你看反汇编不再是「一堆指令」，而是「一串有来历的决定」。
