# Ch 15 — AsmPrinter 与 MC：PTX 文字是怎么印出来的

> **目标**：知道 PTX 文本的每个部分由哪个函数打印、MC 层在 NVPTX 里承担什么（以及不承担什么），并能定位一个符号名的来源。

## 为什么需要这个？

NVPTX 的「后端终点」不是 object 文件，而是文本。这意味着你读的每一行 PTX 都是 `NVPTXAsmPrinter.cpp`（2509 行）里某个函数 `O << ...` 出来的。想改后端输出（加指令、加指令修饰符、改符号名），必须知道该改哪里。

## 先建立直觉

```
emitStartOfAsmFile ──► .version / .target / .address_size
emitDeclarations   ──► .extern .func / .global 声明
emitGlobals        ──► 全局变量定义
emitFunctionEntryLabel ──► .entry/.func + 参数列表 + 指令
setAndEmitFunctionVirtualRegisters ──► .reg 声明
runOnMachineFunction ──► 函数体指令 + 收尾 "}"
```

## 一、文件头：`emitStartOfAsmFile` / `emitHeader`

```ptx
//
// Generated by LLVM NVPTX Back-End
//

.version 6.3
.target sm_75
.address_size 64
```

三行分别来自：

- `.version`：`NVPTXSubtarget::getPTXVersion()`（Ch 3 的映射表）。
- `.target`：`getTargetName()`（会把 `sm_110` 之类的新拼写回写成旧名）。
- `.address_size`：triple 是 `nvptx` 还是 `nvptx64`。

## 二、函数入口：`.entry` / `.func`

`emitFunctionEntryLabel()` 的顺序是：

1. 若还没打印全局声明，先 `emitGlobals`。
2. `emitLinkageDirective`（`.visible` / `.extern`）。
3. 判断 kernel：`.entry`；否则 `.func` + `printReturnValClause`。
4. `emitFunctionParamList`（Ch 4 的 `.param` 列表）。
5. `emitKernelFunctionDirectives`（`.maxntid` / `.minnctid` / `.reqntid` 等）。
6. 打印 `{`，然后 `setAndEmitFunctionVirtualRegisters`。

## 三、`.reg` 声明：`setAndEmitFunctionVirtualRegisters`

Ch 11 已经拆过逻辑，这里补上「名字从哪来」：

```cpp
auto &RCRegMap = VRegMapping[MRI->getRegClass(VR)];
RCRegMap[VR] = RCRegMap.size() + 1;
...
TS->emitRegDirective(bits, prefix, It->second.size() + 1);
```

- 每个寄存器类一张映射表，编号从 1 开始。
- 前缀由 `getVirtualRegisterPrefix(getVirtualRegisterKind(&RC))` 决定（`p`/`rs`/`r`/`rd`/`rq`）。
- 打印成 `.reg .b32 %r<9>` 这种形式。

所以 `%r5` 的含义是「32 位类里的第 5 个虚拟寄存器」，不是「物理 R5」。

## 四、shared 变量为什么被「demote」

`emitFunctionBodyStart()` 里调用 `emitDemotedVars()`。Ch 5 的 `sh` 本来在模块级：

```llvm
@sh = internal addrspace(3) global [8 x float] undef, align 4
```

打印时变成函数内：

```ptx
	// demoted variable
	.shared .align 4 .b8 sh[32];
```

原因：PTX 的 `.shared` 变量作用域是模块或函数；把 internal 的 shared 全局降级到函数内，可以避免符号冲突、也方便驱动按 kernel 分配。注释里的 `// sh has been demoted` 就是标记。

## 五、MC 层：只有「印」，没有「编」

NVPTX 的 `MCTargetDesc` 提供：

- `NVPTXInstPrinter`：把 MCInst 打印成文本。
- `NVPTXMCExpr`：符号/常量表达式。
- `NVPTXMCTargetDesc`：注册 target。

它**没有** MC code emitter，也没有汇编解析器。实测：

```bash
$BIN/llc -mtriple=nvptx64 -mcpu=sm_75 -O2 -filetype=obj add.ll -o add.o
# llc: error: createMCCodeEmitter failed

$BIN/llvm-mc -triple=nvptx64 -show-encoding </dev/null
# <unknown>:0: error: this target does not support assembly parsing.
```

这两条错误是「PTX 不是可汇编的机器码」最直接的证据。PTX 的「汇编器」是 `ptxas`，不在 LLVM 里。

## 六、符号命名

| 符号 | 来源 |
|---|---|
| `add_param_0` | 函数名 + 参数序号 |
| `$L__BB0_2` | 基本块标签，`BB<函数号>_<块号>` |
| `_ZZ4tileE1s` | C++ 名字修饰后的 shared 变量 |
| `__local_depot0` | 栈帧基址符号 |
| `func_retval0` | device 函数返回槽 |

这些名字不是 ABI 的一部分（除了 `func_retval0` 是约定），改它们不影响语义，但会影响可读性和调试。

## 七、内联汇编

PTX 内联汇编在 NVPTX 上是「原样透传」：

```llvm
call void asm sideeffect "bar.sync 0;", ""()
```

AsmPrinter 会把字符串直接输出。这也意味着**内联汇编的语法错误不会在 LLVM 层被发现**，要到 `ptxas` 才报错。

## 踩雷集锦

1. **以为 `-filetype=obj` 只是没实现**：确实没实现，这是设计（Ch 1）。
2. **用 `llvm-mc` 解析 PTX**：不支持；用 `ptxas`。
3. **改 `.reg` 数量想控制寄存器**：改的是虚拟寄存器计数，不影响物理分配。
4. **依赖符号名做 ABI**：只有 `func_retval0` 这类约定名有意义，其余是实现细节。
5. **以为内联汇编会被检查**：不会；错误推迟到 `ptxas`。

## 进阶：自定义 AsmPrinter 输出

如果你想在 PTX 里加自定义指令/修饰符（例如给自研 GPU 加 `.myqualifier`），路径是：

1. 在 `NVPTXInstrInfo.td` 定义指令与打印字符串。
2. 在 `NVPTXInstPrinter` 里处理操作数。
3. 在 `NVPTXAsmPrinter::emitInstruction` / `lowerToMCInst` 里接上。
4. 用 `llvm/test/CodeGen/NVPTX/` 的 lit 测试锁行为。

Ch 17 会走一遍完整流程。

## 本章重点整理

- PTX 文本由 `NVPTXAsmPrinter` 分段打印：头、声明、函数入口、`.reg`、指令、收尾。
- `.reg` 名字是「类内虚拟编号」，不是物理寄存器。
- internal shared 全局会被 demote 到函数内。
- NVPTX 的 MC 层只有打印，没有编码/汇编；`ptxas` 才是汇编器。
