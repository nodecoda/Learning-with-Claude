# Ch 0 — 环境与全链路：llc → .ptx → ptxas → T4

> **目标**：把「LLVM IR → PTX → cubin → GPU」这条链在本机跑通，并知道每一段由谁负责。学完你能独立复现本课所有实验。

> **环境**：LLVM `24.0.0git`（`ct-instr-trunk`， assertions 构建，commit `881d51b5cb17`）、CUDA Toolkit 12.4、驱动 535.216.01、Tesla T4（sm_75）、Ubuntu Linux x86-64。

## 为什么需要这个？

学一个后端，最容易犯的错是「只读源码、不看产物」。NVPTX 的很多设计决定，只有把 `.ll` 丢进去、把 `.ptx` 拿出来、再丢给 `ptxas` 和 GPU，才会变得显然。更现实的原因是：自研 GPU 做 CUDA 兼容，第一步就是决定「在哪一层接入」。如果你连这条链的每一段输出长什么样都没见过，就无从判断该吃 PTX、吃 NVVM IR，还是自己写前端。

这条链还有一个反直觉之处：**LLVM 只走到 PTX 文字为止**。后面真正的寄存器分配、指令调度、SASS 生成，全部由 NVIDIA 的 `ptxas` 完成。本课后半段都在拆这个分工。

## 先建立直觉

```
 add.ll ──llc──► add.ptx ──ptxas──► add.cubin ──driver──► T4
   │               │                  │                    │
 LLVM IR       虚拟 ISA 文字        真实机器码            真正执行
 (你熟)       (无限寄存器)        (物理寄存器/调度)      (SM 里跑)
```

把它想成翻译流程：LLVM 把「意思」翻成一份**标准化的中间稿**（PTX），`ptxas` 再把中间稿翻成**某个具体型号能执行的版本**（SASS）。中间稿故意不写死寄存器数量、不写死指令时序，所以同一份 PTX 能在 sm_75、sm_90、sm_100 上各自编译出不同的 SASS。

## 二、第一段：IR → PTX

先写一个最小 kernel。注意两个细节：`ptx_kernel` 调用约定决定它变成 `.entry`；三个指针参数是 generic 指针（`ptr`），所以后面会出现 `cvta.to.global`。

```llvm
; add.ll
target triple = "nvptx64-nvidia-cuda"

declare i32 @llvm.nvvm.read.ptx.sreg.tid.x()
declare i32 @llvm.nvvm.read.ptx.sreg.ctaid.x()
declare i32 @llvm.nvvm.read.ptx.sreg.ntid.x()

define ptx_kernel void @add(ptr %out, ptr %a, ptr %b, i32 %n) {
entry:
  %tid = call i32 @llvm.nvvm.read.ptx.sreg.tid.x()
  %bid = call i32 @llvm.nvvm.read.ptx.sreg.ctaid.x()
  %ntid = call i32 @llvm.nvvm.read.ptx.sreg.ntid.x()
  %t0 = mul i32 %bid, %ntid
  %idx = add i32 %t0, %tid
  %c = icmp slt i32 %idx, %n
  br i1 %c, label %body, label %exit

body:
  %idx64 = sext i32 %idx to i64
  %pa = getelementptr float, ptr %a, i64 %idx64
  %pb = getelementptr float, ptr %b, i64 %idx64
  %po = getelementptr float, ptr %out, i64 %idx64
  %va = load float, ptr %pa, align 4
  %vb = load float, ptr %pb, align 4
  %s = fadd float %va, %vb
  store float %s, ptr %po, align 4
  br label %exit

exit:
  ret void
}
```

```bash
$BIN/llc -mtriple=nvptx64 -mcpu=sm_75 -O2 add.ll -o add.ptx
```

真实产物（完整）：

```ptx
//
// Generated by LLVM NVPTX Back-End
//

.version 6.3
.target sm_75
.address_size 64

	// .globl	add                     // -- Begin function add
                                        // @add
.visible .entry add(
	.param .u64 .ptr .align 1 add_param_0,
	.param .u64 .ptr .align 1 add_param_1,
	.param .u64 .ptr .align 1 add_param_2,
	.param .b32 add_param_3
)
{
	.reg .pred 	%p<2>;
	.reg .b32 	%r<9>;
	.reg .b64 	%rd<11>;

// %bb.0:                               // %entry
	ld.param.b32 	%r1, [add_param_3];
	mov.u32 	%r2, %tid.x;
	mov.u32 	%r3, %ctaid.x;
	mov.u32 	%r4, %ntid.x;
	mad.lo.s32 	%r5, %r3, %r4, %r2;
	setp.ge.s32 	%p1, %r5, %r1;
	@%p1 bra 	$L__BB0_2;
// %bb.1:                               // %body
	ld.param.b64 	%rd4, [add_param_0];
	ld.param.b64 	%rd5, [add_param_1];
	cvta.to.global.u64 	%rd6, %rd5;
	ld.param.b64 	%rd7, [add_param_2];
	cvta.to.global.u64 	%rd8, %rd7;
	cvta.to.global.u64 	%rd9, %rd4;
	mul.wide.s32 	%rd10, %r5, 4;
	add.s64 	%rd1, %rd6, %rd10;
	add.s64 	%rd2, %rd8, %rd10;
	add.s64 	%rd3, %rd9, %rd10;
	ld.global.b32 	%r6, [%rd1];
	ld.global.b32 	%r7, [%rd2];
	add.rn.f32 	%r8, %r6, %r7;
	st.global.b32 	[%rd3], %r8;
$L__BB0_2:                              // %exit
	ret;
                                        // -- End function
}
```

先注意四件事，后面各章会逐一展开：

1. `.version 6.3` / `.target sm_75` 是 sm_75 的**最低** PTX 版本（Ch 3）。
2. `.reg .pred %p<2>` / `.b32 %r<9>` / `.b64 %rd<11>`：**虚拟寄存器**，不是物理寄存器（Ch 11）。
3. `ld.param` 从参数空间读，`cvta.to.global` 把 generic 指针转成 global 指针（Ch 4、5）。
4. `mad.lo.s32`、`mul.wide.s32` 是指令选择和 DAG combine 的结果（Ch 10）。

## 三、第二段：PTX → cubin

```bash
/usr/local/cuda/bin/ptxas -arch=sm_75 add.ptx -o add.cubin
/usr/local/cuda/bin/cuobjdump -res-usage add.cubin
```

真实输出：

```
Resource usage:
 Common:
  GLOBAL:0
 Function add:
  REG:12 STACK:0 SHARED:0 LOCAL:0 CONSTANT[0]:380 TEXTURE:0 SURFACE:0 SAMPLER:0
```

**你写的 PTX 里一个物理寄存器都没有，这里却出现了 `REG:12`。** 这 12 个寄存器是 `ptxas` 分配的。这是整门课最重要的分界线：LLVM 负责「语义正确 + 结构合理」，`ptxas` 负责「塞进真实硬件」。

## 四、第三段：在 T4 上跑

用 CUDA driver API 直接加载 cubin，不经过 CUDA Runtime，链路最短：

```c
// host.c（节选，完整文件见本章附录）
CUmodule mod;  cuModuleLoad(&mod, "add.cubin");
CUfunction fn; cuModuleGetFunction(&fn, mod, "add");
// add(out, a, b, n)：第一个参数是输出
  void *args[] = {&dc, &da, &db, &n};
cuLaunchKernel(fn, 4, 1, 1, 256, 1, 1, 0, 0, args, 0);
cuCtxSynchronize();
```

```bash
gcc -O2 host.c -o host -I/usr/local/cuda/include -L/usr/local/cuda/lib64 -lcuda
./host add.cubin
```

真实输出：

```
c[0]=0 c[1]=3 c[511]=1533 c[1023]=3069
mismatches=0/1024
```

到这里，一条完整的「LLVM 产物在真实 GPU 上正确执行」的闭环就成立了。后面所有章节的验证，都是往这条链上插观测点。

## 五、一个必须知道的坑：clang 的 fatbinary

如果你想用 clang 直接把 `.cu` 编成 PTX，注意这条命令在本机会失败：

```bash
$BIN/clang -x cuda --cuda-path=/usr/local/cuda --cuda-gpu-arch=sm_75 \
  -O3 -S -emit-llvm -o vadd.ll vadd.cu
# error: nvFatbinAddCubin(...) failed with error fatbinary elf mismatch
```

原因不在你的代码，而在 clang 24 与 CUDA 12.4 的 fatbinary 交互（clang 把 device 产物塞进 host fatbin 时尺寸校验不匹配）。**解法是只编 device 侧**：

```bash
$BIN/clang -x cuda --cuda-path=/usr/local/cuda --cuda-gpu-arch=sm_75 \
  --cuda-device-only -O3 -S -emit-llvm -o vadd-dev.ll vadd.cu
$BIN/llc -mtriple=nvptx64 -mcpu=sm_75 -O2 vadd-dev.ll -o vadd.ptx
```

这条路径本课全程可用，Ch 6 会详细讲它产出的 NVVM IR 长什么样。

## 踩雷集锦

1. **以为 `llc -O2` 的产物已经是优化过的机器码**：不是。它是 PTX 文字，真正的寄存器分配和调度还没发生（Ch 1、16）。
2. **以为 `.reg .b32 %r<9>` 是 9 个物理寄存器**：它是 8 个虚拟寄存器 + 编号 0 的保留位；物理寄存器数量要到 `ptxas` 之后才存在（Ch 11）。
3. **`-mcpu` 拼错**：`-mcpu=sm75`（缺下划线）会报 unknown target CPU。T4 要写 `sm_75`。
4. **PTX 版本和目标不匹配**：默认 `.version 6.3` 在 sm_75 上够用，但你想用动态 alloca（需要 PTX 7.3）就会直接报错（Ch 3 实测）。
5. **驱动版本比 PTX 版本旧**：driver JIT 只认自己支持的 PTX 版本；`cudaErrorUnsupportedPtxVersion` 一类错误通常来自这里。

## 进阶：把 PTX 文字直接丢给驱动 JIT

`cuModuleLoad` 接受 cubin，而 `cuModuleLoadData` 可以直接吃 PTX 字符串，由驱动内部调 `ptxas` 编译。把 `host.c` 的加载改成读文件 + `cuModuleLoadDataEx`，你就复现了「发行版只带 PTX、运行时 JIT」的模式。这也是 CUDA 兼容层最常用的接入方式之一。

## 动手练习

1. 把 `add.ll` 的 `-O2` 换成 `-O0`，diff 两份 PTX，记下三处差异（提示：`ld.b32` vs `ld.global.b32`、`mul+add` vs `mad.lo`、`cvt+shl` vs `mul.wide`）。
2. 把 triple 改成 `nvptx`（32 位），看 `.address_size` 和参数类型怎么变。
3. 把 `-mcpu` 改成 `sm_90a`，看 `.version` 从 6.3 变成多少。

## 本章重点整理

- 链路是 `llc → .ptx → ptxas → cubin → driver → GPU`，LLVM 只负责前两段。
- `llc` 的默认 target 是 `sm_75`，与 T4 正好匹配。
- PTX 里只有虚拟寄存器；物理寄存器数量由 `ptxas` 决定。
- 本机可以用 `--cuda-device-only` 绕过 clang 的 fatbinary 问题。

## 附录：完整的 host.c

```c
#include <cuda.h>
#include <stdio.h>
#include <stdlib.h>

#define N 1024
#define CHECK(x) do { CUresult r = (x); if (r != CUDA_SUCCESS) { \
  const char *s; cuGetErrorString(r, &s); fprintf(stderr, "%s:%d %s\n", __FILE__, __LINE__, s); exit(1);} } while (0)

int main(int argc, char **argv) {
  const char *modpath = argc > 1 ? argv[1] : "add.cubin";
  CHECK(cuInit(0));
  CUdevice dev; CHECK(cuDeviceGet(&dev, 0));
  CUcontext ctx; CHECK(cuCtxCreate(&ctx, 0, dev));
  CUmodule mod; CHECK(cuModuleLoad(&mod, modpath));
  CUfunction fn; CHECK(cuModuleGetFunction(&fn, mod, "add"));

  float *a = malloc(N * sizeof(float)), *b = malloc(N * sizeof(float)), *c = malloc(N * sizeof(float));
  for (int i = 0; i < N; i++) { a[i] = i; b[i] = 2.0f * i; c[i] = -1.0f; }
  CUdeviceptr da, db, dc;
  CHECK(cuMemAlloc(&da, N * sizeof(float)));
  CHECK(cuMemAlloc(&db, N * sizeof(float)));
  CHECK(cuMemAlloc(&dc, N * sizeof(float)));
  CHECK(cuMemcpyHtoD(da, a, N * sizeof(float)));
  CHECK(cuMemcpyHtoD(db, b, N * sizeof(float)));
  CHECK(cuMemcpyHtoD(dc, c, N * sizeof(float)));
  int n = N;
  // add(out, a, b, n)：第一个参数是输出
  void *args[] = {&dc, &da, &db, &n};
  CHECK(cuLaunchKernel(fn, N/256, 1, 1, 256, 1, 1, 0, 0, args, 0));
  CHECK(cuCtxSynchronize());
  CHECK(cuMemcpyDtoH(c, dc, N * sizeof(float)));
  printf("c[0]=%g c[1]=%g c[511]=%g c[1023]=%g\n", c[0], c[1], c[511], c[1023]);
  int bad = 0;
  for (int i = 0; i < N; i++) if (c[i] != 3.0f * i) bad++;
  printf("mismatches=%d/%d\n", bad, N);
  return 0;
}
```

编译与运行：

```bash
gcc -O2 host.c -o host -I/usr/local/cuda/include -L/usr/local/cuda/lib64 -lcuda
./host add.cubin
```
