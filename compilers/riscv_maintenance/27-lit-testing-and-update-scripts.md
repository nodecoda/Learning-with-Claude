# Ch 27 — lit 测试与 update 脚本：把回归变成一行命令

> **目标**：把“改完代码，手工贴汇编”变成“一条命令重生成 CHECK，`git diff` 评审”。能读懂 RISC-V 测试的 RUN 行，能为 CodeGen / Clang / MIR / MC / MCA 五类测试选择正确的 update 脚本，能用 `llvm-lit` 精确定位一个子集，并能判断自动生成的 diff 哪些该接受、哪些是噪声。

> **环境**：源码 `/home/ubuntu/llvm/trees/ct-instr-trunk`（`analysis/riscv-maintenance`，HEAD `0fc5afa04c23`）；构建 `T=/home/ubuntu/llvm/builds/ct-instr-trunk`（`X86;AArch64;RISCV`，assertions ON，`llvm-lit`/`FileCheck`/`not`/`split-file` 齐全）。本章标“实测”的输出均来自该树与该构建；未标注者来自源码或官方文档。

> **前置**：读完 [Ch 04 — 指令的 TableGen 建模](./04-tablegen-instruction-model.md)（知道一条指令的编码从哪来）、[练习 A — 加一条指令并跑通往返](./practice-a-tablegen-and-mc.md)（正例/负例与 `-show-encoding`）、[练习 D — 用 MIR 驱动机器 pass](./practice-d-machine-passes.md)（`-run-pass` 与 MIR 字段）。

## 27.1 为什么测试是贡献的主战场

RISC-V 后端的补丁形状几乎是固定的：**源码改得很少，测试改得很多**。本树最近 200 条 `[RISCV]` 提交里，随手能捞到两个极端样本（**实测**，`git show --stat`）：

```text
27a2da4d2716 [RISCV] Remove X5 from CSR_RT_MostRegs/CSR_RT_MostRegs_RVE
 llvm/lib/Target/RISCV/RISCVCallingConv.td             |   2 +-
 llvm/test/CodeGen/RISCV/calling-conv-preserve-most.ll | 128 +++++-----
```

源码只把一个 `X5` 从 `CalleeSavedRegs` 的 `sub` 列表里拿掉，测试重写了 128 行。另一个 `d4d37b824b91` 是 15 行 `RISCVLegalizerInfo.cpp` 对 516 行测试（4 个 `.mir/.ll`）。

reviewer 先看测试，因为测试决定“这个改动到底承诺了什么行为”。一个只有源码、没有对应 RUN/CHECK 变化的补丁，通常会被直接问：“Where is the test?”

update 脚本的价值不是“帮你写测试”，而是**把机械的 CHECK 重排压缩成一次命令**，让你把时间花在“这个 diff 是否证明了我想证明的行为”上：128 行的测试重写从半小时变成 5 分钟。

| 测试目录 | 规模（本树） | 自动生成情况（实测） |
|---|---:|---|
| `llvm/test/CodeGen/RISCV` | 2,742 个文件（2,244 `.ll` + 497 `.mir` + `lit.local.cfg`） | 2,048 个带 `update_llc_test_checks` note；508 个带 `update_mir_test_checks` |
| `clang/test/CodeGen/RISCV` | 2,824 个文件 | 2,747 个带 `update_cc_test_checks` note |
| `llvm/test/MC/RISCV` | 622 个文件 | 只有 4 个带 `update_mc_test_checks` note |
| `llvm/test/tools/llvm-mca/RISCV` | 358 个（lit 发现数） | 352 个带 `update_mca_test_checks` note |
| `lld/test/ELF/riscv-*` | 52 个 | 手工维护 |

注意 MC 的反差：**编码测试基本是手写的**。`llvm-mc -show-encoding` 的 CHECK 行短、语义强，自动生成反而容易丢信息（27.9 有实测案例）。

## 27.2 先建立直觉：一个 RISC-V 测试从 RUN 到 PASS

```text
llvm/test/CodeGen/RISCV/foo.ll
  RUN: llc -mtriple=riscv64 -mattr=+zba < %s | FileCheck %s
       │                                        │
       └─ llvm-lit → 执行 → 输出 ────────────────┘ 匹配 CHECK
失败时：update_llc_test_checks.py 重写 CHECK 行 → git diff 评审
```

把这张图拆成五步：

1. **发现**：`llvm-lit` 走进 `llvm/test/CodeGen/RISCV`，按 `lit.local.cfg` 的后缀（`.ll`、`.mir`、`.s`）把每个文件变成一个 test。
2. **解析**：lit 读 `RUN:` 行，按 shell 语法执行；`%s` 是当前测试文件的绝对路径，`%t` 是该测试独占的临时路径。
3. **执行**：`llc` 从 stdin 读 IR、把汇编写到 stdout，管道交给 `FileCheck`。
4. **匹配**：FileCheck 按**文件中的顺序**消费 CHECK 行，默认在输出里向后搜索；`CHECK-NEXT` 要求紧邻下一行，`CHECK-SAME` 要求同一行，`CHECK-LABEL` 用来切分函数边界。
5. **判定**：所有 RUN 行退出码为 0 才算 PASS。`not cmd` 把“失败”翻成“成功”；`XFAIL` 把“失败”翻成预期结果。

update 脚本做的事，就是重复第 2–3 步拿到真实输出，然后用通用化后的输出替换文件里的 CHECK 块。所以它天然只能重写“它看得懂的 RUN 行”；看不懂的管道会被跳过或留下错误的 CHECK（27.9 详述）。

## 27.3 五类测试与各自的 update 脚本

| 类别 | 典型目录 | 被测工具 | update 脚本 | RUN 行关键参数 | 重写对象 |
|---|---|---|---|---|---|
| CodeGen | `llvm/test/CodeGen/RISCV` | `llc` | `update_llc_test_checks.py` | `-mtriple`、`-mattr`、`-mcpu`、`-check-prefixes` | 每个 RUN 对应前缀的全部 `CHECK*` |
| Clang CodeGen | `clang/test/CodeGen/RISCV` | `%clang_cc1` | `update_cc_test_checks.py` | `-triple`、`-target-feature`、`-emit-llvm` | 每个函数体的 IR CHECK |
| MIR | `llvm/test/CodeGen/RISCV/*.mir` | `llc -run-pass` | `update_mir_test_checks.py` | `-run-pass`、`-passes`、`-mtriple` | 整个 `body:` 的 CHECK |
| MC | `llvm/test/MC/RISCV` | `llvm-mc` | `update_mc_test_checks.py` | `-show-encoding`、`-filetype=obj`、`-M no-aliases` | `CHECK-ASM`、`CHECK-ERROR` |
| MCA | `llvm/test/tools/llvm-mca/RISCV` | `llvm-mca` | `update_mca_test_checks.py` | `-mtriple`、`-mcpu`、`-timeline` | 调度报告的统计块 |

### 27.3.1 CodeGen：`update_llc_test_checks.py`

真实 RUN 行（`llvm/test/CodeGen/RISCV/or-is-add.ll:2-3`）：

```llvm
; RUN: llc < %s -mtriple=riscv32 | FileCheck %s --check-prefixes=RV32
; RUN: llc < %s -mtriple=riscv64 | FileCheck %s --check-prefixes=RV64
```

用法：

```bash
cd /home/ubuntu/llvm/trees/ct-instr-trunk
T=/home/ubuntu/llvm/builds/ct-instr-trunk
python3 llvm/utils/update_llc_test_checks.py --llc-binary $T/bin/llc /tmp/ch27/zba.ll
```

它重写什么：对每条 `| FileCheck` 的 RUN 行重新跑 `llc`，把该 RUN 用到的每个前缀（`CHECK`、`RV32`、`RV64`、`ZBS`……）的 CHECK 行整块替换；IR 函数体与 RUN 行不动（只更新首行 autogenerated note）。多 RUN/多前缀的典型样本是 `bittest.ll:2-13`：同一个文件 6 条 RUN 命令（12 个物理 `RUN:` 行）、11 个前缀，脚本按前缀分别生成。

三个容易误解的点：

- 脚本**没有** `-mattr`/`-mcpu`/`-check-prefix` 选项；这些是 RUN 行里的 llc/FileCheck 参数，脚本原样复用。
- `--function=name` 只更新一个函数；`-u/--update-only` 只处理已有 autogenerated note 的文件；`--force-update` 允许跨脚本接管。
- 它会把首行写成 autogenerated note；没有 note 的测试也会被处理，所以**先复制到 `/tmp`**。

### 27.3.2 Clang CodeGen：`update_cc_test_checks.py`

真实 RUN 行（`clang/test/CodeGen/RISCV/riscv-abi.cpp:2-3`）：

```cpp
// RUN: %clang_cc1 -triple riscv32 -emit-llvm %s -o - \
// RUN:   | FileCheck -check-prefixes=ILP32-ILP32F-ILP32D,ILP32-ILP32F,ILP32 %s
```

用法：

```bash
python3 llvm/utils/update_cc_test_checks.py --llvm-bin $T/bin --clang $T/bin/clang \
  /tmp/ch27/cc.cpp
```

它重写什么：先用 `clang -ast-dump=json` 拿到函数边界，再按每个 `%clang_cc1` RUN 重新生成 IR 的函数体 CHECK。`--check-attributes` 加属性检查，`--check-globals` 控制全局变量检查，`--function-signature` 保留签名行。

关键限制（`update_cc_test_checks.py:33-38`）：它只认识 `%clang`、`%clang_cc1`、`%clangxx`。RUN 行里写裸 `clang`，会被归为 “non-clang RUN line”：只执行，不生成任何 CHECK。clang 测试的惯例是 `%clang_cc1`，因为它跳过 driver，直接测前端。

### 27.3.3 MIR：`update_mir_test_checks.py`

真实 RUN 行（`llvm/test/CodeGen/RISCV/opt-w-instrs.mir:2-3`）：

```yaml
# RUN: llc -mtriple=riscv64 -mattr='+d,+zfa,+v,+xtheadmempair' -run-pass=riscv-opt-w-instrs %s -o - | FileCheck %s
# RUN: llc -mtriple=riscv64 -mattr='+d,+zfa,+v,+xtheadmempair' -passes=riscv-opt-w-instrs %s -o - | FileCheck %s
```

用法：

```bash
python3 llvm/utils/update_mir_test_checks.py --llc-binary $T/bin/llc /tmp/ch27/mir.mir
```

它重写什么：**整个 `body:`** 的 CHECK，虚拟寄存器被命名成 `[[COPY:%[0-9]+]]` 这样的 FileCheck 变量。YAML 元数据不检查，除非加 `--print-fixed-stack`（只补 `fixedStack`）；函数名仍会生成 `CHECK-LABEL`。这就是 MIR 适合锁机器 pass 的原因：输入固定，差异只可能来自 pass 本身。

### 27.3.4 MC：`update_mc_test_checks.py`

真实 RUN 行（`llvm/test/MC/RISCV/rv64zmmul-valid.s:1-3`）：

```asm
# RUN: llvm-mc %s -triple=riscv64 -mattr=+zmmul -M no-aliases 2>&1 \
# RUN:  | FileCheck -check-prefixes=CHECK-INST %s
```

用法：

```bash
PATH=$T/bin:$PATH python3 llvm/utils/update_mc_test_checks.py \
  --llvm-mc-binary $T/bin/llvm-mc /tmp/ch27/mc2.s
```

它重写什么：`-show-encoding` 的 `CHECK-ASM`、`not llvm-mc` 的 `CHECK-ERROR`；CHECK 行被放到对应输入指令的下方，错误行用 `[[@LINE-2]]` 锁定行号。`--unique` 去重、`--sort` 按字母序重排（会移动非 CHECK 行，慎用）。

必须把构建的 `bin` 放进 `PATH`：脚本会照 RUN 行调用 `llvm-objdump`。只传 `--llvm-mc-binary` 不够，实测会得到 `exit status 127`。实测在 `rv64zmmul-valid.s` 上是 `2 insertions(+), 1 deletion(-)`：note 插到首行、CHECK 移到输入行下方。它把管道倒数第二段当作被测工具：三段式 `llvm-mc | llvm-objdump | FileCheck` 会把 `llvm-objdump` 当工具，静默丢掉 objdump 的前缀（27.9 实测）。

## 27.4 RUN 行语法：lit 的指令、变量与开关

### 27.4.1 注释前缀与续行

`RUN:` 只是注释里的一段文本，注释符随文件类型变化：LLVM `.ll/.mir/.s` 用 `;` 或 `#`，Clang `.c/.cpp` 用 `//`，MC `.s` 用 `#`。行尾 `\` 续行，lit 会把多行拼成一条命令；`RUN:` 可以有多条，全部成功才算 PASS。

### 27.4.2 `REQUIRES` / `UNSUPPORTED` / `XFAIL`

三者都接受逗号分隔的布尔表达式（`llvm/docs/TestingGuide.md:625-690`）：

```llvm
; REQUIRES: asserts
; UNSUPPORTED: target={{.*-windows.*}}
; XFAIL: target=riscv{{.*}}
```

语义必须分清：

- `REQUIRES:` 所有条件为真才运行（`O0-pipeline.ll:8` 要求 assertions 构建）。
- `UNSUPPORTED:` 任一条件为真就**跳过**，不执行（`rv64i-aliases-invalid.s:1` 在 Windows 上跳过）。
- `XFAIL:` 任一条件为真时**仍然执行**，但“失败”算预期；如果它意外通过，结果是 `XPASS`，算失败（`llvm/test/CodeGen/Generic/live-debug-label.ll:10` 因 RISC-V 的双 VirtRegRewriter 标记 XFAIL）。

`REQUIRES`/`UNSUPPORTED` 是发现期过滤，`XFAIL` 是运行期判定。把 `XFAIL` 当“跳过”用，会让坏掉的测试永远不暴露。

### 27.4.3 替换变量

| 变量 | 含义 | 真实用法 |
|---|---|---|
| `%s` | 当前测试文件路径 | `llc < %s`、`llvm-mc %s` |
| `%S` | 当前测试所在目录 | `%S/Inputs/foo.ll` |
| `%t` | 本测试独占的临时文件路径 | `split-file %s %t`、`-o %t` |
| `%clang_cc1` | build 里的 clang，自动带 `-cc1` 与 include 路径 | `%clang_cc1 -triple riscv64 -emit-llvm` |
| `%llc_dwarf` | build 里的 llc；Windows-MSVC 目标额外补 `-mtriple=<target>-gnu` | `%llc_dwarf %s -filetype=obj -o -` |

`%clang_cc1` 定义在 `llvm/utils/lit/lit/llvm/config.py:331`；`%llc_dwarf` 在 `llvm/test/lit.cfg.py:233`。真实用例 `llvm/test/DebugInfo/bit-int-size.ll:1`：`%llc_dwarf %s -filetype=obj -o - | llvm-dwarfdump - | FileCheck %s`。Linux 上它就是 `llc`，但保证 Windows host 仍生成 DWARF 而非 CodeView。

### 27.4.4 FileCheck 前缀与匹配强度

```llvm
; RUN: llc ... | FileCheck %s --check-prefix=RV64
; RUN: llc ... | FileCheck %s -check-prefixes=CHECK,RV64,RV64I
```

`--check-prefix` 与 `-check-prefixes` 是同一选项的单/复数形式，FileCheck 两种拼写都收。前缀让一个文件承载多个 subtarget 的期望。

| 指令 | 语义 | 什么时候用 |
|---|---|---|
| `CHECK:` | 从当前位置向后搜索 | 默认；对插入/删除指令不敏感 |
| `CHECK-NEXT:` | 必须紧接上一匹配行 | 只有“相邻”本身就是断言时 |
| `CHECK-LABEL:` | 切分函数/基本块边界 | 每个函数第一条 |
| `CHECK-DAG:` | 同组内顺序无关 | 调度/分配顺序不稳定的多条指令 |

### 27.4.5 `-verify-machineinstrs`

这是 `llc` 的选项，不是 lit 的。它让机器函数在关键 pass 后跑 verifier，能抓住非法物理寄存器、缺失 `liveins`、坏掉的 PHI 等。

```llvm
; RUN: llc -mtriple=riscv64 -verify-machineinstrs < %s | FileCheck %s
```

`bittest.ll:2-13` 的每条 RUN 都带它。只在 assertions 构建里可靠；本构建 `llc --version` 写明 `Optimized build with assertions.`。MIR 测试如果手写输入，也应加它，否则“pass 没崩”不代表输入合法。

### 27.4.6 `split-file`：一个文件放多个输入

真实用例（`llvm/test/CodeGen/RISCV/target-abi-synthesize-flag.ll:5`）：

```llvm
; RUN: split-file %s %t
; RUN: llc -mtriple=riscv64 -mattr=+d -target-abi lp64f -filetype=obj < %t/none.ll | llvm-readelf -h - | FileCheck %s --check-prefix=LP64F
```

`split-file` 按 `^(.|//)--- <part>` 切分，把 `%t` 建成目录并写入 `none.ll`、`lp64f.ll`、`bogus.ll`。实测 `llc ... < /tmp/ch27/split/none.ll | llvm-readelf -h -` 输出 `Flags: 0x2, single-float ABI`。需要保留 `[[#@LINE+1]]` 这类相对行号时加 `--leading-lines`。

### 27.4.7 `not`：断言“必须失败”

真实用例（`llvm/test/MC/RISCV/rv64zacas-valid.s:6-7`）：

```asm
# RUN: not llvm-mc -triple=riscv64 -mattr=+a -show-encoding %s 2>&1 \
# RUN:        | FileCheck %s --check-prefix=CHECK-ERROR
```

`not` 把子进程的非零退出码翻成 0；子进程意外成功则 `not` 返回非零。断言崩溃用 `not --crash`（`llvm/utils/not/not.cpp:11`）。

## 27.5 `llvm-lit` 实操

统一前缀：`cd /home/ubuntu/llvm/trees/ct-instr-trunk; T=/home/ubuntu/llvm/builds/ct-instr-trunk`。

### 27.5.1 单文件 vs 目录

```bash
$T/bin/llvm-lit -sv llvm/test/CodeGen/RISCV/or-is-add.ll
```

实测：

```text
-- Testing: 1 tests, 1 workers --

Total Discovered Tests: 1
  Passed: 1 (100.00%)
```

```bash
$T/bin/llvm-lit -j16 --no-progress-bar llvm/test/CodeGen/RISCV llvm/test/MC/RISCV
```

实测汇总（节选）：

```text
Testing Time: 31.43s

Total Discovered Tests: 3362
  Passed: 3362 (100.00%)
```

### 27.5.2 `-s` / `-v` / `-a` 的分工

- `-s`：`--succinct`，只显示进度条 + 失败测试名（`cl_arguments.py:170`）。
- `-v`：失败测试打印完整命令与输出（`cl_arguments.py:183`）。
- `-a` 让所有测试都打印输出（`cl_arguments.py:207`），`-q` 等价于“只报错误 + 关闭逐测试输出 + 简洁汇总”；`-sv` 是最常用组合，平时安静，失败时给全日志。

### 27.5.3 `--filter` 跑子集

`--filter` 是大小写不敏感的正则，匹配 `suite :: path` 全名（`cl_arguments.py:446`）：

```bash
$T/bin/llvm-lit -sv --filter='rv64zba' llvm/test/CodeGen/RISCV llvm/test/MC/RISCV
```

实测：

```text
-- Testing: 5 of 3362 tests, 5 workers --
Testing Time: 1.44s
Total Discovered Tests: 3362
  Excluded: 3357 (99.85%)
  Passed  :    5 (0.15%)
```

排掉某类测试用 `--filter-out`；只重跑上次失败用 `--filter-failed`。

### 27.5.4 `--show-unsupported`

```bash
$T/bin/llvm-lit -sv --show-unsupported --filter='rv64i-aliases' llvm/test/MC/RISCV
```

本构建（Linux、RISC-V target 已编）没有 unsupported，输出里没有 UNSUPPORTED 行，只有 `Passed: 2`。这个选项的价值在**构建配置不匹配**时：`llvm/test/CodeGen/RISCV/lit.local.cfg` 先判断 `if not "RISCV" in config.root.targets`，随后置 `config.unsupported = True`；没编 RISC-V 时整目录被标记 unsupported；同理 `REQUIRES: asserts` 在 release 构建里会让测试消失。看到 “0 tests” 或 `Excluded` 异常高，先查 `--show-unsupported` 和构建配置。

### 27.5.5 退出码与常用组合

全 PASS（含预期 XFAIL）→ 0；任一 FAIL/XPASS/TIMEOUT → 1（实测失败文件 `llvm-lit -q fail.ll; echo $?` 得到 `1`）。`--max-failures N` 失败 N 个就停；`--timeout N` 抓挂死；`--xunit-xml-output` 出 CI 报告。

## 27.6 写一个新测试的清单

1. **放对目录**：IR→机器指令放 `llvm/test/CodeGen/RISCV`；编码/汇编语法放 `llvm/test/MC/RISCV`；单个机器 pass 放 `*.mir`；Clang 前端/ABI 放 `clang/test/CodeGen/RISCV`；调度模型放 `llvm/test/tools/llvm-mca/RISCV/<model>`。
2. **先复用文件**：能加函数就不新建文件（`TestingGuide.md` 的 “Put tests in the right place”）。新扩展通常加到 `attributes.ll`、`features-info.ll` 和已有的 `rv*<ext>.ll`。
3. **RUN 行显式写 feature**：`-mattr=+zba` 而不是依赖默认 CPU；需要 subtarget 差异就多写一条 RUN + 新前缀。
4. **正例 + 负例**：正例证明“有 `+zba` 时生成 `sh1add`”；负例证明“没有 `+zba` 时不生成”，或用 `not llvm-mc` 断言汇编器拒绝。
5. **`CHECK` 默认宽松**：`CHECK:` 对插入指令不敏感；只有“必须相邻”才 `CHECK-NEXT`。寄存器分配/调度顺序不稳定时用 `CHECK-DAG`。
6. **每个函数一个 `CHECK-LABEL`**：否则 FileCheck 可能跨函数匹配，测试会在函数重排后假通过/假失败。
7. **`-verify-machineinstrs`**：涉及机器 pass、MIR、pseudo 展开的测试都加；它把“输入非法”变成显式失败。
8. **不要写死 opcode 编号/枚举值**：`ADDI = 13776` 会随 TableGen 变化；断言助记符和编码字节，不断言 `RISCV::ADDI` 的数值。
9. **MIR 用变量捕获虚拟寄存器**：`[[COPY:%[0-9]+]]`，不要写 `%0`；`%0` 在 pass 插入 COPY 后会漂移。
10. **收尾三连**：单文件 `llvm-lit -sv` → 目录 `llvm-lit -j16` → `git diff` 只包含预期源码与测试。仓库有 ninja 目标 `check-llvm-codegen-riscv`、`check-llvm-codegen-mir-riscv`（实测存在），MC 目录没有独立目标，直接用 `llvm-lit`。

## 27.9 踩雷集锦

**1. update 脚本会重写整个文件，而且只重写它看得懂的 RUN 行。**
`update_llc_test_checks.py` 默认更新所有函数的所有前缀；同时它只重写管道倒数第二段能被它识别的模式。实测对 `rv64zacas-valid.s` 跑 `update_mc_test_checks.py`：`CHECK-ASM`/`CHECK-ERROR` 被重写，三段式里的 `CHECK-ASM-AND-OBJ` 整段消失，而**测试仍然通过**，反汇编覆盖被悄悄删掉。先在 `/tmp` 副本上跑、`git diff` 逐行看；单函数用 `--function`，只改已 autogenerated 的文件用 `-u`。

**2. `CHECK-NEXT` 过严，会把无关变化变成失败。**
插入一条 `COPY`、多一个空行、注释变化都会让 `-NEXT` 断链。实测把一条 `CHECK-NEXT` 的立即数改错，FileCheck 报 `expected string not found` 并给出 `possible intended match`。只有“相邻”本身是语义时才用 `-NEXT`。

**3. CHECK 顺序依赖寄存器分配和调度。**
`or-is-add.ll` 加 `+zba` 后，不只是多/少一条 `sh2add`，`a2/a3/a4` 的编号也重排了。测试应断言“指令序列与关键操作数”，不要把整段寄存器分配当成契约；顺序不稳定的多条指令用 `CHECK-DAG`。

**4. `REQUIRES` 与构建配置不匹配，测试会“消失”而不是失败。**
`REQUIRES: asserts` 在 release 构建里直接跳过；`llvm/test/CodeGen/RISCV/lit.local.cfg` 在没编 RISC-V 时把整个目录标记 unsupported。看到 `Excluded` 比例异常，先用 `--show-unsupported` 查，而不是改测试。

**5. `XFAIL` 不是“跳过”。**
它仍然执行，只是把失败当预期；一旦代码修好、测试开始通过，结果变成 `XPASS`，CI 仍然红。临时禁用请用 `UNSUPPORTED`；跟踪已知 bug 才用 `XFAIL`。

**6. `%t` 与 `%s` 混用，测试会读错文件或污染源码目录。**
`%s` 是只读的源文件；`%t` 是本测试独占的临时文件。`split-file %s %t` 之后要读 `%t/foo.ll`，不能继续 `< %s`。`%T` 已弃用，多个测试共享同一目录会产生竞态。

**7. 测试里写死 opcode 编号/枚举值。**
`ADDI = 13776` 是 TableGen 生成顺序的产物，任何新增指令都可能改它。断言助记符、编码字节、`llvm-readobj` 的字段，不要断言 `RISCV::ADDI` 的数值。

**8. `update_cc_test_checks.py` 只认 `%clang`/`%clang_cc1`/`%clangxx`；`update_mc` 还要求 `PATH` 有构建的 `bin`。**
RUN 行里写裸 `clang`，cc 脚本会把它当 non-clang RUN line：执行但不生成 CHECK。MC 脚本会照 RUN 行调用 `llvm-objdump`；实测未设 `PATH` 时报 `CalledProcessError ... exit status 127`。统一先 `export PATH=$T/bin:$PATH`。

## 27.10 本章重点整理

- RISC-V 补丁的常态是“少量源码 + 大量测试”；测试是 reviewer 判断行为承诺的第一入口。
- lit 的本质是“shell 脚本执行器 + FileCheck”：RUN 行决定跑什么，CHECK 决定断言什么，退出码决定 PASS/FAIL。
- 五类测试各有专属 update 脚本：llc、cc、mir、mc、mca；脚本只重写它看得懂的 RUN 行对应的 CHECK 块。
- `-mattr`/`-mcpu`/`-check-prefix` 是 RUN 行参数，不是 update 脚本参数；脚本原样复用 RUN 行。
- `REQUIRES` 是启用条件，`UNSUPPORTED` 是跳过，`XFAIL` 是“预期失败但必须执行”；三者不能混用。
- `%s` 只读源文件，`%t` 是本测试独占临时路径；`split-file %s %t` 是多输入测试的标准写法。
- `llvm-lit -sv` 单文件定位、`-j16` 全目录、`--filter` 子集、`--show-unsupported` 查构建配置。
- 自动生成的 diff 必须逐条解释：指令变化是语义，寄存器/标签重排是噪声；最危险的失败是“测试仍然绿但覆盖没了”。
