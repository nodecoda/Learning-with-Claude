# 第 16 章 从 IR 到 C：生成可加载的 DLL

> **目标**：读懂 `CCodegen` 如何把一张静态 shape 的 IR 降低成 C99 源码；理解 `MINI_EXPORT`、`mini_forward` 的函数签名、arena 分配、指针绑定、算子循环和输出拷贝；能编译生成的 C 为 DLL，用 `ctypes` 调用并与解释器对齐；能定位 softmax 未实现这类 lowering 失败。
>
> **环境**：Windows 10/11 x86_64，Python 3.11.12，torch 2.14.1+cpu，numpy 2.4.6，MSVC 14.43。命令在仓库根目录执行。先设置 `$env:PYTHONPATH = "compilers\mini_ai_compiler\code"` 与 `$env:PYTHONIOENCODING = "utf-8"`。编译需要 `cl`，`find_vcvars64()` 会自动查找 `vcvars64.bat`，也可以设置 `$env:VCVARS64`。本章的 C 片段、错误信息和误差均来自实际生成与运行。

## 为什么需要 C 后端

解释器用 NumPy 执行 IR，适合做语义金标准，不适合部署。它依赖 Python 运行时，每个算子都有 Python 调用开销，内存布局由 NumPy 决定。C 后端把整张图变成一个函数，最终编译成动态链接库（DLL），循环、偏移和缓冲区都在编译期确定，运行时只做一次 arena 分配和一次函数调用。

C 后端还有一个教学价值：它把编译器做出的选择暴露出来。你可以直接看到：

- 哪个值被放在 arena 的哪个偏移。
- 每个算子生成几层循环，循环顺序是什么。
- 广播如何变成索引表达式。
- 输出如何从 arena 拷贝到调用者缓冲区。
- 编译器如何把 `fmaxf`、`expf` 和浮点乘法变成机器码。

LLVM 后端生成的是 IR，最终还要经过 LLVM 优化和代码生成。C 后端把这一层交给 `cl`，源码可读，调试直接。两条路线各有价值，第 21 章之后会对照。

## 先建立直觉

```text
Graph + MemoryPlan
        |
        v
+-------------------+
| CCodegen.emit()   |   遍历 values 和 ops
+-------------------+
        |

        |

+-------------------+

+-------------------+

```

生成的函数形状：

```text
mini_forward(const float* x0, ..., float* out0, ...)

  输入指针  ---> 只读，指向调用者数据
  输出指针  ---> 只写，指向调用者缓冲区

```

## 核心内容

### 1. CCodegen 的构造与 plan

`CCodegen` 在构造时接收图和可选的 `MemoryPlan`：

```python
class CCodegen:
    def __init__(self, graph: Graph, plan: MemoryPlan | None = None, *, function_name: str = "mini_forward") -> None:
        self.graph = graph
        self.plan = plan or plan_memory(graph)
        self.function_name = function_name
        self.input_index = {id(v): i for i, v in enumerate(graph.inputs)}
        self.output_index = {id(v): i for i, v in enumerate(graph.outputs)}
        self.value_name = {id(v): f"v_{v.id}_{_ident(v.name)}" for v in graph.values}
        self.const_name = {id(v): f"C_{v.id}" for v in graph.values if v.kind == "constant"}
```

没有传入 plan 时，构造器自己调用 `plan_memory(graph)`。这意味着代码生成和内存规划是解耦的：你可以先规划、检查、修改 alignment，再把同一个 plan 交给代码生成器；也可以让代码生成器用默认规划。

`value_name` 给每个值一个唯一的 C 标识符，格式是 `v_<id>_<sanitized_name>`。`id` 来自 `Graph._new_value`，保证即使两个值同名也不会冲突。`_ident` 把非字母数字下划线替换成下划线：

```python
def _ident(name: str) -> str:
    return re.sub(r"[^A-Za-z0-9_]", "_", name)
```

常量名是 `C_<id>`，与临时值的 `v_` 前缀分开，避免和用户命名冲突。

`generate_c` 是薄封装：

```python
def generate_c(graph, plan=None, *, function_name="mini_forward") -> str:
    return CCodegen(graph, plan, function_name=function_name).emit()
```

### 2. 文件头与 MINI_EXPORT

生成文件的开头固定是：

```c
/* Generated by mini_ai.codegen_c. */
#include <stddef.h>
#include <math.h>
#if defined(_MSC_VER)
#include <malloc.h>
#endif

#if defined(_MSC_VER)
#define MINI_EXPORT __declspec(dllexport)
#else
#define MINI_EXPORT
#endif
```

`stddef.h` 提供 `size_t`，`math.h` 提供 `fmaxf` 和 `expf`，`malloc.h` 在 MSVC 下提供 `_aligned_malloc` 和 `_aligned_free`。

`MINI_EXPORT` 在 MSVC 下展开为 `__declspec(dllexport)`，把符号放进 DLL 的导出表。没有它，`ctypes.CDLL(...).mini_forward` 会找不到符号。非 MSVC 平台展开为空，依赖默认可见性；在 GCC/Clang 上构建共享库时，可能需要 `__attribute__((visibility("default")))`，这是移植时要注意的差异。

生成的是 C99，不是 C++。函数名 `mini_forward` 在 C 中没有 name mangling，`ctypes` 可以直接按名字查找。如果把它当 C++ 编译，需要 `extern "C"`，否则符号名会被改编，`getattr(lib, "mini_forward")` 失败。

### 3. 函数签名

签名由输入和输出的数量决定：

```python
sig_inputs = [f"const float* x{i}" for i in range(len(self.graph.inputs))]
sig_outputs = [f"float* out{i}" for i in range(len(self.graph.outputs))]
lines.append(
    f"MINI_EXPORT int {self.function_name}({', '.join(sig_inputs + sig_outputs)}) {{"
)
```

MLP 有一个输入和一个输出，生成：

```c
MINI_EXPORT int mini_forward(const float* x0, float* out0) {
```

签名有三个特点：

1. 没有 shape 参数。shape 在编译期已知，直接写进循环边界。
2. 没有 dtype 参数。IR 只支持 float32，指针类型固定为 `const float*` 和 `float*`。
3. 返回 `int` 错误码。0 表示成功，非 0 表示失败；当前实现只返回 1（arena 分配失败）和 0。

输入是 `const`，生成的代码不会写它。输出不是 `const`，函数会写。参数顺序是“所有输入，再所有输出”，`runtime.load_c_function` 按同样的顺序设置 `argtypes`：

```python
fn.argtypes = [ptr] * (n_inputs + n_outputs)
fn.restype = ctypes.c_int
```

调用者必须传对数量。少传一个，`ctypes` 可能读到栈上的垃圾指针，程序崩溃；多传一个，参数被忽略或覆盖。`run_c_graph` 用 `graph.inputs` 和 `graph.outputs` 的顺序构造参数，避免手工排错。

### 4. 常量数组

常量在生成文件里是 `static const float` 数组：

```c
static const float C_2[16] = {
    0.144418865f, 0.13991046f, -0.21862109f, -0.110249668f, -0.330517858f, 0.190050155f, 0.30571416f, 0.115620553f,
    -0.218760729f, 0.186485201f, 0.2934089f, -0.0723317862f, -0.0579561591f, 0.122371405f, 0.0454840362f, -0.11685349f
};
```

这段是真实生成文件的一部分。`_array_literal` 把 `np.ndarray` 展平，每行 8 个值。`_c_float` 负责格式化：

```python
def _c_float(x: float) -> str:
    value = float(x)
    if value == 0.0:
        return "0.0f"
    text = f"{value:.9g}"
    if "e" not in text and "E" not in text and "." not in text:
        text += ".0"
    return text + "f"
```

`9g` 是 float32 的有效十进制位数，足以往返转换。末尾的 `f` 很重要：C 的浮点字面量默认是 `double`，不加 `f` 会先按 double 解析再转换，可能引入额外的舍入，也会让编译器生成不必要的 double 指令。`0.0f` 单独处理，避免输出 `0f` 这种不是合法浮点字面量的形式。

数组长度用 `max(1, v.type.numel)`。标量常量的 `numel` 是 1，数组仍然有一个元素。空张量在 IR 中允许 `numel=0`，但 C 的零长数组不是标准 C99，所以生成器至少给一个元素。

### 5. arena 分配

函数体的第一段是 arena：

```c
const size_t arena_bytes = 320;
#if defined(_MSC_VER)
    float* arena = (float*)_aligned_malloc(arena_bytes, 64);
#else
    float* arena = (float*)aligned_alloc(64, arena_bytes);
#endif
    if (!arena) return 1;
```

`arena = max(64, self.plan.arena_bytes)`。规划器保证 `arena_bytes` 至少 64，这里再兜一层，避免空图或异常 plan 生成 0 字节分配。

MSVC 用 `_aligned_malloc(size, alignment)`，参数顺序是“大小，对齐”。C11 的 `aligned_alloc(alignment, size)` 参数顺序相反，且要求大小是对齐的倍数。生成器为两个平台分别写分支，没有混用。

`_aligned_malloc` 可能返回 NULL，代码检查并返回 1。调用者通过 `ctypes` 看到非零返回码，`load_c_function` 抛 `RuntimeError`。没有这个检查，后续指针绑定会对 NULL 做算术，直接崩溃。

### 6. 指针绑定

分配完 arena，生成器为每个值写一行指针：

```c
const float* v_0_x0 = x0;
const float* v_2_fc1_bias = C_2;
const float* v_3_linear_weight_t = C_3;
const float* v_8_fc2_bias = C_8;
const float* v_9_linear_1_weight_t = C_9;
float* v_12_relu_fused = (float*)((char*)arena + 0);
float* v_13_linear_1_fused = (float*)((char*)arena + 256);
```

这段是 MLP 生成文件的真实片段。输入直接指向 `x0`，常量指向静态数组，临时值指向 arena 的字节偏移。`(char*)arena + off` 按字节移动，再转回 `float*`，原因在第 14 章解释过。

代码生成器只给 plan 里有 allocation 的值生成 arena 指针。判断方式是：

```python
elif id(v) in {id(a.value) for a in self.plan.allocations.values()}:
    off = self.plan.offset_of(v)
    lines.append(f"    float* {self.ptr(v)} = (float*)((char*)arena + {off});")
```

这个集合在每次循环里重新构造，效率不高，但图很小，生成阶段不是瓶颈。更重要的是它保证不会给输入或常量错误地分配 arena 指针。

### 7. 算子 lowering

`_emit_op` 按 `op.kind` 分派：

```python
if kind in {"add", "sub", "mul", "div", "relu", "exp", "add_relu"}:
    self._emit_elementwise(op, lines)
    return
if kind in {"matmul", "matmul_bias", "matmul_bias_relu"}:
    self._emit_matmul(op, lines)
    return
if kind == "sum":
    self._emit_sum(op, lines)
    return
if kind == "softmax":
    raise IRError("C backend does not implement softmax yet; use sum/exp/div")
raise IRError(f"C backend does not support op: {kind}")
```

逐元素算子生成嵌套循环，循环边界来自输出 shape：

```c
for (int i5 = 0; i5 < 4; ++i5) {
    for (int j5 = 0; j5 < 16; ++j5) {
        ...
    }
}
```

matmul 生成三层循环：

```c
for (int i5 = 0; i5 < 4; ++i5) {
    for (int j5 = 0; j5 < 16; ++j5) {
        float acc = 0.0f;
        for (int k5 = 0; k5 < 8; ++k5) {
            acc += v_0_x0[(i5)*8 + (k5)] * v_3_linear_weight_t[(k5)*16 + (j5)];
        }
        acc += v_2_fc1_bias[j5];
        acc = fmaxf(acc, 0.0f);
        v_12_relu_fused[(i5)*16 + (j5)] = acc;
    }
}
```

`matmul_bias_relu` 在累加后加 bias，再做 `fmaxf`，最后写输出。这段循环顺序是 `i -> j -> k`，不是高性能实现；第 18 章会讨论 tiling 和 loop order。第 19 章会讨论 `/O2` 如何向量化这条循环。

`sum` 的 lowering 单独处理 axis 和 keepdims。没有 axis 时，生成一个扁平累加到 `out[0]` 的循环；有 axis 时，按输入 shape 生成嵌套循环，输出索引去掉 axis 或把 axis 置 0。

### 8. 输出拷贝

所有算子执行完后，生成器为每个输出写拷贝循环：

```python
for i, v in enumerate(self.graph.outputs):
    n = max(1, v.type.numel)
    lines.append(f"    for (int i = 0; i < {n}; ++i) out{i}[i] = {self.ptr(v)}[i];")
```

MLP 生成：

```c
for (int i = 0; i < 16; ++i) out0[i] = v_13_linear_1_fused[i];
```

拷贝循环有三个作用：

1. 把结果从 arena 移到调用者拥有的内存。
2. 让 arena 可以在函数返回前释放。
3. 允许输出在 arena 中的偏移是任意合法的 64 字节位置，不需要和 `out0` 对齐。

拷贝必须逐元素，不能用 `memcpy` 吗？可以，但当前实现用循环，原因是简单、类型明确，且编译器通常会把固定长度的拷贝优化成向量指令。对大输出，`memcpy` 可能更快；这是后续优化点。

### 9. 释放与返回

```c
#if defined(_MSC_VER)
    _aligned_free(arena);
#else
    free(arena);
#endif
    return 0;
}
```

释放函数必须和分配函数配对。MSVC 的 `_aligned_malloc` 配 `_aligned_free`，C11 的 `aligned_alloc` 配 `free`。混用会破坏堆。

返回 0 表示成功。函数没有其他错误路径；如果将来加入运行时 shape 检查，可以返回不同的错误码。`runtime.load_c_function` 对任何非零返回码都抛 `RuntimeError`，不区分具体原因；第 20 章会讨论错误码设计。

### 10. 正常路径：生成、编译、调用

用 demo 的 MLP：

```python
result = compile_graph_c(g, ".scratch/mini-ai-demo", name="mlp")
out = run_c_graph(g, {"x0": x.numpy()}, result.dll_path)[0]
```

实际输出：

```text
source: .scratch\mini-ai-demo\mlp.c
dll: .scratch\mini-ai-demo\mlp.dll
max_abs_error: 4.470348358154297e-08
```

`compile_graph_c` 做三件事：

1. `generate_c(graph)` 生成源码。
2. 把源码写到 `build_dir/name.c`。
3. 写一个 `build.bat`，调用 `vcvars64.bat`，执行 `cl /nologo /LD /O2 /fp:fast /Fe:name.dll name.c`。

`/LD` 生成 DLL，`/O2` 开优化，`/fp:fast` 放宽浮点语义以允许更激进的优化。`/fp:fast` 会改变 NaN/Inf 的处理和累加顺序，数值对比要用容差。demo 的误差约 `4.47e-08`，来自 matmul 的累加顺序差异。

`run_c_graph` 按 `graph.inputs` 的顺序取输入，按 `graph.outputs` 的顺序分配输出数组，设置 `argtypes` 和 `restype`，调用函数，检查返回码。它把 `ctypes` 的细节封装起来，测试里比较数组即可。

### 11. 失败路径：softmax 没有 C lowering

C 后端不支持 `softmax`。生成器明确抛出：

```text
IRError C backend does not implement softmax yet; use sum/exp/div
```

复现代码：

```python
g = Graph()
x = g.add_input("x", (2, 3))
s = g.add_op("softmax", [x], {"axis": -1})
g.add_output(s)
generate_c(g)
```

这个错误发生在生成阶段，不会写出 C 文件，也不会调用 `cl`。错误信息给出了替代方案：把 softmax 拆成 `exp`、`sum`、`div`。这不是自动 lowering，需要在前端或 pass 里完成。

失败路径的价值在于定位。看到这条错误，你知道问题不在 ABI、不在编译器、不在数值，而是 C 后端没有实现该算子。不要先去查 `ctypes` 参数，先看 `_emit_op` 的分派表。

## 底层机制

### 静态 shape 与循环边界

所有循环边界都是编译期常量，来自 `TensorType.shape`。这让生成的 C 没有 shape 参数，也没有运行时分支。代价是每换一个 shape 就要重新生成、重新编译。动态 shape 需要把边界变成参数，或者按 shape 特化多份代码。

### 行主序索引

`_linear_index(shape, strides, vars_)` 把多维下标变成一维偏移：

```python
def _linear_index(shape, strides, vars_):
    terms = []
    for d, s, var in zip(shape, strides, vars_):
        if s == 0:
            continue
        if s == 1:
            terms.append(var)
        else:
            terms.append(f"({var})*{s}")
    return " + ".join(terms) if terms else "0"
```

strides 来自 `TensorType.strides`，是行主序的元素步长。`s == 0` 表示广播维度，直接跳过；`s == 1` 省略乘法，生成更短的表达式。标量的 `terms` 为空，返回 `"0"`。

### 广播索引

`_broadcast_index(in_shape, out_shape, vars_)` 先调用 `broadcast_strides` 得到输入在输出 shape 下的步长，再生成线性索引。一个 shape 为 `(3,)` 的 bias 加到 `(4,3)` 的输出上，bias 的 strides 变成 `(0,1)`，索引表达式只剩 `j`，每个 `i` 都读同一个 bias 元素。

### 名称与符号

`value_name` 带 id，避免两个 `relu` 输出重名。`_ident` 只保留 ASCII 字母、数字和下划线；中文名、点号、斜杠都会变成下划线。C 标识符不能以数字开头，但 `v_` 和 `C_` 前缀保证开头是字母。

函数名默认 `mini_forward`，可以通过 `function_name` 参数改。`runtime.load_c_function` 的 `symbol` 参数也要同步改，否则 `getattr` 找不到符号。

### 浮点字面量与精度

`_c_float` 用 `9g` 保留 float32 的有效数字。`0.1` 在 float32 中不是精确值，`9g` 输出 `0.100000001f`，转回 float32 仍然是同一个位模式。用 `%f` 或更少位数会丢失精度，导致权重和 PyTorch 不一致。

## 进一步用法与变体

### 多输出

签名会为每个输出加一个 `float* outN`。拷贝循环按 `graph.outputs` 顺序写。调用者要按同样顺序传缓冲区。`run_c_graph` 已经处理了这一点；手写 `ctypes` 调用时容易把输出顺序弄反。

### 自定义函数名

`generate_c(graph, function_name="mlp_forward")` 生成 `MINI_EXPORT int mlp_forward(...)`。`load_c_function(..., symbol="mlp_forward")` 要传同样的名字。函数名不要用 C 关键字，也不要以数字开头。

### 边界检查插桩

在指针绑定后插入块大小常量，在每个循环写入前检查下标。插桩版本能抓越界，但会拖慢性能。更好的做法是用第 15 章的 debug allocator 或 ASan，在测试构建中检查，发布构建保持干净。

### 跨平台编译

Linux/macOS 用 `cc -shared -fPIC -O2`，`aligned_alloc` 需要 C11。MSVC 的 `_aligned_malloc` 不在标准 C 里，生成器用宏分支处理。移植时先确认 `aligned_alloc` 的大小参数是对齐的倍数，否则返回 NULL。

## 对比与取舍

| 维度 | 解释器 | C 后端 | LLVM 后端 |
| --- | --- | --- | --- |
| 启动成本 | 低，直接跑 | 需要 `cl` 编译 | 需要构建 LLVM 模块 |
| 运行速度 | 慢，Python 开销 | 快，原生循环 | 快，可跨函数优化 |
| 可读性 | 高，Python 代码 | 高，生成 C 可读 | 低，IR 较长 |
| 内存布局 | NumPy 决定 | 显式 arena | workspace 参数 |
| 算子覆盖 | 全部解释器算子 | 子集，softmax 未实现 | 子集，需逐个 lowering |
| 调试难度 | 低 | 中，C 与 ABI | 高，IR 与 JIT |
| 适用场景 | 语义金标准 | 部署、教学 | 研究、跨平台优化 |

C 后端的优势是透明：你能看到每一条循环和每一个偏移。LLVM 后端的优势是优化空间：LLVM 能做跨基本块优化、寄存器分配和目标相关指令选择。两者都实现，才能比较“手写 C + 编译器”与“自己生成 IR”的取舍。

## 踩雷集锦

### 1. 忘记输出拷贝，直接返回 arena 指针

函数返回后 arena 被释放，调用者拿到悬空指针。表现可能是随机数据、崩溃，或者在某些运行下看起来正常。输出必须拷贝到 `outN`，这是生命周期要求，不是可选优化。

### 2. `_aligned_malloc` 配 `free`

MSVC 的 aligned 分配有额外的头部信息，必须用 `_aligned_free` 释放。混用会破坏堆，错误可能延迟到下一次分配才出现。生成器的 `#if defined(_MSC_VER)` 分支要成对修改。

### 3. 忘记 `MINI_EXPORT`

没有 `__declspec(dllexport)`，DLL 编译成功，但导出表里没有 `mini_forward`。`ctypes.CDLL` 加载成功，`getattr(lib, "mini_forward")` 抛 `AttributeError`。Linux 上默认可见性可能让它“碰巧”工作，Windows 上不会。

### 4. `ctypes` 的 `argtypes` 数量不对

`load_c_function` 按 `n_inputs + n_outputs` 设置指针参数。手工调用时少传一个，C 函数会从寄存器或栈上读垃圾地址。症状是崩溃或输出全零。用 `run_c_graph`，不要手写参数列表。

### 5. 浮点字面量没有 `f` 后缀

`0.1` 是 double，`0.1f` 是 float。大量常量以 double 解析再转换，可能让结果与 PyTorch 的 float32 路径出现细微差异，也会让编译器生成 double 指令。`_c_float` 统一加 `f`，自定义生成器不要漏掉。

## 进阶

1. 为 `softmax` 写一个 lowerer：先展开成 `exp`、`sum`、`div`，再交给现有的逐元素和 reduction 生成器。用解释器对比数值。
2. 给生成的 C 加 shape 和指针检查：输入为 NULL、输出为 NULL、arena 分配失败分别返回不同错误码，并在 `runtime` 里映射成异常。
3. 把 `matmul` 的循环顺序改成 `i -> k -> j`，用第 18 章的 autotune 脚本比较性能。注意数值误差可能变化。
4. 生成一个多输出图，手工写 `ctypes` 调用，确认输出顺序与 `graph.outputs` 一致。

## 动手练习

1. 用 `generate_c` 生成一个 `add -> relu -> sum` 的 C 文件，找到逐元素循环和 reduction 循环，标出每个循环的边界来源。
2. 复现 softmax 的 `IRError`，然后把图改写成 `exp -> sum -> div`，确认 C 后端能生成并运行。
3. 修改 `function_name` 为 `my_forward`，用 `compile_graph_c` 编译，再用 `load_c_function(..., symbol="my_forward")` 调用。
4. 在生成的 C 里找到两个临时指针，确认它们的偏移来自 plan，而不是硬编码。把 plan 的 alignment 改成 16，重新生成，观察偏移变化。
5. 给 `run_c_graph` 传错数量的输入，记录异常类型和信息。思考为什么 `ctypes` 不能在调用前发现这个问题。

## 本章重点

- `CCodegen` 把图、plan 和函数名绑定，`emit()` 生成完整 C99 源码。
- `MINI_EXPORT` 在 MSVC 下导出符号，`ctypes` 才能按名字找到 `mini_forward`。
- 签名是“所有 `const float*` 输入，再所有 `float*` 输出”，返回 `int` 错误码。
- 常量是 `static const float C_id[]`，浮点字面量带 `f`，用 9 位有效数字。
- arena 用 `_aligned_malloc(..., 64)` 或 `aligned_alloc(64, ...)`，临时值通过字节偏移绑定。
- 算子 lowering 覆盖逐元素、matmul、sum；softmax 明确未实现并报错。
- 输出必须在释放 arena 前拷贝到调用者缓冲区。
- 真实 MLP 的 C 误差约 `4.47e-08`，与解释器的差异来自浮点累加顺序。

## 延伸阅读

- **《Engineering a Compiler》第 14 章指令选择**：读树覆盖和模式匹配。学 IR 算子如何映射到目标指令；本章的 `_emit_op` 是最直接的手写模式匹配。
