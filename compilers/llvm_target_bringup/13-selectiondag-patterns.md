# Ch 13 — SelectionDAG 选指

> **目标**：读懂 SelectionDAGISel 的选指契约，能用 `Pat`、`ImmLeaf`、`ComplexPattern` 的词汇描述“DAG 节点如何变成机器 opcode”，并跟着 MiniRV 的 `Select`、`MiniRVInstrInfo.td`、`-debug-only=isel` 把 `add3` 从 DAG 追到字节编码。

> **环境**：LLVM 24.0.0git，`/home/ubuntu/llvm/trees/dsl-tablegen`，构建 `/home/ubuntu/llvm/builds/dsl-tablegen`。`B=/home/ubuntu/llvm/builds/dsl-tablegen/bin`；本文命令均在该构建实跑。

## 为什么需要这个？

Ch 12 结束时，DAG 里的节点都已经“合法”：i8/i16/i32 被提升成 i64，`GlobalAddress` 被改写成目标节点，但没有一条指令被选中。合法只回答“这个操作能不能做”，选指才回答“用哪条指令做”。

没有这一层，你要么在 lowering 里手写每个 opcode 的选择（`if add then ADDI else if ...`），要么让后端在遇到没覆盖的组合时崩在 `Cannot select`。表驱动选指解决的是三件事：

1. **声明式**：`def : Pat<(i64 (add GPR:$rs1, simm12:$imm)), (ADDI ...)>` 直接写出“什么形状用什么指令”，不写匹配算法。
2. **可生成**：TableGen 把成百上千条 pattern 编成一张 matcher 表，`SelectCode` 只是查表；匹配顺序、失败回溯都是生成的。
3. **可诊断**：匹配失败会告诉你是哪个节点、试到哪条索引；`-debug-only=isel` 能看到每一步 morph。

代价是：模式表达不了的东西必须退回 C++，而“模式能表达什么”取决于你给节点/操作数起的类型。这一章的重点就是这条边界。

## 先建立直觉

先看全景。MiniRV 的选指不是一步，而是 DAG 的六次快照加一次机器码收尾：

```
LLVM IR
  │  SelectionDAGBuilder
  ▼
Initial selection DAG        ISD::add / ISD::mul / ISD::RET
  │  LegalizeTypes           i8/i16/i32 → i64
  ▼
Type-legalized DAG
  │  LegalizeDAG (operation legalization + LowerOperation)
  ▼
Legalized DAG                GlobalAddress → PseudoLA(machine node)
  │  DAGCombine
  ▼
Optimized legalized DAG
  │  ISel: MiniRVDAGToDAGISel::Select → SelectCode → matcher
  ▼
Selected DAG                 ADD / MUL / LD / BEQ / PseudoCALL
  │  FinalizeISel
  ▼
MachineFunction (MIR)        vreg + machine opcode，Pseudo* 还在
  │  RegAlloc / PEI / AsmPrinter
  ▼
MCInst → 4 字节编码
```

选指器有两个入口，顺序很关键：

```
MiniRVDAGToDAGISel::Select(N)
  ├─ N 已经是 machine opcode?         → 直接返回（别的 pass 已经选过）
  ├─ ISD::ADD + 常量，12 位放不下?     → 手写两条 ADDI
  ├─ ISD::Constant?                   → ADDI x0, imm / LUI+ADDI / 64 位拼装
  ├─ ISD::FrameIndex?                 → ADDI <fi>, 0
  └─ SelectCode(N)                    → 查 MiniRVGenDAGISel.inc 生成的 matcher
```

`Select` 是 target 的“先手”，`SelectCode` 是生成的表。**先手必须是保守的**：它只处理表里表达不了或表达得不好的形状，其余一律落回 `SelectCode`。

## 主线 1：ISel 的契约

`SelectionDAGISel` 是 MachineFunction pass。它的工作循环是：拿到合法化后的 DAG，先给节点编拓扑序号，然后从根节点（chain 的末端）沿列表往入口方向走，对每个有使用者的节点调用虚函数 `Select(SDNode *)`。默认实现就是 `SelectCode`；target 覆盖 `Select` 时，要么自己把节点替换掉，要么最后调用 `SelectCode`。

MiniRV 的写法是标准的：

```cpp
class MiniRVDAGToDAGISel : public SelectionDAGISel {
public:
  MiniRVDAGToDAGISel(MiniRVTargetMachine &TM, CodeGenOptLevel OptLevel)
      : SelectionDAGISel(TM, OptLevel) {}

// Include the pieces autogenerated from the target description.
#include "MiniRVGenDAGISel.inc"

  void Select(SDNode *N) override;
  ...
};
```

`MiniRVGenDAGISel.inc` 在类体里 include，提供 `SelectCode` 和 matcher 表。它由 `llvm-tblgen -gen-dag-isel` 从 `MiniRVInstrInfo.td` 生成，构建目录里可以直接读到：

```console
$ ls /home/ubuntu/llvm/builds/dsl-tablegen/lib/Target/MiniRV/MiniRVGenDAGISel.inc
/home/ubuntu/llvm/builds/dsl-tablegen/lib/Target/MiniRV/MiniRVGenDAGISel.inc
```

契约有四条，违反任何一条都会在 verifier 或后续 pass 里炸：

- **每个节点必须被替换**：`ReplaceNode` / `MorphNodeTo`，或者返回后由 `SelectCode` 处理。你 `return` 得太早，节点保留成 `ISD::add`，最终报 `Cannot select`。
- **替换出来的节点必须是 machine opcode 或合法 DAG**：可以像 MiniRV 的常量物化那样一次生成多条机器指令，但不能再生成 `ISD::add`。
- **chain/glue 要接上**：store、call、branch 都有 chain；call 还多一条 glue，用来串起参数 COPY。断链会变成“指令被调度到错误位置”的隐形 bug。
- **操作数类型要对**：pattern 里写 `(i64 (add ...))`，匹配的是值类型 i64 的 add；i32 add 在 MiniRV 里根本不存在（类型合法化已提升），所以看不到。

两个调试开关要分清：

- `-debug-only=isel` 打开 `SelectionDAGISel` 内部的 `DEBUG_TYPE "isel"`，打印每个快照的 DAG、每个节点的匹配过程。MiniRV 文件里也 `#define DEBUG_TYPE "minirv-isel"`，但目前没有任何 `LLVM_DEBUG` 语句，所以 `-debug-only=minirv-isel` 是空的——bring-up 阶段先靠通用 dump，别去等一个不存在的日志。
- `-stop-after=finalize-isel` 停在 `FinalizeISelPass` 之后，输出 MIR。此时选指完成、虚拟寄存器还在、`Pseudo*` 还没展开。

选指词汇表（先建立映射，后面逐个看 MiniRV 用不用）：

| 概念 | 作用 | MiniRV | RISC-V |
|---|---|---|---|
| `Pat` | 一条“DAG 形状 → 指令”的规则 | 大量使用 | 大量使用 |
| `PatFrag` | 可复用的子模式（带 `ops`/predicate） | **没有** | `ext`、`mul_const_oneuse` 等 |
| `ImmLeaf` | 让常量叶子参与匹配，并绑定到操作数 | `simm12`/`uimm6`/`uimm5`/分支目标 | `simm12`、`uimm6gt32` 等 |
| `ComplexPattern` | 把匹配逻辑交给 C++ 函数，可返回多个操作数 | **没有** | `AddrRegImm`、`BrindRegImm`、`AddrRegRegScale<N>` |
| `SDNode` + `SDTypeProfile` | 自定义目标节点的类型/操作数约束 | `MiniRVbrcc`/`MiniRVcall`/`MiniRVret` 等 | `riscv_brcc`/`riscv_call`/`riscv_ret_glue` 等 |
| `Operand` | 指令操作数类（打印/解析/编码） | `simm12` 同时是 `Operand` 和 `ImmLeaf` | 同 |
| `tglobaladdr`/`texternalsym`/`tframeindex`/`bb` | 特殊叶子的匹配名 | call/tail/frame index/branch 都用 | 同 |
| `TargetConstant` | 已绑定、不能再被 combine 的常量 | 手写 ADDI/LUI 时用 | `selectImm` 里用 |

MiniRV 刻意不用 `ComplexPattern`：它的寻址模式只有一个（base + 12 位立即数），一个 `ImmLeaf` 就够了。RISC-V 的 `AddrRegImm` 要同时处理 frame index、global address、LUI 物化、大常量拆分，所以必须有一个 C++ 回调。**这不是风格差异，是寻址模式复杂度的差异。**

## 主线 2：MiniRV 的 `Select` 逐段读

先说明命名，避免你去找不存在的函数：MiniRV **没有** RISC-V 那样的 `selectImm` 和 `SelectAddr`/`SelectAddrRegImm` 函数。常量物化内联在 `Select` 的 `ISD::Constant` 分支里；地址匹配完全交给 `.td` 里的 `(add GPR:$base, simm12:$off)`，只有 inline asm 的 memory operand 需要手写。我们按 RISC-V 的概念对照着读。

### 第一段：已经是机器节点就退出

```cpp
void MiniRVDAGToDAGISel::Select(SDNode *N) {
  if (N->isMachineOpcode()) {
    N->setNodeId(-1);
    return;
  }
```

`LowerGlobalAddress` 在 operation legalization 阶段就生成了 `PseudoLA` 这个 machine node。等 ISel 走到它时，它已经是机器指令，不需要再选。`setNodeId(-1)` 是告诉 DAG 的拓扑排序“这个节点处理完了”。

### 第二段：ADD + 常量，两条 ADDI

```cpp
  if (N->getOpcode() == ISD::ADD) {
    if (auto *C = dyn_cast<ConstantSDNode>(N->getOperand(1))) {
      int64_t Val = C->getSExtValue();
      if (!isInt<12>(Val) && Val >= -4096 && Val <= 4094) {
        ...
        int64_t First = Val < 0 ? -2048 : 2047;
        ...
        SDValue Partial = SDValue(
            CurDAG->getMachineNode(MiniRV::ADDI, DL, VT, Base,
                                   CurDAG->getTargetConstant(First, DL, MVT::i64)),
            0);
        ReplaceNode(N, CurDAG->getMachineNode(
                           MiniRV::ADDI, DL, VT, Partial,
                           CurDAG->getTargetConstant(Val - First, DL, MVT::i64)));
        return;
      }
    }
  }
```

这是“表表达不了”的典型例子：一条 `add` 的立即数放不进 12 位，但拆成两条 ADDI 就够。范围 `[-4096, 4094]` 不是随手写的：第一条取 `2047`（或 `-2048`），剩余部分必须仍能放进 12 位，所以上界是 `2047 + 2047 = 4094`，下界是 `-2048 + -2048 = -4096`。

注意 `Base` 如果是 `ISD::FrameIndex`，这里先换成 `TargetFrameIndex`，让第一条 ADDI 继续携带 FI，等 PEI 的 `eliminateFrameIndex` 再解析。**手写选指也要尊重后续 pass 的约定**，否则 frame index 提前变成常量，栈帧一大就错。

### 第三段：常量物化（MiniRV 版的 `selectImm`）

```cpp
  if (N->getOpcode() == ISD::Constant) {
    auto Val = cast<ConstantSDNode>(N)->getSExtValue();
    ...
    if (isInt<12>(Val)) {
      SDValue Zero = CurDAG->getRegister(MiniRV::X0, VT);
      ReplaceNode(N, CurDAG->getMachineNode(
                         MiniRV::ADDI, DL, VT, Zero,
                         CurDAG->getTargetConstant(Val, DL, MVT::i64)));
      return;
    }
```

小常量用 `addi rd, x0, imm`。大常量的 `BuildWord` 做 `LUI + ADDI`；`Word >= 0x80000000` 时先按有符号 32 位造，再用 `SLLI 32`/`SRLI 32` 清零高半部，得到零扩展的 32 位模式；超过 32 位则高低两个字分别物化，`SLLI 32` 后 `OR`。

对照 RISC-V：`RISCVDAGToDAGISel::Select` 的 `ISD::Constant` 分支最后调用 `static SDValue selectImm(SelectionDAG *CurDAG, const SDLoc &DL, const MVT VT, int64_t Imm, const RISCVSubtarget &STI)`，它用 `RISCVMatInt::generateInstSeq` 生成最短指令序列（LUI/ADDI/SLLI/ADD 等），并按 `+zbb`/`+zbs` 等 feature 选替代序列。MiniRV 没有 feature，也没有 `RISCVMatInt`，所以手写了三种情况。

### 第四段：frame index 作为值

```cpp
  if (N->getOpcode() == ISD::FrameIndex) {
    ...
    SDValue FI = CurDAG->getTargetFrameIndex(
        cast<FrameIndexSDNode>(N)->getIndex(), VT);
    ReplaceNode(N, CurDAG->getMachineNode(
                       MiniRV::ADDI, DL, VT, FI,
                       CurDAG->getTargetConstant(0, DL, MVT::i64)));
    return;
  }

  SelectCode(N);
}
```

“取栈对象地址”不是 load/store，而是一条 `ADDI <fi>, 0`。`<fi>` 这个操作数在 PEI 之后会被 `eliminateFrameIndex` 换成 `sp/fp + offset`；offset 太大时它还会再插一条地址物化（Ch 14）。

### 第五段：没模式可用的 inline asm

`SelectInlineAsmMemoryOperand` 把一个地址拆成 `Base` + `Disp`，只在 `m`/`o` 约束下工作。它和 load/store 的寻址模式是同一个模型：base 寄存器 + 12 位有符号位移。

## 主线 3：`MiniRVInstrInfo.td` 里的 pattern

### 算术：寄存器形态和立即数形态是两条 pattern

```tablegen
def : Pat<(i64 (add GPR:$rs1, GPR:$rs2)), (ADD GPR:$rs1, GPR:$rs2)>;
def : Pat<(i64 (sub GPR:$rs1, GPR:$rs2)), (SUB GPR:$rs1, GPR:$rs2)>;
...
def : Pat<(i64 (add GPR:$rs1, simm12:$imm)), (ADDI GPR:$rs1, simm12:$imm)>;
def : Pat<(i64 (and GPR:$rs1, simm12:$imm)), (ANDI GPR:$rs1, simm12:$imm)>;
def : Pat<(i64 (or  GPR:$rs1, simm12:$imm)), (ORI  GPR:$rs1, simm12:$imm)>;
def : Pat<(i64 (xor GPR:$rs1, simm12:$imm)), (XORI GPR:$rs1, simm12:$imm)>;

def : Pat<(i64 (shl GPR:$rs1, uimm6:$imm)), (SLLI GPR:$rs1, uimm6:$imm)>;
```

读法：

- 左边的 `(i64 (add ...))` 是**匹配**，右边的 `(ADDI ...)` 是**生成**。`$rs1`/`$imm` 是绑定变量，左边绑、右边用。
- 根类型写 `i64`：MiniRV 只有 i64 合法，显式写死可以避免 TableGen 从操作数推出 `iAny`/`iPTR` 之类的类型变量。
- `simm12` 同时是 `Operand<i64>` 和 `ImmLeaf<i64, [{ return isInt<12>(Imm); }]>`。作为 `Operand` 它负责打印/解析/解码；作为 `ImmLeaf` 它让 matcher 在常量叶子上做范围判断。**一个 record 两种角色**，这是 TableGen 常见的写法。
- `uimm6` 用于 64 位移位（RV64 的 shamt 是 6 位），`uimm5` 用于 `*W` 的 5 位移位。范围写在 `ImmLeaf` 里，写错就会出现“编码时断言”。

### 32 位：目标节点保留宽度

i32 被提升成 i64 后，`add` 会变成 64 位 add，丢掉 32 位回绕语义。MiniRV 的做法是自定义节点：

```tablegen
def MiniRVaddw : SDNode<"MiniRVISD::ADDW", SDT_MiniRVBinOpW>;
...
def : Pat<(MiniRVaddw GPR:$rs1, GPR:$rs2), (ADDW GPR:$rs1, GPR:$rs2)>;
def : Pat<(MiniRVaddw GPR:$rs1, simm12:$imm), (ADDIW GPR:$rs1, simm12:$imm)>;
```

`MiniRVISD::ADDW` 是 operation legalization 里 `LowerOperation` 把 i32 ADD 改写出来的（Ch 12）。它在 DAG dump 里叫 `MiniRVISD::ADDW`，不是 `ISD::ADD`。**目标节点是“把语义信息带过类型提升”的载体**，这也是 `getTargetNodeName` 必须实现的原因：否则日志里只有 opcode 数字。

### 内存：base + simm12，以及 frame index

```tablegen
def : Pat<(i64 (load (add GPR:$base, simm12:$off))),
          (LD GPR:$base, simm12:$off)>;
def : Pat<(i64 (load GPR:$base)), (LD GPR:$base, 0)>;
def : Pat<(i64 (load tframeindex:$fi)), (LD tframeindex:$fi, 0)>;
```

三条 pattern 覆盖三种地址：`base + 常量`、纯 `base`、`frame index`。注意 `load` 外面套了 `(i64 ...)`：MiniRV 的 load 结果类型总是 i64，窄 load 用 `sextloadi8`/`zextloadi16` 等 flavour 区分，模式里再选 `LB/LBU/LH/LHU/LW/LWU`。store 同理，`truncstorei32` → `SW`。

`tframeindex` 的 `0` 是位移操作数的占位；真正的 offset 在 PEI 里由 `eliminateFrameIndex` 填。

### 分支：`BccPat` 一个 multiclass 生成 18 条 pattern

```tablegen
multiclass BccPat<CondCode Cond, MiniRVInst Inst> {
  def : Pat<(MiniRVbrcc GPR:$lhs, GPR:$rhs, Cond, bb:$dst),
            (Inst GPR:$lhs, GPR:$rhs, simm13_lsb0_bb:$dst)>;
  def : Pat<(MiniRVbrcc GPR:$lhs, 0, Cond, bb:$dst),
            (Inst GPR:$lhs, (i64 X0), simm13_lsb0_bb:$dst)>;
  def : Pat<(MiniRVbrcc 0, GPR:$rhs, Cond, bb:$dst),
            (Inst (i64 X0), GPR:$rhs, simm13_lsb0_bb:$dst)>;
}

defm : BccPat<SETEQ,  BEQ>;
defm : BccPat<SETNE,  BNE>;
defm : BccPat<SETLT,  BLT>;
defm : BccPat<SETGE,  BGE>;
defm : BccPat<SETULT, BLTU>;
defm : BccPat<SETUGE, BGEU>;
```

三个要点：

- 条件码 `Cond` 是 pattern 的常量参数，`SETEQ` 只匹配 `seteq` 的 BRCC。
- 零形态写成 `(i64 X0)`，直接引用物理寄存器 `x0`。寄存器合并不保证会把零值折成 `x0`，所以 pattern 显式写死。RISC-V 的 `BccPat` 也这么干，注释意思相同：“The register coalescer doesn't always do it.”
- `bb:$dst` 匹配基本块，`simm13_lsb0_bb` 是分支目标操作数（`OPERAND_PCREL`，低 bit 隐式）。`simm13_lsb0`（带 `ImmLeaf`）用于 `jal` 的立即数形态，`_bb` 版本不带 leaf matcher，因为这里给的是块。

### 调用/返回/间接跳转：记录自己带 pattern

```tablegen
def PseudoRET : MiniRVInst<(outs), (ins), "ret", "", [(MiniRVret)], InstFormatI>,
                PseudoInstExpansion<(JALR X0, X1, 0)> { ... };

def PseudoCALL : MiniRVInst<(outs), (ins bare_symbol:$dst), "jal", "x1, $dst",
                            [(MiniRVcall tglobaladdr:$dst)], InstFormatJ>,
                 PseudoInstExpansion<(JAL X1, simm21_lsb0:$dst)> { ... };

def : Pat<(MiniRVcall texternalsym:$dst), (PseudoCALL texternalsym:$dst)>;

def PseudoTAIL : MiniRVInst<(outs), (ins bare_symbol:$dst), "jal", "x0, $dst",
                            [(MiniRVtail tglobaladdr:$dst)], InstFormatJ>,
                 PseudoInstExpansion<(JAL X0, simm21_lsb0:$dst)> { ... };

def PseudoBRIND : MiniRVInst<(outs), (ins GPR:$rs), "jr", "$rs",
                             [(brind GPR:$rs)], InstFormatI>,
                  PseudoInstExpansion<(JALR X0, GPR:$rs, 0)> { ... };
```

- `[(MiniRVret)]` 直接挂在指令记录上，等价于一条 `Pat`，只是省了单独写。
- `PseudoInstExpansion<...>` 声明“这条伪指令最终展开成什么”。MiniRV 的 `PseudoRET` 在 AsmPrinter 里展开（`MiniRVAsmPrinter::emitInstruction` 调用 `lowerPseudoInstExpansion`），不是在 ISel 里。
- `isCodeGenOnly = 1` 把记录排除在汇编器的匹配表之外：`ret` 和 `Pseudo*` 这些拼写只存在于 CodeGen，汇编器只认真实的 `jal`/`jalr`；`isCall`/`isReturn`/`isTerminator`/`isBarrier` 是给后续 pass 看的语义标志。
- `PseudoCALL` 的 pattern 只匹配 `tglobaladdr`；外部符号由单独一条 `Pat` 走 `texternalsym`。直接调用 callee 在 `LowerCall` 里已经被转成 `TargetGlobalAddress`/`TargetExternalSymbol`，剩下寄存器 callee 走 `MiniRVISD::CALL_REG`。

## 主线 4：为什么 MiniRV 需要 BRCC / CALL / TAIL / RET 节点

这四个节点不是“重复造轮子”，而是把 target 需要的**操作数布局和语义标志**带进 DAG，让 pattern 能一条匹配到位。对照 RISC-V 最清楚：

| 语义 | MiniRV 节点 | RISC-V 节点 | 伪指令 | 展开 |
|---|---|---|---|---|
| 比较+条件分支 | `MiniRVISD::BRCC` | `riscv_brcc` (`RVSDNode<"BR_CC", ...>`) | — | BEQ/BNE/BLT/... |
| 直接调用 | `MiniRVISD::CALL` | `riscv_call` | `PseudoCALL` | `JAL X1, off` |
| 间接调用 | `MiniRVISD::CALL_REG` | `riscv_call`（同节点，callee 是寄存器） | `PseudoCALLReg` | `JALR X1, rs, 0` |
| 尾调用 | `MiniRVISD::TAIL` / `TAIL_REG` | `riscv_tail` | `PseudoTAIL` | `JAL X0, off` |
| 返回 | `MiniRVISD::RET` | `riscv_ret_glue` | `PseudoRET` | `JALR X0, X1, 0` |
| 间接跳转 | `ISD::BRIND` | `ISD::BRIND` | `PseudoBRIND` | `JALR X0, rs, 0` |

### 为什么分支要合并成一个节点

generic DAG 里条件分支长这样：`brcond chain, (setcc a, b, cc), bb`。如果分别选指，`setcc` 会先变成 `SLT`（写一个 0/1 到寄存器），再 `brcond` 变成 `BNE`，一条分支变两条。

MiniRV 在 `LowerBRCOND` 里把 `brcond(setcc a,b,cc)` 改写为 `MiniRVISD::BRCC chain, a, b, cc, bb`，`BccPat` 就能把“比较 + 分支”一条匹配成 `BLT`。这和 RISC-V 的 `lowerBRCOND` 思路一致。

`LowerBranchCC` 还做了两件规范化：

1. **换成 corpus 里有的条件**：corpus 只有 `<` 和 `>=` 的记录，所以 `SETGT`/`SETLE`/`SETUGT`/`SETULE` 通过交换操作数落到 `SETLT`/`SETGE`/`SETULT`/`SETUGE`（分别对应 BLT/BGE/BLTU/BGEU）。
2. **把“和 1 比”改回“和 0 比”**：DAG builder 会把 `x > 0` 规范化成 `x >= 1`、`x <= 0` 规范化成 `x < 1`，这样零形态的 pattern 匹配不到。`LowerBranchCC` 把它们改写成 `0 < x` / `0 >= x`，让 `BccPat` 的 `(i64 X0)` 形态生效。这个改动是 commit `dcd9fdb`，提交信息记录了改之前的代码是 `addi x3, x0, 1; blt x10, x3`。

### 为什么调用要自定义节点

generic 的 `ISD::CALL` 也能被 pattern 匹配，但 target 需要控制三件事：

- **glue 链**：参数 COPY 通过 glue 串在调用节点上，保证它们不被调度到 call 之后。`SDT_MiniRVCall` 声明 `[SDNPHasChain, SDNPOptInGlue, SDNPOutGlue, SDNPVariadic]`，正是为了这个。
- **变长操作数**：调用节点除了 callee 还有参数寄存器、regmask、glue，`SDNPVariadic` 允许 pattern 只匹配前缀（`MiniRVcall tglobaladdr:$dst`）。
- **结果类型**：`NodeTys = {Other, Glue}`，`LowerCall` 要拿 glue 继续接 `CALLSEQ_END` 和返回值的 `CopyFromReg`。

`TAIL` 和 `CALL` 共用 `SDT_MiniRVCall`，但 `TAIL` 不返回 glue：尾调用之后这个块就结束了，callee 直接返回到 caller 的 caller。

### 为什么返回也要自定义节点

`ISD::RET` 在 generic 里会被 `LowerReturn` 处理，但 target 仍然需要一个自己的终结节点来携带“返回哪些寄存器”的可变操作数和 glue 链。MiniRV 的 `LowerReturn` 生成 `MiniRVISD::RET chain, $x10, glue`，pattern 再匹配成 `PseudoRET`。RISC-V 的 `riscv_ret_glue` 是同一角色，连 `PseudoRET` 的展开都一样是 `JALR X0, X1, 0`。

这解释了为什么 `getTargetNodeName` 必须列出这些 opcode：`-debug-only=isel` 的 DAG dump 直接调它。MiniRV 的 `MiniRVTargetLowering::getTargetNodeName` 把 `BRCC`/`CALL`/`CALL_REG`/`TAIL`/`TAIL_REG`/`RET` 和十个 `*W` 节点都映射成字符串。

## 实测：从 DAG 到字节

测试文件只有一个函数，方便逐节点对照：

```console
$ cat add3.ll
define i64 @add3(i64 %a, i64 %b, i64 %c) {
entry:
  %s = add i64 %a, %b
  %m = mul i64 %s, %c
  ret i64 %m
}
```

### 第一步：初始 DAG

```console
$ $B/llc -mtriple=minirv64 -O2 -debug-only=isel add3.ll -o - 2>&1 | sed -n '1,16p'
	FastISel is disabled



=== add3

Initial selection DAG: %bb.0 'add3:entry'
SelectionDAG has 12 nodes:
    t0: ch,glue = EntryToken
  t2: i64,ch = CopyFromReg t0, Register:i64 %0
  t4: i64,ch = CopyFromReg t2:1, Register:i64 %1
  t6: i64,ch = CopyFromReg t4:1, Register:i64 %2
      t7: i64 = add t2, t4
    t8: i64 = mul t7, t6
  t10: ch,glue = CopyToReg t6:1, Register:i64 $x10, t8
  t11: ch = MiniRVISD::RET t10, Register:i64 $x10, t10:1
```

读法：

- `t2/t4/t6` 是三个参数，`CopyFromReg` 从物理 `$x10/$x11/$x12` 读进来（`LowerFormalArguments` 的结果）。
- `t7`/`t8` 还是 `ISD::add`/`ISD::mul`，没有指令。
- `t11` 已经是 `MiniRVISD::RET`，因为 `LowerReturn` 在 legalization 阶段就把它建好了。**“初始 DAG”里也能有目标节点**，别以为选指前全是 ISD。
- `FastISel is disabled` 是 MiniRV 没有实现 FastISel；`-O0` 也走 SelectionDAG。

### 第二步：匹配过程

```console
$ $B/llc -mtriple=minirv64 -O2 -debug-only=isel add3.ll -o - 2>&1 | sed -n '80,94p'
ISEL: Starting selection on root node: t8: i64 = mul t7, t6
ISEL: Starting pattern match
  Initial Opcode index to 1434
  Morphed node: t8: i64 = MUL t7, t6
ISEL: Match complete!

ISEL: Starting selection on root node: t6: i64,ch = CopyFromReg t4:1, Register:i64 %2

ISEL: Starting selection on root node: t7: i64 = add t2, t4
ISEL: Starting pattern match
  Initial Opcode index to 1065
  Match failed at index 1070
  Continuing at 1082
  Morphed node: t7: i64 = ADD t2, t4
ISEL: Match complete!
```

`Initial Opcode index to 1065` 是 matcher 表的入口（由 `add` 的 opcode 决定）。`Match failed at index 1070` 说明入口后的第一条候选没匹配上，`Continuing at 1082` 换下一条，最后 `Morphed node` 成 `ADD`。**表是顺序试的，失败就跳到下一条**，这解释了为什么 pattern 的书写顺序和具体程度会影响生成代码。

### 第三步：选指结束的 MIR

```console
$ $B/llc -mtriple=minirv64 -O2 -stop-after=finalize-isel -simplify-mir add3.ll -o - 2>&1 | sed -n '/^body:/,$p'
body:             |
  bb.0.entry:
    liveins: $x10, $x11, $x12
  
    %2:gpr = COPY $x12
    %1:gpr = COPY $x11
    %0:gpr = COPY $x10
    %3:gpr = ADD %0, %1
    %4:gpr = MUL %3, %2
    $x10 = COPY %4
    PseudoRET implicit $x10
...
```

这是“DAG 节点 → 机器 opcode”的证据：`add` 变成 `ADD`，`mul` 变成 `MUL`，`MiniRVISD::RET` 变成 `PseudoRET`。虚拟寄存器 `%0..%4` 还在，物理寄存器分配和 prologue 都还没发生。注意 `selected: false` 这个字段会误导人（Ch 9 也提过），判断选指看 `body` 里是不是机器 opcode。

### 第四步：最终汇编与编码

```console
$ $B/llc -mtriple=minirv64 -O2 add3.ll -o - | sed -n '/^add3:/,/Lfunc_end/p'
add3:                                   # @add3
	.cfi_startproc
# %bb.0:                                # %entry
	add	x3, x10, x11
	mul	x10, x3, x12
	jalr	x0, 0(x1)
.Lfunc_end0:
	.size	add3, .Lfunc_end0-add3
	.cfi_endproc
```

`PseudoRET` 在这里才展开成 `jalr x0, 0(x1)`（`PseudoInstExpansion` + `MiniRVAsmPrinter`）。寄存器分配把 `%3` 放到 `x3`，`%4` 直接合并进 `x10`。

```console
$ printf 'add x3, x10, x11\nmul x10, x3, x12\n' | $B/llvm-mc -triple=minirv64 -show-encoding
	add	x3, x10, x11                    # encoding: [0xb3,0x01,0xb5,0x00]
	mul	x10, x3, x12                    # encoding: [0x33,0x85,0xc1,0x02]
```

手工拆 `add x3, x10, x11`：`0x00b501b3`，低 7 位 `0x33` 是 OP，`rd=3`，`funct3=0`，`rs1=10`，`rs2=11`，`funct7=0`。这就是三步演练的终点：**DAG 节点 `t7: add` → 机器 opcode `ADD` → MCInst → 4 字节编码**。

### 第五步：分支与调用的目标节点

```console
$ $B/llc -mtriple=minirv64 -O2 -debug-only=isel br.ll -o - 2>&1 \
    | grep -E "t20: ch = MiniRVISD::BRCC|Morphed node: t20|ISEL: Starting selection on root node: t20" \
    | sed 's/0x[0-9a-f]*/0xADDR/g' | tail -4
    t20: ch = MiniRVISD::BRCC t4:1, t2, t4, setge:ch, BasicBlock:ch<f 0xADDR>
    t20: ch = MiniRVISD::BRCC t4:1, t2, t4, setge:ch, BasicBlock:ch<f 0xADDR>
ISEL: Starting selection on root node: t20: ch = MiniRVISD::BRCC t4:1, t2, t4, setge:ch, BasicBlock:ch<f 0xADDR>
  Morphed node: t20: ch = BGE t2, t4, BasicBlock:ch<f 0xADDR>, t4:1
```

（`sed` 把基本块指针地址统一改成 `0xADDR`；DAG 快照里同一节点会出现两次，所以前两行重复。）

`brcond(setcc)` 先变成 `MiniRVISD::BRCC`，再一条匹配成 `BGE`。最终汇编是：

```console
$ $B/llc -mtriple=minirv64 -O2 br.ll -o - | sed -n '/^max:/,/Lfunc_end/p'
max:                                    # @max
	.cfi_startproc
# %bb.0:                                # %entry
	bge	x10, x11, .LBB0_2
# %bb.1:                                # %t
	addi	x10, x11, 0
.LBB0_2:                                # %f
	jalr	x0, 0(x1)
```

调用节点同理：`MiniRVISD::CALL` → `PseudoCALL` → `jal x1, callee`；尾调用 `MiniRVISD::TAIL` → `PseudoTAIL` → `jal x0, callee`：

```console
$ $B/llc -mtriple=minirv64 -O2 call.ll -o - | sed -n '/^tailcaller:/,/Lfunc_end1/p'
tailcaller:                             # @tailcaller
	.cfi_startproc
# %bb.0:
	jal	x0, callee
```

## 反直觉与踩雷

1. **错误直觉**：`Pat` 是按书写顺序“最后写的优先”。→ **正确认识**：matcher 表按 opcode 分组，同组内按 pattern 的具体程度和 TableGen 的排序生成；`-debug-only=isel` 的 `Initial Opcode index`/`Continuing at` 是唯一可靠的观察方式。你在 `.td` 里调换两行的顺序，生成的匹配路径可能不变，也可能变；不要靠“看起来更具体”来推理，跑日志。

2. **错误直觉**：`-debug-only=isel` 里 “Legalized selection DAG” 还是 `ISD::add`，说明选指没生效。→ **正确认识**：那个快照在选指**之前**；选指后的快照叫 “Selected selection DAG”，节点会变成大写机器 opcode。要看选指结果，找 `Selected selection DAG` 或 `Morphed node`。

3. **错误直觉**：`Select` 里 `return` 之后框架会自动把节点标成已处理。→ **正确认识**：不会。`Select` 的契约是“你负责替换”。MiniRV 的每个分支都以 `ReplaceNode(...)` 结束；漏掉就会在 `DoInstructionSelection` 之后留下未选的节点，报 `Cannot select: tN: i64 = add ...`。

4. **错误直觉**：`-stop-after=finalize-isel` 的 MIR 里已经是最终指令，`PseudoRET` 只是打印名字不同。→ **正确认识**：`PseudoRET`/`PseudoCALL`/`PseudoLA` 都是没有编码的伪指令，真正展开发生在 AsmPrinter（`PseudoInstExpansion`）或 `emitSymbolAddress`。拿 MIR 去对照字节会对不上。

5. **错误直觉**：`MiniRVbrcc GPR:$lhs, 0, ...` 会匹配任何“右边是零”的分支。→ **正确认识**：DAG builder 会把 `x > 0` 规范化成 `x >= 1`，常量是 1 不是 0，零形态匹配不到。MiniRV 必须在 `LowerBranchCC` 里改写（commit `dcd9fdb`），否则每条零比较都先 `addi x3, x0, 1`。**pattern 的“零”是 literal 0，不是“值为零的表达式”。**

6. **错误直觉**：有 `ImmLeaf` 就能匹配任意常量。→ **正确认识**：`ImmLeaf` 只作用于 `ConstantSDNode`，而且是在合法化后的类型上。i32 常量在 MiniRV 里已经被提升/重写成 i64，pattern 里写 `i32` 永远匹配不到；写 `simm12` 时也要确认操作数确实以常量节点存在，而不是已经被物化成寄存器。

7. **错误直觉**：MiniRV 应该像 RISC-V 一样用 `ComplexPattern` 做地址匹配，否则“不专业”。→ **正确认识**：MiniRV 的寻址模式只有 base+simm12，`(add GPR:$base, simm12:$off)` 已经覆盖；引入 `ComplexPattern` 只会多一个 C++ 回调和一层间接。**抽象要跟复杂度匹配**。反过来说，当你要支持“base + index*scale + disp”或“global + offset 自动折进 LUI”时，就必须上 `ComplexPattern`，否则每条 pattern 都要重复同样的判断。

## 进阶：再往深一层

- **matcher 表长什么样**：`MiniRVGenDAGISel.inc` 里是 `MatcherTable` 字节数组和 `SelectCode` 的 switch。`-debug-only=isel` 打印的索引就是这张表的偏移。想验证“某条 pattern 到底在不在表里”，直接在这个文件里搜指令名或 opcode 常量，比读 `.td` 更接近事实。
- **RISC-V 的 C++ 选指分层**：`RISCVDAGToDAGISel::Select` 先 `switch (Opcode)` 处理 `Constant`/`ConstantFP`/`FrameIndex`/`GlobalAddress` 等，再 `SelectCode`；地址相关的工作交给 `SelectAddrRegImm`（`ComplexPattern` 回调），它内部调用 `SelectAddrFrameIndex`、`selectConstantAddr`、`RISCVMatInt::generateInstSeq`。这是“模式负责形状、C++ 负责代价”的分工。
- **GlobalISel 的同一件事**：GlobalISel 把选指拆成 IRTranslator → Legalizer → RegBankSelect → InstructionSelect，`Pat` 仍然复用，但多了 `GIComplexOperandMatcher` 和寄存器银行。MiniRV 只实现了 SelectionDAG 路径；对照见 `../globalisel_instruction_select/README.md`。
- **选指与调度**：选指出来的 DAG 还带着依赖边，`ScheduleDAG` 才决定顺序。MiniRV 的 `hasNoSchedulingInfo = 1` 让调度器退回默认 latency；RISC-V 有完整的 `SchedRW` 模型。选指阶段的 morph 会改变 DAG 形状，从而改变调度结果，这也是 `-debug-only=isel` 和 `-debug-only=machine-scheduler` 要一起看的原因，详见 `../llvm_isel_sched_riscv/README.md`。

## 本章重点整理

- 选指契约：`SelectionDAGISel` 遍历 DAG，调用 target 的 `Select`；target 要么 `ReplaceNode`，要么 `SelectCode`；漏选就是 `Cannot select`。
- `Select` 是“先手”，只处理表表达不了的形状；MiniRV 的先手是 ADD 两条 ADDI、常量物化、frame index 地址。
- `Pat` 左边匹配、右边生成；`ImmLeaf` 让常量参与匹配并绑定；`ComplexPattern` 把匹配交给 C++ 并返回多个操作数；MiniRV 只用前两者。
- MiniRV 的地址模式是 `(add GPR, simm12)`；没有 `SelectAddr` 函数，也没有 `ComplexPattern`。
- `MiniRVISD::BRCC` 合并比较和分支；`CALL`/`TAIL` 携带 chain/glue/变长参数；`RET` 携带返回寄存器和 glue。四者都有对应的 `Pseudo*` 和 `PseudoInstExpansion`。
- `BccPat` 用 multiclass 生成 18 条 pattern；零形态显式写 `(i64 X0)`，因为寄存器合并不保证。
- `-debug-only=isel` 看 DAG 快照和匹配路径；`-stop-after=finalize-isel` 看机器 opcode；`-show-encoding` 看字节。三步演练缺一不可。
- RISC-V 的 `selectImm`/`SelectAddrRegImm`/`riscv_brcc`/`riscv_call`/`riscv_ret_glue` 与 MiniRV 的对应物是同一套设计，只是复杂度不同。
