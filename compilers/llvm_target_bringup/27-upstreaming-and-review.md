# Ch 27 — 上游化与评审

> **目标**：把一个“在我机器上能跑”的 target 拆成上游能评审的补丁系列；知道 `DeveloperPolicy` / `CodeReview` / `Maintainers` 会拿什么卡你；并能用 RISC-V 的真实提交历史解释“为什么不能急”。

> **环境**：LLVM 24.0.0git，`/home/ubuntu/llvm/trees/dsl-tablegen`，构建 `/home/ubuntu/llvm/builds/dsl-tablegen`。

## 为什么需要这个？

Ch 03–26 的验收标准是“我的树里能跑”：`llc` 出码、`llvm-mc` 出字节、e2e 跑通。上游的验收标准不是这个。上游只问四个问题：

1. **回归面**：这段代码会不会改变其他 target 的行为？`ninja check-llvm` 必须全绿。
2. **可验证性**：每个新行为有没有 `llvm/test` 下的 lit 测试？`dev/e2e` 脚本不算。
3. **可审性**：维护者能不能在半小时内理解这个 diff？生成代码从哪来？为什么改共享文件？
4. **可持续性**：`llvm/Maintainers.md` 里谁愿意长期接这个 target？

MiniRV 的 42 个 commit 是一次 bring-up 的**工作日志**，不是 42 个可提交的补丁。本章做的事，就是把工作日志翻译成补丁系列；下一章再回头算这次 bring-up 的成本。

## 先建立直觉

上游接收一个 target，不是“收一个大 patch”，而是“按可回滚单元收一串小 patch”：

```
你的树：42 commits / 9 小时 09 分 / 7519 行 target 代码
   │
   │  拆：一个 commit = 一个可回滚的行为变化 + 一个 lit 测试
   ▼
补丁系列：P0 RFC → P1 registry → P2 MC → P3 records
          → P4 machine → P5 ISel/ABI → P6 runtime
          → P7 link/unwind → P8 clang → P9 lld/runtime
   │
   │  门禁：clang-format / git diff --check / ninja check-llvm
   ▼
维护者 review（若动到 RISC-V 相关代码：asb, topperc, preames, lenary）
   │
   │  逐块 land；坏了只 revert 一块，不回滚整个 target
   ▼
main
```

关键直觉：**补丁的边界不是“我写了哪些文件”，而是“reviewer 能否独立验证这一个行为”**。MiniRV 的 `33d9ec8` 同时改了 CMake、Triple、MC、语料和测试——这在上游是四个 patch。

## 主线：从“我的树能跑”到“上游能收”

### 27.1 离开你的树，规则换了

| 维度 | 你的树 | 上游 |
|---|---|---|
| 构建 | 自己的 `cmake` + `ninja` | 必须进 `LLVM_TARGETS_TO_BUILD`，且不破坏其他 target |
| 测试 | `dev/e2e/run.sh`、手跑 `llc` | `llvm/test/**` 下的 lit + FileCheck，`ninja check-llvm` |
| 格式 | 能编译就行 | `clang-format`、`git diff --check` 是 CI 门禁 |
| 提交 | 一个 commit 一个里程碑 | 一个 commit 一个逻辑变更，可单独 revert |
| 评审 | 自己 / 同事 | GitHub PR + 维护者；大改要 RFC |
| 文档 | 无 | Release Notes、target 文档、`Maintainers.md` |
| 出处 | 无所谓 | 生成代码、AI 辅助都要说明 |

**当前树里的政策文件是 `.md`，不是 `.rst`。** 你可能见过 `DeveloperPolicy.rst` / `CodeReview.rst` / `HowToSubmitABug.rst` 这些旧路径，它们已经迁移：

```console

ls: cannot access 'llvm/docs/CodeReview.rst': No such file or directory
ls: cannot access 'llvm/docs/HowToSubmitABug.rst': No such file or directory
$ ls llvm/docs | grep -E 'DeveloperPolicy|CodeReview|HowToSubmitABug|AIToolPolicy'
AIToolPolicy.md
CodeReview.md
DeveloperPolicy.md
HowToSubmitABug.md
```

读这四份就够开始：

- **`llvm/docs/DeveloperPolicy.md`**：`Test Cases` 一节写得很直白——“Developers are required to create test cases for any bugs fixed and any new features added.” 同节还明确要求测试放 `llvm/test`、优先 FileCheck、用 `llc` 测后端。`Maintainers` 一节定义了维护者的职责：保证提交得到高质量评审、帮忙确认 issue、在分歧中促成共识。
- **`llvm/docs/CodeReview.md`**：评审在 GitHub PR 上进行；一个 reviewer 批准即可，但 PR 指定了 required reviewers 就必须全过。影响用户或下游的大改要先发 RFC。
- **`llvm/docs/HowToSubmitABug.md`**：它讲的是报 bug，但它定义的“最小可复现用例”标准，和回归测试是同一种 reduction 思路（`llvm-reduce`、预处理文件、run script）。你写 crash 报告的能力，等于你写回归测试的能力。
- **`llvm/docs/AIToolPolicy.md`**：LLM 生成的代码由提交者负全责，提交者必须先自己读懂；用 `Assisted-by: <tool>` trailer 标注。MiniRV 的 42 个 commit 全部带这个 trailer：

```console
$ git log --format='%b' -- llvm/lib/Target/MiniRV | grep -c 'Assisted-by: Codex'
42
```

合规不代表可提交：政策同时说“reviewer 的时间是稀缺资源”，把未消化的生成代码丢给维护者是在**提取**他们的劳动。这正是 MiniRV 不能直接上游的根本原因之一。

### 27.4 MiniRV 为什么不能 as-is 上游

四个硬阻塞，每个都有可复查的证据：

**1. auto-td 生成的记录。** 5000 多行 target 代码里，相当一部分是生成物。Reviewer 不会逐行审 generated records——他们要审生成器、语料和可复现性。需要：`AutoTD.cmake` 单独一个系列、语料 YAML 可读、opcode 数据库许可证明确（`auto-td/opcodes/LICENSE`）、一条命令能重新生成、生成物是否入库有明确说法。MiniRV 的 `config.yaml` 甚至自称 “a demo MC-only target”——demo 不是上游 target 的理由。

**2. 没有 clang 支持。**

```console
$ grep -ril 'minirv' clang/ | wc -l
0
```

没有 `clang/lib/Basic/Targets/MiniRV.{cpp,h}`，没有 driver `ToolChain`，没有 `clang/test/Driver/minirv*.c`。上游一个 target 的“可用”标准包含 `clang --target=...` 能编译、能选对 ABI、能报对诊断。Ch 26 的接入点在这里变成硬性验收。

**3. 没有完整 ABI。** TLS、stackmap/patchpoint、可伸缩向量参数是“明确拒绝”而不是“实现”（`188665d`、`ac86a8a`、`48b9276`）；i128 只覆盖 helper 调用；soft-float 只到 libcall；没有 psABI 文档、没有 libc/compiler-rt 端口、没有动态链接。拒绝是好的工程习惯，但它不是上游 target 的完成态。

**4. 实验树。** 分支叫 `feat/riscv-trim`，auto-td 与 RVTrim 同树；triple 名 `minirv64` 是 demo 名；对象格式复用 `EM_RISCV`，`llvm-readobj` 显示 `Machine: EM_RISCV`，lld 会按 RISC-V 规则处理。上游需要：真实 ISA、公开规范、一位愿意长期维护的 owner、以及不与其他 target 冲突的 triple / object format 说辞。

| 缺口 | 需要做什么 | 验收 |
|---|---|---|
| 生成记录 | 生成器 RFC + 语料 + 许可证 + 复现命令 | `check-autotd` 在干净树上通过 |
| clang | `TargetInfo` + `ToolChain` + builtins | `clang/test/Driver` + `clang -target minirv64 -c` |
| ABI | psABI 文档、varargs/i128/soft-float 全测 | ABI 测试矩阵 |
| 链接/运行时 | lld 规则、crt、libc/compiler-rt | 一个真实 hello world |
| 维护 | `Maintainers.md` 条目 | 有人签字 |
| 文档 | `ReleaseNotes.md` 条目 | 发布说明可见 |

- **MC 层在 2017 年才补齐。** `RISCVAsmParser` 是 2017-08-08，`RISCVInstPrinter` 是 2017-08-15。也就是说，从 stub 到“能汇编、能打印”用了九个月。
- **代码生成是 2018–2019 年的事。** 2019-01-12 才出现 `[RISCV] Introduce codegen patterns for RV64M-only instructions`。

### 27.6 Reviewer 会问什么

| Reviewer 的疑问 | 你要给的证据 | MiniRV 现状 |

### 27.7 补丁系列长什么样

把 42 个 commit 折叠成 10 个可独立评审的单元：

```
P0  RFC / design          目标、ISA 子集、ABI、测试计划、维护者
     │
P1  registry              Triple、DataLayout、TargetInfo、CMake、TripleTest
     │
P2  MC core               AsmInfo、InstrInfo、RegInfo、InstPrinter、Emitter
     │
P3  MC parse/encode       AsmParser、Disassembler、fixup、relocation、MC 测试
     │
P4  records               auto-td 语料（或在 P0 已单独 land 的生成器）
     │
P5  machine               TargetMachine、Subtarget、InstrInfo、FrameLowering
     │
P6  isel/abi              CallingConv、LowerFormalArguments、LowerReturn、Call
     │
P7  runtime surface       varargs、i128、soft-float、atomics、diagnostics
     │
P8  link/unwind/debug     ELF writer、relocations、CFI、debug info
     │
P9  frontend/integration  clang TargetInfo + driver、lld、release notes
```

每个 P 的验收都是“`ninja check-llvm` 绿 + 本 P 新增 lit 全过”。P2 与 P3 可以并行评审，P5 依赖 P4，P6 依赖 P5——这就是 stacked PR 的依赖图。

## 反直觉与踩雷

1. **错误直觉**：“我的 53 个测试全绿，所以可以上游了。”
   **正确认识**：53 个测试只证明 MiniRV 自己没坏；上游要证明**你没弄坏别人**（`ninja check-llvm`），还要证明**每个提交都有测试**（38/42 不够），以及**clang/lld 能用**（0 个测试）。

2. **错误直觉**：“先把 target 提上去，auto-td 生成器以后再说。”
   **正确认识**：生成器才是争议中心。reviewer 无法逐行审 5000 行生成代码，只能审生成器、语料、许可证和复现命令。把生成器留到后面，等于让 reviewer 先接受一个黑盒——这在 LLVM 是不可能的。正确顺序是 P0 RFC 里就把 auto-td 的定位讲清楚。

3. **错误直觉**：“格式问题是小事，功能对了就行。”
   **正确认识**：109 处 clang-format + 1 处 EOF 空行是**可自动检测的返工**。它们不会让代码错，但会让 reviewer 认为你没跑过基本工具链，从而对设计部分也更苛刻。上游评审是人对人的，信号成本是真实的。

4. **错误直觉**：“RISC-V 一开始就是个完整后端，我们照它的文件列表抄就行。”
   **正确认识**：2016-11-01 的 RISC-V 只是一个 stub，`llc -march=riscv32` 直接失败；MC 层 2017 年才补齐，codegen patterns 2019 年才出现。照抄 2026 年的文件列表，等于跳过十年的评审历史。

5. **错误直觉**：“复用 `EM_RISCV` 没关系，反正 objdump 能看。”
   **正确认识**：`llvm-readobj` 显示 `Machine: EM_RISCV` 意味着 linker 会按 RISC-V 的 relocation/ABI 规则处理你的对象。上游必须明确回答“这是 RISC-V 的一个变体，还是独立 target”；含糊会把问题推给 lld 维护者。

## 进阶：再往深一层

- **用 `git range-diff` 维护补丁系列。** 你改完第 3 版补丁后，`git range-diff v2..v3` 能告诉 reviewer “只改了 P4 的测试”，比重新贴 diff 有效得多。
- **用 `update_llc_test_checks.py` 生成 CHECK。** 手写 `CHECK` 容易漏寄存器名；脚本生成的基线更适合大 target，但要在 PR 里说明“这是 generated checks”。
- **诊断也要 `-verify`。** `clang` 侧用 `-verify`，`llc` 侧用 `not llc ... 2>&1 | FileCheck`。MiniRV 的 12 个 `*-error.ll` 已经是这个模式，但还没用 `-verify` 的结构化断言。
- **把 `check-autotd` 当成生成器的 lit。** 生成器的正确性不该靠人眼；`check-autotd` 校验语料覆盖率和 record 引用，这就是生成器世界的 FileCheck。

## 本章重点整理

- 上游接收的是**补丁系列**，不是 bring-up 工作日志；一个补丁 = 一个可回滚行为 + 一个 lit 测试。
- 规则文件在当前树是 `DeveloperPolicy.md` / `CodeReview.md` / `HowToSubmitABug.md` / `AIToolPolicy.md`；`CODE_OWNERS.TXT` 已于 2024-10-04 迁到 `Maintainers.md`。
- MiniRV 的四个硬阻塞：auto-td 生成物、无 clang、ABI 不完整、实验树 + `EM_RISCV` 复用。
- RISC-V 的上游化是 **stub（2016）→ MC（2017）→ codegen（2018–2019）→ 十年 8876 commits** 的增量过程。
- 本地 53/53 只是起点；`git diff --check`、`clang-format`、`ninja check-llvm`、clang/lld 测试才是上游门禁。
