# Ch 28 — 复盘：42 个 commit 的 bring-up 时间线

> **目标**：用 42 个真实 commit 的数据算出 bring-up 的成本分布，识别返工点，并给出下一个 target 的排序策略。

> **环境**：LLVM 24.0.0git，`/home/ubuntu/llvm/trees/dsl-tablegen`，构建 `/home/ubuntu/llvm/builds/dsl-tablegen`。

## 为什么需要这个？

Bring-up 的计划通常按“层”排：Triple → MC → ISel → ABI → 链接。但**实际成本按“返工”分布**。MiniRV 的 42 个 commit 里，有三个大栈帧 commit、两次调用序列修正、一次分支范围补课——这些不是计划内的层，而是“上一层设计没考虑下一层约束”的利息。

这一章只做三件事：把 42 个 commit 按阶段算账、把六条返工链拆开看、把结论变成下一个 target 的排序规则。数据全部来自 `git log` / `git show`，命令可复现。

- **M3 只有 637 行 target 代码，却有 1634 行全仓新增**：ABI 阶段 60% 以上的改动是测试（varargs、i128、soft-float、atomics、错误诊断）。这是好事：ABI 的验收靠测试，不靠代码量。

- **M4 的 1249 行里 1078 行是 `e186e2a` 的 `dev/` harness**：17 个 e2e 程序、5 个 bench 程序、两个脚本。它不是 target 代码，但它是后面所有返工的度量工具，值得单独一个里程碑。

### 28.4 六条返工链

返工不是“写错了重写”，而是“后一层发现前一层不成立的假设”。下面每条都给出真实提交和它解决的问题。

#### 链 1：大栈帧，三次才收敛（`d93cc60` → `90e179c` → `6e7e7ab`）

**`d93cc60`（23:11，190 行）**：2047 字节以上的 frame 直接 fatal error。三处修改：

- `MiniRVFrameLowering::adjustReg` 用 `lui+addi` 物化调整量；当 SP 同时是源和目的时，常量必须先放 `x6`，否则 `lui` 会覆盖还没加的值。
- 打开 `LocalStackSlotAllocation`（`requiresVirtualBaseRegisters`），让离 SP 超过 2047 的对象通过基址寄存器寻址。
- `eliminateFrameIndex` 处理寄存器分配后的残余：load/store 退回保留的 scratch `x5`；同时把 `x5`、`x6` 标成 reserved。

**`90e179c`（03:21，50 行）**：`lui+addi+add` 三条指令太浪费。当调整量落在 `(-4096, 2*(2048-Align)]` 时，直接发两条 `addi`；两步都是栈对齐的倍数，中间 SP 仍然对齐。2416 字节的 frame 变成 `-2048` 再 `-368`。实测收益：bigframe/bigframe2 36→32，vla 114→102。

**`6e7e7ab`（03:32，87 行）**：真正的问题是 callee-saved spill 的位置。frame 大于 2047 时，spill slot 超出 12 位位移，每次 spill/reload 都要两条 `addi` 重算地址。照 RISC-V 的做法：先降 `2048-Align`，在中间 SP 上 spill/restore，再降剩余部分；epilogue 反序，unwind 状态每步更新。收益：vla 100→88，bigframe 30→26，spill 序列变成单条 store/load。

#### 链 3：裸 frame index 读越界（`7717339`）

`7717339`（02:45，28 行）修的是 `LocalStackSlotAllocation` 和 `eliminateFrameIndex` 的共同假设：frame index 后面一定跟一个位移。`llvm.localescape` 只写 frame index 本身，两条路径都会读越过 operand list。修法：把“没有后续 immediate 的 FI”当作非地址使用；给 `LOCAL_ESCAPE` 补 escaped offset；`llvm.localrecover` 没有选择，直接诊断。

这类 bug 的可怕之处是它不在你的 target 测试里，而在**通用 pass 遍历所有 FI 指令**时出现。`llvm/test/CodeGen/MiniRV/localescape-error.ll` 是事后补的。

#### 链 4：分支范围，静默错误比崩溃更贵（`f597d37`）

`f597d37`（02:56，139 行）之前，超出 ±4 KiB 的条件分支 / ±1 MiB 的 `jal` 会被**编码成回绕的位移**，跳到一个错误地址但不报错。修法是一整套接口：

- `getInstSizeInBytes`（含 inline asm、bundle、`PseudoLA`=8 字节、callseq=0）；
- `getBranchDestBlock`、`isBranchOffsetInRange`（条件 `isInt<13>`、`JAL/PseudoBR` `isInt<21>`）；
- `reverseBranchCondition`（六种分支的镜像）；
- `insertIndirectBranch`（`PseudoLA x5` + `PseudoBRIND`，x5 保留所以不需要 restore block）。

```console
$ sed -n '1,8p' llvm/test/CodeGen/MiniRV/branch-relaxation.ll
; RUN: llc -mtriple=minirv64 < %s -o - | FileCheck %s

; The conditional branches reach +-4 KiB and jal reaches +-1 MiB.  A target
; beyond those limits used to be encoded with a wrapped displacement, which
; silently jumped somewhere else.  BranchRelaxation now rewrites the branch.

; A far conditional target is reached by inverting the condition so that the
; fallthrough block gets a short branch, then jumping over it.
```

测试里用 `.space 1100000` 制造 far target。**这是本章记录的返工里唯一一个“错了会生成能跑但结果错”的 bug**，优先级应该高于任何代码尺寸优化。

#### 链 5：x0 规范化，两条指令的收益分两次拿（`dcd9fdb` → `6a2366d`）

`dcd9fdb`（03:14，54 行）：DAG builder 把 `x > 0` 规范成 `x >= 1`、`x <= 0` 规范成 `x < 1`，于是零比较匹配不上 `BccPat`，每次都要先 `addi x3, x0, 1`。修法是在 `LowerBranchCC` 里把这些形态改写回“0 在左边”，并补 `(MiniRVbrcc 0, GPR, ...)` 的镜像 pattern。收益：add/mul/axpy 13→12，reduction 11→10，memcpy 10→9。

+  // against one ("x > 0" becomes "x >= 1", "x <= 0" becomes "x < 1").  Rewrite
+  // those back to a zero comparison so that the x0 forms can match; otherwise
+  // every such branch first materialises the constant one.
+  if (auto *C = dyn_cast<ConstantSDNode>(RHS)) {

`6a2366d`（03:26，3 行）补另一半：select lowering 用“0 减去 setcc 结果”造 mask，`sub` 的 pattern 只认寄存器，于是先 `addi x7, x0, 0`；改成匹配字面零、直接用 x0。这两条本可以合成一个 commit——上游 review 大概率会这么要求。

#### 链 6：debug/unwind，最后一层最杂（`8bffd72`）

`8bffd72`（02:38，161 行 target，17 个文件，380 行全仓）让 `.eh_frame` 真正可用：CFA 跟随 SP 调整、有 frame pointer 时切到 X8、callee-saved 按 CFA 相对槽位列出、epilogue 反序。为此 MC 层修了三处：初始 frame state 声明 entry SP 为 CFA；FDE 的 PC 相对字段用 `R_RISCV_32_PCREL` 且加 specifier 以免被当成符号差；数据里的符号差变成 ADD/SUB relocation 对。顺手拒绝 `llvm.readcyclecounter`（没有 cycle CSR，通用展开会静默返回 0），并接受 GNU 的 `.half/.word/.dword`。

这条链说明：**unwind/debug 不是“加个 flag”，它会反向要求 MC 的 relocation 语义正确**。放在最后做是对的，但要在 M2 就把 CFI 测试挂上，否则最后会一次爆出很多问题。

### 28.5 教训：下一个 target 怎么排

| 决策 | 证据 | 规则 |
|---|---|---|
| 先做 MC-only | `33d9ec8` 18:23 就有 2 个 MC 测试；RISC-V 2016 也是 stub 起步 | 编码能用字节验证，是唯一当天可闭环的层 |
| 早做端到端 | `751291d` 20:50 已手工 link+qemu；harness 到 03:08 才自动化 | 先手动跑通一次，再补脚本；不要等 harness |
| 推迟稀疏特性 | TLS、RVV 参数、stackmap、cycle counter、localrecover 全部用诊断拒绝 | “not supported + diagnostic” 是合法完成态 |
| 先正确后优化 | 分支范围（`f597d37`）在优化（`dcd9fdb`）之前 | 静默错误优先级最高 |
| 预留返工预算 | 大栈帧 3 次、调用序列 2 次 | frame/ABI/branch range 各留 20% 时间 |

推荐排序（按“依赖 + 返工成本”而不是按教材章节）：

```
1. Triple + DataLayout + registry
2. MC: encode/decode/print/parse + MC tests        ← 第一个可验收点
3. TableGen records + ISel 骨架（直线代码）
4. frame + call + ABI（args/returns/varargs）      ← 返工高发区
5. object/link/run（e2e）                          ← 第一次真实验收
6. diagnostics（拒绝未实现）
7. unwind/debug/profile
8. 代码尺寸/性能优化
```

“先做 MC”不是为了好看，而是因为它把“指令编码是否正确”变成可在毫秒级验证的事实。M1 之后所有的错误都变成“语义错误”，定位成本高一个数量级。

## 反直觉与踩雷

1. **错误直觉**：“commit 数就是工作量，42 个 commit 说明 42 份工作。”
   **正确认识**：5 个 commit 占 65% 的 target 新增行；18 个加固 commit 平均只有 81 行/commit。commit 数衡量的是**决策次数**，不是打字量。排期时应该按“层 + 返工预算”估，不按 commit 数估。

2. **错误直觉**：“先写完整 ABI，再写 MC 和 ISel，省得返工。”
   **正确认识**：反了。ABI 依赖 frame layout、call sequence、spill 位置，这些都是 MC/ISel 的下游。MiniRV 的顺序是 MC → 直线代码 → 调用/栈 → ABI，所以每个阶段都有可验证的产物。先写 ABI 会让所有错误延迟到 e2e 才出现。

3. **错误直觉**：“大栈帧是边角 case，最后补一下就行。”
   **正确认识**：`d93cc60 → 90e179c → 6e7e7ab` 三次返工、327 行、4 小时 21 分。它同时碰 frame layout、callee-saved spill、unwind 描述三组不变量；越晚做，牵连越多。应该在 M2 就用一个 `>2047` 的测试盯住。

4. **错误直觉**：“分支超范围 BranchRelaxation 会自动处理，不用管。”
   **正确认识**：`f597d37` 之前，超范围分支被编码成回绕位移，**能跑但跳错**。必须自己实现 `isBranchOffsetInRange`、`reverseBranchCondition`、`insertIndirectBranch`，并给 `.space 1100000` 的 far target 写测试。静默错误比 crash 贵得多。

5. **错误直觉**：“优化应该第一优先，代码越短越好。”
   **正确认识**：`dcd9fdb`/`6a2366d` 的收益是 1 条指令，但它们是 canonicalization 层面的修正，必须在正确性稳定、e2e 和 bench 可量化之后做。顺序错了会把“优化引入的 miscompile”和“本来就没实现”混在一起。

6. **错误直觉**：“RISC-V 有 V/调度/code model，我们也该有。”
   **正确认识**：RISC-V 是 210 文件 / 137,976 行 / 8,876 commit。MiniRV 41 文件 / 5,381 行就覆盖了标量正确性，bench 达到 0.83–1.00。day one 追功能列表，只会把 bring-up 变成永远完不成的项目。

## 进阶：再往深一层

- **给每个 commit 打“层”标签。** 用 `git log --format='%h %s'` + 一个 `layers.tsv` 映射，就能算出“每层返工了几次”。本章的阶段表是手工分的，工程上应该脚本化。
- **用 `-stop-after` 定位返工层。** 例如 `llc -stop-after=finalize-isel` 看 ISel 输出、`-stop-after=prologepilog` 看 frame 结果；返工时先确定“哪一层的输出开始不对”，比读 diff 快。
- **把 e2e 的退出码变成断言。** 现在 `run.sh` 只比较 MiniRV 与 RISC-V 的退出码；上游化时可以再加“期望退出码”第三列，防止两边一起错。
- **bench 的 ratio 要标注前提。** 它是 `-O2` 下的静态指令数，不含 cache/分支预测；不要把它写成性能结论。这也是本章唯一不给“加速比”的原因。

## 本章重点整理

- 42 个 commit、9h09m、target 新增 7519 行；前三个里程碑 4h48m，ABI 与加固占其余时间。
- 阶段成本：M1 脚手架 1738 行 / 2 commits；M3 ABI 637 行代码 + 997 行测试；H 1466 行但 80% 是测试与判断。
- 六条返工链：大栈帧（3 次）、调用序列（2 次）、裸 frame index、分支范围、x0 规范化（2 次）、unwind/debug。
- 排序规则：MC-only 先行 → 直线代码 → frame/call/ABI → e2e → 诊断 → unwind → 优化。
- 与 RISC-V 的差距是 26 倍代码 / 211 倍 commit；不要 day one 对齐功能列表。
