# Ch 03 — 里程碑 0：MC-only target

> **目标**：说清“MC-only”能做什么、不能做什么，并逐文件解剖 MiniRV 的第一个 commit（48 个文件、1484 行插入），拿到 `llvm-mc` 往返和 ELF 对象两套验收证据。

> **环境**：LLVM 24.0.0git，`/home/ubuntu/llvm/trees/dsl-tablegen`，构建 `/home/ubuntu/llvm/builds/dsl-tablegen`。下文记 `BUILD=/home/ubuntu/llvm/builds/dsl-tablegen`，`B=$BUILD/bin`，`TREE=/home/ubuntu/llvm/trees/dsl-tablegen`。

## 为什么需要这个？

给 LLVM 加 target，最危险的不是“不会写”，而是“太早写 CodeGen”。一旦 `TargetMachine`、`Subtarget`、`ISelLowering` 同时存在，任何一个错误都会以“ISel 选错指令”“寄存器分配崩了”“栈帧不对”的形式出现，而你无法判断到底是 MC 层编码错了，还是 CodeGen 层语义错了。

MC-only 是我们把问题切成两半的第一刀：

- **MC 层**只回答“这段文本/这些字节/这个 ELF 对象是否自洽”。它不关心函数、栈、寄存器分配、ABI。
- **CodeGen 层**才回答“IR 应该变成哪些 MachineInstr”。它依赖 MC 层，但 MC 层完全不依赖它。

所以里程碑 0 的验收标准非常硬：`llvm-mc` 能编、能反汇编、能出 ELF；`llc` 仍然不能编译 IR。这个“不能”不是缺陷，而是**边界证明**——证明你没有偷偷把 CodeGen 的半成品混进来。

MiniRV 的第一个 commit `33d9ec8c1aed` 就是这条边界：48 个文件、1484 行插入，没有 `TargetMachine`、没有 `Subtarget`、没有 `ISelLowering`、没有 `FrameLowering`，但已经能产出带 `EM_RISCV` 的 ELF 对象。

## 先建立直觉

把 MC-only 想成两条独立的生产线，左边是“文本 → 对象”，右边是“对象 → 文本”；中间共享同一套 `MCInstrInfo`/`MCRegisterInfo`/编码表。

```
  .s 汇编文本
      │
      │  AsmParser::parseInstruction
      ▼
   MCInst ──► MCCodeEmitter::encodeInstruction ──► 4 字节机器码
      │                                             │
      │  InstPrinter::printInst                     │  ELFObjectWriter
      ▼                                             ▼
  .s 反汇编文本                                  .o 可重定位对象
      ▲                                             │
      │  MCDisassembler::getInstruction             │
      └──────────────  MCInst  ◄────────────────────┘

  .ll IR
      │
      │  llc: TargetMachine::getSubtargetImpl → ISel → MachineInstr → AsmPrinter
      ▼
   ???   ← milestone 0 这里不存在，llc 直接报错
```

关键直觉：**MC-only 的“输出”是对象文件，不是函数**。它可以让 `llvm-mc` 和 `llvm-objdump` 工作，但 `llc` 找不到 `TargetMachine`，所以连一条 IR 都编译不了。

## 主线一：“MC-only”的精确含义

| 能力 | milestone 0 | 依赖的接口 |
|---|---|---|
| 汇编 `.s` → `.o` | ✅ | `MCTargetAsmParser`、`MCCodeEmitter`、`MCAsmBackend`、`MCObjectTargetWriter` |
| `-show-encoding` 打印字节 | ✅ | `MCCodeEmitter` + `MCInstPrinter` |
| 反汇编字节 → `.s` | ✅ | `MCDisassembler` + `MCInstPrinter` |
| 发 ELF relocatable | ✅ | `MCELFObjectTargetWriter`（`MiniRVELFObjectWriter`） |
| `llvm-readobj`/`llvm-objdump` 读对象 | ✅ | 标准 ELF + `EM_RISCV` |
| IR → 汇编 | ❌ | 需要 `TargetMachine`、`Subtarget`、`ISelLowering`、`ISelDAGToDAG`、`AsmPrinter` |

“MC-only”不是“后端写了一半”，而是**只实现了 LLVM 的 MC 子系统的 target 接口**。它和 CodeGen 共享 TableGen 记录，但不共享编译管线。

### 5. `llc` 仍然失败

里程碑 0 的 `llc` 不能编译 IR。这个 commit 只有 `RegisterTarget`，没有 `RegisterTargetMachine`；`Target::createTargetMachine` 为空，`llc` 在 `llcdriver.cpp` 里拿到 null 后打印 `could not allocate target machine`。这是**源码依据**，不是本机在当前构建上跑出来的：当前树已经进入后续 CodeGen commit，`llc` 能成功；里程碑 0 的树没有 `TargetMachine`。换句话说，**Ch 03 的验收只看 `llvm-mc`/`llvm-objdump`/`llvm-readobj`；`llc` 是下一章之后的事。**

## 主线四：复用 `EM_RISCV` 的代价与收益

收益很直接：

- **对象格式兼容**：`llvm-readobj` 识别为 `elf64-littleriscv`，`file` 识别为 UCB RISC-V。
- **链接器兼容**：`ld.lld`/GNU ld 看到 `EM_RISCV` 就按 RISC-V 的 relocation 规则处理；`R_RISCV_JAL`/`R_RISCV_BRANCH` 的语义不需要新写。
- **工具链复用**：`llvm-objdump`、`llvm-readelf`、`objcopy`、`strip` 都能直接读，不需要为 MiniRV 写新的二进制工具。

代价也很直接：

1. **编码必须逐位兼容**。`add`/`mul` 的字节已经验证与 RISC-V 完全一致；一旦 MiniRV 的 auto-td 语料里出现“同助记符、不同编码”，链接器仍会按 RISC-V 语义修 relocation，结果不会报错，只会跑错。
2. **不能发新的 relocation ID**。ELF relocation 类型是全局注册表；MiniRV 若需要新语义，只能复用现有 ID 或改 linker。复用现有 ID 但改变语义，是最隐蔽的 ABI bug。
3. **对象头会“冒充” RISC-V**。`file basic.o` 会显示 `UCB RISC-V, soft-float ABI`；`llvm-objdump --triple=riscv64` 也能读它，但默认 feature 不同会解出 `<unknown>`：

```console
$ $B/llvm-objdump -d --triple=riscv64 /tmp/bringup-ev/basic.o | sed -n '6,10p'
0000000000000000 <main>:
       0: 00c58533     	add	a0, a1, a2
       4: 02c50533     	<unknown>
       8: 02a50513     	addi	a0, a0, 0x2a
       c: 00008067     	ret

$ $B/llvm-objdump -d --triple=riscv64 --mattr=+m /tmp/bringup-ev/basic.o | sed -n '6,10p'
0000000000000000 <main>:
       0: 00c58533     	add	a0, a1, a2
       4: 02c50533     	mul	a0, a0, a2
       8: 02a50513     	addi	a0, a0, 0x2a
       c: 00008067     	ret
```

同一个对象，RISC-V 反汇编器默认看不到 `mul`，加 `+m` 才看到；MiniRV 反汇编器则因为自己的语料包含 `mul`，默认就能解。**对象里的 `EM_RISCV` 只说明“按 RISC-V 的容器格式装”，不说明“目标能力等于 RISC-V”**。

## 主线五：最小 MC-only 脚手架清单

我们把第一个 commit 压缩成一张“缺一不可”的清单：

| # | 组件 | MiniRV 文件/符号 | 缺了会怎样 |
|---:|---|---|---|
| 1 | Triple 条目 | `Triple::minirv64`、`isMiniRV()` | `llvm-mc -triple=minirv64` 报 `No available targets` |

## 主线六：为什么构建系统必须有 MC-only 分支

`llvm_expand_pseudo_components` 的职责是把 `-link-components` 里的“伪组件”（比如 `MiniRV`）展开成真实的库名。旧逻辑假设每个 target 至少满足以下之一：

- 有 `LLVM${c}CodeGen`（普通 CodeGen target）；或
- 有 `LLVM${c}`（只有核心库、没有 CodeGen 的 target）。

MiniRV 是第三种：有 `add_llvm_component_group(MiniRV)`，有 `LLVMMiniRVDesc`/`LLVMMiniRVInfo`/`LLVMMiniRVAsmParser`/`LLVMMiniRVDisassembler`，但没有 `LLVMMiniRV` 核心库，也没有 `LLVMMiniRVCodeGen`。旧代码会直接 `FATAL_ERROR "Target MiniRV is not in the set of libraries."`，连配置都过不去。

新分支的判断顺序值得记：

1. `LLVM${c}CodeGen` 存在 → 加 CodeGen；
2. 否则 `LLVM${c}` 存在 → 加核心库；
3. 否则 `TARGET ${c}` 且 `LLVM${c}Desc` 存在 → 认定是 MC-only，**不加核心库**，让后面的 `foreach` 把 `AsmParser/Desc/Disassembler/Info` 加进来；
4. 都不满足 → 仍然是 `FATAL_ERROR`。

`TARGET ${c}` 这一半很关键：`add_llvm_component_group(MiniRV)` 创建的是 CMake target，不是库；只看 `LLVM${c}Desc` 可能误判一个没有组件组的 target。两个条件一起，才精确表达“组件组存在且 MC 描述库存在”。

还有 `Targets.def`。构建系统为每个 target 生成 `LLVM_TARGET(MiniRV)`，最终需要 `LLVMInitializeMiniRVTarget` 符号。常规 target 在 `TargetMachine.cpp` 里定义它；MiniRV 没有 `TargetMachine.cpp`，所以在 `MiniRVMCTargetDesc.cpp` 里定义成 `LLVMInitializeMiniRVTargetInfo()` + `LLVMInitializeMiniRVTargetMC()`。这不是偷懒，而是 MC-only 的初始化链本来就只需要这两步。

## 反直觉与踩雷

1. **错误直觉**：MC-only 是“后端写了一半”，再补个 ISel 就能跑。
   **正确认识**：MC-only 和 CodeGen 是两条管线。MC-only 有 `MCInst`、编码器、解码器；CodeGen 需要 `MachineInstr`、`TargetMachine`、合法化、寄存器分配、栈帧。中间没有“半条 ISel”可复用，只有共享的 TableGen 记录。

2. **错误直觉**：对象里 `Machine: EM_RISCV`，所以 MiniRV 对象就是 RISC-V 对象，随便拿 RISC-V 工具链处理。
   **正确认识**：容器格式相同，能力集合不一定相同。`llvm-objdump --triple=riscv64` 默认把 `mul` 解成 `<unknown>`，加 `--mattr=+m` 才解对；`llc -mtriple=riscv64` 会把 `mul` 降成 `__muldi3`。对象兼容不等于语义兼容。

3. **错误直觉**：`RegisterTarget` 注册了 target，`llc` 就能用了。
   **正确认识**：`RegisterTarget` 只提供名字和 ArchMatchFn；`llc` 还需要 `RegisterTargetMachine`。第一个 commit 没有后者，所以 `llc` 会在 `createTargetMachine` 拿到 null，打印 `could not allocate target machine`。

4. **错误直觉**：48 个文件说明这个 target 很复杂。
   **正确认识**：19 个是 auto-td 数据（14 个指令 YAML 每个 5 行），5 个是 TableGen 外壳，真正的手写 C++ 约 870 行。复杂度在“接口对齐”，不在“代码量”。

5. **错误直觉**：MiniRV 复用了 RISC-V 的助记符，所以 `ret`、`%pcrel_hi` 这些伪指令/修饰符也应该能用。
   **正确认识**：MiniRV 的 parser 只实现自己的操作数语法。`ret` 会报 `invalid instruction mnemonic`；`%pcrel_hi(...)` 更隐蔽——`%` 走不到 `ParseOperand` 的分支，整行可能被静默丢掉。写测试时要用 `jalr x0, 0(x1)` 和显式标签，别假设 GNU 汇编器的全套伪指令都在。

```console
$ printf 'ret\n' | $B/llvm-mc -triple=minirv64 2>&1
<stdin>:1:1: error: invalid instruction mnemonic
ret
^
```

## 进阶：再往深一层

- **看生成物**。`$BUILD/lib/Target/MiniRV/MiniRVGenAsmMatcher.inc`、`MiniRVGenMCCodeEmitter.inc`、`MiniRVGenDisassemblerTables.inc` 是“YAML → TableGen → C++”的中间产物。把 `add` 在三个文件里的片段对照读，能彻底理解 matcher/encoder/decoder 的分工。
- **加一条指令**。练习 A 会让你从 `auto-td/instructions/rv-i/` 里复制一个 YAML，改 mnemonic/opcode key/taxonomy，再跑 `llvm-mc -show-encoding` 和 lit。那是检验本章 checklist 是否真的理解的最好方式。

## 本章重点整理

- MC-only = 能汇编、反汇编、编码/解码、发 ELF；不能把 IR 编译成汇编。
- 第一个 commit 48 个文件、1484 行插入，核心是 Triple、TargetInfo、MCTargetDesc、AsmParser、Disassembler、TableGen 外壳和 14 条指令语料（8 R + 4 I + 2 U）。
- MiniRV 复用 `EM_RISCV`：对象格式和 relocation 直接兼容 RISC-V 工具链，代价是编码必须逐位一致、不能发新 relocation ID。
