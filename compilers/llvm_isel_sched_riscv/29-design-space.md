# Ch 29 — 设计空间：SelectionDAG vs GlobalISel、pre-RA vs post-RA、VLIW 与未来

> **目标**：把前 28 章的具体机制收成一张设计地图。学完你能回答：为什么 LLVM 同时存在 SelectionDAG 和 GlobalISel；RISC-V 今天该用哪一个；pre-RA/post-RA 调度的取舍是什么；VLIW/向量后端为什么需要不同的调度模型；以及「表驱动」与「手写」各自的代价。
>
> **环境**：LLVM 24.0.0git；本机构建只含 X86、AArch64、RISCV 三个 target。RISC-V 的 GlobalISel 实测用 `llc -global-isel`；Hexagon 的 VLIW/PACKET 未在本机构建，涉及处明确标注为概念讨论，不伪造运行结果。

## 为什么最后一章讲「设计空间」而不是「更多细节」

面试里最难的一类问题不是「这个 pass 干什么」，而是：

> 「如果让你给一个新 ISA 写后端，你选 SelectionDAG 还是 GlobalISel？」
> 「为什么 RISC-V 的 GlobalISel 还不能全面替代 SelectionDAG？」
> 「VLIW 机器的调度和 RISC-V 有什么本质不同？」

这些问题没有唯一答案，只有取舍。前 28 章给了你每个零件的知识；这一章把它们放回设计者的位置：如果预算有限、时间有限、团队有限，你会先做哪一层，后做哪一层，哪些坑可以先欠着。

## 先建立直觉：四个正交的设计维度

很多人把「SelectionDAG vs GlobalISel」当成一个二选一，其实设计空间至少有四个维度：

```text
维度 1：选择发生在哪一层
  DAG（SelectionDAG）  ←→  MIR（GlobalISel）

维度 2：调度发生在哪一层
  DAG 内调度（ScheduleDAGSDNodes） ←→ MIR 调度（MachineScheduler pre-RA/post-RA）

维度 3：知识怎么表达
  TableGen 表（pattern / matcher） ←→ 手写 C++（switch / helper）

维度 4：ISA 的形状
  定长 RISC（RISC-V） ←→ VLIW（Hexagon） / 向量（RVV）
```

四个维度不是绑死的。RISC-V 今天的选择是：

```text
选择：SelectionDAG（默认） + GlobalISel（部分）
调度：DAG 内调度 + pre-RA MachineScheduler + post-RA scheduler
表达：SDAG 用 .td pattern；GISel 用生成的 matcher + 手写 selector
ISA：定长 32/16-bit，RVV 作为可选向量扩展
```

这四行就是本章要展开的内容。

## 主线一：SelectionDAG 与 GlobalISel 的实测差异

用第 18 章的 `sel.ll`，同一个 `-mcpu=sifive-u74`，只切换选择器：

```bash
# SelectionDAG（默认）
$ llc -mtriple=riscv64 -mattr=+m,+zicond -mcpu=sifive-u74 sel.ll -o sdag.s
# GlobalISel
$ llc -mtriple=riscv64 -mattr=+m,+zicond -mcpu=sifive-u74 \
      -global-isel -global-isel-abort=2 sel.ll -o gisel.s
$ diff sdag.s gisel.s
```

本机只有一处差异（7 行），在 `sel0`（`select %c, %a, 0`）：

```asm
# SelectionDAG
sel0:
	czero.eqz	a0, a0, a2
	ret

# GlobalISel
sel0:
	bnez	a2, .LBB1_2
	li	a0, 0
.LBB1_2:
	ret
```

这是一个非常典型的覆盖差异：SelectionDAG 有 Zicond 的 select pattern（`czero.eqz`），GlobalISel 在这个形状上没有对应的 matcher/combine，于是退回「分支 + 常数」。

再看 `mem3.ll`：两者输出**逐字节相同**。说明基础的整数/浮点 load/store、算术、分支，GISel 已经覆盖。

再看向量 `rvv.ll`：

```bash
$ llc ... -global-isel -global-isel-abort=2 rvv.ll -o -
warning: Instruction selection used fallback path for vadd
warning: Instruction selection used fallback path for vmul
```

GISel 对 RVV 的函数**逐函数回退**到 SelectionDAG。把 abort 模式改成 1（遇到失败直接 abort）：

```bash
$ llc ... -global-isel -global-isel-abort=1 rvv.ll -o /dev/null
LLVM ERROR: unable to legalize instruction: %5:_(<4 x s64>) = G_ADD %3:_, %4:_ (in function: vadd)
```

`-global-isel-abort` 的三个值（`CodeGenOptions.td` / `TargetOptions.h`）：

| 值 | 枚举 | 行为 | 本机观察 |
|---|---|---|---|
| 0 | `Disable` | 静默回退 | 无警告 |
| 1 | `Enable` | 失败即 abort | `LLVM ERROR: unable to legalize ...` |
| 2 | `DisableWithDiag` | 回退 + 诊断 | `warning: ... fallback path` |

这三个值经常被记反。写测试时用 2（要看到回退范围），做覆盖统计时用 1（让缺口变成硬失败）。

补充一个容易忽略的事实：RISC-V **没有 FastISel**。LLVM 的三个选择器里，RISC-V 只有 SelectionDAG（默认）和 GlobalISel（opt-in）；`-O0` 也走 SelectionDAG，只是少开优化。这解释了第 10 章的观察：RISC-V 的 `-O0` 汇编仍然有完整的 DAG 选择流程，不会像 x86 那样有一条「快速但粗糙」的独立路径。

本机验证：

```bash
$ llc -mtriple=riscv64 -O0 -fast-isel -debug-pass=Structure ch30.ll -o /dev/null
...
  RISC-V DAG->DAG Pattern Instruction Selection
  Fast Register Allocator
```

即使显式传 `-fast-isel`，pipeline 里出现的仍是 DAG 选择器，没有 FastISel pass。

## 主线二：两条管线的结构差异

用 `-debug-pass=Structure` 看同一个函数在两种模式下的 pass：

```text
# SelectionDAG
RISC-V DAG->DAG Pattern Instruction Selection
Finalize ISel and expand pseudo-instructions

# GlobalISel
gisel-known-bits
riscv-prelegalizer-combiner
legalizer
riscv-postlegalizer-combiner
reg-bank-select
instruction-select
riscv-isel
finalize-isel
```

结构上的关键差别：

- **SelectionDAG**：IR → DAG → 选择 → DAG 调度 → 回到 MIR。DAG 层的 combine/legalize 直接操作 `SDNode`，chain/glue 表达内存与副作用顺序（第 4、9 章）。
- **GlobalISel**：IR → MIR（`IRTranslator`）→ 通用 `G_*` 指令 → legalize → regbank → select。整个过程留在 MIR，类型和寄存器约束用 generic opcode 表达。

对调度的直接影响：

1. **GISel 没有 DAG 内调度**。它的第一层调度就是 `MachineScheduler`（pre-RA），少了一次「DAG 顺序 → MIR 顺序」的转换。
2. **GISel 保留更多 pseudo**。legalize 之后还有 `G_*`，选择之后才变成目标指令；这给 combine 更多机会，也让 `-stop-after` 的断点更多。
3. **SDAG 的 chain 在 GISel 里变成内存操作顺序**。GISel 用 MIR 的 memory operand 和 `MachineMemOperand` 表达，不再有 `chain`/`glue` 这种 DAG 概念。

这就是为什么第 1 章说「两条调度主线」：一条在 DAG 内，一条在 MIR。选 GISel 相当于**删掉第一条**。

## 主线三：表驱动 vs 手写

SelectionDAG 的选择知识几乎全在 `.td`：

```tablegen
def SH1ADD : ALU_rr<0b0010000, 0b010, "sh1add">,
             Sched<[WriteSHXADD, ReadSHXADD, ReadSHXADD]>;
def : Pat<(add GPR:$rs1, (shl GPR:$rs2, 1)), (SH1ADD GPR:$rs1, GPR:$rs2)>;
```

GlobalISel 的 RISC-V 实现是混合的。`RISCVInstructionSelector.cpp` 文件头写得很直白：

```text
/// \file
/// This file implements the targeting of the InstructionSelector class for
/// RISC-V.
/// \todo This should be generated by TableGen.
```

本机行数：

| 文件 | 行数 | 角色 |
|---|---:|---|
| `GISel/RISCVInstructionSelector.cpp` | 2378 | 选择器；包含生成的 matcher 与手写 helper |
| `GISel/RISCVLegalizerInfo.cpp` | 1917 | legalize 规则 |
| `GISel/RISCVRegisterBankInfo.cpp` | — | 寄存器 bank 映射 |
| `GISel/RISCVRegisterBanks.td` | — | bank 定义的 TableGen 部分 |

它同时 `#include "RISCVGenGlobalISel.inc"`（TableGen 生成的 matcher），所以不是纯手写；但大量边界情况仍要 C++ 兜底。

两种表达的取舍：

| 维度 | TableGen 表 | 手写 C++ |
|---|---|---|
| 新增一条简单 pattern | 几行，自动生成 matcher | 要改 switch/helper，容易漏 |
| 复杂多指令 lowering | 难写、难调 | 灵活，可读 |
| 覆盖统计 | 天然按 pattern 组织 | 要靠测试和 `-stats` |
| 调试 | `-debug-only=isel` 看 pattern 尝试 | 断点/日志直接 |
| 上游 review | 表改动小、易审 | 大段 C++，审得慢 |

这解释了为什么 RISC-V 的 SDAG 覆盖比 GISel 全：SDAG 的 pattern 已经积累了多年，GISel 还在补。**不是 GISel 设计不好，而是覆盖是体力活。**

把「表驱动 vs 手写」放进成本模型：

| 成本项 | TableGen 表 | 手写 C++ |
|---|---|---|
| 新增覆盖的边际成本 | 低（几行 pattern） | 高（switch/helper/测试） |
| 表达复杂 lowering | 高（要拆 pattern、加 pseudo） | 低（直接写） |
| 错误定位 | 中（pattern 尝试顺序） | 低（断点） |
| 上游 review 成本 | 低（diff 小） | 高（大段逻辑） |
| 覆盖遗漏的可见性 | 高（pattern 列表即清单） | 低（只能靠测试） |

这解释了一个常见的团队决策：**先用表驱动把 80% 的简单指令铺开，再用手写 C++ 处理 20% 的边界**。RISC-V 的 SDAG 是前者，GISel 的 selector 是两者的混合。

## 主线四：pre-RA 与 post-RA 的取舍

第 16、17 章讲过细节，这里放回设计空间：

```text
pre-RA 调度：寄存器还是虚拟的，可以自由重排，但要预测压力
post-RA 调度：物理寄存器已定，只能在不破坏依赖的前提下填空隙
```

| 维度 | pre-RA | post-RA |
|---|---|---|
| 自由度 | 高（可改变寄存器生命周期） | 低（受物理寄存器约束） |
| 目标 | 延迟 + 压力平衡 | 填延迟槽、减少 stall |
| 风险 | 排得太激进 → spill | 改不动大结构 |
| RISC-V 现状 | 默认开 | 由 `use-postra-scheduler` feature 控制 |

RISC-V 的 `sifive-u74` 带 `use-postra-scheduler`（第 13、17 章），所以它在 RA 后还会再排一次；`rocket-rv64` 默认不开。这就是为什么同一个 `-O2`，不同 `-mcpu` 的最终顺序可能不同：**不是选择变了，是第二层调度的开关不同**。

设计上的判断：

- 顺序核（in-order）更依赖 post-RA：RA 后的 stall 是真实的，pre-RA 看不到。
- 乱序核（OoO）post-RA 收益小：硬件会自己重排，编译器只需保证依赖和资源不炸。
- 寄存器压力大的函数，pre-RA 应该更保守；这也是 `ShouldTrackPressure` 的由来（第 15 章）。

## 主线五：VLIW、向量与「打包」约束

RISC-V 是定长指令（32-bit，可选 16-bit 压缩），调度器决定的是**顺序**。VLIW 不一样：它要决定**哪些指令打包进同一个 bundle**，以及 bundle 内的槽位。

本机构建没有 Hexagon，所以下面只给概念和源码位置，不给运行结果：

- VLIW 后端通常有 `Bundle`/`PACKET` 概念，调度器输出的是「指令组」而不是线性序列。
- 打包约束包括：槽位类型（ALU/load/store/branch）、跨槽依赖、bundle 内的延迟槽。
- LLVM 里 Hexagon 用 `MachineBundle`/`BundlePacket` 相关 pass 表达；调度策略与 RISC-V 的 `MachineScheduler` 不同。

RISC-V 的 RVV 虽然不是 VLIW，但有类似的「隐式状态」问题：

- `vsetvli` 设置 VL/SEW/LMUL，后续向量指令依赖这个状态。
- `vsetvli` 在 RA 之后才插入（第 23 章），所以调度器必须先排向量指令、再插配置指令。
- LMUL 改变会改变向量寄存器组的占用，等价于「一条指令占用多个物理寄存器」——这和 VLIW 的槽位占用在建模上有相似之处。

一个可迁移的直觉：**当指令的效果依赖「机器状态」而不只是操作数时，调度器必须把状态也当成依赖**。RISC-V 的 `vsetvli`、VLIW 的 bundle、x86 的 flags 都是这个模式。

## 主线六：RISC-V 后端的未来方向

把前 28 章的坑按「投入产出」排一下：

1. **GISel 覆盖**：先把标量整数/浮点的 pattern 补齐（`czero`、`sh*add`、`zext.w` 等），再谈向量。每补一条都要有 `.mir`/`.ll` 测试。
2. **sched model 精度**：`Sched<[]>` 还有 135 处（第 25 章）；厂商扩展的模型尤其缺。补模型的门槛不是写 `WriteRes`，而是拿到可信的 latency/吞吐。
3. **post-RA 策略**：`use-postra-scheduler` 目前是 per-CPU feature；未来可能按函数特征（压力、循环深度）动态决定。
4. **RVV 调度**：`vsetvli` 插入、LMUL 变化、mask 依赖，都是现有 `MachineScheduler` 没有充分建模的。
5. **选择与调度的联合优化**：目前 selection 先做、scheduling 后做；MachineCombiner 是少数「看着调度代价改选择」的 pass（第 21 章）。更激进的方案是 cost model 驱动的选择，但工程复杂度高。

面试里如果被问「你觉得 RISC-V 后端最该改进什么」，一个有理有据的回答是：

> 「短期补 GISel 的标量覆盖和厂商模型的 `Sched<[]>`；中期把 RVV 的 `vsetvli`/LMUL 纳入调度代价；长期才谈 selection 和 scheduling 的联合搜索。因为前两项是覆盖问题，能靠测试和文档推进；后一项是研究问题，收益不确定。」

## 踩雷清单

1. **`-global-isel-abort` 的值记反**。0=静默回退、1=abort、2=回退+诊断；写测试用 2，做覆盖率门槛用 1。
2. **把「GISel 能编译」当成「GISel 覆盖了」**。`rvv.ll` 在 abort=2 下能出汇编，因为每个函数都回退了；只有 abort=1 才暴露缺口。
3. **用 `-mcpu=generic` 研究调度**。`generic` 会落到某个具体模型（本机是 SpacemitX60），不是「无模型」；要无模型用 `-mcpu=andes-ax25`（第 0、25 章）。
4. **把 VLIW 的概念硬套到 RISC-V**。RISC-V 没有 bundle，`vsetvli` 也不是打包；相似的是「隐式状态依赖」，不是指令分组。
5. **以为 post-RA 一定更好**。OoO 核上 post-RA 可能白费；in-order 核上它才关键。先看 `use-postra-scheduler` 和 CPU 类型。
6. **用 SDAG 的经验估 GISel 的工作量**。GISel 的 legalize/regbank 是另一套抽象，pattern 不能直接搬。

## 重点整理

| 设计维度 | 选项 A | 选项 B | RISC-V 现状 | 判断依据 |
|---|---|---|---|---|
| 选择层 | SelectionDAG | GlobalISel | 默认 SDAG，GISel 部分覆盖 | 覆盖 vs 长期可维护 |
| 调度层 | DAG 内调度 | MIR MachineScheduler | 两者都有 | GISel 没有 DAG 调度 |
| 调度时机 | pre-RA | post-RA | 按 CPU feature | in-order 更需要 post-RA |
| 知识表达 | TableGen | 手写 C++ | SDAG 表驱动，GISel 混合 | 覆盖速度 vs 灵活性 |
| ISA 形状 | 定长 RISC | VLIW/向量 | 定长 + RVV | 状态依赖的建模方式 |

- SelectionDAG 的优势是成熟和覆盖；GlobalISel 的优势是统一的 MIR 抽象和更少的中间层。
- RISC-V 的 GISel 缺口是真实的：Zicond select 退回分支、RVV 整函数回退。
- pre-RA/post-RA 不是「新老」之分，而是「自由度 vs 真实性」的取舍。
- VLIW 的核心是打包约束；RVV 的核心是隐式状态（`vsetvli`/LMUL）。两者都要求调度器把「非操作数依赖」建模进去。
- 设计空间没有标准答案，只有「在当前覆盖、团队、时间下的最优欠债」。
