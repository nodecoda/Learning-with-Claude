# Ch 28 — 上游 PR 与 review：RISC-V backend 的规矩

> **目标**：把一个 sched model / instruction selection 的改动，做成上游愿意合并的形状。学完你知道一个模型 patch 应该包含哪些文件、commit message 该写什么、reviewer 会问哪几类问题、本地有哪些机械门禁可以先跑，以及为什么「测试比代码大」在 sched model 里是正常的。
>
> **环境**：LLVM 24.0.0git；源码树 `/home/ubuntu/llvm/trees/explore`（含上游历史）；本机门禁脚本 `/home/ubuntu/llvm/toolset/pre-pr-check.sh`。本章引用的 commit 都是该树里的真实提交，diff 与 message 为本机 `git show` 输出。

## 为什么 sched model 的 review 和普通 patch 不一样

普通代码 patch 的正确性可以由测试直接证明：输入、输出、断言。sched model 不行：

- reviewer 手里没有你的芯片，无法验证 `Latency = 3` 是不是真的 3。
- 模型错了不会崩，只会让 scheduler 排得更好或更坏；测试只能证明「模型自洽」，不能证明「模型正确」。
- 一个 `WriteRes` 改动会影响所有引用该 `SchedWrite` 的指令，以及所有复用该模型的 CPU。

所以 review 的重点不是「代码能不能跑」，而是三件事：

1. **来源**：这个数字从哪来（厂商文档、实测、还是猜的）。
2. **范围**：改了哪些指令、哪些 CPU、哪些测试。
3. **可回归**：以后有人改坏了，哪个测试会红。

本章用三个真实 commit 拆这三件事。

## 先建立直觉：一个 patch 的生命周期

```text
fetch upstream ──► branch ──► code ──► tests ──► local lit ──► format
      │                                                          │
      └────────────── rebase（只 rebase，不 merge）◄────────────┘
                                                                 │
                                                          pre-pr-check.sh
                                                                 │
                                                              push / PR
                                                                 │
                                                       review ──► squash merge
```

以及 review 的三个同心圆：

```text
        ┌─────────────────────────────┐
        │ 正确性：数字有出处、语义对   │
        │  ┌───────────────────────┐  │
        │  │ 覆盖：所有 CPU/指令/测试│  │
        │  │  ┌─────────────────┐  │  │
        │  │  │ 可维护：命名、注释│  │  │
        │  │  └─────────────────┘  │  │
        │  └───────────────────────┘  │
        └─────────────────────────────┘
```

reviewer 的评论顺序通常是从外往里：先问「这数字哪来的」，再问「你测了哪些 CPU」，最后才讨论命名。

## 主线一：一个「小」模型修正长什么样

真实提交 `78b651a2cba9`：

```text
[RISCV] Fix the pipe used by `fmv.x.<fp>/<fp>.x` in SiFive7 sched model (#187740)

These FP <-> Integer conversion instructions should use PipeA instead.
```

改动只有 6 行：

```diff
-  def : WriteRes<WriteFMovI16ToF16, [PipeB]>;
-  def : WriteRes<WriteFMovF16ToI16, [PipeB]>;
-  def : WriteRes<WriteFMovI32ToF32, [PipeB]>;
-  def : WriteRes<WriteFMovF32ToI32, [PipeB]>;
-  def : WriteRes<WriteFMovI64ToF64, [PipeB]>;
-  def : WriteRes<WriteFMovF64ToI64, [PipeB]>;
+  def : WriteRes<WriteFMovI16ToF16, [PipeA]>;
+  def : WriteRes<WriteFMovF16ToI16, [PipeA]>;
+  def : WriteRes<WriteFMovI32ToF32, [PipeA]>;
+  def : WriteRes<WriteFMovF32ToI32, [PipeA]>;
+  def : WriteRes<WriteFMovI64ToF64, [PipeA]>;
+  def : WriteRes<WriteFMovF64ToI64, [PipeA]>;
```

但测试必须同步改。`llvm-mca` 的 `-instruction-tables=full` 会打印每条指令占用的资源，`PipeB` 变 `PipeA` 之后，mca 测试里的资源列也跟着变：

```diff
-# CHECK-NEXT:  1      3     1.00   3   VLEN128X100SiFive7PipeAB,VLEN128X100SiFive7PipeB FMV_X_W  fmv.x.w a2, fs7
+# CHECK-NEXT:  1      3     1.00   3   VLEN128X100SiFive7PipeA,VLEN128X100SiFive7PipeAB FMV_X_W  fmv.x.w a2, fs7
```

这个 diff 教了三件事：

1. **资源改动会改变 mca 的可见输出**，所以 mca 测试既是回归也是「改动的证据」。
2. `PipeA` 与 `PipeAB` 同时出现，说明 `PipeAB` 是一个 `ProcResGroup`（A 或 B 的集合）；资源列的顺序不是语义，但测试是字符串匹配，顺序变了也要更新。
3. commit message 只有一句 why（「应该用 PipeA」），没有解释「为什么以前用错了」。这是可以接受的，因为改动小、来源明确；如果改动涉及一整个 CPU 模型，就必须写清楚依据。

reviewer 在这个 patch 上会问的典型问题：

- 「`WriteFMov*` 还被哪些指令引用？」（`grep -rn 'WriteFMov' RISCVInstrInfo*.td`）
- 「SiFive7 的其他变体（VLEN128/512/1024）都覆盖了吗？」（`multiclass` 里的 `WriteRes` 会被所有变体继承，答「是」）
- 「RV32 的 `fmv.x.w` 和 RV64 的 `fmv.x.d` 都改了吗？」（6 条覆盖了 16/32/64）

## 主线二：新增一个 CPU 模型，测试比代码大是正常的

真实提交 `1d9762a07765`：

```text
[RISCV] Add scheduling models for `sifive-x160` and `sifive-x180` (#187089)

Assign scheduling models to `sifive-x160` and `sifive-x180`.

Currently both of them share the same model, which is a variant of the
SiFive7 scheduling model with VLEN=128. Because of this commonality, most
tests only use `-mcpu=sifive-x180`, whose instruction set is a superset
of `sifive-x160`'s.
```

diff 统计（本机 `git show --stat`）：

```text
 llvm/lib/Target/RISCV/RISCVProcessors.td           |    8 +-
 llvm/lib/Target/RISCV/RISCVSchedSiFive7.td         |    9 +-
 .../llvm-mca/RISCV/SiFiveX100/atomic.test          |  219 +
 .../llvm-mca/RISCV/SiFiveX100/floating-point.test  |  163 +
 .../llvm-mca/RISCV/SiFiveX100/integer.test         |  155 +
 .../llvm-mca/RISCV/SiFiveX100/rvv/arithmetic.test  | 4523 ++++++++++++++++++++
 .../llvm-mca/RISCV/SiFiveX100/rvv/fp.test          | 3703 +++++++++++++
 ...
```

代码 17 行，测试两万多行。第一次看到会以为作者疯了；其实是 mca 测试的粒度决定的：

- 一个 CPU 模型要覆盖标量整数、浮点、原子、向量、掩码、置换、归约、段访问……
- 每个 `.test` 用 `-instruction-tables=full` 打印**每条指令**的 uOps/latency/吞吐/资源。
- 这些表是 autogenerated 的，但作者必须读过关键行；reviewer 抽查的是「资源分组是否合理」，不是逐行读 4523 行。

这类 PR 的 review 重点：

1. **模型是不是复制粘贴**：`SiFive7SchedMachineModel<128>` 的变体参数是否正确，`VLEN` 是否影响向量指令的吞吐。
2. **InstructionItinerary 是否覆盖**：新 CPU 的 `ProcessorModel` 指向哪个 `SchedMachineModel`，`UnsupportedFeatures` 是否漏了。
3. **测试是否真的跑了新 CPU**：`-mcpu=sifive-x180` 出现在每个 `.test` 的 RUN 行里。
4. **有没有 `CompleteModel` 缺口**：TableGen 全量构建会替 reviewer 检查（第 25 章）。

面试里如果被问「你怎么给一个新 CPU 加模型」，答案的骨架就是这三层：`RISCVProcessors.td` 的 `ProcessorModel`、`RISCVSched*.td` 的 `WriteRes`、`llvm-mca` 的 `.test`。

## 主线三：修一个「反直觉」的模型 bug

真实提交 `63c052008276` 的 message 值得整段读：

```text
[RISCV] Use BufferSize = 0 for ProcResGroup in SiFive7 scheduling models (#194754)

As it turns out, even if a `ProcResGroup` consists of in-order pipes, as
long as its (the group's) BufferSize is not zero, Machine Scheduler will
not use in-order scheduling on instructions that consume it. Since
BufferSize also defaults to -1 for `ProcResGroup`, we have been
scheduling the resource consumption of SiFive7's `PipeAB` (scalar pipes)
and `VA1OrVA2` (vector pipes) in an out-of-order fashion!

Co-authored-by: Min Hsu <min.hsu@sifive.com>
```

这段 message 的结构是教科书：

1. **现象**：`ProcResGroup` 的 `BufferSize` 默认是 -1。
2. **机制**：非零 `BufferSize` 会让 MachineScheduler 对该资源的消费者改用乱序调度。
3. **影响**：SiFive7 的 `PipeAB` 和 `VA1OrVA2` 一直被当成 OoO 资源在排。
4. **修复**：显式 `BufferSize = 0`。

reviewer 对这类 patch 的追问通常是：

- 「为什么之前没发现？」——因为模型能跑、mca 数字也「合理」，只是调度策略悄悄变了。
- 「影响哪些 CPU？」——所有复用 SiFive7 模型的处理器（u74、x100、x160/x180……）。
- 「有没有性能回归测试？」——mca 只能证明资源占用，调度策略的变化要靠 lit 的顺序测试或目标板。

这也是第 27 章「归因」的反面教材：**模型里的一个默认值，能让整个调度策略从 in-order 变成 OoO，而汇编可能完全一样**。

## 主线四：commit message 与 PR 描述

本机规则（`/home/ubuntu/admin/AGENTS.md` §4）：

- 标题带子系统前缀：`[RISCV]`、`[clang]`、`[LV]`……
- 标题只答 what，短：目标 ≤ 60 字符，硬上限 72；首字母大写、不加句号、不写 issue 号。
- body 写 why、影响、未决问题；squash 后 PR 标题会变成 main 上的 commit subject。
- 一个 PR 只做一件事；顺手重构另开。
- 历史线性，只 rebase，不 merge。
- AI 辅助要写 `Assisted-by: <tool> (<model>)` trailer，并在 PR 描述里声明人工审阅。

对比三个真实标题：

```text
[RISCV] Fix the pipe used by `fmv.x.<fp>/<fp>.x` in SiFive7 sched model (#187740)
[RISCV] Add scheduling models for `sifive-x160` and `sifive-x180` (#187089)
[RISCV] Use BufferSize = 0 for ProcResGroup in SiFive7 scheduling models (#194754)
```

第三个 71 字符，已经在硬上限边缘；它仍然合格，因为 what 足够具体。反面例子是把标题写成「Fix a bug in the scheduler」——reviewer 无法从标题判断影响面。

## 主线五：本地门禁 `pre-pr-check.sh`

本机脚本 `/home/ubuntu/llvm/toolset/pre-pr-check.sh` 在提交后跑，十项检查：

| # | 检查 | 失败/警告 |
|---|---|---|
| 1 | 工作区干净 | 有未提交改动 → FAIL |
| 2 | 无 merge commit | 有 merge → FAIL |
| 3 | 与 `upstream/main` 同步 | behind → warn，要求 rebase |
| 4 | `git diff --check` | 空白错误 → FAIL |
| 5 | `git clang-format --diff --binary <build>/bin/clang-format upstream/main` | 会改行 → FAIL |
| 6 | 改动 C/C++ 行 ≤ 80 列 | 超长 → FAIL |
| 7 | `.mir` 里没有 `# CHECK` | 有 → FAIL（假通过风险） |
| 8 | 标题长度、`Assisted-by`、`Fixes #N` | 标题 >72 → FAIL；其余 warn |
| 9 | issue 标签/重复 PR | `good first issue` → FAIL；已有 PR → warn |
| 10 | 改动的 lit 测试列表 | 没有 → warn |

第 7 项值得单独解释。第 26 章复现过这个假通过：MIR body 里写 `# CHECK` 会让 `llc` 解析失败，而 `not llc ... 2>&1 | FileCheck` 会把报错里回显的源码行当成匹配，测试显示 PASS。脚本用

```bash
grep -Hn '^[[:space:]]*#[[:space:]]*CHECK' <changed .mir files>
```

把它拦在推送之前。这类检查不涉及语义，但能挡掉最浪费时间的一类 review 往返。

另外两条硬规则：

- **只用构建树的 clang-format**。系统 `/usr/bin/clang-format` 14 读不了 `llvm/.clang-format` 的 `LineEnding`，会直接报错。
- **格式化基准是 `upstream/main`**，不是 `HEAD`；否则只检查了最后一个 commit。

## 主线六：reviewer 会问什么，以及拿什么回答

| reviewer 的问题 | 你要拿出的证据 |
|---|---|
| 「这个 latency/吞吐从哪来？」 | 厂商手册页码、实测数据、或同系列 CPU 的既有模型 + 差异理由 |
| 「改了哪些指令？」 | `grep` 该 `SchedWrite` 的所有引用；列出 opcode |
| 「哪些 CPU 受影响？」 | `grep -l` 该模型文件；列出 `ProcessorModel` |
| 「`CompleteModel` 覆盖了吗？」 | 全量 `ninja` 通过；TableGen 没报 `does not define resources` |
| 「RV32/RV64 都对吗？」 | 两个 `-mtriple` 的测试；必要时 `SchedVariant` + `Feature64Bit` |
| 「为什么没有测试？」 | mca `.test`（资源/延迟）+ lit（选择/顺序） |
| 「这是 NFC 吗？」 | 如果汇编/周期会变，标题不能写 NFC；NFC 只允许重命名/重组 |
| 「性能数据呢？」 | 目标板 `perf` 或 mca 对比；说明模型边界 |

第 7 条是高频翻车点。真实的 NFC 例子是 `77efa4af205f`：

```text
[RISCV][NFC] Simplify the vector pipe names in SiFive7 sched model (#181268)
```

它只改名字，不改任何 `Latency`/资源集合；reviewer 可以用「diff 里只有 identifier 变化」快速确认。如果你在 NFC 标题下顺手把 `PipeB` 改成 `PipeA`，会被要求拆 PR。

## 踩雷清单

1. **只改一个 `CompleteModel` 的 CPU**。第 25 章实测：新增 `WriteCBO` 只改 SiFive7，TableGen 在 Andes45 上直接报 `Processor does not define resources for WriteCBO`，整棵构建挂掉。新增 `SchedWrite` 前先 `grep -l 'CompleteModel' RISCVSched*.td`。
2. **mca 测试 autogenerated 就直接提交**。`update_mca_test_checks.py` 生成的是现状；如果模型本身错了，测试会把错误固化。至少抽查 latency/资源分组是否符合预期。
3. **在 `.mir` 里写 `# CHECK`**。解析失败 + `not` 假通过；用 `; CHECK`，并且负向测试不要 `2>&1` 喂给 FileCheck。
4. **标题带 issue 号或超过 72 字符**。issue 放 body 的 `Fixes #N`；标题只写 what。
5. **把行为改动藏在 NFC 里**。NFC 只允许不改变生成代码的重构；sched model 的任何资源/延迟改动都不是 NFC。
6. **一个 PR 混多个模型**。修 u74 的 `fmv` 管道，就只改 `WriteFMov*`；顺手重命名别的 pipe 会让 review 无法聚焦。
7. **没有同步上游就 push**。reviewer 看到 behind 会要求 rebase 重测；用 `--force-with-lease`，不要 `--force`。

## 动手练习

1. 读 `78b651a2cba9` 的完整 diff。回答：这 6 个 `SchedWrite` 分别被哪些指令引用？如果只改 `WriteFMovI32ToF32`，mca 测试会红在哪一行？
2. 给一个假想的 patch 写 commit message：把 `SiFive7` 的 `WriteIALU` latency 从 3 改成 2，影响 u74 的整数链。要求标题 ≤60 字符、body 写出来源与影响面、带 `Assisted-by`。
3. 在本机造一个 `# CHECK` 的 `.mir`，跑 `not llc ... 2>&1 | FileCheck` 复现假通过；再用 `; CHECK` 重写，确认测试变成真失败/真通过。
4. 跑一次 `pre-pr-check.sh`（可以在一份临时 worktree 上），记录十项里哪些是 FAIL、哪些是 warn，并解释第 5 项为什么要指定 `upstream/main`。
5. **guided**：挑一个 `llvm/test/tools/llvm-mca/RISCV/` 下的 `.test`，用 `update_mca_test_checks.py` 重新生成，确认无 diff；然后改一个 `Latency`，看测试红在哪。
6. 找一条 `[RISCV][NFC]` 提交，验证它的 diff 真的只改名字/结构，没有改数字。

## 重点整理

一个 sched model patch 的最小交付物：

- [ ] `RISCVSchedule.td` 的 `SchedWrite`/`SchedRead`（如果新增类）
- [ ] 每个受影响 CPU 的 `WriteRes`/`ReadAdvance`（`CompleteModel` 全覆盖）
- [ ] 指令的 `Sched<[...]>` 绑定
- [ ] `llvm-mca` 的 `.test`（`-instruction-tables=full`）
- [ ] 选择/顺序相关的 lit 测试（`.ll` 优先，`.mir` 用 `; CHECK`）
- [ ] commit message：what + why + 影响面 + 来源
- [ ] `pre-pr-check.sh` PASS

review 的三层证据：

| 层 | 证据 | 回答什么问题 |
|---|---|---|
| 模型自洽 | TableGen 全量构建、mca 表 | 有没有漏、有没有矛盾 |
| 行为覆盖 | lit（选择/顺序）、mca（资源） | 改了哪些指令/CPU |
| 现实依据 | 手册、实测、目标板 perf | 数字对不对 |

- sched model 的 review 是「证据审查」，不是「代码审查」。
- 测试比代码多是正常的；mca 的粒度决定了这一点。
- NFC 只用于不改生成代码的重构；模型数字改动永远不是 NFC。
- 本地门禁能挡掉机械问题，语义问题仍要靠第 27 章的归因链。
