## 27.1 测试分布与本树基线

以下数字用 `llvm-lit --show-tests` 在本树实测（不是文件数估算）：

| 目录 | 用例数 | 说明 |
|---|---:|---|
| `llvm/test/CodeGen/LoongArch` | **978** | SelectionDAG、机器 pass、ABI |
| `llvm/test/MC/LoongArch` | **335** | 汇编/反汇编/编码/重定位 |
| `lld/test/ELF` 中文件名含 loongarch | **48** | 链接、relaxation、TLS |
| `clang/test/CodeGen/LoongArch` | **48** | clang IR 生成（ABI、builtin） |
| `clang/test/Driver` 中文件名含 loongarch | **28** | driver 选项 |

对比：整个 `lld/test/ELF` 是 2,049 个用例，`clang/test/Driver` 是 1,532 个。
2026-11-08 在本树重跑，五个子集全绿：

```text
CodeGen/LoongArch        978 / 978 passed
MC/LoongArch             335 / 335 passed
lld/test/ELF (filter)     48 /  48 passed
clang/CodeGen/LoongArch   48 /  48 passed
clang/Driver  (filter)    28 /  28 passed
```
**LoongArch 在 lld 里只占 2.3%**，但 relaxation 相关的用例密度很高——这就是 Ch 12/29 那类 bug 容易漏的原因。

每个目录还有一个 `lit.local.cfg`：

```python
# llvm/test/MC/LoongArch/lit.local.cfg
if not "LoongArch" in config.root.targets:
    config.unsupported = True
```

`llvm/test/CodeGen/LoongArch/lit.local.cfg` 同样存在。**如果构建时没开 `LoongArch`，这 1,313 个 LLVM 用例会被标记 unsupported 而不是 failed**——测试报告仍然是绿的。这就是本课一开始必须先检查 `llvm-config --targets-built` 的原因。

## 27.2 一个 CodeGen 测试的骨架

```llvm
; RUN: llc --mtriple=loongarch32 -mattr=+d < %s | FileCheck %s --check-prefixes=CHECK,LA32
; RUN: llc --mtriple=loongarch64 -mattr=+d < %s | FileCheck %s --check-prefixes=CHECK,LA64

define signext i32 @bittest_7_i32(i32 signext %a) nounwind {
; LA32-LABEL: bittest_7_i32:
; LA64-LABEL: bittest_7_i32:
  %shr = lshr i32 %a, 7
  ...
}
```

三个惯例：

1. **同一个 `.ll` 同时跑 LA32/LA64**，用 `CHECK,LA32` / `CHECK,LA64` 双前缀区分。LoongArch 的 i32/i64 差异（Ch 13 的 legalization）大多靠这种方式锁住。
2. **`-mattr=+d` 而不是 `-march=`**：`llc` 没有 `-march` 选项，feature 用 `-mattr`。
3. **`signext`/`zeroext` 要写在 IR 里**：ABI 的扩展语义是测试的一部分，不是装饰。

单文件运行实测：

```text
$ llvm-lit llvm/test/CodeGen/LoongArch/bittest.ll
PASS: LLVM :: CodeGen/LoongArch/bittest.ll (1 of 1)
  Passed: 1 (100.00%)
```

注意 `llvm-lit` 接受**源码树路径**也可以，因为 site config 里已经注册了 build 的 test 根；用绝对路径最稳。

## 27.3 `update_llc_test_checks.py`：先纠正一个过时的用法

网上很多教程写：

```bash
update_llc_test_checks.py --llvm-bin=/path/to/build/bin test.ll
```

本树已经**不支持**这个参数：

```text
update_llc_test_checks.py: error: unrecognized arguments: --llvm-bin=...
```

脚本改成从 `PATH` 里找 `llc`（以及 `llvm-mc`、`opt` 等）。正确用法：

```bash
PATH=$T/bin:$PATH python3 llvm/utils/update_llc_test_checks.py test.ll
```

`--help` 里仍然保留 `--llc-binary`，可以显式指定单个工具；但 `--llvm-bin` 这个“一次指定整个 bin 目录”的旧接口没了。

### 实测：给一个测试追加函数后自动生成断言

把 `bittest.ll` 复制到 `/tmp/upd1`，追加：

```llvm
define i64 @demo_add(i64 %a, i64 %b) {
  %r = add i64 %a, %b
  ret i64 %r
}
```

运行脚本后，新函数自动获得两套断言：

```text
; LA32-LABEL: demo_add:
; LA32:       # %bb.0:
; LA32-NEXT:    add.w $a1, $a1, $a3
; LA32-NEXT:    add.w $a2, $a0, $a2
; LA32-NEXT:    sltu $a0, $a2, $a0
; LA32-NEXT:    add.w $a1, $a1, $a0
; LA32-NEXT:    move $a0, $a2
; LA32-NEXT:    ret
;
; LA64-LABEL: demo_add:
; LA64:       # %bb.0:
; LA64-NEXT:    add.d $a0, $a0, $a1
; LA64-NEXT:    ret
```

这段输出本身就是 Ch 13 的复习材料：**LA32 上一个 i64 加法要 4 条 `add.w` + `sltu` 进位**，LA64 只要 1 条 `add.d`。

对未修改的测试再跑一次脚本，**输出零 diff**（实测）——说明脚本是幂等的，可以安全地放进“改完代码后批量刷新”的流程。

### 覆盖率

```text
$ grep -rl update_llc_test_checks llvm/test/CodeGen/LoongArch | wc -l
735
```

978 个用例里 735 个用了自动生成（75%）。文件头会写：

```text
; NOTE: Assertions have been autogenerated by utils/update_llc_test_checks.py UTC_ARGS: --version 6
```

`UTC_ARGS` 的 `--version` 在本树分布是 3/4/5/6 都有。**不要手改 `UTC_ARGS` 行**，它是脚本下次运行的输入。

## 27.5 lld 测试：为什么用 `yaml2obj` 而不是汇编器

本课修的 #239812 的回归测试（`lld/test/ELF/loongarch-tls-le-relax-order.s`）开头是：

```text
# REQUIRES: loongarch
# RUN: yaml2obj %s -o %t.o
# RUN: ld.lld %t.o -o %t
# RUN: llvm-objdump --no-print-imm-hex -d --no-show-raw-insn %t | FileCheck %s
```

关键在 `yaml2obj`：这个 bug 只在 **`R_LARCH_RELAX` 排在配对重定位之前**时触发，而汇编器总是按“重定位在前、标记在后”的顺序发。用 `.s` + `llvm-mc` 根本造不出反例，只能直接用 YAML 描述 ELF 的 `.rela.text` 顺序。

**这是 lld 测试的通用模式**：凡是“顺序/偏移/非法组合”类 bug，都用 `yaml2obj` 精确控制输入。

单文件运行：

```text
$ llvm-lit lld/test/ELF/loongarch-tls-le-relax-order.s
PASS: lld :: ELF/loongarch-tls-le-relax-order.s (1 of 1)
```

## 27.6 clang 测试：`update_cc_test_checks.py`

`clang/test/CodeGen/LoongArch` 的 48 个用例里 24 个用了 `update_cc_test_checks.py`，检查的是 **IR** 而不是汇编：

```text
// RUN: %clang_cc1 -triple loongarch64 -emit-llvm %s -o - | FileCheck %s
```

注意是 `%clang_cc1`（前端直接调用），不是 `%clang`（driver）。ABI 的 `signext`、`byval`、`sret` 属性都在这一层锁定；driver 选项则在 `clang/test/Driver` 用 `%clang -###` 检查参数文本。

## 27.7 跑子集的正确姿势

```bash
T=/home/ubuntu/llvm/builds/ct-instr-trunk
R=/home/ubuntu/llvm/trees/ct-instr-trunk

# 单文件
$T/bin/llvm-lit $R/llvm/test/CodeGen/LoongArch/bittest.ll

# 整个目录（978 个）
$T/bin/llvm-lit -q $R/llvm/test/CodeGen/LoongArch

# 过滤
$T/bin/llvm-lit -q $R/llvm/test/CodeGen/LoongArch --filter='tls|relax'

# lld 子集
$T/bin/llvm-lit -q $R/lld/test/ELF --filter=loongarch
```

`--filter` 匹配的是用例名（路径 + 方法名），不是文件内容。想按内容筛，先 `--show-tests | grep`。

## 27.8 反直觉点

1. **`lit.local.cfg` 会让整目录变成 unsupported**，报告仍然全绿。
2. **`--llvm-bin` 已被移除**，只能靠 `PATH`。
3. **`llc` 没有 `-march`**：测试里是 `--mtriple` + `-mattr`。
4. **`update_llc_test_checks.py` 对未改测试是零 diff**，可以放心反复跑。
5. **lld 的 relaxation 测试用 `yaml2obj`**，因为汇编器造不出“标记在前”的顺序。
6. **clang CodeGen 测试用 `%clang_cc1` 而不是 `%clang`**。
7. **测试数量不是文件数量**：`--show-tests` 会把一个 `.ll` 里的多 RUN 算成多个用例。

## 27.11 延伸阅读

1. **官方 regression test 结构** — `llvm/docs/TestingGuide.md`
   - 读什么：`## Regression test structure` 下的 `### Writing new regression tests`、`### Generating assertions in regression tests`、`### Best practices for regression tests`、`### Constraining test execution`。
   - 学到什么：本章的 RUN/CHECK 骨架只是最小形态；官方指南补上 `REQUIRES`/`UNSUPPORTED` 的使用、测试命名、fragile test 的取舍，以及自动生成断言脚本的边界。读完能把 27.1 的 `lit.local.cfg` 和 27.3 的 `update_llc_test_checks.py` 放回完整测试规范里。
   - 前提：读过 27.1–27.3，跑过至少一个 `llvm-lit` 用例。

2. **lit 的选择器与本地配置** — `llvm/docs/CommandGuide/lit.md`
   - 读什么：`## SELECTION OPTIONS` 的 `--filter`/`--filter-out`/`--filter-failed`、`## OUTPUT OPTIONS` 的 `--show-tests`/`--show-used-features`，以及 `## LIT INFRASTRUCTURE` 的 `### LOCAL CONFIGURATION FILES`。
   - 学到什么：精确控制“跑哪些用例”、用 `--show-used-features` 查看 `REQUIRES`/`UNSUPPORTED` 声明了哪些 feature，并理解 `lit.local.cfg` 的发现顺序。本章 27.7 只给了命令，这里补上 lit 的发现模型，能解释为什么“全绿”可能意味着整目录没跑。
   - 前提：用过 `llvm-lit`；读过 27.1、27.7。

3. **FileCheck 的前缀与顺序约束** — `llvm/docs/CommandGuide/FileCheck.md`
   - 读什么：`### The FileCheck -check-prefixes option`、`### The "CHECK-NEXT:" directive`、`### The "CHECK-LABEL:" directive`、`### The "CHECK-DAG:" directive`。
   - 学到什么：本章双 triple 测试为什么用 `CHECK,LA32`/`CHECK,LA64`；什么时候该用 `NEXT` 锁指令顺序、什么时候用 `DAG` 容忍调度变化。27.2 只说了“双前缀”，这里补上匹配语义和误用后果。
   - 前提：读过 27.2、27.4。

4. **MC 测试里的 relax 序列** — `llvm/test/MC/LoongArch/Relocations/`
   - 读什么：目录下的 `relax-tls-le.s`、`relax-align.s`、`relax-attr.s`，重点看 `# RUN:` 行如何组合 `llvm-mc` 与 `llvm-readobj`/`llvm-objdump`，以及汇编输入里 `R_LARCH_RELAX` 的出现位置。
   - 学到什么：看清汇编器实际把 marker 放在配对重定位之后，这解释了 27.5 为什么 lld 的顺序 bug 只能用 `yaml2obj` 构造；同时补上“MC 测试如何同时锁编码与重定位”的写法。本章只列了目录名，这里补上具体文件。
   - 前提：读过 27.4–27.5，知道 `llvm-mc` 的 `-show-encoding`/`-filetype=obj` 用法。
