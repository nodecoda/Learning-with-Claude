# Ch 12 — lit.site.cfg 与 CMake：构建树怎么接进来

> **目标**：能说清 `lit.site.cfg.py.in` 到 `build/test/lit.site.cfg.py` 的生成过程，读懂 `configure_lit_site_cfg()`、`add_lit_target()`、`add_lit_testsuite()` 的参数，并能给自己的项目写一份最小 CMake 集成。

> **环境**：LLVM `24.0.0git` / lit `24.0.0dev`；构建目录为 `/home/ubuntu/llvm/builds/pr-lane`。本章在 `/tmp` 用 CMake 3.31.10 真实生成了一个 toy 项目并跑了 `check-toy`。`check-llvm` 的完整运行**未实测**，只读取了 `build.ninja` 里的真实命令。

## 12.1 为什么需要 site cfg

源码树里的 `llvm/test/lit.cfg.py` 是「suite 定义」：suffixes、test format、features、substitutions。但它不知道：

- 这次构建的 `opt` 在哪个绝对路径；
- 这次构建启用了哪些 target；
- 有没有 assertions、zlib、zstd、plugins；
- 同一个源码目录被几个构建目录同时使用。

这些信息每次构建都不同，不能写进源码。于是 CMake 在**构建树**里生成一份 site cfg：

```
源码树（共享）                       构建树（每个 build 一份）
llvm/test/lit.cfg.py                 build/test/lit.site.cfg.py
llvm/test/lit.site.cfg.py.in  ──►    （由 CMake configure_file 生成）
```

真实链路：

```
build/test/lit.site.cfg.py          ← 先被 lit 发现（site 优先）
        │  lit_config.load_config()
        ▼
llvm/test/lit.cfg.py                ← 再加载源码配置
        │
        ▼
各目录 lit.local.cfg.py             ← 最后按目录覆盖
```

所以「site cfg 是 CI 的额外配置」是误解。它是构建树的**主入口**；源码树的 `lit.cfg.py` 反而是被它回加载的。

## 12.2 模板与生成物

`llvm/test/lit.site.cfg.py.in` 的第一行是占位符：

```python
# llvm/test/lit.site.cfg.py.in:1
@LIT_SITE_CFG_IN_HEADER@
```

中间是一串 `@VAR@`：

```python
# llvm/test/lit.site.cfg.py.in:5-32（节选）
config.host_triple = "@LLVM_HOST_TRIPLE@"
config.target_triple = "@LLVM_TARGET_TRIPLE@"
config.llvm_src_root = path(r"@LLVM_SOURCE_DIR@")
config.llvm_obj_root = path(r"@LLVM_BINARY_DIR@")
config.llvm_tools_dir = lit_config.substitute(path(r"@LLVM_TOOLS_DIR@"))
...
config.targets_to_build = "@TARGETS_TO_BUILD@"
config.native_target = "@LLVM_NATIVE_ARCH@"
```

最后回加载源码：

```python
# llvm/test/lit.site.cfg.py.in:79-84
import lit.llvm
lit.llvm.initialize(lit_config, config)

# Let the main config do the real work.
lit_config.load_config(
    config, os.path.join(config.llvm_src_root, "test/lit.cfg.py"))
```

生成物在 `build/test/lit.site.cfg.py`。真实开头（节选）：

```
# Autogenerated from /home/ubuntu/llvm/trees/pr-lane/llvm/test/lit.site.cfg.py.in
# Do not edit!

# Allow generated file to be relocatable.
import os
import platform
def path(p): ...   # 完整定义见 12.2.1

config.host_triple = "x86_64-unknown-linux-gnu"
...
config.llvm_src_root = path(r"../../../trees/pr-lane/llvm")
config.llvm_obj_root = path(r"..")
config.llvm_tools_dir = lit_config.substitute(path(r"../bin"))
```

两个关键点：

1. `@LIT_SITE_CFG_IN_HEADER@` 不是普通变量，它被替换成「注释 + `path()` 函数定义」。所以你可以在生成物里直接用 `path(...)`，也可以 `import os`。
2. 路径被写成相对路径（`../../../trees/pr-lane/llvm`、`../bin`），再交给 `path()` 相对 `__file__` 解析。这样整个构建目录可以移动，不会因为绝对路径写死而失效。

### 12.2.1 `path()` 到底做什么

`path()` 由 `AddLLVM.cmake:2184-2195` 拼进 header。生成物里就是前面看到的那段：

```python
def path(p):
    if not p: return ''
    if platform.system() == 'Windows':
        return os.path.abspath(os.path.join(os.path.dirname(__file__), p))
    else:
        return os.path.realpath(os.path.join(os.path.dirname(__file__), p))
```

`path(r"../bin")` 等价于「相对这个 site cfg 文件所在目录，解析 `../bin`」。Linux 上走 `realpath`，会展开符号链接；Windows 上走 `abspath`，保留盘符。

### 12.2.2 `@VAR@` 没定义会怎样

`configure_file(... @ONLY)` 只替换 `@VAR@` 形式。**未定义的变量会被替换成空字符串，不会报错**。实测：在模板里加 `config.not_set = "@NOT_SET@"`，生成物是：

```python
config.not_set = ""
```

这比「报错」更危险：配置能加载，但值是空的，错误会推迟到运行期。所以模板里每个 `@VAR@` 都要能在 CMake 里找到来源。

## 12.3 `configure_lit_site_cfg()` 做了什么

函数从 `AddLLVM.cmake:2208` 开始。逐段看。

```cmake
# AddLLVM.cmake:2208-2214
function(configure_lit_site_cfg site_in site_out)
  cmake_parse_arguments(ARG "" "" "MAIN_CONFIG;PATHS" ${ARGN})

  if ("${ARG_MAIN_CONFIG}" STREQUAL "")
    get_filename_component(INPUT_DIR ${site_in} DIRECTORY)
    set(ARG_MAIN_CONFIG "${INPUT_DIR}/lit.cfg")
  endif()
```

- `site_in`：模板路径。
- `site_out`：生成物路径。
- `MAIN_CONFIG`：源码树的 suite 配置；不写就默认模板同目录的 `lit.cfg`。
- `PATHS`：后面会讲，是一组「需要转成相对路径的 CMake 变量名」。

接着准备一批通用变量（`AddLLVM.cmake:2216-2255`）：`TARGETS_TO_BUILD`、`SHLIBEXT`、`LLVM_SOURCE_DIR`、`LLVM_BINARY_DIR`、`LLVM_TOOLS_DIR`、`LLVM_LIBS_DIR`、`SHLIBDIR`、`HOST_OS`、`HOST_ARCH`、`HOST_CC`、`HOST_CXX`、`HOST_LDFLAGS` 等。然后拼 header：

```cmake
# AddLLVM.cmake:2257-2260
string(CONCAT LIT_SITE_CFG_IN_HEADER
  "# Autogenerated from ${site_in}\n# Do not edit!\n\n"
  "${LLVM_LIT_PATH_FUNCTION}"
  )
```

如果设置了 `LLVM_TARGET_TRIPLE_ENV`，还会往 header 里追加一段「从环境变量读 target triple」的代码（`AddLLVM.cmake:2262-2274`）。

### 12.3.1 `PATHS` 与相对路径

`PATHS` 里的变量会被 `make_paths_relative()` 转成相对于**生成物所在目录**的路径：

```cmake
# AddLLVM.cmake:2276-2309（节选）
if (ARG_PATHS)
  foreach(path ${ARG_PATHS})
    list(APPEND ARG_PATH_VALUES "${${path}}")
  endforeach()
  get_filename_component(OUTPUT_DIR ${site_out} DIRECTORY)
  make_paths_relative(
      ARG_PATH_VALUES_RELATIVE "${OUTPUT_DIR}" "${ARG_PATH_VALUES}")
  ...
endif()
```

`make_paths_relative()` 在 `AddLLVM.cmake:2152-2179`，实际用 Python 的 `os.path.relpath()`；如果路径跨盘符或含符号链接，就保留绝对路径。所以：

- 模板里写 `path(r"@LLVM_TOOLS_DIR@")` 的变量，应该放进 `PATHS`；
- 模板里写 `"@CMAKE_SOURCE_DIR@"` 这种不在 `PATHS` 里的，会保留绝对路径；
- 放进 `PATHS` 后，生成物里可能是 `../bin`，`path()` 负责还原。

最后 `configure_file(${site_in} ${site_out} @ONLY)`（`AddLLVM.cmake:2309`），并把「源码主配置 + 生成的 site 配置」记进全局属性 `LLVM_LIT_CONFIG_FILES`（`AddLLVM.cmake:2311-2315`）。

### 12.3.2 `build_mode` 从哪来

多配置生成器（Visual Studio、Xcode）里，`CMAKE_CFG_INTDIR` 不是 `.`。`add_lit_target()` 会追加：

```cmake
# AddLLVM.cmake:2382-2384
if (NOT CMAKE_CFG_INTDIR STREQUAL ".")
  list(APPEND LIT_ARGS --param build_mode=${CMAKE_CFG_INTDIR})
endif ()
```

`configure_lit_site_cfg()` 里 `set_llvm_build_mode()` 把 `LLVM_BUILD_MODE` 设成 `%(build_mode)s`（`AddLLVM.cmake:2138-2145`），site cfg 里的路径就用 `%(build_mode)s` 占位。lit 启动时 `lit_config.substitute()`（Ch 10）把 `--param build_mode=...` 填进去。单配置生成器（Ninja/Makefiles）里 `CMAKE_CFG_INTDIR == "."`，不会加这个参数，所以普通 Linux 构建看不到 `build_mode`。

## 12.4 回加载源码配置与 `lit.llvm.initialize()`

site cfg 的最后两行：

```python
# llvm/test/lit.site.cfg.py.in:79-84
import lit.llvm
lit.llvm.initialize(lit_config, config)

lit_config.load_config(
    config, os.path.join(config.llvm_src_root, "test/lit.cfg.py"))
```

`lit.llvm.initialize()` 的实现只有三行（`llvm/utils/lit/lit/llvm/__init__.py:6-9`）：

```python
def initialize(lit_config, test_config):
    global llvm_config

    llvm_config = config.LLVMConfig(lit_config, test_config)
```

它做两件事：

1. 创建全局 `llvm_config`，让源码 `lit.cfg.py` 可以直接 `from lit.llvm import llvm_config` 使用。
2. `LLVMConfig.__init__` 顺手加平台/sanitizer feature、在 Windows 上调整 PATH、从宿主拿 `ASAN_OPTIONS` 等变量（`llvm/config.py:27-140`）。

然后 `lit_config.load_config()` 调用 `config.load_from_path()`（Ch 10 的 `LitConfig.py:167-172`），把源码 `lit.cfg.py` `exec` 到**同一个 `config` 对象**上。所以源码配置看到的 `config` 已经带着 site cfg 注入的 `llvm_src_root`、`llvm_obj_root`、`llvm_tools_dir`、`targets_to_build`。

### 12.4.1 为什么不能在源码树直接跑

直接跑源码树的 `lit.cfg.py`，它第一行就会读 site cfg 才有的字段：

```bash
cd /home/ubuntu/llvm/llvm-project
python3 llvm/utils/lit/lit.py llvm/test/Transforms/InstCombine/add.ll
```

真实输出（节选）：

```
lit.py: .../TestingConfig.py:168: fatal: unable to parse config file
'/home/ubuntu/llvm/llvm-project/llvm/test/lit.cfg.py', traceback: ...
  File ".../llvm/test/lit.cfg.py", line 26, in <module>
    if config.enable_profcheck
AttributeError: 'TestingConfig' object has no attribute 'enable_profcheck'
EXIT=2
```

`enable_profcheck` 来自 site cfg（`lit.site.cfg.py.in:65`），源码树里没有。这不是「路径不对」，而是「你跳过了 site cfg 这一层」。

## 12.5 `add_lit_target()` / `add_lit_testsuite()` / `add_lit_testsuites()`

### 12.5.1 `add_lit_target(target comment ...)`

签名在 `AddLLVM.cmake:2378-2379`，参数：

- `target`：CMake target 名。
- `comment`：构建时显示的注释。
- `PARAMS`：每个都变成 `--param NAME=VALUE`。
- `DEPENDS`：依赖的 CMake target。
- `ARGS`：lit 参数。
- 位置参数：传给 lit 的测试路径。

核心拼装：

```cmake
# AddLLVM.cmake:2380-2398（节选）
set(LIT_ARGS "${ARG_ARGS} ${LLVM_LIT_ARGS}")
separate_arguments(LIT_ARGS)
if (NOT CMAKE_CFG_INTDIR STREQUAL ".")
  list(APPEND LIT_ARGS --param build_mode=${CMAKE_CFG_INTDIR})
endif ()
...
set(LIT_COMMAND "${Python3_EXECUTABLE};${lit_base_dir}/${lit_file_name}")
list(APPEND LIT_COMMAND ${LIT_ARGS})
foreach(param ${ARG_PARAMS})
  list(APPEND LIT_COMMAND --param ${param})
endforeach()
```

最终命令顺序：

```
python3 <lit 脚本> [ARG_ARGS] [LLVM_LIT_ARGS] [--param build_mode=...] [--param PARAMS...] <测试路径...>
```

注意 `ARG_ARGS` 在前、`LLVM_LIT_ARGS` 在后；`PARAMS` 在两者之后。`LIT_OPTS` 不在 CMake 里，它在 lit 启动后追加（见 12.6）。

### 12.5.2 `add_lit_testsuite(target comment ...)`

签名在 `AddLLVM.cmake:2465-2466`，参数是 `target`、`comment`、`EXCLUDE_FROM_CHECK_ALL`、`PARAMS`、`DEPENDS`、`ARGS` 和位置参数。它做两件事：

1. 如果不在 `EXCLUDE_FROM_CHECK_ALL`，把测试路径/PARAMS/DEPENDS/ARGS 登记到当前 umbrella（`check-all` 之类）的全局属性里（`AddLLVM.cmake:2469-2478`）。
2. 调用 `add_lit_target()` 创建同名 target（`AddLLVM.cmake:2481-2486`）。

LLVM 的 `check-llvm` 就是一行：

```cmake
# llvm/test/CMakeLists.txt:281-285
add_lit_testsuite(check-llvm "Running the LLVM regression tests"
  ${CMAKE_CURRENT_BINARY_DIR}
  ${exclude_from_check_all}
  DEPENDS ${LLVM_TEST_DEPENDS} UnitTests
  )
```

位置参数是**构建树的测试目录** `${CMAKE_CURRENT_BINARY_DIR}`，不是 target 名。`DEPENDS` 才是 target 名列表。把路径写进 `DEPENDS`、把 target 名当位置参数，都会在构建期出问题。

生成出来的真实命令（`build.ninja`，为可读性折行）：

```
COMMAND = cd /home/ubuntu/llvm/builds/pr-lane/test && \
  /usr/bin/python3.10 /home/ubuntu/llvm/builds/pr-lane/./bin/llvm-lit -sv \
  /home/ubuntu/llvm/builds/pr-lane/test
DESC = Running the LLVM regression tests
```

`-sv` 就是 `LLVM_LIT_ARGS` 的默认值：

```cmake
# llvm/CMakeLists.txt:846-853
set(LIT_ARGS_DEFAULT "-sv")
if (MSVC_IDE OR XCODE)
  set(LIT_ARGS_DEFAULT "${LIT_ARGS_DEFAULT} --no-progress-bar")
endif()
set(LLVM_LIT_ARGS "${LIT_ARGS_DEFAULT}" CACHE STRING "Default options for lit")
```

### 12.5.3 `add_lit_testsuites(project directory ...)`

签名在 `AddLLVM.cmake:2489-2496`。它用 `file(GLOB_RECURSE ...)` 扫目录，给每个子目录建一个 `check-<project>-<dir>` target；跳过路径里含 `Inputs`/`Output` 的目录，`SKIP` 里的正则也跳过。

```cmake
# AddLLVM.cmake:2505-2545（节选）
file(GLOB_RECURSE to_process LIST_DIRECTORIES true ${directory}/*)
foreach(lit_suite ${to_process})
  ...
  string(FIND ${lit_suite} Inputs is_inputs)
  string(FIND ${lit_suite} Output is_output)
  if (NOT (is_inputs EQUAL -1 AND is_output EQUAL -1))
    continue()
  endif()
  add_lit_target("check-${name_var}" "Running lit suite ${lit_suite}"
    ${lit_args} PARAMS ${ARG_PARAMS} DEPENDS ${ARG_DEPENDS} ARGS ${ARG_ARGS})
endforeach()
```

LLVM 的调用在 `llvm/test/CMakeLists.txt:290-295`，带 `SKIP "^FileCheck" "^TableGen" "^Unit"`。这会生成大量 `check-llvm-analysis`、`check-llvm-codegen-x86` 之类的子 target。`check-llvm` 是 umbrella，`add_lit_testsuites` 生成的是按目录切的细粒度 target。

## 12.6 `LLVM_EXTERNAL_LIT`、`LLVM_LIT_ARGS`、`LIT_OPTS` 的优先级

| 名字 | 类型 | 作用 | 谁覆盖谁 |
|---|---|---|---|
| `LLVM_EXTERNAL_LIT` | CMake cache 变量 | 指定用哪个 lit 脚本 | 只决定「跑哪个 lit」，不决定 lit 参数 |
| `LLVM_LIT_ARGS` | CMake cache 变量 | 给所有 `check-*` target 的默认参数 | 被 `LIT_OPTS` 覆盖 |
| `LIT_OPTS` | 环境变量 | 用户临时追加/覆盖 lit 参数 | 在 CLI 之后解析，最后赢 |

`LLVM_EXTERNAL_LIT` 的处理在 `get_llvm_lit_path()`（`AddLLVM.cmake:2326-2350`）：如果它非空且文件存在，就用它的目录和文件名；如果路径不存在，只警告一次，然后回退到构建树自己的 `llvm-lit`。真实警告：

```
CMake Warning at .../AddLLVM.cmake:2343 (message):
  LLVM_EXTERNAL_LIT set to /no/such/llvm-lit, but the path does not exist.
```

`LIT_OPTS` 的解析在 `cl_arguments.py:538-539`：

```python
# LIT is special: environment variables override command line arguments.
env_args = shlex.split(os.environ.get("LIT_OPTS", ""))
...
args, time_tests = _extract_time_tests_args(sys.argv[1:] + env_args)
```

`env_args` 拼在 `sys.argv[1:]` **后面**，argparse 对重复的标量选项取最后一个。所以 `LIT_OPTS` 覆盖命令行。实验：

```bash
LIT_OPTS=--test-output=all \
  python3 /home/ubuntu/llvm/llvm-project/llvm/utils/lit/lit.py \
  --test-output=off tests/hello.test
```

真实输出仍然打印 `# executed command:` 和 `# | toy`，说明 `all` 生效；反过来把两个值对调（`LIT_OPTS=--test-output=off` + CLI `--test-output=all`）只打印 PASS 摘要。这与 lit 自测 `llvm/utils/lit/tests/lit-opts.py` 的断言一致。

## 踩雷集锦

| 错误直觉 | 正确认识 |
|---|---|
| 「在源码树跑 `lit llvm/test` 也行」 | 不行。源码 `lit.cfg.py` 依赖 site cfg 注入的 `enable_profcheck` 等字段，直接跑会 `AttributeError`，退出码 2。 |
| 「`@VAR@` 没定义会报错」 | `configure_file(... @ONLY)` 会把未定义变量替换成空字符串，配置能加载，错误推迟到运行期。 |
| 「`LLVM_EXTERNAL_LIT` 指向哪都行」 | 路径不存在时只警告一次，然后回退到构建树的 `llvm-lit`；你以为在用外部 lit，其实没有。 |
| 「`LIT_OPTS` 会被命令行覆盖」 | 相反。`LIT_OPTS` 拼在 `sys.argv` 后面，标量选项取最后一个，所以它覆盖命令行。 |
| 「`add_lit_testsuite` 的位置参数是 target」 | 位置参数是测试路径；target 名是第一个参数，依赖 target 放 `DEPENDS`。 |
| 「`PATHS` 里的变量会自动变绝对路径」 | 它先被 `make_paths_relative()` 转成相对路径，再由生成的 `path()` 还原；不写 `path()` 就拿到相对路径。 |
| 「`add_lit_testsuites` 会生成一个万能 target」 | 它按目录生成许多 `check-<project>-<dir>`；umbrella 要另外用 `add_lit_testsuite` 或 `umbrella_lit_testsuite_*`。 |

## 重点整理

- site cfg 是构建树的主入口：`lit.site.cfg.py.in` 经 `configure_lit_site_cfg()` 生成 `build/test/lit.site.cfg.py`，再 `load_config()` 回源码 `lit.cfg.py`。
- `@LIT_SITE_CFG_IN_HEADER@` 注入注释和 `path()`；`PATHS` 里的变量先转相对路径，再由 `path()` 相对 `__file__` 还原。
- `@VAR@` 未定义会变成空字符串，不会报错；这是最常见的「配置看起来生成了，运行期才炸」。
- `lit.llvm.initialize()` 创建全局 `llvm_config`，给源码配置提供 `with_environment()`、`use_default_substitutions()` 等工具。
- `add_lit_target()` 拼命令：`ARG_ARGS` → `LLVM_LIT_ARGS` → `--param build_mode=...` → `PARAMS` → 测试路径。
- `add_lit_testsuite()` 创建 `check-*` 并登记 umbrella；`add_lit_testsuites()` 按目录批量生成子 target。
- 优先级：`LLVM_EXTERNAL_LIT` 只选 lit；`LLVM_LIT_ARGS` 是默认参数；`LIT_OPTS` 最后解析，覆盖命令行。
