# Ch 11 ODS 入门：定义第一个 Op

> **目标**：把一张 `.td` 声明表变成可编译的 C++ op 类型。学完本章，你能写出最小的 `toy.add`，用 `mlir-tblgen` 亲手生成 `.h.inc` 与 `.cpp.inc`，并说清 `arguments`、`results`、`assemblyFormat`、`Pure` 各自在生成物里留下了什么。

## 为什么需要这个？

在 Ch 2 我们看到过 `Operation` 的对象模型：name、operands、results、attributes、regions 全是运行时的通用容器。可写 pass 时你想要的是 `addOp.getLhs()`，不是 `op->getOperand(0)`；是 `AddOp::create(builder, loc, type, lhs, rhs)`，不是手拼 `OperationState` 再 `addOperands` 两次。

这中间的桥就是 **ODS（Operation Definition Specification）**：你用 TableGen 描述"这个 op 叫什么、吃几个操作数、结果是什么类型、文本怎么写"，`mlir-tblgen` 生成 C++ 类，把通用容器包装成强类型接口。

手写这条路也不是不行：`getOperationName()`、`parse`/`print`、`verifyInvariants()`、若干 `build` 重载、operand/result 下标映射、properties 的序列化与 hash，一个 op 就是两三百行。写十个 op 就是重复劳动，而且每一处手写的类型检查都可能和 `print` 里的假设不一致。

ODS 的价值不是"少打字"，而是**让声明成为唯一事实来源**：verifier、parser、printer、builder 从同一份声明推导，不可能互相矛盾。代价是你得接受一层间接：`.td` 不是 C++，错误发生在生成期，生成物有固定形状。本章先建立"声明 → 生成物"的对应；Ch 12 加约束与验证；Ch 13 逐段拆生成物。

## 先建立直觉：一张表，两份文件

把 ODS 想成"给 op 建一张登记表"，`mlir-tblgen` 是读表的排版工：

```text
toy.td ── mlir-tblgen -gen-op-decls ──▶ toy.h.inc    类声明（含 Adaptor、build 签名）
       └─ mlir-tblgen -gen-op-defs  ──▶ toy.cpp.inc  类定义（含 build/verify/parse/print）
```

两份文件都不是独立编译单元，而是"等着被 `#include` 的片段"：声明进头文件，定义进 `.cpp`。**同一份 `.td` 跑两次，产出互补的两半**。

`toy.add` 的完整声明如下（`.scratch\tblgen-work\toy.td`，本章所有实验都用它）：

```tablegen
#ifndef TOY_OPS
#define TOY_OPS

include "mlir/IR/OpBase.td"
include "mlir/Interfaces/SideEffectInterfaces.td"

def Toy_Dialect : Dialect {
  let name = "toy";
  let cppNamespace = "::toy";
  let summary = "A tiny tensor dialect used by the course.";
}

class Toy_Op<string mnemonic, list<Trait> traits = []>
    : Op<Toy_Dialect, mnemonic, traits>;

def Toy_AddOp : Toy_Op<"add", [Pure]> {
  let summary = "element-wise addition of two tensors";
  let description = [{
    Adds two tensors of the same shape element-wise.
  }];
  let arguments = (ins TensorOf<[F64]>:$lhs, TensorOf<[F64]>:$rhs);
  let results = (outs TensorOf<[F64]>:$result);
  let assemblyFormat = [{
    $lhs `,` $rhs attr-dict `:` type($lhs) `,` type($rhs) `->` type($result)
  }];
}

#endif
```

29 行（含末尾空行），一个 dialect 加一个 op。下面逐块拆。

### `Dialect`：op 名字的前缀从哪来

`name = "toy"` 决定 op 全名是 `toy.<mnemonic>`；`cppNamespace = "::toy"` 决定生成类落在 `namespace toy` 里。op 只写后缀 `"add"`，全名由 dialect 拼出来——这就是 `getOperationName()` 返回 `"toy.add"` 的原因。

`class Toy_Op<...> : Op<Toy_Dialect, mnemonic, traits>` 是本 dialect 的私有模板，只用来省掉每次重复写 `Toy_Dialect`。官方 Toy 教程同款，不是必需语法。

### `arguments` / `results`：操作数与结果

```tablegen
let arguments = (ins TensorOf<[F64]>:$lhs, TensorOf<[F64]>:$rhs);
let results   = (outs TensorOf<[F64]>:$result);
```

`ins` / `outs` 不是关键字，只是 TableGen 里约定俗成的"列表构造器"。真正重要的是每条声明的形状：`<约束>:$<名字>`。

- `TensorOf<[F64]>` 是 **TypeConstraint**，表示"元素类型为 f64 的 tensor"；
- `$lhs` 是名字，生成 `getLhs()`；
- `ins` 里的顺序就是 operand 下标顺序：`lhs` 是 0，`rhs` 是 1。

名字不是装饰。`getLhs()` 会去 `getODSOperands(0)` 取第一个操作数再 `cast`；`$lhs` 写错位置，`getLhs()` 就取错值，而 C++ 编译期不会报错——两个操作数类型一样。这类 bug 只有 verifier 或运行时能抓。

### `assemblyFormat`：一段格式串，两个函数

```tablegen
let assemblyFormat = [{
  $lhs `,` $rhs attr-dict `:` type($lhs) `,` type($rhs) `->` type($result)
}];
```

这串 DSL 同时生成 parser 与 printer：

- 反引号包住的是字面量（`` `,` ``、`` `:` ``、`` `->` ``），必须原样匹配；
- `$lhs` 表示"在这里解析/打印一个操作数"；
- `attr-dict` 是属性字典的落点，**任何自定义格式都必须有它**（否则 tblgen 直接报错）；
- `type(...)` 声明类型从哪里读。

于是文本形态固定成：

```mlir
%0 = toy.add %a, %b : tensor<2xf64>, tensor<2xf64> -> tensor<2xf64>
```

三个类型都写全了，这不是啰嗦：`resolveOperands` 需要每个操作数的类型才能建 SSA 值引用，少写一个 `type(...)`，parser 就解析不出对应操作数。ODS 不会替你推断，只照格式串生成代码。

## `summary` 与 `description`：不只是注释

```tablegen
let summary = "element-wise addition of two tensors";
let description = [{
  Adds two tensors of the same shape element-wise.
}];
```

它们不参与 C++ 语义，但会生成 `///` 注释，并被 `-gen-op-doc` 抓出来变成方言文档。这一点常被忽略：**文档和代码同源**，不会出现"注释说 f32、代码收 f64"的漂移。

实测（`-gen-op-doc`）：

```powershell
$mlir = "D:\Learning-with-Claude\.scratch\mlir-env\Library\bin"
& "$mlir\mlir-tblgen.exe" -gen-op-doc .scratch\tblgen-work\toy.td `
  -I .scratch\llvm-23.1.4-src\mlir\include -o .scratch\tblgen-work\toy.md
```

实测输出（`toy.md` 节选，末尾的 Operands/Results 表略）：

````markdown
<!-- Autogenerated by mlir-tblgen; don't manually edit -->

### `toy.add` (::toy::AddOp)

_Element-wise addition of two tensors_

Syntax:

```
operation ::= `toy.add` $lhs `,` $rhs attr-dict `:` type($lhs) `,` type($rhs) `->` type($result)
```

Adds two tensors of the same shape element-wise.

Traits: `AlwaysSpeculatableImplTrait`

Interfaces: `ConditionallySpeculatable`, `NoMemoryEffect (MemoryEffectOpInterface)`

Effects: `MemoryEffects::Effect{}`
````

`Syntax:` 那段是 `assemblyFormat` 的规范化回显，不是手写的；改了格式串，文档自动跟着变。`summary` 变成斜体一行，`description` 变成正文——所以 summary 写一句话、description 写细节，别反过来。

## `Pure` trait：一行声明，三个 trait 加一个空函数

`[Pure]` 最容易被当成"性能开关"，它实际做的是**声明这个 op 没有内存副作用且结果可推测**。它定义在 `mlir/Interfaces/SideEffectInterfaces.td`，所以 `.td` 顶部必须 include——漏了就是 `Variable not defined: 'Pure'`（实测）。

对照实验最说明问题。把 `[Pure]` 换成 `[]` 再生成声明，基类列表从：

```cpp
class AddOp : public ::mlir::Op<AddOp, ::mlir::OpTrait::ZeroRegions, ::mlir::OpTrait::OneResult, ::mlir::OpTrait::OneTypedResult<::mlir::TensorType>::Impl, ::mlir::OpTrait::ZeroSuccessors, ::mlir::OpTrait::NOperands<2>::Impl, ::mlir::OpTrait::OpInvariants, ::mlir::ConditionallySpeculatable::Trait, ::mlir::OpTrait::AlwaysSpeculatableImplTrait, ::mlir::MemoryEffectOpInterface::Trait> {
```

变成：

```cpp
class AddOp : public ::mlir::Op<AddOp, ::mlir::OpTrait::ZeroRegions, ::mlir::OpTrait::OneResult, ::mlir::OpTrait::OneTypedResult<::mlir::TensorType>::Impl, ::mlir::OpTrait::ZeroSuccessors, ::mlir::OpTrait::NOperands<2>::Impl, ::mlir::OpTrait::OpInvariants> {
```

（两段都是本机 `-gen-op-decls` 的真实输出。）

差三个：`ConditionallySpeculatable`、`AlwaysSpeculatableImplTrait`、`MemoryEffectOpInterface`。落到 `.cpp.inc` 里还有一个空函数：

```cpp
void AddOp::getEffects(::llvm::SmallVectorImpl<::llvm::SideEffects::EffectInstance<::mlir::MemoryEffects::Effect>> &effects) {
}
```

空函数体就是"没有效应"的机器可读表达。少了 `Pure`，这个函数不生成，接口也没有实现——于是 LICM、CSE、DCE 会保守地认为它可能写内存，不敢移动、不敢删。

**结论**：纯计算 op 一律加 `Pure`，别等性能出问题才回头补。

## 底层机制：TableGen 是个"记录数据库"

`.td` 语法只有三件事：`def` 定义记录、`class` 定义模板、`let` 覆盖字段。`include` 拉入别的 `.td`，`-I` 指定搜索路径。`mlir-tblgen` 把所有记录读进内存，再用一个**生成器**遍历记录、拼字符串输出。

`Op` 类本身（`mlir/IR/OpBase.td:335`）只是一堆字段的容器：`mnemonic`、`arguments`、`results`、`assemblyFormat`、`traits`、`hasVerifier`……生成器读这些字段决定输出什么。

两个生成器的入口都在 `mlir/tools/mlir-tblgen/OpDefinitionsGen.cpp`：

| 生成器 | 产出 | 关键实现位置（源码依据） |
|---|---|---|
| `-gen-op-decls` | 类声明、Adaptor、build 签名 | `OpDefinitionsGen.cpp:2219`（`getODSOperands`）、`:2407`（`getODSResults`）、`:4183`（`getOperationName`） |
| `-gen-op-defs` | build/verify/parse/print 定义 | `OpDefinitionsGen.cpp:3866`（`verifyInvariantsImpl`）、`:3899`（`hasVerifier` 分支）、`:3840` 与 `:3857`（自定义格式分支） |
| `-gen-op-doc` | Markdown 文档 | `OpDocGen.cpp`（本章只用它的输出） |

字段自身的位置（源码依据，均已核对）：`assemblyFormat` 在 `OpBase.td:402`，`hasCustomAssemblyFormat` 在 `:409`，`hasVerifier` 在 `:418`。

一条实操经验：`-I` 指向安装目录的 `Library\include` 或源码树的 `mlir\include`，输出逐字节相同。本机用 `Get-FileHash` 比对过两份 `toy.cpp.inc`，哈希一致。所以跑 tblgen 不必 clone 源码；但读生成器实现时源码树仍然必要。

```powershell

& "$mlir\mlir-tblgen.exe" -gen-op-decls "$w\toy.td" `
```

实测：退出码 0，`toy.h.inc` 共 202 行。文件开头是"给不关心实现的人看的"前向声明：

```cpp
/*===- TableGen'erated file -------------------------------------*- C++ -*-===*\
|* Op Declarations                                                            *|
|* Automatically generated file, do not edit!                                 *|
|* From: toy.td                                                               *|
\*===----------------------------------------------------------------------===*/

namespace toy {

/// element-wise addition of two tensors

class AddOp;

} // namespace toy
```

`summary` 与 `description` 都变成了 `///` 注释——这是它们进入 C++ 代码的唯一方式。

真正的类体在 `#ifdef GET_OP_CLASSES` 块里（Ch 13 展开）：

```cpp
class AddOp : public ::mlir::Op<AddOp, ::mlir::OpTrait::ZeroRegions, ::mlir::OpTrait::OneResult, ::mlir::OpTrait::OneTypedResult<::mlir::TensorType>::Impl, ::mlir::OpTrait::ZeroSuccessors, ::mlir::OpTrait::NOperands<2>::Impl, ::mlir::OpTrait::OpInvariants, ::mlir::ConditionallySpeculatable::Trait, ::mlir::OpTrait::AlwaysSpeculatableImplTrait, ::mlir::MemoryEffectOpInterface::Trait> {
public:
  using Op::Op;
  using Op::print;
  using Adaptor = AddOpAdaptor;
  template <typename RangeT>
  using GenericAdaptor = AddOpGenericAdaptor<RangeT>;
  static constexpr int odsIndex_lhs = 0;
  static constexpr int odsIndex_rhs = 1;

  static constexpr ::llvm::StringLiteral getOperationName() {
    return ::llvm::StringLiteral("toy.add");
  }
```

`OneTypedResult<::mlir::TensorType>` 与 `NOperands<2>::Impl` 是**从 `arguments`/`results` 反推的 trait**：你只写了两个 `TensorOf`，生成器数出 2，并因为约束能归约到 `TensorType` 而选了 typed result。`odsIndex_lhs = 0` 则是 `$lhs` 的下标。

builder 生成了整族重载（实测，`toy.h.inc:177-188` 共 12 条）。最常用的两条：

```cpp
  static void build(::mlir::OpBuilder &odsBuilder, ::mlir::OperationState &odsState, ::mlir::Type result, ::mlir::Value lhs, ::mlir::Value rhs);
  static AddOp create(::mlir::OpBuilder &builder, ::mlir::Location location, ::mlir::Type result, ::mlir::Value lhs, ::mlir::Value rhs);
```

其余是"结果类型范围""通用 ValueRange""带 Properties"三种变体，各自再配一个 `ImplicitLocOpBuilder` 版本。`create` 只是"建 `OperationState` → `builder.create` → `dyn_cast`"的糖，真正干活的是 `build`。

最后是 parse/print 声明：

```cpp
  static ::mlir::ParseResult parse(::mlir::OpAsmParser &parser, ::mlir::OperationState &result);
  void print(::mlir::OpAsmPrinter &_odsPrinter);
  void getEffects(::llvm::SmallVectorImpl<::llvm::SideEffects::EffectInstance<::mlir::MemoryEffects::Effect>> &effects);
```

参数名 `_odsPrinter` 是生成器的约定：加下划线提醒你"这是生成的，别在自定义定义里重名"。

## 示例二：跑 `-gen-op-defs`

同一份 `.td`，换生成器：

```powershell
& "$mlir\mlir-tblgen.exe" -gen-op-defs "$w\toy.td" `
  -I ".scratch\llvm-23.1.4-src\mlir\include" -o "$w\toy.cpp.inc"
```

实测：退出码 0，共 313 行。第一个有意思的段落是最简单的 builder：

```cpp
void AddOp::build(::mlir::OpBuilder &odsBuilder, ::mlir::OperationState &odsState, ::mlir::Type result, ::mlir::Value lhs, ::mlir::Value rhs) {
  odsState.addOperands(lhs);
  odsState.addOperands(rhs);
  odsState.addTypes(result);
}
```

没有任何类型检查。`build` 只负责**把值塞进 `OperationState`**，正确性由 verifier 事后保证。这是 MLIR 的一贯分工：构造便宜，验证独立。所以 pass 里 `create` 出来的 op 可能暂时非法，直到 `verify()` 跑过——这也是 conversion 框架允许中间态存在 `unrealized_conversion_cast` 的原因之一。

第二个是 `print`，把格式串逐字翻译成打印调用（节选）：

```cpp
void AddOp::print(::mlir::OpAsmPrinter &_odsPrinter) {
  _odsPrinter << ' ';
  _odsPrinter << getLhs();
  _odsPrinter << ",";
  _odsPrinter << ' ';
  _odsPrinter << getRhs();
  // ... attr-dict 与类型的打印略
}
```

`<< ' '` 这种"先打一个空格"看起来笨，但它是为了保证 `toy.add %a, %b : ...` 里每个词之间恰好一个空格——格式串里没写空格，生成器自己补。理解这点，调试打印结果时就不会再怀疑"我明明没写空格"。

## 对比与取舍

同一个 op 有三种定义方式，选错会在后期付代价：

| 方式 | 写多少 | 得到什么 | 什么时候用 |
|---|---|---|---|
| `assemblyFormat` | 一行 DSL | 自动 parse/print + 文档 | 默认选择，90% 的 op |
| `hasCustomAssemblyFormat = 1` + 手写 C++ | 两个函数 | 完全自由的语法 | 格式依赖上下文、要嵌套解析、或兼容旧语法 |
| 不写格式（generic form） | 0 | 只有 `"toy.add"(%a, %b) : ...` | 内部临时 op、调试 |

第一种的边界很清楚：格式串是**线性**的，从左到右匹配。一旦需要"根据第一个操作数的类型决定后面怎么读"，或者要把 region 终止符写进语法，DSL 就不够用，别硬凑，直接上第二种（Ch 12 有完整例子）。

第三种看似省事，但 generic form 暴露属性字典和完整类型列表，人读起来痛苦，而且 op 名拼错就退化成"未注册方言"错误。生产方言不要留这种 op。

还有一处易混：`assemblyFormat` 与 `hasCustomAssemblyFormat` **互斥**。两个都写，tblgen 报错；一个都不写，就是 generic form。这三态必须记牢。

## 踩雷集锦

1. **忘了 include `SideEffectInterfaces.td` 却用了 `Pure`**。实测：`error: Variable not defined: 'Pure'`。`Pure` 不是内置词，是那个 `.td` 里的 record。
2. **忘了 `-I`**。实测：`error: could not find include file 'mlir/IR/OpBase.td'`，紧跟一条 `Unexpected token at top level`——第二条是级联错误，修第一条即可。
3. **`assemblyFormat` 漏 `attr-dict`**。实测：`error: 'attr-dict' directive not found in custom assembly format`。哪怕没有任何属性也必须写。
4. **多个 variadic 操作数没给尺寸依据**。实测：`error: op has multiple variadic operands but no specification over their sizes`，后跟 stack dump。解法是加 `AttrSizedOperandSegments`，Ch 13 详解。
5. **生成物编不过，先怀疑头文件**。`OpBuilder`、`ImplicitLocOpBuilder`、`OpAsmPrinter` 在生成物里是直接使用，不是声明。补 `Builders.h` 与 `OpImplementation.h`，别改 `.inc`。
6. **用 PowerShell 的 `2>` 抓 stderr，满屏 `At line:...`**。PS 5.1 会把原生命令 stderr 包成 ErrorRecord；教材里所有 `mlir-opt` 报错都用 `Start-Process -RedirectStandardError` 抓。

## 进阶：再往深一层

### 练习 1：改 mnemonic，验证名字从哪来

**任务**：把 `"add"` 改成 `"addf"`，其余不动。

**测试用例**：
1. `-gen-op-decls` 退出码 0。
2. 生成物里 `"toy.addf"` 恰好一处，`"toy.add"` 消失。
3. `class AddOp` 这个名字**不变**。

**步骤**：复制 `.td` → 替换 mnemonic → 重跑 decls → `Select-String -Pattern 'toy\.add'` → 解释结果。

<details>
<summary>参考解答</summary>

```powershell
(Get-Content .scratch\tblgen-work\toy.td -Raw) -replace '"add"', '"addf"' |
  Set-Content .scratch\tblgen-work\toy_addf.td -Encoding ascii
& "$mlir\mlir-tblgen.exe" -gen-op-decls .scratch\tblgen-work\toy_addf.td `
  -I .scratch\llvm-23.1.4-src\mlir\include -o .scratch\tblgen-work\toy_addf.h.inc
Select-String .scratch\tblgen-work\toy_addf.h.inc -Pattern 'toy\.add'
```

只剩 `getOperationName()` 里一处 `toy.addf`。类名来自 `def Toy_AddOp`，与 mnemonic 无关。

</details>

**常见卡点**：连 `def` 名一起改，类变成 `AddfOp`，`ops.cpp` 里的 `AddOp` 就找不到了。

### 练习 2：加第三个操作数

**任务**：在 `$rhs` 后加 `TensorOf<[F64]>:$bias`，先不改 `assemblyFormat`。

**测试用例**：
1. 不改格式串时 tblgen 退出码 1。
2. 报错原文包含 `operand #2, named 'bias', not found` 与 `suggest adding a '$bias' directive`。
3. 补上 `$bias` 后基类出现 `NOperands<3>::Impl` 与 `odsIndex_bias = 2`。
4. 第一个 `build` 的参数顺序变为 `(Type result, Value lhs, Value rhs, Value bias)`。

**步骤**：改 `arguments` → 跑 decls 记录报错 → 改格式串 → 再跑 → `Select-String` 核对 trait 与下标。

<details>
<summary>参考解答</summary>

```tablegen
  let arguments = (ins TensorOf<[F64]>:$lhs, TensorOf<[F64]>:$rhs,
                       TensorOf<[F64]>:$bias);
  let assemblyFormat = [{
    $lhs `,` $rhs `,` $bias attr-dict `:` type($lhs) `,` type($rhs) `,` type($bias) `->` type($result)
  }];
```

测试用例 2 是本章实测原文；tblgen 除了报错，还会给出修复建议。

</details>

**常见卡点**：只改 `arguments` 就以为完事。`resolveOperands` 数量对不上时，报错落在生成的 parser 代码里，不在 `.td` 行上。

### 练习 3：改成双结果

**任务**：`results` 改为 `(outs TensorOf<[F64]>:$sum, TensorOf<[F64]>:$diff)`，并同步改格式串。

**测试用例**：
1. 只改 `results` 不改格式串，报 `expected variable to refer to an argument, region, result, or successor`，指向 `type($result)`。
2. 同步改成 ``type($sum) `,` type($diff)`` 后，基类出现 `NResults<2>::Impl`，并多出 `OpAsmOpInterface::Trait`。
3. `-gen-op-defs` 里出现 `assert(resultTypes.size() == 2u && "mismatched number of results");`。

**步骤**：改 `results` → 跑 decls 记录报错 → 改格式串 → 跑 decls/defs → 核对 trait 与断言。

<details>
<summary>参考解答</summary>

三条都是本机实测。`OpAsmOpInterface` 是双结果才出现的：多结果 op 需要额外接口决定结果如何排布打印。断言是**运行期**的，Release 构建（本机 conda 包）里被编掉。

</details>

**常见卡点**：以为 `NResults<2>` 会自动带来双结果语法；实际上 `assemblyFormat` 里必须显式列出两个 `type(...)`。

### 练习 4：把生成物编一遍

**任务**：用练习 2 的三操作数版本重新生成两份 `.inc`，沿用 `ops.cpp` 骨架编译。

**测试用例**：
1. 只 include `OpDefinition.h` 时复现 `C2027 使用了未定义类型 "mlir::OpBuilder"`。
2. 补 `Builders.h`、`OpImplementation.h`、`SideEffectInterfaces.h` 后 `cl /c` 退出码 0。
3. 生成物本身一行都不用改。

<details>
<summary>参考解答</summary>

三个头各管一摊：`Builders.h` 给 `OpBuilder`/`ImplicitLocOpBuilder`，`OpImplementation.h` 给 `OpAsmPrinter`/`OpAsmParser`，`SideEffectInterfaces.h` 给 `Pure` 生成的 `getEffects` 签名。报错位置全在 `.inc` 里，但根因永远是你的 include 列表。

</details>

**常见卡点**：只 `#define GET_OP_CLASSES` 一次就 include 两个文件；两份 `.inc` 各需一次。

## 本章重点整理

- ODS 是"声明即事实来源"：verifier、parser、printer、builder 从同一份 `.td` 推导，不会漂移。
- 一份 `.td` 跑两次：`-gen-op-decls` 出声明（202 行），`-gen-op-defs` 出定义（313 行）。
- `arguments`/`results` 的顺序就是下标顺序；`$name` 决定访问器名。
- `assemblyFormat` 是线性 DSL，`attr-dict` 必写；`type(...)` 写多少就解析多少。
- `summary`/`description` 进 `///` 注释与 `-gen-op-doc` 文档，是唯一文档来源。
- `Pure` 生成三个 trait 加一个空 `getEffects`；它是副作用契约，不是可选优化。
- 生成物不自包含：`Builders.h`、`OpImplementation.h` 得自己 include。
