# Ch 19 — MIR/lit 测试与上游质量标准

> **目标**：把 RegBankSelect 的行为变成可回归、可 review、可维护的测试：知道什么时候写 MIR/lit，什么时候写 `RegisterBankInfo` 单元测试，怎样生成和审查 CHECK 行，以及如何报告编译时间与代码质量。
>
> **环境**：LLVM 23.1.4 源码树与官方 Windows x86_64 预编译包。本课程用到的工具中，该包只有 `llc` 可用；没有 `FileCheck`、`llvm-lit` 或 `not`（实测 `Test-Path` 均为 false）。
>
> **证据约定**：源码和测试文件的内容来自 `.scratch/llvm-23.1.4-src`，标“源码依据”；`update_mir_test_checks.py` 的运行结果在本机复现，标“实测”；所有 lit、gtest、assertions build 结果都标 `guided`，不伪造 PASS 输出。

## 为什么需要这个？

RegBankSelect 的错误很少表现为“程序算错”。它更常表现为：

- bank 选错，但最终汇编仍然能跑；
- 多插了三条 COPY，功能完全正确；
- Fast 与 Greedy 在某条指令上分叉，只有一种模式退化；
- 手写 MIR 破坏了不变量，verifier 报错但 RBS 本身没问题。

这些行为在最终汇编里几乎看不出来，所以测试必须直接断言 **bank、COPY、物理寄存器边界和 pass 状态**。上游的 `regbankselect-*.mir` 正是为此存在：它们不追求覆盖整个后端，而是把 RBS 的输出固定成可读的 MIR。

测试还是上游 review 的通用语言。一个 mapping 改动如果只附“我跑了一个 IR，汇编看起来对”，reviewer 无法判断：

- 改的是默认 mapping 还是 alternative；
- 影响的是 Fast、Greedy，还是两者；
- COPY 数量变了没有；
- 是否需要新的 negative test；
- 编译时间是否被重新扫描拖慢。

本章把这些要求拆成可执行的测试流程。

## 先建立直觉

把 RBS 测试想成三层漏斗：

```text
                 ┌─────────────────────────────┐
                 │ 全 pipeline / 性能基准       │  用户可见行为、编译时间
                 └──────────────▲──────────────┘
                                │
                 ┌──────────────┴──────────────┐
                 │ MIR/lit：单 pass 行为        │  bank、COPY、PHI、边界
                 └──────────────▲──────────────┘
                                │
                 ┌──────────────┴──────────────┐
                 │ 单元测试：数据模型与算法     │  mapping 是否合法、代价
                 └─────────────────────────────┘
```

越往下，测试越稳定、越快、越容易定位；越往上，越接近真实用户，但噪声也越大。

一个实用原则：**断言离行为越近越好**。如果问题是“`G_OR` 的 FPR alternative 是否存在”，单元测试最直接；如果问题是“RBS 在这份 MIR 上插了几条 COPY”，MIR/lit 最直接；如果问题是“Greedy 让编译时间涨了多少”，只有基准测试能回答。

## 核心概念

### 上游测试的分布

在 23.1.4 的 `llvm/test/CodeGen/AArch64/GlobalISel` 下（实测目录统计）：

| 类别 | 数量 | 说明 |
| --- | --- | --- |
| 全部 `.mir` | 586 | GlobalISel 的 MIR 测试主体 |
| `regbankselect-*.mir` | 7 | 直接以 RBS 为 RUN 的测试 |
| `regbank-*.mir` | 25 | 以 bank 选择/使用为主题的测试 |

7 份 `regbankselect-*.mir` 覆盖的主题并不相同：

| 文件 | 主要覆盖 |
| --- | --- |
| `regbankselect-default.mir` | 各类 opcode 的默认 GPR/FPR 选择 |
| `regbankselect-reductions.mir` | 向量归约结果落在 FPR |
| `regbankselect-fp-loads.mir` | 浮点 load 的数据 bank |
| `regbankselect-build-vector.mir` | build vector 的 bank 与 COPY |
| `regbankselect-unmerge-vec.mir` | unmerge 向量的 bank |
| `regbankselect-reg_sequence.mir` | `REG_SEQUENCE` 的 copy-like 处理 |
| `regbankselect-dbg-value.mir` | debug value 对 RBS 的影响 |

不要被“只有 7 份”误导。`regbank-*.mir` 和大量 `instruction-select-*.mir` 也会间接锁定 bank 行为；改 RBS 时要按 opcode/主题搜索，而不是只看文件名。

### 一份 MIR 测试的骨架

以 `regbankselect-reductions.mir` 为例（源码依据）：

```text
# NOTE: Assertions have been autogenerated by utils/update_mir_test_checks.py
# RUN: llc -mtriple=aarch64-unknown-unknown -verify-machineinstrs \
# RUN:   -run-pass=regbankselect -global-isel-abort=1 %s -o - | FileCheck %s

---
name:            fadd_v2s32
legalized:       true
tracksRegLiveness: true
body:             |
  bb.1:
    liveins: $d0


    ; CHECK-LABEL: name: fadd_v2s32
    ; CHECK-NEXT: [[COPY:%[0-9]+]]:fpr(<2 x s32>) = COPY $d0
    ; CHECK-NEXT: [[VECREDUCE_FADD:%[0-9]+]]:fpr(s32) = G_VECREDUCE_FADD [[COPY]](<2 x s32>)
    ; CHECK-NEXT: $w0 = COPY [[VECREDUCE_FADD]](s32)
    %0:_(<2 x s32>) = COPY $d0
    %1:_(s32) = G_VECREDUCE_FADD %0(<2 x s32>)
    $w0 = COPY %1(s32)
```

四层信息缺一不可：

1. **RUN 行**：用哪个 `llc`、什么 triple、哪个 pass、是否 verifier、abort 模式。
2. **YAML 头部**：`legalized: true` 是 RBS 的输入契约；`tracksRegLiveness` 影响 live 信息。
3. **输入 MIR**：故意保留 `_`，让 RBS 决定 bank；输出再与 CHECK 比较。
4. **CHECK 行**：锁定 bank 后缀、COPY 位置和关键操作数。

如果输入 MIR 已经写了 `%0:gpr`，测试就不再验证“RBS 会选 GPR”，只验证“RBS 不会改掉已有 bank”。这两种测试的目的完全不同。

### CHECK 行在断言什么

| 写法 | 断言 | 常见误用 |
| --- | --- | --- |
| `[[COPY:%[0-9]+]]:fpr` | 捕获 vreg 且 bank 为 FPR | 只匹配 vreg 编号，不检查 bank |
| `CHECK-NEXT` | 下一条必须完全匹配 | 对无关指令顺序过度敏感 |
| `CHECK-LABEL` | 函数边界 | 缺失时跨函数串检查 |
| `{{  $}}` | 匹配 MIR 缩进/空行细节 | 误以为在匹配语义 |
| `CHECK-NOT` | 某段范围内不得出现 | 范围过宽导致假阴性/假阳性 |

自动生成的 CHECK 行通常用 `CHECK-NEXT` 锁定整个函数体。它对回归非常敏感，但也意味着任何无关的 MIR 打印变化都会让测试失败。手工 review 时，可以在不影响意图的前提下把无关行放宽为 `CHECK`，但不要删除对 bank 和 COPY 的断言。

### Fast 与 Greedy 的双 RUN

`arm64-regbankselect.mir` 展示了另一种模式（源码依据）：

```text
# RUN: llc -O0 -debugify-and-strip-all-safe -run-pass=regbankselect %s -o - \
# RUN:   -verify-machineinstrs | FileCheck %s --check-prefix=CHECK --check-prefix=FAST
# RUN: llc -O0 -debugify-and-strip-all-safe -run-pass=regbankselect \
# RUN:   -regbankselect-greedy %s -o - -verify-machineinstrs \
# RUN:   | FileCheck %s --check-prefix=CHECK --check-prefix=GREEDY
```

它把共同断言放在 `CHECK`，把模式特有断言放在 `FAST`/`GREEDY`。适用场景：

- 两种模式应产生相同 bank：共同 `CHECK` 足够。
- Greedy 应减少 COPY：用 `GREEDY` 单独断言。
- Greedy 在某个反例上更差：用 `GREEDY` 锁定“更差”的现状，防止无意改变。

如果只跑默认 Fast，你无法证明 Greedy 的 alternative mapping 仍可用；如果只跑 Greedy，你也无法发现 Fast 的默认 mapping 退化。

## 底层机制

### `update_mir_test_checks.py` 做了什么

脚本的 docstring 说得很清楚（源码依据）：

- 它更新 MIR 测试里的 FileCheck 检查；
- 检查覆盖它处理的每个函数的**整个 body**；
- 虚拟寄存器会被命名为 FileCheck 变量；
- **YAML metadata 默认不检查**，除了函数名和 `--print-fixed-stack` 打开时的 `fixedStack`；
- 有多个 `llc` RUN 行时，每种 check prefix 都会重复生成整套检查。

脚本的执行路径：

```text
读取测试文件
  → 找到 # RUN 行
  → 拆出 llc 命令和 FileCheck 命令
  → 对每个 prefix 调 llc（MIR 自动加 -x mir）
  → 解析输出 MIR
  → 重写 CHECK 行
```

两个实现细节值得记住：

- 它要求 RUN 行里有 `|`，并且左侧以 `llc ` 开头、右侧以 `FileCheck ` 开头；否则跳过并警告。
- 它把 `\r\n` 统一成 `\n`，所以在 Windows 上“内容没变”也可能导致文件字节数和 hash 变化。

### 生成不等于验证

自动生成只保证“CHECK 与当前输出一致”，不保证：

- 当前 bank 是**正确**的，而不是刚被改坏的；
- 测试覆盖了你想覆盖的路径；
- YAML 里的 `legalized`、`selected`、`failedISel` 状态合理；
- COPY 数量是你期望的，而不是恰好被全量 CHECK 固化。

正确的流程是：先手写输入和关键意图，再生成 CHECK，最后人工 review 差异。生成器是排版工具，不是 oracle。

### 当前环境能跑到哪一步

| 工具/步骤 | 官方包是否具备 | 本章如何处理 |
| --- | --- | --- |
| `llc` | 是 | 实测 |
| `FileCheck` | 否 | lit 结果标 `guided` |
| `llvm-lit` | 否 | lit 结果标 `guided` |
| `not` | 否 | negative test 标 `guided` |
| `update_mir_test_checks.py` | 源码脚本 + Python | 实测（生成到临时副本） |
| gtest / assertions build | 否 | 单元测试标 `guided` |

这意味着本章可以真实展示“生成 CHECK 前后内容是否变化”，但不能声称“lit 全部通过”。任何 `PASS`、`FAIL` 行都不会出现在本章。

### 单元测试的基座

`GISelMITest.h` 提供 `AArch64GISelMITest`，它构造一个 AArch64 `TargetMachine`，解析内联 MIR，并暴露（源码依据）：

- `MachineFunction *MF`
- `MachineBasicBlock *EntryMBB`
- `MachineRegisterInfo *MRI`
- `SmallVector<Register, 4> Copies`
- `collectCopies(Copies, MF)`

`collectCopies` 遍历整个函数，把所有 `TargetOpcode::COPY` 的目的寄存器收集起来。这就是写“COPY 数量”单元测试的现成工具。

但在 23.1.4 的 `llvm/unittests/CodeGen/GlobalISel` 中没有专门的 `RegisterBankInfo` 测试文件；现有测试主要覆盖 IRTranslator、Legalizer、InstructionSelect、MachineIRBuilder 等。给 `RegisterBankInfo` 增加 gtest 是合理的补强，但属于新测试，必须自己在完整构建里编译验证。

### 编译时间与性能证据

RBS 的质量不只在正确性，还在编译时间。第 17 章在同一份 legal MIR 上做过实测：

| 实验 | Fast | Greedy | 结论 |
| --- | --- | --- | --- |
| `or.ll` 跨 bank COPY | 3 | 0 | Greedy 的 alternative 有效 |
| `optnone` 的 `or.ll` | 3 | 3 | `optnone` 强制 Fast |
| 3000 函数全 pipeline 中位数 | 1678 ms | 1708 ms | 差异被解析/打印淹没 |
| RBS-only `-time-passes` 中位数 | 0.026 s | 0.040 s | 粗粒度，约 1.5× |

上报性能时必须写清测量层级：全 pipeline 的数字不能证明 RBS pass 本身慢，`-time-passes` 的 10 ms 级数字也不适合宣称 1.5× 的精确比例。正确做法是同时报告输入、样本数、顺序、中位数和输出大小。

## 实验一：精读一份上游 MIR 测试

`regbankselect-reductions.mir` 的 `fadd_v2s32` 函数（源码依据，已截取核心部分）：

```yaml
name:            fadd_v2s32
legalized:       true
tracksRegLiveness: true
body:             |
  bb.1:
    liveins: $d0
    %0:_(<2 x s32>) = COPY $d0
    %1:_(s32) = G_VECREDUCE_FADD %0(<2 x s32>)
    $w0 = COPY %1(s32)
```

这份测试的 CHECK（见“核心概念”中的完整片段）断言了三件事：

1. 向量 `COPY` 的结果在 `fpr`；
2. `G_VECREDUCE_FADD` 的结果在 `fpr`；
3. 回到 `$w0` 时发生一次物理寄存器 COPY。

它没有断言 YAML 的 `legalized` 或 `tracksRegLiveness`，因为生成器默认不检查 YAML metadata。也就是说，如果你把 `legalized: true` 误删，CHECK 仍可能通过，但 pass 会因缺少前置属性而拒绝运行。review 时要单独看头部。

`guided`：在完整构建中用 `llvm-lit`（Windows 构建中也可能叫 `llvm-lit.py`）直接跑该文件；当前包没有该工具，因此不展示 PASS 输出。

## 实验二：运行 `update_mir_test_checks.py` 并检查差异

把测试复制到临时目录，避免改动源码树：

```powershell
$src = 'llvm/test/CodeGen/AArch64/GlobalISel/regbankselect-reductions.mir'
$dst = Join-Path $env:TEMP 'rbs-p3\upd-check.mir'
Copy-Item -LiteralPath $src -Destination $dst -Force

python llvm/utils/update_mir_test_checks.py `
  --llc-binary $llc $dst
```

实测结果：

```text
EXIT=0
SRC_LINES=67
DST_LINES=67
TEXT_EQUAL=True
SRC_BYTES=2029 (LF-normalized)
DST_BYTES=2029
SRC_BYTES_ON_DISK=2096 (CRLF)
DST_BYTES_ON_DISK=2029 (LF)
```

要点：

- **文本内容完全一致**，行数都是 67；说明现有 CHECK 与 23.1.4 的 `llc` 输出一致。
- 字节数变化来自换行：源文件是 CRLF，脚本重写为 LF。不要把这个差异误判为测试内容变化。
- SHA-256 因此不同；比较时应先统一换行，或用 `git diff` 看行级差异。
- 如果脚本真的改了 CHECK，diff 会显示 bank、vreg 捕获或 COPY 行变化；这时必须逐行 review，而不是直接接受。

## 实验三：给 `RegisterBankInfo` 写一个 guided 单元测试

下面是一个**未编译、未运行**的 gtest 草图，目标是锁定 AArch64 `G_OR` 的默认 GPR mapping 和 FPR alternative。它应放在 `llvm/unittests/CodeGen/GlobalISel/`，并加入该目录的 `CMakeLists.txt`；当前官方包没有 gtest 构建，因此全部标 `guided`。

```cpp
#include "GISelMITest.h"
#include "llvm/CodeGen/GlobalISel/RegisterBankInfo.h"

using namespace llvm;

TEST_F(AArch64GISelMITest, OrHasGPRDefaultAndFPRAlternative) {
  setUp(R"(
    %3(s32) = G_OR %0, %1
  )");
  if (!TM)
    GTEST_SKIP();

  MachineInstr *Or = nullptr;
  for (MachineInstr &MI : *EntryMBB)
    if (MI.getOpcode() == TargetOpcode::G_OR)
      Or = &MI;
  ASSERT_NE(Or, nullptr);

  const RegisterBankInfo &RBI = *MF->getSubtarget().getRegBankInfo();
  const InstructionMapping &Default = RBI.getInstrMapping(*Or);
  ASSERT_TRUE(Default.isValid());
  const ValueMapping &Op0 = Default.getOperandMapping(1);
  ASSERT_TRUE(Op0.isValid());
  EXPECT_STREQ(Op0.BreakDown[0].RegBank->getName(), "GPR");

  bool HasFPR = false;
  for (const InstructionMapping *M : RBI.getInstrPossibleMappings(*Or)) {
    const ValueMapping &V = M->getOperandMapping(1);
    if (V.isValid() && V.BreakDown[0].RegBank->getName() == StringRef("FPR"))
      HasFPR = true;
  }
  EXPECT_TRUE(HasFPR);
}
```

这份测试的边界：

- `Default` 检查的是**默认 mapping**，不是 RBS 最终选择；最终选择还受 repair 代价和 use 影响。
- `getInstrPossibleMappings` 检查的是**候选集合**，适合验证 alternative 是否存在。
- 若要验证 Greedy 最终选 FPR，应跑 `RegBankSelect` pass 或写 MIR/lit，而不是只查候选集合。
- 代码中的 API 名称来自 23.1.4 头文件（源码依据），但没有在本书环境编译；实际提交前必须在完整构建中跑 gtest。

## 对比与取舍

| 测试层 | 优点 | 局限 | 适合锁定 |
| --- | --- | --- | --- |
| gtest / `RegisterBankInfo` | 快、定位准、可直接断言 mapping 对象 | 不验证 pipeline、repair、最终 bank | 数据模型、默认/候选 mapping |
| MIR/lit | 真实跑 pass，输出可读 | 依赖 FileCheck/lit，CHECK 可能脆弱 | bank、COPY、PHI、边界指令 |
| 全 pipeline | 覆盖 fallback、ISel、RA | 噪声大，失败定位远 | 用户可见回归 |
| 性能基准 | 能发现编译时间退化 | 对机器和顺序敏感 | Greedy 扫描、bank 数量 |

对 RBS 改动，推荐组合是：

1. **单元测试**锁 mapping 表本身（如果改了 `getInstrMapping`/alternatives）。
2. **MIR/lit**锁 Fast 和 Greedy 的实际输出，至少覆盖一个 COPY 变化和一个边界类型。
3. **全 pipeline**只在怀疑 fallback 或跨 pass 交互时使用。
4. **基准**只在改扫描策略、bank 数量、repair 算法时使用，并报告方法。

### 提交前 review 清单

- [ ] 默认 mapping 与每个 alternative 都有测试，或明确说明为何不需要。
- [ ] Fast 与 Greedy 的行为分别有断言，COPY 数量变化有解释。
- [ ] RUN 行包含 `-verify-machineinstrs` 与 `-global-isel-abort=1`。
- [ ] YAML 的 `legalized`、`isSSA`、`tracksRegLiveness` 与输入阶段一致。
- [ ] 生成 CHECK 后的 diff 已人工审查，没有把错误 bank 固化。

## 踩雷集锦

### 1. 声称“lit 通过”，但其实只跑了 `llc`

`llc ... -o -` 成功只说明 pass 没崩；FileCheck 才负责比较 CHECK。当前包没有 FileCheck，正确写法是“`llc` 实测，lit `guided`”。

### 2. 直接接受自动生成的 CHECK

生成器覆盖整个 body，默认不检查 YAML metadata。它会把当前行为（包括刚引入的错误 bank）原样固化。正确做法是先审查输入和期望，再看生成 diff 是否只包含预期变化。

### 3. 只测 Fast，或只测 Greedy

默认模式是 Fast，但 Greedy 的 alternative 路径完全独立。只测一个模式，另一个模式退化时不会报警。正确做法是用双 RUN 或两份 MIR，明确哪些断言共享、哪些分模式。

### 4. 只断言“有 COPY”，不断言 bank 和数量

`CHECK: COPY` 可能匹配任意一条 COPY，无法证明修复发生在正确位置。正确做法是捕获 vreg 并断言 bank、操作数和相邻指令；必要时用 `CHECK-NOT` 限定范围内不得出现额外跨 bank COPY。

### 5. 用全 pipeline 时间证明 RBS 变快

解析、ISel、RA 和输出打印都会淹没 RBS 的差异。正确做法是先用 `-time-passes` 或 pass 级计时隔离，再报告全 pipeline 作为辅助；不要用一次运行下结论。

## 进阶

### negative test 与崩溃路径

上游会用 `not --crash llc ...` 检查预期崩溃，但当前包没有 `not`。写这类测试时（`guided`）：

```text
# RUN: not --crash llc -mtriple=aarch64-- -run-pass=regbankselect \
# RUN:   -global-isel-abort=1 %s -o /dev/null 2>&1 | FileCheck %s
```

负向测试要断言错误串和退出行为，而不是只断言“失败”。错误串变化时应同步更新测试，否则会把真实的诊断退化掩盖掉。

### assertions build 与 verifier

`BestMapping->verify(MI)` 等断言只在 assertions build 生效。CI 至少应有一个 assertions 配置跑 RBS 测试；release 配置则依赖 `-verify-machineinstrs` 捕获不变量问题。两者不能互相替代。

### 自动生成器的细节开关

`update_mir_test_checks.py` 还支持 `--print-fixed-stack` 和 `--remove-common-prefixes`。前者把 `fixedStack` 纳入检查，后者处理多个 RUN 行共享 prefix 的情况。使用前先读脚本帮助，不要凭记忆加参数。

### 编译时间基准的最小协议

1. 固定同一份 legal MIR，避免 Legalizer 差异。
2. 交替运行 Fast/Greedy，抵消缓存和热漂移。
3. 至少 10 轮，报告 median 和范围。
4. 同时记录输出大小，防止“更快但少做事”。
5. 区分 pass-only 与 full pipeline。

## 动手练习

1. **给 `or.ll` 写双模式测试**：从第 17 章的 `or-fast.mir`/`or-greedy.mir` 提取一个函数，写 `FAST` 断言 3 条跨 bank COPY、`GREEDY` 断言 0 条。要求使用 `-verify-machineinstrs -global-isel-abort=1`。
2. **审查生成 diff**：复制 `regbankselect-default.mir` 到临时目录，跑 `update_mir_test_checks.py`，统一换行后比较内容。要求说明为什么字节数可能变化而文本不变。
3. **设计一个单元测试**：为 AArch64 `G_BITCAST` 写 gtest 草图，断言默认 mapping 和候选 mapping 的 bank。标明哪些断言需要跑 pass 才能验证，哪些只查 `RegisterBankInfo` 就够。

## 本章重点整理

- RBS 测试要直接断言 bank、COPY、物理寄存器边界和 pass 状态，不能只看最终汇编。
- 上游 23.1.4 有 7 份 `regbankselect-*.mir`、25 份 `regbank-*.mir`，共 586 份 AArch64 GlobalISel MIR。
- MIR 测试的四要素是 RUN 行、YAML 前置状态、输入 MIR、CHECK 行。
- `update_mir_test_checks.py` 覆盖整个 body，默认不检查 YAML metadata；生成后必须人工 review。
- 当前官方包没有 FileCheck/lit/not，所有 lit 与 gtest 结论都必须标 `guided`。
