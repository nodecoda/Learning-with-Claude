# Ch 20 — AArch64 RegisterBankInfo 源码走读

> **目标**：把 AArch64 的 RegBankSelect 支持拆成四层——TableGen 的 bank 定义、生成的 bank 表、手写的 mapping 表、以及 `getInstrMapping` / `getInstrAlternativeMappings` / `applyMappingImpl` 的策略代码——并说清每一层“谁生成、谁维护、出错会怎样”。读完你能沿着一次 `llc -stop-after=regbankselect` 的决策路径，指出某个 vreg 的 bank 是在哪一行被决定的。
>
> **环境**：LLVM 23.1.4，源码快照 `.scratch/llvm-23.1.4-src`；生成物片段用官方 23.1.4 包的 `llvm-tblgen` 现场生成。RISC-V 作为对照。
>
> **证据约定**：C++ 片段均标 `源码依据` 并给出文件与行号；生成的枚举/覆盖表标 `实测生成物`；没有运行 lit、没有自建 `llc`，凡涉及构建与测试的步骤都标 `guided`。

## 为什么需要这个？

前面十九章讲的是“RegBankSelect 怎么工作”。这一章回答另一个问题：**AArch64 是怎么把这个 pass 喂饱的**。

只看 `RegBankSelect.cpp`，会以为 bank 选择是通用算法。实际上算法只负责“比较候选、算代价、插 COPY”；候选从哪来、每个操作数该在哪个 bank、跨 bank 搬一次多贵，全部由 target 的 `RegisterBankInfo` 决定。AArch64 把这部分拆得很碎：

- `AArch64RegisterBanks.td` 只写三行 `def`，描述“有哪些 bank、每个 bank 覆盖哪些寄存器类”。
- `AArch64GenRegisterBank.inc` 由 TableGen 生成，提供 bank ID、`RegisterBank` 实例、覆盖位图、`getRegBankFromRegClass`。
- `AArch64GenRegisterBankInfo.def` 是**手写**的（文件头明确写着 `\todo This should be generated by TableGen.`），提供 partial/value mapping 表。
- `AArch64RegisterBankInfo.cpp` 是策略层：默认 mapping、alternative mapping、copyCost、applyMapping。

这四层的边界，正是上游 review 最容易被问倒的地方：“这个 bank ID 哪来的？”“为什么 GPR 覆盖 42 个寄存器类？”“为什么 `G_OR` 有 FPR alternative，`G_AND` 没有？”能沿着源码回答，才算真正读懂。

## 先建立直觉

把 AArch64 的 bank 支持想成一家机场：

```text
AArch64RegisterBanks.td     航站楼规划书：有几座楼，每座楼接纳哪些登机口
        │  llvm-tblgen -gen-register-bank
        ▼
AArch64GenRegisterBank.inc  楼号、容量、登机口归属表（机器生成，别手改）
        │
        ├── AArch64GenRegisterBankInfo.def   座位图（手写：哪种值坐哪座楼）
        ▼
AArch64RegisterBankInfo.cpp 调度策略：默认停哪、备选停哪、摆渡车多少钱
        ▼
RegBankSelect.cpp           通用调度算法：选方案，必要时开摆渡车（COPY）
```

两个容易混淆的点：

1. **航站楼规划书不是座位图**。`.td` 只决定“GPR 覆盖哪些寄存器类”，不决定“`G_OR` 该停在哪”；后者在 `.def` 和 `.cpp`。
2. **机器生成的只是“楼号与归属”**。`.def` 里的 `PartMappings` / `ValMappings` 至今仍是手写表，这是 AArch64 与“完全 TableGen 化”之间的最大缺口。

bank ID 的顺序会影响所有按 ID 索引的表。23.1.4 生成出来是 `CC=0`、`FPR=1`、`GPR=2`，不是源码里写死的枚举；本章例 1 给出真实生成结果。

## 核心概念

### 四层各自的职责

| 层 | 文件 | 谁维护 | 决定什么 | 改错的典型症状 |
| --- | --- | --- | --- | --- |
| bank 定义 | `AArch64RegisterBanks.td` | 人 | 有哪些 bank、覆盖哪些 regclass | 某类没有 bank，查询时直接 unreachable |
| 生成表 | `AArch64GenRegisterBank.inc` | TableGen | bank ID、实例、覆盖位图、regclass→bank | 手改会在下次构建被覆盖 |
| mapping 表 | `AArch64GenRegisterBankInfo.def` | 人 | 每种 bank/位宽的 partial/value mapping | `getValueMapping` 返回 invalid |
| 策略 | `AArch64RegisterBankInfo.cpp` | 人 | 默认/备选 mapping、copyCost、apply | bank 选错、COPY 异常、Greedy 无候选 |

### bank 覆盖不是“列出的那几个类”

`.td` 里写的是：

```tablegen
def GPRRegBank : RegisterBank<"GPR", [XSeqPairsClass]>;
def FPRRegBank : RegisterBank<"FPR", [QQQQ, ZPR]>;
def CCRegBank : RegisterBank<"CC", [CCR]>;
```

看起来 GPR 只覆盖 `XSeqPairsClass`，FPR 只覆盖 `QQQQ` 和 `ZPR`。但 `RegisterBankEmitter` 会递归加入显式列出的类、它们的所有子类、以及由这些类的子寄存器构成的 subreg class。所以生成出来的覆盖位图远不止三个条目。本次生成后，覆盖数组里分别有 CC=1、FPR=87、GPR=42 个置位（数的是寄存器类，不是寄存器个数）。

这解释了构造函数为什么要断言 `RBGPR.covers(GPR32RegClassID)`、`RBFPR.covers(QQRegClassID)`、`RBFPR.covers(FPR64RegClassID)`：这些类不是显式写的，而是通过子类/子寄存器关系被纳入的。

### partial / value / instruction mapping

```text
PartialMapping { StartIdx, Length, RegBank }      一个值的一段连续位落在哪个 bank
ValueMapping { BreakDown, NumBreakDowns }         一个操作数由几段组成
InstructionMapping { ID, Cost, OperandsMapping }  一条指令所有操作数的组合 + target ID
```

AArch64 的 `.def` 里，`PartMappings` 前几项是 FPR 16/32/64/128/256/512，然后是 GPR 32/64/128；`ValMappings` 再按“3 操作数同 bank”成组展开。后面的 `getValueMapping` 用 `First3OpsIdx + (RBIdx - PMI_Min + offset) * 3` 做下标运算。

```cpp
const RegisterBankInfo::PartialMapping AArch64GenRegisterBankInfo::PartMappings[]{
        /* StartIdx, Length, RegBank */
        // 0: FPR 16-bit value.
        {0, 16, AArch64::FPRRegBank},
        // 1: FPR 32-bit value.
        {0, 32, AArch64::FPRRegBank},
        // 2: FPR 64-bit value.
        {0, 64, AArch64::FPRRegBank},
        // 3: FPR 128-bit value.
        {0, 128, AArch64::FPRRegBank},
        // 4: FPR 256-bit value.
        {0, 256, AArch64::FPRRegBank},
        // 5: FPR 512-bit value.
        {0, 512, AArch64::FPRRegBank},
        // 6: GPR 32-bit value.
        {0, 32, AArch64::GPRRegBank},
        // 7: GPR 64-bit value.
        {0, 64, AArch64::GPRRegBank},
        // 8: GPR 128-bit value.
        {0, 128, AArch64::GPRRegBank},
    };
```

`InstructionMapping::ID` 不是装饰。默认 mapping 用 `DefaultMappingID`，框架自己会调 `applyDefaultMapping`；任何非默认 ID 都必须由 target 在 `applyMappingImpl` 里处理。AArch64 的 alternative 用 1/2/3/4，`applyMappingImpl` 就断言 ID 在 1..4。

## 底层机制

### 1. 从 `.td` 到 `.inc`

`CMakeLists.txt` 里有一行：

```cmake
tablegen(LLVM AArch64GenRegisterBank.inc -gen-register-bank)
```

`AArch64.td` 通过 `include "AArch64RegisterBanks.td"` 把三个 `def` 带进 TableGen。`RegisterBankEmitter::run` 做三件事：收集所有 `RegisterBank` 派生定义；对每个 bank 的显式寄存器类调用 `visitRegisterBankClasses`，递归加入子类和 subreg class；输出三段受宏保护的代码——`GET_REGBANK_DECLARATIONS`、`GET_TARGET_REGBANK_CLASS`、`GET_TARGET_REGBANK_IMPL`。

头文件这样用：

```cpp
#define GET_REGBANK_DECLARATIONS
#include "AArch64GenRegisterBank.inc"

class AArch64GenRegisterBankInfo : public RegisterBankInfo {
protected:
#define GET_TARGET_REGBANK_CLASS
#include "AArch64GenRegisterBank.inc"
};
```

实现文件用 `#define GET_TARGET_REGBANK_IMPL` 再 include 一次。同一个 `.inc` 被 include 三次，每次只展开对应宏段。

生成物还提供 `getRegBankFromRegClass` 的查表实现：regclass ID → 2 bit bank ID，未覆盖的类直接 `llvm_unreachable`。所以 target 必须特判“没有 bank 覆盖、但确实会被查询”的类——AArch64 特判 `GPR64sponlyRegClassID`，RISC-V 特判 `VCSRRegClassID`。

### 2. 构造函数：一次初始化，三类断言

`AArch64RegisterBankInfo` 用 `llvm::call_once` 保证 bank 表只初始化一次。源码注释解释了原因：AArch64 只有一套 bank，与 subtarget 无关。

第一类检查是 ID 顺序：

```cpp
const RegisterBank &RBGPR = getRegBank(AArch64::GPRRegBankID);
assert(&AArch64::GPRRegBank == &RBGPR &&
       "The order in RegBanks is messed up");
```

第二类是覆盖与容量：

```cpp
assert(RBGPR.covers(*TRI.getRegClass(AArch64::GPR32RegClassID)) &&
       "Subclass not added?");
assert(getMaximumSize(RBGPR.getID()) == 128 &&
       "GPRs should hold up to 128-bit");
```

第三类是 `.def` 与 `.inc` 的一致性检查：`checkPartialMappingIdx`、`checkPartialMap`、`checkValueMapImpl`，最后 `assert(verify(TRI) && "Invalid register bank information");`。它们只在 assertions build 生效，却是改 `.def` 时最便宜的保险。

### 3. `copyCost`：5 与 4 的不对称

```cpp
if (&A == &AArch64::GPRRegBank && &B == &AArch64::FPRRegBank)
  // FMOVXDr or FMOVWSr.
  return 5;
if (&A == &AArch64::FPRRegBank && &B == &AArch64::GPRRegBank)
  // FMOVDXr or FMOVSWr.
  return 4;

return RegisterBankInfo::copyCost(A, B, Size);
```

基类实现是 `return &A != &B;`：同 bank 为 0，不同 bank 为 1。AArch64 覆盖成 5/4，注释说是 FMOV，并带 `FIXME: This should be deduced from the scheduling model.`。这两个数不是周期数，只是相对权重；它们影响 Greedy 的比较和 repair 排序，不影响 Fast 选默认 mapping。

`copyCost(A, B)` 表示“A = COPY B”，A 是目的、B 是源。`A=GPR, B=FPR` 是 FPR→GPR，返回 5（FMOVXDr/FMOVWSr）；`A=FPR, B=GPR` 是 GPR→FPR，返回 4（FMOVDXr/FMOVSWr）。二手资料常把方向写反，以头文件与 FMOV 指令名为准。

### 4. `getInstrMapping`：先兜底，再分派

函数开头先处理“不属于 generic opcode”或 `G_PHI` 的情况：

```cpp
if ((Opc != TargetOpcode::COPY && !isPreISelGenericOpcode(Opc)) ||
    Opc == TargetOpcode::G_PHI) {
  const RegisterBankInfo::InstructionMapping &Mapping =
      getInstrMappingImpl(MI);
  if (Mapping.isValid())
    return Mapping;
}
```

`G_PHI` 是 generic opcode，但 bank 应由已有操作数/约束推断，而不是走后面的“按 opcode 猜”。`COPY` 刻意不进入这个分支，因为 AArch64 要在下面自己处理物理寄存器与跨 bank 复制。

然后是算术/位运算/浮点的一组：`G_ADD`、`G_SUB`、`G_PTR_ADD`、`G_MUL`、`G_SDIV`、`G_UDIV`、`G_AND`、`G_OR`、`G_XOR`、`G_FADD`、`G_FSUB`、`G_FMUL`、`G_FDIV`、`G_FMAXIMUM`、`G_FMINIMUM` 都 `return getSameKindOfOperandsMapping(MI);`。它的判断只有一句：

```cpp
bool IsFPR = Ty.isVector() || isPreISelGenericFloatingPointOpcode(Opc);
PartialMappingIdx RBIdx = IsFPR ? PMI_FirstFPR : PMI_FirstGPR;
```

也就是说：向量和浮点指令的所有操作数整体进 FPR，其余进 GPR。它假设操作数不超过 3 个（有 assert），且类型/位宽一致（debug 下有检查）。这就是 `G_ADD` 标量在 GPR、向量在 FPR 的原因。

`G_BITCAST` 如果源 bank 已知，就返回同 bank 的 copy mapping，cost 为 0——bitcast 不改位，同 bank 内免费。`COPY` 分两类：一边是物理寄存器时从已知边推另一边；两边都是 generic vreg 时按“非向量且 ≤64 位 → GPR，否则 FPR”猜，代价都用 `copyCost`。

最后是默认批量猜测：向量进 FPR，标量与指针进 GPR，浮点指令的标量进 FPR，位宽 >64 进 FPR；再按 `G_CONSTANT`、`G_FCONSTANT`、`G_DUP`、`G_TRUNC`、`G_SITOFP`、`G_FPTOSI`、`G_FCMP`、`G_LOAD`、`G_STORE`、`G_SELECT`、`G_INTRINSIC` 等逐 opcode 修正。结构始终是“先粗猜、再修正、最后构造 mapping”；任一操作数的 `ValueMapping` 无效就返回 invalid。

### 5. `getInstrAlternativeMappings`：只有三类

| opcode | 条件 | 候选 |
| --- | --- | --- |
| `G_OR` | 32/64 位，正好 3 个操作数 | GPR（ID 1）、FPR（ID 2），cost 都是 1 |
| `G_BITCAST` | 32/64 位，正好 2 个操作数 | GPR→GPR、FPR→FPR、GPR→FPR、FPR→GPR（ID 1/2/3/3） |
| `G_LOAD` | 64 位，正好 2 个操作数 | 结果 GPR 或 FPR，地址固定 GPR64（ID 1/2） |

其他 opcode 落到 `return RegisterBankInfo::getInstrAlternativeMappings(MI);`，基类实现直接返回空列表。所以“Greedy 会尝试所有 bank 组合”是误解：它只在 target 给出的候选里选。

`G_OR` 的注释是“32 and 64-bit or can be mapped on either FPR or GPR for the same cost”。这就是 Ch 0 里 `or.ll` 能让 Greedy 把 `G_OR` 留在 FPR 的全部原因。

`G_BITCAST` 的四个候选里，两个跨 bank 候选的 cost 都写成 `copyCost(AArch64::GPRRegBank, AArch64::FPRRegBank, ...)`，也就是都取 5。对 `FPRToGPRMapping`（Dst=GPR, Src=FPR）这是正确的 FPR→GPR 代价；对 `GPRToFPRMapping`（Dst=FPR, Src=GPR）方向相反，按 API 应取 4，源码却仍取 5。源码如此，读时不要假设两个方向自动对称。

### 6. `applyMappingImpl`：默认 mapping 之外才进来

`RegisterBankInfo::applyMapping` 先看 ID：`DefaultMappingID` 直接 `applyDefaultMapping`，其余才调 `applyMappingImpl`。所以 target 只需要处理自己造出来的非默认 ID。

AArch64 的 `applyMappingImpl` 做两类事：

1. **小类型修正**：`G_CONSTANT` / `G_FCONSTANT` / `G_STORE` / `G_LOAD` 在 GPR 上小于 32 位时，插入 `G_TRUNC` / `G_ANYEXT`，或把 `G_TRUNC` 折叠回 32 位常量；
2. **alternative 的落地**：`G_OR` / `G_BITCAST` 断言 ID 在 1..4，然后 `applyDefaultMapping`。

`G_DUP` 也有自定义逻辑。整体上，`applyMappingImpl` 不是“重新实现 repair”，而是处理“mapping 虽然合法，但物理上需要改指令形状”的情况。真正插 COPY 的是 `RegBankSelect::repairReg`，不是这里。

### 7. RISC-V 对照：更薄的一层

RISC-V 的 bank 定义同样三行：

```tablegen
def GPRBRegBank : RegisterBank<"GPRB", [GPR, GPRPair]>;
def FPRBRegBank : RegisterBank<"FPRB", [FPR64]>;
def VRBRegBank  : RegisterBank<"VRB", [VRM8]>;
```

但实现策略明显更薄：`PartMappings` / `ValueMappings` 直接手写在 `.cpp`；只有 9 个 partial mapping（GPR 32/64、FPR 16/32/64、VR 64/128/256/512）；**没有覆盖 `copyCost`**，跨 bank 代价用基类的 1；**没有覆盖 `getInstrAlternativeMappings`**，Greedy 的候选集只有默认 mapping；`getInstrMapping` 用一个大 `switch` 直接返回各 opcode 的 mapping，`G_PHI` 走 `getInstrMappingImpl`；`getRegBankFromRegClass` 只特判 `VCSRRegClassID`。

这意味着：在 23.1.4 上，RISC-V 的 Greedy 通常和 Fast 选出相同的 bank，因为根本没有第二个候选。它不是“Greedy 不工作”，而是“target 没给 Greedy 可选项”。这一点在第 22 章会展开成设计取舍。

## 三个源码片段

### 例 1：生成物里的 ID、容量与覆盖（实测生成物）

在本次工作区用官方 23.1.4 的 `llvm-tblgen` 对 `AArch64.td` 执行 `-gen-register-bank`，输出的开头是：

```cpp
enum : unsigned {
  InvalidRegBankID = ~0u,
  CCRegBankID = 0,
  FPRRegBankID = 1,
  GPRRegBankID = 2,
  NumRegisterBanks,
};
```

同一份生成物里的容量表是 `32, 512, 128`，顺序与 ID 一致：CC=32、FPR=512、GPR=128。构造函数的三个 `getMaximumSize` 断言就是对着这三个数写的。

覆盖数组的置位数（本次对生成文本计数）：CC=1、FPR=87、GPR=42。这个数字不是“寄存器个数”，而是“被覆盖的寄存器类个数”；它包含子类与 subreg class，所以远大于 `.td` 里显式列出的类。命令本身可复现；换 include 路径或 LLVM 版本，数字可能变化。

### 例 2：`copyCost` 与 `G_OR` alternative（源码依据）

```cpp
unsigned AArch64RegisterBankInfo::copyCost(const RegisterBank &A,
                                           const RegisterBank &B,
                                           const TypeSize Size) const {
  if (&A == &AArch64::GPRRegBank && &B == &AArch64::FPRRegBank)
    return 5;
  if (&A == &AArch64::FPRRegBank && &B == &AArch64::GPRRegBank)
    return 4;
  return RegisterBankInfo::copyCost(A, B, Size);
}
```

```cpp
const InstructionMapping &GPRMapping = getInstructionMapping(
    /*ID*/ 1, /*Cost*/ 1, getValueMapping(PMI_FirstGPR, Size),
    /*NumOperands*/ 3);
const InstructionMapping &FPRMapping = getInstructionMapping(
    /*ID*/ 2, /*Cost*/ 1, getValueMapping(PMI_FirstFPR, Size),
    /*NumOperands*/ 3);
```

把这两段和 Ch 0 的 `or.ll` 对上：

- Fast：默认 mapping 是 GPR。两个 `G_BITCAST` 的结果在 FPR，喂给 `G_OR` 需要 FPR→GPR 两次，每次 5；返回值从 GPR 回到 `$s0` 需要 GPR→FPR 一次，4。三条跨 bank COPY，与 Ch 0 的实测输出一致。
- Greedy：候选里有 FPR mapping。整条链都在 FPR，跨 bank 代价为 0，所以选 FPR。

### 例 3：RISC-V 的映射表（源码依据）

RISC-V 直接在 `.cpp` 里写 `PartMappings[]`，没有 `.def`、没有偏移运算；`ValueMappings[]` 只是把每个 partial mapping 重复三次供 3 操作数指令使用。简单、好读，但加新位宽要手工补数组。

## 对比与取舍

| 维度 | AArch64 | RISC-V |
| --- | --- | --- |
| bank 数 | 3（GPR/FPR/CC） | 3（GPRB/FPRB/VRB） |
| mapping 表 | 手写 `.def` + 偏移运算 | 手写 `.cpp` 数组 |
| copyCost | 覆盖，5/4 | 未覆盖，基类 1 |
| alternative | 3 个 opcode | 无 |
| Greedy 实际效果 | 有候选可选 | 通常只有默认候选 |
| 特殊 regclass | `GPR64sponly` | `VCSR` |

AArch64 的做法更复杂，但换来了：一张表覆盖 16/32/64/128/256/512 六个位宽；跨 bank copy mapping 能复用同一套索引；少量 opcode 的 alternative 就能消掉常见 FP 链上的 COPY。

RISC-V 的做法更直白，代价是：新位宽/新 bank 要手工加数组项；没有 alternative，Greedy 基本没有发挥空间；没有 copyCost，跨 bank 代价一律按 1，无法表达“FPR↔GPR 更贵”。

这不是“谁更先进”，而是两个 target 在支持成熟度上的差异。读源码时要能看出“缺的是实现，不是算法”。

## 踩雷集锦

1. **以为 `AArch64GenRegisterBankInfo.def` 是 TableGen 生成的。**
   文件名和 `Gen` 前缀很容易让人误会，但文件头写着 `\todo This should be generated by TableGen.`；它现在是手写文件。改 mapping 表时改的是这个 `.def`，不是 `.td`。

2. **以为 `.td` 里列出的类就是全部覆盖。**
   `GPRRegBank` 只写了 `XSeqPairsClass`，生成物却覆盖 42 个寄存器类。Emitter 会递归加入子类和 subreg class。判断“某个类有没有 bank”，要看生成覆盖表或直接 `covers()`，不要数 `.td` 的列表长度。

3. **以为 AArch64 的所有整数指令都有 FPR alternative。**
   23.1.4 只有 `G_OR`、`G_BITCAST`、`G_LOAD` 三类。`G_AND`、`G_XOR`、`G_ADD` 在 Greedy 下仍然只有默认 mapping。Ch 0 的练习让你把 `or` 换成 `and`/`xor`，结论就来自这里。

4. **把 `copyCost` 当成对称的。**
   `copyCost(A, B)` 是“A = COPY B”：`A=GPR, B=FPR`（FPR→GPR）为 5，`A=FPR, B=GPR`（GPR→FPR）为 4。写代价计算或读 Greedy 结果时，方向搞反会得到不同的比较结果。还要记住基类对“不同 bank”只给 1，AArch64 的两个数不是全局默认。

5. **在 `getInstrMapping` 里漏掉 `G_PHI` 的兜底。**
   `G_PHI` 是 generic opcode，但它的 mapping 应该从已有操作数推断。AArch64 在函数开头显式把 `G_PHI` 送进 `getInstrMappingImpl`；如果只按 opcode switch，PHI 很容易拿到不合适的默认 bank。

## 进阶

- **读 `RegisterBankEmitter.cpp` 的 `visitRegisterBankClasses`**。它解释了“为什么覆盖数远大于显式列表”，也解释了 subreg class 怎么被纳入。
- **看 `getValueMapping` 的下标运算**。`First3OpsIdx + (RBIdx - PMI_Min + offset) * DistanceBetweenRegBanks` 把“bank × 位宽 × 3 操作数”压成一维数组；理解它才能安全加新位宽。
- **对比 `G_LOAD` 的 alternative 为什么只支持 64 位**。32 位标量 load 通常直接进 GPR，FP load 由默认 mapping 的 `isLoadFromFPType` / use 分析处理；alternative 只覆盖需要“结果 bank 二选一”的 64 位情况。
- **在 assertions build 里打开 `-debug-only=regbankselect`**（guided）。官方预编译包没有这个选项；自建后可以看到每个候选的 mapping 与 cost。

## 本章重点整理

- AArch64 的 bank 支持分四层：`.td` 定义、`.inc` 生成、`.def` mapping 表、`.cpp` 策略。
- bank ID 由 TableGen 生成；23.1.4 的顺序是 CC=0、FPR=1、GPR=2，容量分别是 32/512/128。
- bank 覆盖会递归包含子类和 subreg class，不能只看 `.td` 的显式列表。
- `copyCost` 在 AArch64 是 FPR→GPR=5、GPR→FPR=4（`copyCost(A=GPR, B=FPR)` 与 `copyCost(A=FPR, B=GPR)`）；基类对不同 bank 只给 1。
- `getInstrMapping` 先兜底 `G_PHI`/非 generic，再按 opcode 分派；算术/位运算/浮点走 `getSameKindOfOperandsMapping`。
- alternative 只有 `G_OR`、`G_BITCAST`、`G_LOAD` 三类；其余 opcode 的 Greedy 没有第二候选。
- `applyMappingImpl` 只处理非默认 ID；默认 mapping 由框架直接 `applyDefaultMapping`。
- RISC-V 更薄：无 copyCost 覆盖、无 alternative、mapping 表直接写在 `.cpp`。
