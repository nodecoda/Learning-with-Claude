# Ch 7 — target mapping 表：opcode/type 分派
> **目标**：读懂 AArch64 的 `AArch64GenRegisterBankInfo.def`：`PMI_FirstGPR` / `PMI_FirstFPR` 是什么、`PartMappings` / `ValMappings` 如何排布、`getValueMapping` 的索引如何算、`getInstrMapping` 如何先看 opcode 再看类型。最后能用 RISC-V 的表结构做对照。
>
> **环境**：LLVM 23.1.4 源码；本章的索引计算、表布局标为**源码依据**，没有重新跑 TableGen 或构建。MIR 片段若引用，均来自官方 23.1.4 包（实测）。
>
> **证据约定**：`AArch64GenRegisterBank.inc` 是构建期生成的产物，源码树里没有；本章对它的内容只按生成器 `RegisterBankEmitter.cpp` 的模板做 **guided** 复述，不当成逐字生成结果。
## 为什么需要这个？
Ch 6 的 `getInstrMappingImpl` 只解决“有编码约束”和“copy-like”两种情况。AArch64 的 generic 指令大多数没有 regclass 约束，所以真正决定 bank 的是 target 自己的表：

- `AArch64RegisterBanks.td` 定义 GPR / FPR / CC 三个 bank 及其覆盖的寄存器类；
- TableGen 生成 `AArch64GenRegisterBank.inc`（bank 对象、`RegBanks[]`、`Sizes[]`、`getRegBankFromRegClass`）；
- 手写的 `AArch64GenRegisterBankInfo.def` 定义 `PartMappings[]` / `ValMappings[]`，即“哪个 bank、多大、对应哪个 partial mapping”；
- `AArch64RegisterBankInfo.cpp` 的 `getInstrMapping` 用 opcode switch + 类型启发式，把这些表项拼成 `InstructionMapping`。

不理解这张表，就只能把 `PMI_FirstGPR` 当成魔法数字；理解之后，你能算出 `G_ADD i64` 为什么落在 `ValMappings[22]`，也能解释为什么 `G_OR i32` 的 FPR alternative 是 `ValMappings[4]`。
## 先建立直觉
把 `ValMappings` 想成一排**货架**，每个 `(bank, size)` 占**连续三格**：
```text
0: invalid
1..3 FPR16 | 4..6 FPR32 | 7..9 FPR64 | 10..12 FPR128 | 13..15 FPR256 | 16..18 FPR512
19..21 GPR32 | 22..24 GPR64 | 25..27 GPR128
28..43 cross-bank copy（成对） | 44..51 FP ext | 52 shift imm
```
为什么每个 `(bank, size)` 要三格？因为一条二元/三元指令的三个操作数通常同 bank、同大小；`getValueMapping` 返回这一组的第一格，`InstructionMapping` 用 `NumOperands = 3` 直接往后读三格。三元指令不需要为每个操作数单独建 `ValueMapping`，直接复用连续三格。

`PartMappings` 则是更底层的“单格”：
```text
PartMappings 索引 = PMI 枚举值 - PMI_Min
```
`PMI_Min` 是 `PMI_FirstFPR`（也就是 `PMI_FPR16 = 1`），所以 `PMI_FPR16` 对应 `PartMappings[0]`，`PMI_GPR128` 对应 `PartMappings[8]`。
## 核心概念
### bank 从 `.td` 来，mapping 从 `.def` 来
`AArch64RegisterBanks.td` 只有三行有效定义：
```tablegen
def GPRRegBank : RegisterBank<"GPR", [XSeqPairsClass]>;
def FPRRegBank : RegisterBank<"FPR", [QQQQ, ZPR]>;
def CCRegBank  : RegisterBank<"CC",  [CCR]>;
```
`RegisterBank<Name, [CoveredClasses]>` 的第二个参数是“覆盖的寄存器类”。TableGen 会递归把子类也算进去。AArch64 构造函数里的断言给出了最终大小：
```cpp
assert(getMaximumSize(RBGPR.getID()) == 128 && "GPRs should hold up to 128-bit");
assert(getMaximumSize(RBFPR.getID()) == 512 && "FPRs should hold up to 512-bit via QQQQ sequence");
assert(getMaximumSize(RBCCR.getID()) == 32 && "CCR should hold up to 32-bit");
```
`AArch64GenRegisterBank.inc` 是构建期生成的，源码树里没有这个文件。下面按 `RegisterBankEmitter.cpp` 的模板**复述**它大致包含什么（guided，不是逐字生成结果）：
```cpp
const RegisterBank *AArch64GenRegisterBankInfo::RegBanks[] = {
  &AArch64::GPRRegBank, &AArch64::FPRRegBank, &AArch64::CCRegBank,
};
const unsigned AArch64GenRegisterBankInfo::Sizes[] = { /* 每个 bank 的最大 spill size */ };
AArch64GenRegisterBankInfo::AArch64GenRegisterBankInfo(unsigned HwMode)
    : RegisterBankInfo(RegBanks, AArch64::NumRegisterBanks, Sizes, HwMode) { ... }
```
以及 `getRegBankFromRegClass` 的查表实现。生成器会把 RC ID 映射到 bank ID，打包进 `RegClass2RegBank[]`；如果 RC 不在任何 bank 的覆盖范围，生成代码走：
```cpp
llvm_unreachable("Target needs to handle register class ID 0x...");
```
AArch64 为 `GPR64sponlyRegClassID` 写了特判（见 Ch 6）；RISC-V 也为 `VCSRRegClassID` 写了特判。
### `AArch64GenRegisterBankInfo.def` 不是生成文件
文件名里有 `Gen`，但源码注释说得很清楚：

> This file defines all the static objects used by AArch64RegisterBankInfo.
> \todo This should be generated by TableGen.

`AArch64RegisterBankInfo.cpp` 里也写着：
```cpp
// This file will be TableGen'ed at some point.
#include "AArch64GenRegisterBankInfo.def"
```
也就是说：

- `AArch64GenRegisterBank.inc`：**生成**的（bank 对象/覆盖表/`getRegBankFromRegClass`）；
- `AArch64GenRegisterBankInfo.def`：**手写**的（`PartMappings` / `ValMappings` / 索引函数）。

读代码时不要把两者混为一谈。你修改 `.def` 是改源码；修改 `.inc` 会在下一次构建被覆盖。
### `PMI_*` 枚举与别名
`AArch64RegisterBankInfo.h` 里的 `PartialMappingIdx`：
```cpp
enum PartialMappingIdx {
  PMI_None = -1,
  PMI_FPR16 = 1,
  PMI_FPR32,
  PMI_FPR64,
  PMI_FPR128,
  PMI_FPR256,
  PMI_FPR512,
  PMI_GPR32,
  PMI_GPR64,
  PMI_GPR128,
  PMI_FirstGPR = PMI_GPR32,
  PMI_LastGPR = PMI_GPR128,
  PMI_FirstFPR = PMI_FPR16,
  PMI_LastFPR = PMI_FPR512,
  PMI_Min = PMI_FirstFPR,
};
```
所以：

| 名称 | 值 | 用途 |
| --- | --- | --- |
| `PMI_FirstFPR` | 1 | FPR 组的起点 |
| `PMI_FirstGPR` | 7 | GPR 组的起点 |
| `PMI_Min` | 1 | 数组下标偏移 |
| `PMI_LastGPR` | 9 | GPR128 |
| `PMI_LastFPR` | 6 | FPR512 |

`PMI_FirstGPR` 不是 `GPRRegBankID`。它是“表项枚举”，不是 bank ID；`getRegBank(PMI_FirstGPR)` 这种写法是错的。
### `PartMappings[]`：9 个单格
```cpp
const RegisterBankInfo::PartialMapping AArch64GenRegisterBankInfo::PartMappings[]{
    /* StartIdx, Length, RegBank */
    {0, 16,  AArch64::FPRRegBank},   // 0: PMI_FPR16
    {0, 32,  AArch64::FPRRegBank},   // 1: PMI_FPR32
    {0, 64,  AArch64::FPRRegBank},   // 2: PMI_FPR64
    {0, 128, AArch64::FPRRegBank},   // 3: PMI_FPR128
    {0, 256, AArch64::FPRRegBank},   // 4: PMI_FPR256
    {0, 512, AArch64::FPRRegBank},   // 5: PMI_FPR512
    {0, 32,  AArch64::GPRRegBank},   // 6: PMI_GPR32
    {0, 64,  AArch64::GPRRegBank},   // 7: PMI_GPR64
    {0, 128, AArch64::GPRRegBank},   // 8: PMI_GPR128
};
```
全部是 `StartIdx = 0`、单 partial。AArch64 的表不支持把 64 位拆成两个 32 位 GPR；如果需要，得自己加 `ValueMapping`，并处理 `getBreakDownCost` / repair（Ch 10）。
### `ValMappings[]`：三连组 + 跨 bank 组
前 28 项可以概括成：
```cpp
{nullptr, 0},                         // 0: invalid
// 每个 (bank, size) 连续 3 个相同项
{&PartMappings[PMI_FPR16 - PMI_Min], 1}, { ... }, { ... },  // 1..3
{&PartMappings[PMI_FPR32 - PMI_Min], 1}, { ... }, { ... },  // 4..6
...
{&PartMappings[PMI_GPR128 - PMI_Min], 1}, { ... }, { ... }, // 25..27
```
跨 bank copy 从 index 28 开始，按“两格一组”排列：
```cpp
// 28: FPR16 -> GPR（物理寄存器场景）
{&PartMappings[PMI_FPR16 - PMI_Min], 1},
{&PartMappings[PMI_GPR32 - PMI_Min], 1},
// 30: FPR32 -> GPR32
// 32: FPR64 -> GPR64
// 34/36/38: 128/256/512 -> GPR（invalid）
// 40: GPR32 -> FPR32
// 42: GPR64 -> FPR64
```
`ValueMappingIdx` 里的常量：
```cpp
InvalidIdx = 0, First3OpsIdx = 1, Last3OpsIdx = 25, DistanceBetweenRegBanks = 3,
FirstCrossRegCpyIdx = 28, LastCrossRegCpyIdx = 42, DistanceBetweenCrossRegCpy = 2,
FPExt16To32Idx = 44, FPExt16To64Idx = 46, FPExt32To64Idx = 48,
FPExt64To128Idx = 50, Shift64Imm = 52,
```
`Last3OpsIdx = 25` 是**最后一个三连组的起点**（GPR128），不是最后一个有效下标。三连组实际到 27。这个命名很容易误导，读断言时要小心。
### `getRegBankBaseIdxOffset`：大小分桶
```cpp
if (RBIdx == PMI_FirstGPR)
  return Size <= 32 ? 0 : Size <= 64 ? 1 : Size <= 128 ? 2 : -1;
if (RBIdx == PMI_FirstFPR) {
  if (Size.isScalable()) return 3;
  const unsigned Min = Size.getKnownMinValue();
  return Min <= 16 ? 0 : Min <= 32 ? 1 : Min <= 64 ? 2 :
         Min <= 128 ? 3 : Min <= 256 ? 4 : Min <= 512 ? 5 : -1;
}
return -1;
```
几个直接后果：

- `i1` / `i8` / `i16` 在 GPR 上都落到 32 位组（offset 0）；AArch64 没有 1/8/16 位 GPR 寄存器类。
- `i128` 在 GPR 上落到 128 位组（offset 2），由 `XSeqPairsClass` 覆盖。
- scalable vector 直接落到 FPR128 组（offset 3），因为最小尺寸至少 128 bit。
- 超过 128 的 GPR、超过 512 的 FPR 返回 `-1`，最终 `getValueMapping` 返回 invalid。
### `getValueMapping`：组起点索引
```cpp
unsigned ValMappingIdx =
    First3OpsIdx + (RBIdx - PartialMappingIdx::PMI_Min + BaseIdxOffset) *
                       ValueMappingIdx::DistanceBetweenRegBanks;
assert(ValMappingIdx >= First3OpsIdx && ValMappingIdx <= Last3OpsIdx);
return &ValMappings[ValMappingIdx];
```
`DistanceBetweenRegBanks = 3`。代入 `G_ADD i64`：
```text
RBIdx = PMI_FirstGPR = 7
PMI_Min = 1
BaseIdxOffset(GPR, 64) = 1
ValMappingIdx = 1 + (7 - 1 + 1) * 3 = 22
```
`ValMappings[22]` 是 GPR64 三连组的第一格；`NumOperands = 3` 时读 22、23、24。三个月后你也能从索引反推：22 属于 GPR64，不是 FPR。
### `getCopyMapping`：跨 bank 的成对表
```cpp
if (DstRBIdx == SrcRBIdx)
  return getValueMapping(DstRBIdx, Size);

assert(Size <= 64 && "GPR cannot handle that size");
unsigned ValMappingIdx =
    FirstCrossRegCpyIdx +
    (DstRBIdx - PMI_Min + getRegBankBaseIdxOffset(DstRBIdx, Size)) *
        ValueMappingIdx::DistanceBetweenCrossRegCpy;
return &ValMappings[ValMappingIdx];
```
同 bank copy 直接复用 `getValueMapping`；跨 bank copy 只支持 `Size <= 64`，索引按 `DistanceBetweenCrossRegCpy = 2` 跳。比如 `getCopyMapping(GPR, FPR, 32)`：
```text
DstRBIdx = PMI_FirstGPR = 7
offset(GPR, 32) = 0
idx = 28 + (7 - 1 + 0) * 2 = 40
```
`ValMappings[40]` 是 GPR32 项，对应“目标是 GPR 的跨 bank copy”。`getCopyMapping(FPR, GPR, 32)` 则是：
```text
idx = 28 + (1 - 1 + 1) * 2 = 30
```
`ValMappings[30]` 是 FPR32 项。注意参数顺序：`getCopyMapping(Dst, Src, Size)`，不是 `Src, Dst`。
### `getFPExtMapping`：FP extension 的专用表
`G_FPEXT` 不走三连组，而是按 `(DstSize, SrcSize)` 选固定表项：

| (Dst, Src) | 表项 |
| --- | --- |
| (32, 16) | `FPExt16To32Idx = 44` |
| (64, 16) | `FPExt16To64Idx = 46` |
| (64, 32) | `FPExt32To64Idx = 48` |
| (128, 64) | `FPExt64To128Idx = 50` |

每个表项也是两个连续的 `ValueMapping`：第一个是目标，第二个是源。`getInstrMapping` 的 `G_FPEXT` 分支直接：
```cpp
return getInstructionMapping(DefaultMappingID, /*Cost*/ 1,
                             getFPExtMapping(DstTy.getSizeInBits(),
                                             SrcTy.getSizeInBits()),
                             /*NumOperands*/ 2);
```
这就是为什么 `G_FPEXT` 的 mapping 不能简单用 `getSameKindOfOperandsMapping`：源和目标大小不同，不能共用同一个三连组。
## 底层机制
### `getInstrMapping` 的三层分派
AArch64 的 `getInstrMapping` 可以概括成：
```text
1. 非 generic 且非 COPY，或 G_PHI ──► getInstrMappingImpl（编码约束/copy-like）
2. opcode switch ──► 专用规则（G_ADD、G_BITCAST、G_LOAD、G_SELECT...）
3. 类型回退 ──► 按 operand 类型选 PMI_FirstGPR / PMI_FirstFPR
```
第 3 层在 switch 之后，对每个 reg operand 做：
```cpp
if (Ty.isVector())
  OpRegBankIdx[Idx] = PMI_FirstFPR;
else if (isPreISelGenericFloatingPointOpcode(Opc) ||
         (MO.isDef() && onlyDefinesFP(MI, MRI, TRI)) ||
         (MO.isUse() && onlyUsesFP(MI, MRI, TRI)) ||
         Ty.getSizeInBits() > 64)
  OpRegBankIdx[Idx] = PMI_FirstFPR;
else
  OpRegBankIdx[Idx] = PMI_FirstGPR;
```
然后统一构造 mapping，`Cost` 默认 1；某些 opcode 会改成 0、2 或 `copyCost`。
### `getSameKindOfOperandsMapping`：二元/三元指令的主力
```cpp
LLT Ty = MRI.getType(MI.getOperand(0).getReg());
bool IsFPR = Ty.isVector() || isPreISelGenericFloatingPointOpcode(Opc);
PartialMappingIdx RBIdx = IsFPR ? PMI_FirstFPR : PMI_FirstGPR;

return getInstructionMapping(DefaultMappingID, 1,
                             getValueMapping(RBIdx, Size), NumOperands);
```
它要求 `NumOperands <= 3`，并断言所有操作数大小落在同一个桶、类型同为 FPR 或 GPR。`G_ADD`、`G_SUB`、`G_MUL`、`G_AND`、`G_OR`、`G_XOR`、`G_FADD` 等都走这里。
### `G_FCMP`：scalar 结果不是 CC bank
源码：
```cpp
case TargetOpcode::G_FCMP: {
  AArch64GenRegisterBankInfo::PartialMappingIdx Idx0 =
      MRI.getType(MI.getOperand(0).getReg()).isVector() ? PMI_FirstFPR
                                                        : PMI_FirstGPR;
  OpRegBankIdx = {Idx0,
                  /* Predicate */ PMI_None, PMI_FirstFPR, PMI_FirstFPR};
  break;
}
```
scalar `G_FCMP` 的结果用 `PMI_FirstGPR`，predicate 是 `PMI_None`（非寄存器，不映射），两个输入是 FPR。这个源码事实支持 Ch 4 的结论：在普通 AArch64 GlobalISel 路径里，不要把 CC bank 当成默认 boolean bank。`CCRegBank` 存在，但 `G_FCMP` 的默认 mapping 不把结果放进去。
## 示例一：`G_ADD i64` 的索引
【源码依据】`G_ADD` 走 `getSameKindOfOperandsMapping`：

- `Ty = i64`，不是 vector；
- `G_ADD` 不是浮点 opcode；
- `RBIdx = PMI_FirstGPR = 7`；
- `BaseIdxOffset(GPR, 64) = 1`；
- `ValMappingIdx = 1 + (7 - 1 + 1) * 3 = 22`。

所以 mapping 是：
```text
InstructionMapping {
  ID = DefaultMappingID
  Cost = 1
  NumOperands = 3
  Operands[0..2] = ValueMapping { BreakDown = {0, 64, GPR}, N = 1 }
}
```
对应 MIR：
```yaml
%2:gpr(i64) = G_ADD %0, %1
```
## 示例二：`G_FADD f32` 与 `G_OR i32`
`G_FADD f32`：

- `isPreISelGenericFloatingPointOpcode(G_FADD)` 为 true；
- `RBIdx = PMI_FirstFPR = 1`；
- `BaseIdxOffset(FPR, 32) = 1`；
- `ValMappingIdx = 1 + (1 - 1 + 1) * 3 = 4`。

`ValMappings[4..6]` 是 FPR32 三连组。输出：
```yaml
%2:fpr(f32) = G_FADD %0, %1
```
`G_OR i32`：

- `G_OR` 不是浮点 opcode，`i32` 不是 vector；
- `RBIdx = PMI_FirstGPR`；
- `BaseIdxOffset(GPR, 32) = 0`；
- `ValMappingIdx = 1 + (7 - 1 + 0) * 3 = 19`。

`ValMappings[19..21]` 是 GPR32 三连组。Fast 模式下 `G_OR` 默认落 GPR，这就是 Ch 0 里那三条跨 bank COPY（两条 repair + 一条 ABI）的来源。Greedy 模式会尝试 `getInstrAlternativeMappings(G_OR)` 返回的 FPR mapping，其 `getValueMapping(PMI_FirstFPR, 32)` 指向 `ValMappings[4]`。
## 示例三：`G_BITCAST` 与 `G_LOAD` 的选择
`G_BITCAST` 的默认分支优先看源 bank：
```cpp
Register SrcReg = MI.getOperand(1).getReg();
const RegisterBank *SrcRB = getRegBank(SrcReg, MRI, TRI);
if (SrcRB) {
  TypeSize Size = getSizeInBits(SrcReg, MRI, TRI);
  return getInstructionMapping(DefaultMappingID, 0,
      getCopyMapping(SrcRB->getID(), SrcRB->getID(), Size), 2);
}
```
所以 `%2:fpr(i32) = G_BITCAST %0(f32)` 的 mapping 是 FPR32/FPR32，cost 0；`%5:gpr(f32) = G_BITCAST %4(i32)` 在 `%4` 为 GPR 时是 GPR32/GPR32，cost 0。跨 bank 的组合只出现在 alternative mapping（ID 3；Greedy 才会看），两个方向都按 `copyCost(GPR, FPR)` 记 5。默认分支不会产生跨 bank 的 bitcast。

`G_LOAD` 的规则更偏启发式：
```cpp
case TargetOpcode::G_LOAD: {
  if (OpRegBankIdx[0] != PMI_FirstGPR) { Cost = 2; break; }
  if (cast<GLoad>(MI).isAtomic()) { OpRegBankIdx[0] = PMI_FirstGPR; ... break; }
  if (isLoadFromFPType(MI)) { OpRegBankIdx[0] = PMI_FirstFPR; break; }
  if (any_of(MRI.use_nodbg_instructions(...), ... onlyUsesFP ...))
    OpRegBankIdx[0] = PMI_FirstFPR;
  ...
}
```
它先看默认类型分桶，再看 MMO 是否来自 FP 类型，再看用途是否只被 FP 指令使用。默认加载到 GPR；如果判断是浮点加载，则改 FPR。Greedy 的 `getInstrAlternativeMappings(G_LOAD)` 只为 64 位、2 操作数的 `G_LOAD` 提供 GPR/FPR 两套 dest mapping，地址固定 GPR64。
## 对比与取舍
### AArch64 vs RISC-V
| 维度 | AArch64 | RISC-V |
| --- | --- | --- |
| bank 定义 | `AArch64RegisterBanks.td`：GPR / FPR / CC | `RISCVRegisterBanks.td`：GPRB / FPRB / VRB |
| 覆盖类 | GPR `[XSeqPairsClass]`；FPR `[QQQQ, ZPR]`；CC `[CCR]` | GPRB `[GPR, GPRPair]`；FPRB `[FPR64]`；VRB `[VRM8]` |
| mapping 表 | 手写 `.def` + 生成 `.inc` | 手写在 `RISCVRegisterBankInfo.cpp` 里的 `PartMappings` / `ValueMappings` |
| `copyCost` | 覆写，GPR/FPR 4/5 | 不覆写，用基类 0/1 |
| alternative mappings | `G_OR` / `G_BITCAST` / `G_LOAD` | 不覆写，基类返回空 |
| `applyMappingImpl` | 有（sub-32-bit、custom ID） | 不覆写 |

结论：RISC-V 的 bank 结构更简单，mapping 表直接在 `.cpp` 里；AArch64 的表更大、分派更细，也因此 Greedy 有更多可选 bank。不要把 AArch64 的 `PMI_FirstGPR` / 三连组布局当成所有 target 的通用模式。
### 表驱动 vs 手写 switch
| 方案 | 优点 | 代价 |
| --- | --- | --- |
| 表驱动（`ValMappings`） | 索引计算统一、易复用、易断言 | 表布局有隐含约定（三连组、成对跨 bank） |
| opcode switch | 能表达 opcode 特有语义（`G_LOAD`、`G_SELECT`） | 分支多，容易漏；需要持续维护 |
| 类型回退 | 覆盖未知 generic opcode | 可能选错 bank，依赖后续 repair |

AArch64 实际是三者混用：表提供“材料”，switch 提供“策略”，类型回退提供“兜底”。
## 踩雷集锦
### 1. 以为 `AArch64GenRegisterBankInfo.def` 是 TableGen 生成的
错：
```text
改 .def 没用，下次构建会被重新生成
```
对。`.def` 是手写源码；生成的是 `AArch64GenRegisterBank.inc`。源码的 `\todo` 写着 “This should be generated by TableGen.”，也就是还没生成。
### 2. 忘记减 `PMI_Min`
错：
```cpp
&PartMappings[PMI_FPR32]   // 越界，且语义错
```
对。`PartMappings` 的下标是 `PMI - PMI_Min`：
```cpp
&PartMappings[PMI_FPR32 - PMI_Min]
```
`PMI_FPR32 = 2`，`PMI_Min = 1`，所以下标是 1。
### 3. 把 `Last3OpsIdx` 当成最后一个有效下标
错：
```cpp
assert(ValMappingIdx + NumOperands - 1 <= Last3OpsIdx);
```
对。`Last3OpsIdx = 25` 是 GPR128 三连组的**起点**；真正的最后一项是 27。`getValueMapping` 的断言只检查起点，不检查 `+2`。如果 `NumOperands > 3`，会读到下一组（跨 bank 表），结果完全错误。
### 4. 认为 `PMI_FirstGPR` 就是 `GPRRegBankID`
错：
```cpp
getRegBank(PMI_FirstGPR);   // PMI 是表项枚举，不是 bank ID
```
对。`PMI_FirstGPR = 7` 是 `PartialMappingIdx`；bank ID 来自 `AArch64::GPRRegBankID`。两者数值可能碰巧不同，语义完全不同。
### 5. 对超过 128 的 GPR / 超过 512 的 FPR 仍期待有效 mapping
错：
```cpp
getValueMapping(PMI_FirstGPR, 256);  // 返回 invalid
```
对。`getRegBankBaseIdxOffset` 对 GPR >128、FPR >512 返回 `-1`，`getValueMapping` 返回 `&ValMappings[InvalidIdx]`。调用方必须检查 `Mapping->isValid()`；AArch64 的 `getInstrMapping` 在逐操作数构造 mapping 时会：
```cpp
if (!Mapping->isValid())
  return getInvalidInstructionMapping();
```
## 进阶
- **读 `AArch64RegisterBankInfo` 构造函数的断言**：它同时检查 bank 顺序、最大 size、PMI 顺序、每个 partial/value mapping 的内容。这是修改表后最快的自检。
- **读 `getRegBankBaseIdxOffset` 的 scalable 分支**：scalable vector 不按 `getKnownMinValue()` 走普通桶，而是直接落到 FPR128；这会影响 `vscale` 类型的 mapping。
- **读 `G_SELECT` / `G_BUILD_VECTOR` / `G_UNMERGE_VALUES` 的特判**：它们不是简单的“按 def 类型选 bank”，而是看 uses/defs 的 FP 约束、向量性、常量性。AArch64 的启发式大量集中在这里。
- **读 `getCopyMapping` 的 `assert(Size <= 64)`**：跨 bank copy 表只做到 64 位；128 位 GPR/FPR 之间的 copy 在 AArch64 上不是靠这张表，而是靠指令/repair 的其它路径。

## 本章重点整理
- AArch64 的 bank 来自 `.td`，bank 对象/覆盖表/`getRegBankFromRegClass` 来自生成的 `.inc`。
- `AArch64GenRegisterBankInfo.def` 是手写表，不是 TableGen 生成物。
- `PMI_FirstGPR = 7`、`PMI_FirstFPR = 1`、`PMI_Min = 1`；`PartMappings` 下标要减 `PMI_Min`。
- `ValMappings` 每个 `(bank, size)` 连续 3 项，供 2–3 操作数指令复用。
- `getValueMapping` 的索引 = `1 + (PMI - PMI_Min + sizeOffset) * 3`。
- `getCopyMapping(Dst, Src, Size)` 走 28..43 的成对表，只支持 `Size <= 64`。
- `G_FCMP` scalar 结果默认在 GPR，不在 CC bank。
- RISC-V 的表更简单，没有 `copyCost` / alternatives 覆写。
